Day 10 / 共 20 天 · 第 2 周收官

记忆系统

助理怎么"记得你"？OpenClaw 有两套并存的记忆：静态 bootstrap 文件注入（Day 09 见过）+ 动态语义检索（memory_search 工具 + 向量嵌入）。今天讲全，并收官第 2 周。

L01

两套记忆

静态注入（bootstrap）动态检索（语义）
时机每次运行都注入系统提示模型按需调 memory_search 工具
内容SOUL/USER/MEMORY.md 等固定文件MEMORY.md + memory/*.md 的相关片段
代价每次都占 token（有字符预算）只在需要时检索，省 token
代码workspace.ts + bootstrap-files.tssrc/memory/ + memory-tool.ts
"随身笔记" vs "档案室" 静态注入像助理口袋里的随身便签——最重要的几条（你是谁、我的性格、核心记忆）每次都带着。动态检索像一间档案室——记了成百上千条，不可能每次全带，需要时"去档案室按关键词查相关的几条"。两者互补：便签保证基本一致性，档案室提供海量长期记忆而不撑爆上下文。一个成熟助理两者都要。
L02

静态：bootstrap 文件

Day 09 见过：loadWorkspaceBootstrapFiles（workspace.ts:481-541）读取工作区的 AGENTS/SOUL/USER/MEMORY.md 等，resolveBootstrapContextForRun（bootstrap-files.ts:98-118）按 context-mode、字符预算过滤后注入 # Project Context 段。

读法：子 Agent 用 MINIMAL_BOOTSTRAP_ALLOWLIST（workspace.ts:543-549）只保留部分文件（呼应 Day 09 的 minimal 模式）。MEMORY 项由 resolveMemoryBootstrapEntry 解析（优先 MEMORY.md，缺失才 memory.md）。这套是"每次都带的随身记忆"。
L03

动态：语义检索

动态记忆暴露为两个工具：memory_search（语义搜索）、memory_get（按路径取）。入口 getMemorySearchManager（search-manager.ts:25）。工具定义（memory-tool.ts:40）：

const MemorySearchSchema = Type.Object({          // TypeBox 参数 schema
  query: Type.String(),
  maxResults: Type.Optional(Type.Number()),
  minScore: Type.Optional(Type.Number()),
});
return {
  label: "Memory Search", name: "memory_search",
  description: "Mandatory recall step: semantically search MEMORY.md ...",
  parameters: MemorySearchSchema,
  execute: async (_id, params) => { /* getMemorySearchManager().search() */ },
};
读法：这是一个标准工具（Day 11 讲工具形状）：名字 + 描述 + 参数 schema + execute。模型想回忆就调它，传 query，拿回相关记忆片段。检索对象是 MEMORY.md + memory/*.md（可选含会话转录）。
L04

双后端 + 回退

语义检索有两个后端，失败自动回退（search-manager.ts）：

  • QmdMemoryManager（:31-42）：外部 qmd 进程后端。
  • MemoryIndexManager（manager.ts）：内建索引后端。
  • FallbackMemoryManager（:104）：qmd 失败时切内建。
读法：又是"接口/实现分离 + 优雅降级"：优先用外部 qmd（更强），挂了自动退到内建索引（保底）。和 Day 07 的模型故障转移同一种"永不彻底失败"的韧性哲学，这里用在记忆检索上。记忆也能作为扩展提供（extensions/memory-core、memory-lancedb，Day 12）。
L05

混合检索

内建索引不是简单的向量搜索，而是一套组合拳（src/memory/）：

文件作用
embeddings*.ts多 provider 向量嵌入（openai/gemini/mistral/voyage/ollama）
sqlite-vec.ts向量存储（SQLite 向量扩展）
hybrid.ts向量 + 关键词混合检索
mmr.ts最大边际相关，去冗余
temporal-decay.ts时间衰减（新记忆权重更高）
query-expansion.ts查询扩展
为什么不只用向量搜索？ 纯向量搜索有短板：可能漏掉精确关键词、返回一堆重复内容、把很旧的记忆和新记忆同等对待。OpenClaw 叠加了：关键词混合（补向量的漏）、MMR 去重（结果更多样）、时间衰减（新记忆更重要）、查询扩展（把"我车"扩成"我的汽车/座驾"）。这些是工业级记忆/RAG 系统的标配技巧——目标是"检索出真正相关且不冗余的记忆"，而不是"向量最近的几条"。
L06

强制召回

系统提示里的 ## Memory Recall 段（system-prompt.ts:38-63，仅当具备 memory 工具时出现）强制模型"回答历史相关问题前先检索"，可带引用 Source: <path#line>。工具描述里也写了 "Mandatory recall step"。

读法：光有 memory_search 工具还不够——模型可能"懒得"用。所以在提示词里强制它"答历史问题前必须先搜记忆"。这是"用提示词约束模型行为"的典型：能力（工具）+ 纪律（提示指令）双管齐下，才能保证记忆真的被用起来。带 Source 引用则让回答可追溯。
L07

仅追加回写

助理产生新记忆要写回文件时，OpenClaw 限制得很紧（pi-tools.ts:538-559）：

// memoryFlushWritePath + MEMORY_FLUSH_ALLOWED_TOOL_NAMES
// wrapToolMemoryFlushAppendOnlyWrite：把 write 包装成"仅追加"到指定记忆文件
// 记忆刷写运行时只允许受限的几个工具
为什么只能"追加"不能"覆盖"？ 记忆是宝贵的长期资产。如果允许模型随意覆盖/删除记忆文件，一次幻觉或提示注入就可能抹掉你多年的记忆。所以回写被限制成只能往指定记忆文件末尾追加（append-only），且只有受限的几个工具能做。这是"最小权限 + 防误删/防攻击"的安全设计——宁可记多了（可后续整理），也不让它有能力毁掉已有记忆。Day 17 会看到更多这类安全纵深。
