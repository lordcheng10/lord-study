Day 06 / 共 20 天 · 第 2 周 Pregel 引擎

Pregel / BSP 模型

LangGraph 的执行引擎。它借鉴 Google Pregel（图计算）/ BSP（整体同步并行）模型——按"超步（super-step）"执行图。读 pregel/main.py 的 docstring。

📍 你在整门课的位置
invoke旅程→Pregel引擎→Channels→super-step
L01

不是传统调用链

🤔 痛点假设三个节点想同时改同一份状态（比如都往 count 里写）。传统写法里它们各自读一下、算一下、写回去——但"读"和"写"之间别人可能已经改了，于是结果乱套（竞态 race condition）。要靠加锁解决，又慢又容易死锁。怎么让"多个节点同时干活"既快又不出错？
💡 本质Pregel/BSP 的答案是"分步走 + 步内快照 + 步末统一提交"：把执行切成一个个"超步"，同一超步里的节点都读同一份"步初快照"（谁也改不了别人正在读的数据），各自的写入先攒着，等这一步所有节点跑完，才在超步之间统一合并提交。竞态从根上消失了——不用加锁，因为"读的时候没人写"。

LangGraph 的运行时不是"函数 A 调用函数 B"的传统调用链，而是 Pregel / BSP 模型。pregel/main.py:450 的 class Pregel docstring 说得清楚："Pregel combines actors and channels... following the Pregel Algorithm / Bulk Synchronous Parallel model."

Pregel / BSP 是什么？（一句话） Pregel 是 Google 为超大规模图计算设计的模型，BSP（Bulk Synchronous Parallel，整体同步并行）是它的执行范式。核心思想：计算分成一个个"超步（super-step）"，每个超步里"该干活的节点并行干活、干完统一同步一次状态"，然后进入下一超步。就像多人协作："大家各自干（并行）→ 到点了统一汇报同步（barrier）→ 再各自干下一轮"。LangGraph 把这个模型用于执行 Agent 图——比传统 while 循环更适合"并行 + 可中断 + 可持久化"。
BSP 就像生活中上班族开例会：会前各自埋头干活（超步内并行）→ 到点全员进会议室对齐进度、更新共识（屏障同步）→ 散会后再各自干下一轮。谁也不会在会议进行到一半时偷偷改掉公共白板。
L02

actor + channel

Pregel 的两个主角：actor（节点/PregelNode）和 channel（通道）。核心心智：

节点之间不直接通信，而是通过通道间接通信。actor 从它"订阅（subscribe）"的 channel 读数据、往 channel 写数据。一个 actor 只有在它订阅的 channel 在上一步被更新过时，才会在下一步运行。这就是 Day 04 讲的"通道触发"——节点不互相调用，靠"写通道→通道触发订阅者"解耦。
为什么用"通道间接通信"？ 如果节点 A 直接调用 B（b(a())），它们就耦合了——A 必须知道 B 存在。而"A 写通道、B 订阅通道"则解耦——A 只管往通道写，谁订阅了谁就被触发，A 不用知道 B。好处：能并行（多个节点同时读同一通道）、能动态路由（改订阅关系就改了流程）、能持久化（通道值就是可存的状态）。这是分布式系统的经典解耦思想。
L03

三阶段超步

每个超步分三阶段（main.py:464）：

同一超步内 A/B/C 并行算 → 到屏障统一同步 → 下一超步接着并行
Plan 计划选出这步要跑的节点→ Execution 执行并行跑这些节点→ Update 更新把写入应用到通道↺
🎵 记忆口诀（超步三拍） 「取任务 → 并行跑 → 齐提交」——Plan 取任务、Execution 并行跑、Update 齐提交，跑完看还有没有活儿，有就再来一拍。三个字记一辈子：取、跑、交。
读法：Plan：第一步选订阅 input 通道的节点；后续步选"订阅了上一步被更新的通道"的节点。Execution：并行跑所有选中节点，直到全完成。Update：把节点写出的值用 reducer 应用到通道。重复，直到没有节点可选。（这就是 Day 05 每个超步的三阶段。）
L04

快照隔离（关键设计）

main.py:2960 的注释是精华，值得背下来：

# Channel updates from step N are only visible in step N+1
# channels are guaranteed to be immutable for the duration of the step,
# with channel updates applied only at the transition between steps.
💬 小白 vs 老师 👶 小白：为什么不让节点算完就立刻把结果写进状态？那多直接。
👨‍🏫 老师：因为同一步还有别的节点正在读这份状态。你立刻改，它就读到"改了一半"的数据了。
👶 小白：那攒到最后一起写，会不会慢？
👨‍🏫 老师：几乎不慢，却换来了"结果确定、可复现、不用加锁"。就像开例会：讨论时以会前的会议纪要为准，新决定散会后才统一更新纪要——没人边开会边改纪要，才不会乱。
快照隔离：一步之内通道不变 关键规则：一个超步执行期间，通道是"冻结"的（不可变）——节点看到的是这一步开始时的状态快照。所有写入都攒着，只在超步之间（transition）统一应用。第 N 步的更新，第 N+1 步才可见。为什么这么设计？避免并行节点互相干扰！如果 A、B 同一步并行跑，B 读的状态不会被 A 中途改掉（都读同一份快照）——结果确定、可复现，不用担心竞态。"一步之内快照隔离、步末统一提交"是 BSP 让并行安全的核心。这和数据库的快照隔离一个道理。
L05

版本号触发

怎么判断"一个节点这步该不该跑"？_triggers（_algo.py:1260）——两个条件：

for chan in proc.triggers:            # 遍历节点订阅的触发通道
    if channels[chan].is_available()  # ① 通道有值
       and versions.get(chan) > seen.get(chan):  # ② 通道版本 > 节点上次见过的版本
        return True                    # 该跑！
📝 例子：版本号怎么防重复 通道 messages 初始版本 v0。节点 A 上次处理时记下 seen[messages]=v0。这一步有节点往 messages 写了新值 → 版本涨到 v1。下一步 Plan 检查 A：v1 > v0？是 → A 该跑。A 跑完把 seen[messages] 更新成 v1。再下一步若没人写 messages，版本仍是 v1，v1 > v1 不成立 → A 不会被无谓地再跑一遍。这就是"同一次更新只触发一次"。
版本号防重复触发 每个通道有个版本号（每次被更新就 +1）；每个节点记录它上次见过每个通道的版本。触发条件：通道有值 且 当前版本 > 节点上次见过的版本（说明这通道被新更新了、节点还没处理）。处理后节点更新"已见版本"，于是同一次更新不会重复触发同一节点。这个 channel_versions vs versions_seen 的机制保证了幂等触发——BSP 里"上一步更新才触发下一步"的精确实现。
L06

何时停

超步循环一直转到没有节点可跑（main.py:464："Repeat until no actors are selected"）。tick()（_loop.py:652）：没有任务 → status="done"、循环终止。

"没节点可跑"就是自然结束 Plan 阶段如果发现"没有任何节点的触发通道被更新"——就没节点要跑了，图执行结束。对 Agent 图：走到 END 意味着不再点亮任何节点的触发通道 → 下一步 Plan 选不出节点 → 停机。还有个安全网：recursion_limit（超步数上限），防止无限循环（tick 里 status="out_of_steps"）。正常靠"无节点可跑"结束，异常靠超步上限兜底——和其它框架的 max_iterations 一个思路。
L07

为什么用 BSP（回味）

  • 并行安全：快照隔离让同步的节点互不干扰、结果确定。
  • 可持久化：超步之间是清晰的"边界"，正好在这存检查点（Day 11）。
  • 可中断：超步边界可以暂停（human-in-the-loop，Day 14）。
  • 可重放：状态全在通道、每步存档，能回到任意超步重跑（时间旅行，Day 13）。
为什么不用简单的 while 循环？ while 循环里状态是内存变量，难并行（要手动加锁）、难持久化（内存不能存档）、难中断（跑到一半停不下来）。BSP 的"超步边界"给了天然的"暂停/存档/恢复点"——LangGraph 的持久执行、时间旅行、人在环，全建立在这个模型上。选 Pregel/BSP 不是炫技，是为了这些能力。这和 eino 的 Pregel 引擎（也叫这个名）异曲同工。
