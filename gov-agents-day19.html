Day 19 / 共 20 天 · 第 4 周 平台化与收官

从零开发一个新 Agent + L4 Skills

学了 18 天，今天把知识用起来——亲手 scaffold 一个新 agent，跑通全流程。再讲清 L4 Skills（让 IDE 一句话就调 agent）。

L01

两种起 agent 的方式

框架提供两条路径，先搞清你该走哪条：

① 平台 monorepo 内加

agent 直接进 apps/，成为 workspace 成员。用 agentctl new agent 脚手架 + agent-onboarding skill 指路。大多数情况走这条。

② 独立 git 仓开发

在自己的仓里，通过公司 Nexus 一行 BOM 依赖用 toolkit。用 standalone-repo-agent skill + examples/ 模板。没有 monorepo 权限时走这条。

今天主要讲①（monorepo 内），L07 简单过②。回忆 Day 05：无论哪条，agent 的目录结构完全一致（state/builder/nodes/specialists/prompts/server），所以学会一种就都会。

L02

决策树：动手前先问自己

agent-onboarding skill 会带你走一棵决策树。核心几问（呼应 Day 01 的分层铁律）：

Q1：这个能力是横切的（≥2 个 agent 会用）吗？

是 → 应该放进 toolkit（L2），不是新 agent。否 → 继续。

Q2：是单个 agent 的业务逻辑吗？

是 → 放 apps/（L3），起新 agent。

Q3：需要严格的规格评审流程吗？

是 → 走 OpenSpec cookbook（Day 20）。否 → 走快速 cookbook（docs/new-agent-cookbook.md，30 分钟起一个）。

Q4：复杂度多高？

简单 → 只动 nodes/+builder.py，specialists//tools/ 留空。复杂 → 上多专家并行。

为什么先问"是不是横切能力"？ 这是 Day 01 铁律的直接应用——如果一个能力多个 agent 都要用，它就该沉到 toolkit，而不是在某个 agent 里写死（否则第二个 agent 要用就得复制，违反渐进抽象）。动手前想清楚"这东西属于哪一层"，比急着写代码重要。
L03

scaffold 骨架

用 CLI 脚手架一键生成骨架（Day 13 提过）。它有 6 个 Jinja2 模板 pattern，按你的 agent 类型选：

# 6 个 pattern：minimal / rag / monitor / doc / business-data / supervisor
uv run agentctl new agent my-analyzer --pattern minimal

生成的骨架就是 Day 05 讲的标准结构：state.py / builder.py / nodes/ / specialists/ / prompts/ / server.py / main.py / pyproject.toml / tests/。省掉 80% 的样板代码——护栏、envelope、可观测的接线都是现成的。

命名铁律（new-agent-cookbook.md:72）：每个 agent 的顶层 Python 包名必须全仓唯一（如 my_analyzer，连字符转下划线）。因为所有包装在同一个 workspace 里，重名会冲突。脚手架会帮你处理这个转换。
L04

填 builder：你真正要写的业务图

骨架生成后，你 80% 的精力花在 builder.py——用 Day 03/05 学的那套 StateGraph → add_node → add_edge → compile 搭你的业务流程。简单 agent 可能就三个节点：

from langgraph.graph import StateGraph, START, END
from ai_trust_toolkit.llm import get_llm      # ← 走注入点，不 import anthropic

def build_graph():
    builder = StateGraph(MyState)
    builder.add_node("analyze", analyze_node)  # 你的业务节点
    builder.add_node("critic", build_business_critic_l1([...]))  # 复用 toolkit
    builder.add_edge(START, "analyze")
    builder.add_edge("analyze", "critic")
    builder.add_edge("critic", END)
    return builder.compile()

要点全是前面学的：调 LLM 走 get_llm()（Day 11）；工具用 @safe_tool_result（Day 11）；要专家就用 make_specialist_node（Day 05）；要 Critic 就 import toolkit 的（Day 07）；节点要能被 wrap_with_fallback 包（Day 08）。你只写业务，护栏全 import。

L05

加评测样本 + Critic（准入门槛）

回忆 Day 10 的硬规矩：新 Agent 必须先有评测样本 + Critic，才能合并。所以别忘了：

  • 在 data/eval_samples.jsonl 写几条 golden 样本（Day 10 的格式）；
  • 加一个 Critic 节点（满配用 build_critic_node，轻量用 build_business_critic_l1）；
  • tests/ 里的测试必须能用 FakeLLM 跑通（Day 11）——conftest.py 里 set_llm_factory(SystemAwareFake(...))。
# 跑一遍确认（不联网、几秒完成）
uv run --extra test pytest apps/my-analyzer -q
# 跑评测看分
uv run python apps/my-analyzer/scripts/run_eval.py
为什么把这俩设成准入门槛？ 因为它们是"可信"的最低保障——Critic 防这个新 agent 胡说，评测样本让 CI 能盯住它以后别退步。没有这两样，一个 agent 就是"不可信"的，不该进平台。这也是 AGENTS.md 收尾金句"保持评测样本同库、保持 Critic 兜底"的落地。
L06

注册：4 处必改（呼应 Day 12）

Day 12 讲过"发现机制是显式注册表，不是自动扫描"。所以新 agent 要手动接进平台，改 4 个地方（new-agent-cookbook.md）：

pyproject.toml

根 workspace members 加一条你的 agent 路径

pyproject.toml

pytest testpaths 加一条，让 CI 跑你的测试

gov_agents_server/main.py

AGENT_REGISTRY 加一行 "my-agent": ("my_agent.server", "build_router")

uv.lock

uv lock 重新生成，和上面改动放进同一 PR（Day 17）

做完这 4 步，ENABLED_AGENTS=my-agent uv run uvicorn gov_agents_server.main:app 就能把你的 agent 跑起来了，走 /v1/agent/my-agent/invoke 调用——所有治理（鉴权/限流/预算/envelope/落库/指标）白拿（Day 12 的 build_v1_router）。

完整 echo-agent 范例：new-agent-cookbook.md:444 有一个最小 30 行的 echo-agent，从 _invoke 到 build_v1_router 一应俱全，是你写第一个 agent 的最佳抄写对象。
L07

独立仓形态（没 monorepo 权限时）

如果你在自己的独立 git 仓开发，用 examples/standalone-agent-template/ 模板（平台也提供免登录 zip 下载）+ standalone-repo-agent skill 的 9 步。关键差异：

  • 不进 workspace，而是通过公司 Nexus 一行依赖 ai-trust-toolkit-bom[core]==0.6.0 拉 toolkit（需配 ~/.netrc Nexus 凭据）。
  • 结构和 monorepo 内一致（builder/state/nodes/specialists/prompts + core.py + cli.py + server.py），只是 core.py 多一层 telemetry 包装。
  • 三种形态入口：CLI / pod / 可扩 MCP。

"5 步起手"：改名 → 配 Nexus 凭据 → uv sync + .env 填 key → 填 builder.py 业务图 + 改领域 effect key → uv run --extra test pytest。依赖走 Nexus BOM 而非 vendor 源码，全平台升级只改一处。

📎 这条独立仓路径值得单独展开——完整的手把手 9 步（下模板 → Nexus 凭据 → 跑通 → 写业务图 → telemetry → CLI/MCP/pod 形态 → 测 → 安全自检 → obelisk 上线）+ 三大坑点，见 番外篇 · 独立仓 Agent 开发手把手 9 步 →

为什么区分两种形态？ 平台核心团队在 monorepo 里迭代（形态①，改 toolkit 立即生效）；外部业务团队没有 monorepo 权限，就在自己仓里用发布到 Nexus 的 toolkit（形态②）。BOM 让两种形态用的是同一套 toolkit，只是获取方式不同——一个 workspace 本地引用，一个 Nexus 拉包。
L08

L4 Skills：让 IDE 一句话调 agent

最后补上 Day 01 架构图最顶层的 L4 —— skills/。它是给 IDE 里的 AI（Claude Code / Cursor）用的一句话 SOP：把"该怎么调这些 agent"的操作流程沉淀成可触发的技能。

每个 skill = 一个目录 + 一个 SKILL.md（含 name/description/tier/触发词）。分三档 tier：developer / oncall / user-facing。举几个：

skill触发场景
agent-onboarding"我想加个新 agent" → 走决策树指路（L02 那个）
release-gate"这个 PR 能合吗" → 调 risk-reviewer 出 risk_score
eval-replay"这条 case eval 不达标" → 重放对比 5 维评分
case-to-eval-sample"把这个线上 case 变成回归样本"（Day 18 提过）
incident-postmortem"复盘这次 P0" → 拉 RCA envelope 出复盘

它进 git、团队共享（skills/registry.json 由 agentctl skill index 生成），区别于 .claude/（个人本地）。L4 只向下调 MCP tools / agentctl / OpenAPI，L1-L3 绝不 import skills——又是分层铁律。

Skill 和 MCP 的区别？ MCP（Day 13）是"给 IDE 的 AI 提供工具"；Skill 是"给 IDE 的 AI 提供操作流程 SOP"——告诉它"遇到这类需求，按这个步骤、调这些工具"。一个是工具，一个是使用工具的说明书。两者配合：Skill 编排流程，底层调 MCP/agentctl 执行。
