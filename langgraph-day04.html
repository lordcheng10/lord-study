条件边与路由

让图学会"if/router"。add_conditional_edges 用一个路由函数看状态、决定下一步去哪。这是 ReAct Agent"要不要继续调工具"的核心。读 graph/_branch.py。

📍 你在整门课的位置（第 1 周主线）
全景→StateGraph→State+reducer→条件边→invoke旅程
L01

条件边 = if/router

普通边（Day 02）是"固定连接"——a 之后一定是 b。条件边（add_conditional_edges，state.py:969）是"运行时决定"——从某节点出来后，跑一个路由函数、用它的返回值决定下一个去哪。

🤔 痛点：只有固定边，Agent 就"死板"了 👶 小白：Day 02 的 add_edge("a","b") 不是挺好？为什么还要条件边？
👨‍🏫 老师：固定边意味着"a 之后永远是 b"。可 Agent 的关键恰恰是"看情况"——LLM 这轮说要查天气就得去 tools，说能直接回答就该结束。固定边表达不了"看 LLM 输出临时决定去哪"，你只能又回到手写 if。
👶 小白：那条件边怎么知道去哪？
👨‍🏫 老师：你给它一个"路由函数"，它读状态、返回一个节点名字符串，框架就往那个节点走。
💡 本质：把"下一步去哪"从写死的连线，变成一次运行时的函数调用 普通边 = 编译期就定死的箭头；条件边 = 运行期才计算的箭头。本质就是把边的终点从常量换成"一个返回终点名的函数"——有了它，图才能表达"分支、循环、按 LLM 意图走不同路"的动态控制流。
agent 节点调 LLM→ 路由函数看状态 返回 "tools"→ tools 节点 返回 END→ 结束
一个 agent 节点，后面接条件边：路由函数看状态里最后一条消息，有 tool_calls 走 tools，没有就走 END
条件边就是图里的"岔路口" 普通边是"直路"，条件边是"看情况走哪条路的岔路口"。ReAct Agent 的核心判断"LLM 想调工具吗？想就去 tools 节点，不想就结束"就是一条条件边。有了它，图能表达"根据状态走不同路径"的复杂控制流。和 eino Graph 的 Branch、CrewAI Flow 的 @router 一个概念。
这就像生活中的客服热线：你说完问题，转接员（路由函数）判断该转哪个部门——"按 1 转账单、按 2 转技术"。而 path_map（L03）就是那张"按键→部门"的对照表。
L02

路由函数

def should_continue(state) -> Literal["tools", "__end__"]:
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END   # 看状态返回下一节点名

builder.add_conditional_edges("agent", should_continue)
读法：路由函数（path）读 state、返回"目标节点名"（字符串）。框架据此决定下一个跑哪个节点。add_conditional_edges 把它包装成 BranchSpec（_branch.py:83）存进 self.branches（state.py:1014）。运行时由 BranchSpec.run（_branch.py:122）调用你的路由函数、再由 _route（_branch.py:146）把返回值翻译成"点亮哪个下游"。
📝 例子：路由函数就是一个"翻译官" 假设某轮跑完 agent，State 最后一条消息是 AIMessage(tool_calls=[get_weather(...)])。
→ should_continue(state) 取 state["messages"][-1]，看到 last.tool_calls 非空 → return "tools"；
→ 框架收到字符串 "tools"，就去点亮 tools 节点。
换个场景：这轮 AI 直接回答了（tool_calls 为空）→ 函数 return END → 图停机。路由函数不"执行"什么业务，它只把"当前状态"翻译成"下一个节点的名字"。
L03

path_map 与自动推断

path_map（可选）把路由函数的返回值映射到真实节点名。若路由函数返回类型标注 Literal["a","b"]，BranchSpec.from_path（_branch.py:110）自动推断 path_map：

if get_origin(rtn_type) is Literal:
    path_map_ = {name: name for name in get_args(rtn_type)}   # 从 Literal 自动推断
⚠️ 小白常误以为 路由函数返回什么字符串都会被"当节点名"直接用。其实当你给了 path_map（或写了 Literal 注解），返回值是先过一遍映射表再落到真实节点——所以路由函数可以返回像 "continue"/"stop" 这类"业务标签"，由 path_map 翻译成真实节点名，读起来更清楚。
为什么要 path_map / Literal 注解？ 主要为了可视化和校验——框架需要提前知道"这个路由可能去哪些节点"才能画出图、检查目标节点都存在。你给路由函数标 -> Literal["tools", "__end__"]，框架就自动知道所有可能的分支目标。不标也能跑（返回值直接当节点名），但标了更清晰、可视化更准。"从类型注解自动推断"——又是 LangGraph 的约定优于配置。
L04

返回列表 = 并发扇出

路由函数可以返回一个列表 → 同时触发多个目标节点（_branch.py:_finish:192）：

def route(state):
    return ["node_a", "node_b", "node_c"]   # 同时触发三个节点并行跑
扇出（fan-out）= 一变多 返回单个名字 = 走一条路；返回列表 = 同时启动多个节点并行执行（fan-out/扇出）。用途：比如"同时问三个不同的专家节点"、map-reduce 的 map 阶段。还可以返回 Send 对象做动态并发（为每个数据项派一个任务，真正的 map-reduce）。条件边不只是"二选一"，还能"一变多"——图的表达力很强。配合 Day 03 的 reducer（多个并行节点的输出用 reducer 合并），扇出后能优雅汇总。
L05

循环（回头边）

条件边 + 普通回头边 = 循环（ReAct Agent 的核心）：

builder.add_conditional_edges("agent", should_continue)  # agent 后判断
builder.add_edge("tools", "agent")   # ★ tools 跑完回到 agent（回头边 = 循环）
读法：agent → 条件边（要工具就去 tools，不要就 END）→ tools 跑完 → 回头边把它连回 agent → agent 再判断…… 直到某轮不再要工具，走 END。这就是 ReAct 循环的图结构。
"循环"就是图里有一条回头边 传统编程用 while 循环。LangGraph 里"循环"= 图里有一条边指回之前的节点（tools → agent）。Agent 反复"调 LLM → 调工具 → 回到 LLM"就是在这个环里转，直到条件边判断"够了"走向 END。把循环表达成"图里的环"——清晰、可持久化（每轮存检查点）、可中断。这和 eino Graph 的"回头边=循环"、Day 16 的 create_react_agent 完全一致。
这就像生活中的老师改作业：交上去 → 老师看（agent 判断）→ 有错就打回重做（去 tools 补充）→ 再交 → 再看……直到某次老师说"过了"（不再要求修改）就结束。改几轮不是写死的，是"看质量"临时决定的——这正是条件边 + 回头边的循环。
🔍 单步走查表：跟一个真实输入"北京天气?"走完循环
步当前节点此刻发生什么走哪条边 → 去哪
1agentLLM 输出"我要调 get_weather"（带 tool_calls）条件边：有 tool_calls → tools
2tools执行 get_weather(北京) 得"25℃"回头边 → agent
3agentLLM 看到 25℃，直接答（无 tool_calls）条件边：无 → END 停机
同一条条件边，第 1 步把它送去 tools，第 3 步把它送去 END——差别只在"那一刻状态里有没有 tool_calls"。
L06

通道触发机制（边怎么"启动"下一个节点）

初学者最困惑：边到底怎么"启动"下游节点？答案是通道触发（编译时焊接，state.py:1512）：

  • 每个节点有个专属触发通道 branch:to:<节点名>，节点"订阅"它作为触发条件。
  • 普通边 a→b（attach_edge）：让 a 跑完往 branch:to:b 通道写一下 → 点亮 b。
  • 条件边（attach_branch）：把路由函数的输出（目标节点集合）翻译成"往哪些 branch:to:* 通道写"。
节点不直接调用彼此 关键设计：节点之间不直接互相调用，而是通过"写通道 → 通道触发订阅者"解耦。a 跑完不是"调用 b"，而是"往 b 的触发通道写一下"，下一超步引擎发现 b 的触发通道被更新了就跑 b。好处：同一超步能并发跑多个节点，引擎在步末统一合并所有写入（Day 06 的 Pregel）。这个"发布-订阅"解耦是并发、可中断、可重放的根基——Day 07 详讲通道。
L07

汇合 barrier

Day 02 的多起点边 add_edge(["a","b"], "c")（等 a、b 都完成才跑 c）靠 NamedBarrierValue 通道实现（state.py:1546）——一个"栅栏"通道，等所有起点都写过才放行 c。

barrier（栅栏）= 等齐再走 扇出（L04）是"一变多"，汇合（fan-in）是"多变一"——比如三个并行节点都完成后，才跑"汇总"节点。NamedBarrierValue 是一道栅栏：记录"还差谁没到"，所有上游都写过了才放行下游。这样"等所有并行分支完成再汇总"就自动成立。扇出 + 汇合 = map-reduce：先分成多路并行（map），再等齐汇总（reduce）。LangGraph 的图能优雅表达这种并行模式。
