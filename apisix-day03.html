Day 03 / 共 20 天 · 第 1 周 全景与请求生命周期

启动流程：从命令到就绪

今天看 APISIX 怎么"开机":从 apisix start 命令，到根据 config.yaml 生成 nginx.conf，再到 OpenResty 拉起后在 init/init_worker 阶段初始化各子系统。理解启动，才知道请求处理时那些对象是何时准备好的。

L01

bin/apisix 命令

你用 apisix start / stop / reload / test 管理 APISIX。这个命令背后是 apisix/cli/apisix.lua——一个用 LuaJIT 直接跑的脚本。apisix.lua:26-31 设置 Lua 包路径（找到 deps/ 里的依赖）。

CLI 和"网关本体"是两回事 别混淆：apisix/cli/ 是"管理命令行"（生成配置、启停 OpenResty），它只在你敲命令时跑一下；真正处理请求的是 OpenResty 加载的 apisix/init.lua 等（长期运行）。CLI 的活是"准备好配置文件、然后把 OpenResty 拉起来"，之后就退出了。好比"点火开关"（CLI）和"发动机"（OpenResty + init.lua）。
L02

CLI 目录

apisix/cli/
  apisix.lua    入口（设包路径 → 调 ops）
  ops.lua       start/stop/reload/test 等操作实现
  ngx_tpl.lua   nginx.conf 模板（Lua 字符串模板）
  config.lua    读取合并 conf/config.yaml
  schema.lua    校验 config.yaml
  etcd.lua      启动时初始化 etcd（建目录、写默认值）
  env.lua / file.lua / ip.lua / util.lua   辅助
读法：核心是 ops.lua（操作逻辑）+ ngx_tpl.lua（配置模板）。启动时：读 config.yaml → 校验 → 渲染 ngx_tpl 生成 nginx.conf → 初始化 etcd → 用 openresty 命令拉起。
L03

生成 nginx.conf

关键一步：ngx_tpl.lua 是一个大的 Nginx 配置模板，启动时用 config.yaml 的值填充，生成真正的 conf/nginx.conf。模板里包含昨天说的阶段绑定：

-- ngx_tpl.lua 里（简化）
init_by_lua_block { require("apisix").http_init() }
init_worker_by_lua_block { require("apisix").http_init_worker() }
access_by_lua_block { require("apisix").http_access_phase() }
header_filter_by_lua_block { require("apisix").http_header_filter_phase() }
body_filter_by_lua_block { require("apisix").http_body_filter_phase() }
log_by_lua_block { require("apisix").http_log_phase() }
"配置即代码"的生成 APISIX 不让你手写 nginx.conf——它根据你的 config.yaml（简单的 YAML）自动生成完整的 nginx.conf。你只关心"用哪个 etcd、监听哪个端口、开哪些功能",复杂的 Nginx 配置由模板生成。生成的 nginx.conf 里把每个 Nginx 阶段绑到 apisix 模块的对应函数——这就是昨天说的"Lua 挂到阶段"的落地。你可以 apisix test 只生成配置不启动，去 conf/nginx.conf 看生成结果。
L04

http_init（master 一次）

init.lua:85-104：

function _M.http_init(args)
    core.resolver.init_resolver(args)   -- DNS 解析器
    core.id.init()                       -- 生成/读取实例 id
    core.env.init()                      -- 环境变量
    local process = require("ngx.process")
    process.enable_privileged_agent()    -- 特权 agent 进程（做需要 root 的活）
    if core.config.init then
        core.config.init()               -- 初始化配置中心（etcd）
    end
    xrpc.init()                          -- stream 的 RPC 框架
end
读法：master 阶段只做"全局一次性"准备：DNS、实例 id、环境、配置中心连接、特权 agent。特权 agent 是 OpenResty 的一个特殊进程，用来干"需要特权/只需一个进程干"的活（比如证书自动续期）。
L05

http_init_worker（每 worker）

init.lua:107-140 逐个初始化子系统（每个 worker 都跑）：

function _M.http_init_worker()
    math.randomseed(seed)                        -- 随机种子
    require("apisix.events").init_worker()
    discovery.init_worker()                       -- 服务发现（Day 16）
    require("apisix.balancer").init_worker()      -- 负载均衡
    require("apisix.admin.init").init_worker()    -- Admin API（Day 17）
    require("apisix.timers").init_worker()        -- 定时器框架
    core.config.init_worker()                     -- 配置中心 worker（etcd watch）
    plugin.init_worker()                          -- 插件系统（Day 11）
    router.http_init_worker()                     -- 路由（Day 06）
    require("apisix.consumer").init_worker()      -- 消费者（Day 14）
    -- global_rules / upstream / control_api ... 逐个 init_worker
    plugin.init_prometheus()                      -- 放最后确保所有 worker 就绪
end
这是 APISIX 的"零件清单" 这个函数几乎列全了 APISIX 的所有子系统——router、plugin、consumer、discovery、balancer、admin、timers…每个都在 worker 启动时 init_worker 一下（建立 etcd watch、起后台定时任务）。本课后面每一天，几乎都在讲这里初始化的某个子系统。读懂这个函数，就有了整个 APISIX 的"目录"。
L06

子系统 init_worker 干什么

各子系统的 init_worker 通常做两件事：

  • 建立 etcd watch：订阅自己关心的配置（router 订阅 /routes、consumer 订阅 /consumers…），配置变了内存里更新。
  • 起后台定时任务：健康检查、指标上报、配置轮询兜底等（用 timers 框架）。
读法：这就是"全动态"的实现——每个子系统在 worker 里 watch 自己那部分 etcd 数据，配置一变立刻在内存生效。Day 07 会深入 config_etcd 看 watch 机制。
L07

启动时序图

1
apisix start → cli/ops.lua：读 config.yaml + 校验
2
渲染 ngx_tpl.lua → 生成 conf/nginx.conf（含阶段绑定）
3
初始化 etcd（建目录/默认配置）→ 用 openresty 命令拉起
4
OpenResty master：init_by_lua → http_init（全局初始化）
5
每个 worker：init_worker_by_lua → http_init_worker（各子系统 watch etcd + 起定时器）
6
就绪，开始接请求 → http_access_phase（Day 04）
