LLM 抽象

大模型是 Agent 的"智力"。今天读 llm.py：litellm 如何统一上百种模型、"原生 SDK + litellm 兜底"的双轨设计、function calling 和流式。

L01

LLM 是 Agent 的"智力"

🤔 场景：老板说"把 GPT 换成 Claude 试试效果" 你的 Agent 项目原本用 OpenAI。现在想换成 Anthropic 的 Claude、或本地跑的开源模型比比效果。难道要把所有调用 OpenAI API 的代码全部重写一遍？每家模型的 API 参数、返回格式都不一样啊。
💡 一句话本质：LLM 抽象 = 统一插座 / litellm = 万能转接头 各家模型像各国不同的插头，你的 Agent 代码是"电器"。LLM 抽象层提供一个统一插座，底层的 litellm 是万能转接头，把上百家模型都适配成同一种插法。换模型 = 换个插头（改一行 model 字符串），电器（业务代码）纹丝不动。

Day 02 说 Agent 由 LLM 驱动。这个 LLM 就是 LLM(BaseLLM)（llm.py:368），它统一封装了对各家大模型的调用，让 Agent/Task/Crew 不用关心"到底调的是 GPT 还是 Claude"。

Agent 只调统一的 LLM 接口，底层 litellm 用一个 provider/name 字符串路由到 OpenAI / Anthropic / Gemini / 本地等上百家模型。换模型只需改这个字符串。
📝 最小例子：一行字符串切换模型 用 OpenAI：Agent(llm="gpt-4o", ...)
想换 Claude？只改这一行：Agent(llm="anthropic/claude-sonnet-4-20250514", ...)
想跑本地？Agent(llm="ollama/llama3", ...)
业务逻辑、任务、工具一个字都不用动——这就是抽象层的价值：model="provider/name" 一根字符串统管全部。
为什么需要 LLM 抽象层？ 每家模型的 API 不一样（OpenAI/Anthropic/Google 各一套）。如果 Agent 代码直接写 OpenAI 的调用，换模型就得改一堆代码。LLM 抽象层把"怎么调各家模型"的差异封装起来，对上提供统一接口。你改个模型名字符串就能换模型，Agent 逻辑纹丝不动——这就是"自带模型"（bring your own model）的基础。
🔌 生活类比：LLM 抽象 = 家里的"标准插座"，litellm = 万能转接头 你家墙上的插座是统一标准：不管插电视、充电器还是台灯，插孔都一样，电器不用关心发电厂用的是水电还是核电。LLM 抽象层就是这个标准插座——Agent（电器）只管往里插。出国旅行插头对不上？带个万能转接头（litellm），什么国家的插座都能转。换模型 = 换个插头形状（改 model 字符串），插座标准和电器都不动。今天整节课就围绕"插座 + 转接头"这个世界观。
🔢 数字具象感受一下 litellm 这个"万能转接头"有多能转：它统一对接了 100+ 家模型供应商（OpenAI、Anthropic、Google、Azure、AWS Bedrock、Mistral、Cohere、Ollama 本地……）。也就是说这一个抽象层背后，理论上你能一行字符串切换上百种大模型。
💬 对话体：换个模型到底要不要重写代码？ 小白问：老板让我把 GPT 换成 Claude 比效果，是不是得把项目里所有调 OpenAI 的地方全重写？
答：不用。有 LLM 抽象层，你只改一处：llm="gpt-4o" → llm="anthropic/claude-sonnet-4-20250514"。
小白问：那 Agent、任务、工具那些代码呢？
答：一个字都不动。它们只认"统一插座"，不管背后插的是哪家模型。
小白问：万一那家模型很冷门、没原生支持呢？
答：自动走 litellm 兜底（L02 的双轨），照样能接——这就是为什么"换模型"在 CrewAI 里几乎是零成本。
L02

双轨设计：原生 SDK + litellm 兜底

CrewAI 用 litellm 统一对接上百个模型供应商，但对主流供应商优先走原生 SDK：

  • 主流供应商（OpenAI/Anthropic/Azure/Bedrock/Gemini）：走原生 SDK 实现（更精准、支持更多特性）。
  • 其他所有：回退到 litellm（万能适配，覆盖上百种）。
为什么"双轨"而不只用 litellm？ litellm 覆盖广但是"最大公约数"——为了统一，可能不支持某家模型的独特高级特性。对最常用的几家（OpenAI/Claude），直接用它们的官方 SDK，能用上全部特性、更稳定；对长尾的上百家，用 litellm 兜底，保证"什么都能接"。常用的走精品路线、长尾的走通用路线——两全其美。接着"插座"的类比：主流几家是"原装专用插座"（贴合、支持全部功能），长尾上百家走"万能转接头"（能插但只保证通用功能）——两种插法并存。
L03

__new__ 工厂路由

路由发生在 __new__（llm.py:393）——根据 model 字符串决定返回哪种实现：

# 概念：LLM("gpt-5") 或 LLM("anthropic/claude-...")
# 若前缀是原生供应商（openai/anthropic/... provider_mapping :432）
#   且模型在常量表里 → 返回原生实现类（llm.py:478）
# 否则 → 回退到 litellm 实现
读法：__new__ 是 Python 的"对象创建工厂"——在这里根据你传的 model 字符串，决定实例化哪个实现类。你写 LLM("gpt-4o")，框架帮你选了 OpenAI 原生实现；写一个冷门模型，就选 litellm 实现。对你完全透明。
这是"工厂模式"：用一个统一入口 LLM(...)，根据参数返回不同的具体实现。调用方（Agent）只知道拿到一个"能调模型的东西"，不关心底层是原生还是 litellm。和 Day 02 的 create_llm（字符串→LLM 对象）配合，构成"配置即代码"的完整链条。
L04

litellm 懒加载

litellm 是懒加载的（_ensure_litellm，llm.py:113）——只在真正需要时才 import。

为什么懒加载 litellm？ litellm 这个库 import 时会做一些副作用（比如自动 load_dotenv() 加载环境变量），而且它比较重。如果你用的是原生 SDK 路径（比如就用 OpenAI），根本不需要 litellm——那就别 import 它，省启动时间、避免不必要的副作用。只有当真的走到 litellm 路径时才 import。"用到才加载"——和 Day 12 的 Flow 懒加载接线、Day 15 的双轨一样，都是"按需付出成本"的优化。
L05

call：高层调用入口

call()（llm.py:1820）是统一的调用入口，流程：

# call 流程
# 1. 发 LLMCallStartedEvent（事件总线）
# 2. 校验参数、把 str 消息转成 [{"role":"user",...}]
# 3. 跑 before-hook
# 4. _prepare_completion_params（:748）
# 5. 按是否流式分流：
if self._effective_stream():
    result = self._handle_streaming_response(...)     # 流式
else:
    result = self._handle_non_streaming_response(...)  # 非流式
读法：call 统一了"发事件 → 规范化消息 → 准备参数 → 流式/非流式分流"这套流程。无论底层是原生还是 litellm，调用方都用同一个 call。发 LLMCallStartedEvent 让 LLM 调用可被监控（Day 18 事件系统）。
L06

function calling 支持

Day 07/14 讲的"原生函数调用"就靠这里：

  • supports_function_calling（llm.py:2402）：判断当前模型支不支持原生函数调用（litellm 路径用 litellm.utils.supports_function_calling）。
  • 非流式响应 _handle_non_streaming_response（:1220）里，若返回了 tool_calls 且提供了 available_functions，就调 _handle_tool_call（:1356）执行工具。
available_functions 就是 Day 14 讲的"函数名→tool.run 映射"。整条链串起来：工具转 OpenAI schema（Day 14）→ 发给 LLM → LLM 返回 tool_call → LLM 层从 available_functions 找到函数执行（Day 14/15）→ 发 ToolUsageStartedEvent（Day 18）。Day 07/14/15/18 讲的是同一条工具调用链的不同环节。
L07

流式与降级

_handle_streaming_response（llm.py:800）遍历流式 chunk，累积内容与增量 tool_calls。有个健壮性设计：

流式的自动降级 :934——如果流式模式下一个 chunk 都没收到（某些模型/配置下流式可能异常），会自动降级回非流式再调一次。这样即使流式出问题，用户也能拿到结果，不会空手而归。"优雅降级"——首选方案失败时自动退到备选，保证功能可用。这和 Day 07 的"原生模式不支持就降级到文本 ReAct"、Day 15 的"非主流模型降级到 litellm"是同一种健壮性思维。好框架处处有兜底。
流式为什么重要？让用户看到"打字机效果"、能提前发现跑偏——和 OpenHands Day 14 讲的一致。整个流式过程通过 _handle_emit_call_events（:2150）发事件，接入可观测性。
