Day 17 / 共 20 天 · 第 4 周 Agent/Workflow/生态

Agent 智能体

建在 Workflow 上的 Agent——能让 LLM 自主决定"用哪个工具、怎么多步解决问题"。今天看 FunctionAgent（工具调用）和 ReActAgent（推理-行动循环），以及 RAG 怎么作为 Agent 的一个工具。

L01

什么是 Agent

Agent = 会用工具、能多步推理的 LLM 普通 LLM 只会"聊天"。Agent 给它加了两样：① 工具（能调函数：查数据库、算数、搜网、跑 RAG）；② 自主循环（自己决定"该用哪个工具、用完看结果再决定下一步",直到解决问题）。比如问"北京今天气温比上海高几度?"——Agent 会：调天气工具查北京 → 调天气工具查上海 → 算差值 → 回答。这超越了 RAG 的"一次检索一次生成"——是"多步、动态、自主"的。LlamaIndex 的 Agent 都建在 Day 16 的 Workflow 上（agent/workflow/）。
L02

tools 工具

tools/：BaseTool、FunctionTool（把普通 Python 函数包成工具）、QueryEngineTool（把查询引擎包成工具）。工具 = 名字 + 描述 + 参数 schema + 可调用的函数。

from llama_index.core.tools import FunctionTool
def multiply(a: int, b: int) -> int:
    """两数相乘"""
    return a * b
tool = FunctionTool.from_defaults(fn=multiply)   # 函数 → 工具
工具的"描述"是给 LLM 看的 工具的名字、docstring（描述）、参数类型会被转成 LLM 能理解的"工具规格"。LLM 看着这些描述，决定"这个任务该调哪个工具、传什么参数"（回想 Day 15 的 function calling）。所以工具的描述要写清楚——LLM 靠它判断何时用。QueryEngineTool 把 Day 12 的查询引擎包成工具——这样 RAG 就成了 Agent 的一种能力（L06）。
L03

FunctionAgent

agent/workflow/function_agent.py:19：class FunctionAgent(BaseWorkflowAgent)——基于 LLM 原生的"函数调用"能力的 Agent。

from llama_index.core.agent.workflow import FunctionAgent
agent = FunctionAgent(tools=[multiply_tool, weather_tool], llm=llm)
response = await agent.run("北京比上海气温高几度?")   # 自主调工具、多步、给答案
依赖 LLM 的原生工具调用 现代 LLM（GPT-4/Claude）原生支持"函数调用"——你给它工具列表，它直接返回"我要调 weather('北京')"这样的结构化决策。FunctionAgent 就用这个：把工具给 LLM，LLM 决定调哪个，Agent 执行工具、把结果喂回 LLM，循环直到 LLM 给出最终答案。这是最主流、最可靠的 Agent 形式（模型原生支持，比让模型"用文字描述要调什么"稳）。
L04

take_step

function_agent.py:33-48 的 take_step（简化）：

async def take_step(self, current_llm_input: List[ChatMessage], tools, ...):
    # 把对话历史 + 工具列表喂给 LLM，让它决定：直接答 or 调工具
    response = await self.llm.achat_with_tools(tools=tools, chat_history=current_llm_input, ...)
    # 返回 LLM 的决策（含要调的工具 + 参数，或最终答案）
Agent 的一"步" take_step 是 Agent 循环里的一步：把当前对话 + 工具喂给 LLM，LLM 要么"决定调某工具",要么"给出最终答案"。这个 take_step 被包在 Day 16 的 Workflow 里循环执行：调工具 → 结果加进对话 → 再 take_step → 直到 LLM 不再调工具（给出答案）。Workflow 的"事件循环"正好表达这个"想-做-看-再想"的循环——这就是为什么 Agent 建在 Workflow 上。
L05

ReActAgent

agent/workflow/react_agent.py:38：ReActAgent——用 ReAct（Reasoning + Acting）范式，让 LLM 用文字输出"思考-行动-观察"：

Thought: 我需要先查北京气温        # 推理（:169-171 的提示词格式）
Action: get_weather
Action Input: {"city": "北京"}      # 行动
Observation: 北京 15°C             # 观察（工具返回）
Thought: 再查上海...               # 继续循环
... Thought: 我知道答案了
Answer: 北京比上海高 3 度
Thought推理→ Action调工具→ Observation看结果→ 循环直到 Answer
FunctionAgent vs ReActAgent FunctionAgent 用模型原生函数调用（结构化、可靠，需模型支持）；ReActAgent 让模型用文字输出 Thought/Action/Observation（不需原生函数调用，任何模型都能用，但要解析文字、稍不稳）。回想你学过的 crewAI/langgraph 里的 ReAct——同一个经典范式。有原生函数调用的模型优先 FunctionAgent；老模型/开源模型用 ReActAgent。
L06

RAG 作为工具

QueryEngineTool.from_defaults(query_engine, name, description) 把 Day 12 的查询引擎包成工具，给 Agent 用。

RAG 和 Agent 的结合（本课两条主线汇合） 前三周的 RAG 查询引擎，可以作为 Agent 的一个"工具"——Agent 遇到"需要查资料"的问题时，调这个 RAG 工具检索答案。比如一个客服 Agent 有多个工具：RAG 工具（查产品手册）、订单查询工具、退款工具。用户问啥，Agent 自主决定用哪个。这就是"Agentic RAG"——RAG 不再是固定流程，而是 Agent 能按需调用的能力之一。本课的两条主线（RAG + Agent）在这里汇合。
L07

多智能体

agent/workflow/multi_agent_workflow.py：AgentWorkflow 支持多个 Agent 协作——不同 Agent 各有专长和工具，互相"移交"（handoff）任务。

读法：复杂任务可以拆给多个专家 Agent：一个负责研究、一个负责写作、一个负责审核，互相传递。它们也建在 Workflow 上（Agent 之间用事件通信）。回想你学过的 crewAI（多智能体协作）、AutoGPT——LlamaIndex 的 AgentWorkflow 是它对标的多智能体能力。codeact_agent.py 还有能写代码执行的 CodeAct Agent。
