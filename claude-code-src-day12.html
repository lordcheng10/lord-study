MCP 客户端

MCP 让 Claude Code 能接入任意外部工具（数据库、浏览器、内部 API…）。今天讲它怎么连、怎么发现工具、怎么把外部工具和内置工具无缝并给模型用。

L01

MCP 是什么

MCP（Model Context Protocol，模型上下文协议）是一个开放标准，让 AI 应用能"即插即用"地接入外部工具和数据源。你写一个 MCP server（比如封装你公司的内部 API），任何支持 MCP 的客户端（Claude Code、Cursor…）都能连上它、用它提供的工具——不用改客户端代码。

打个比方：MCP 之于 AI 工具，就像 USB 之于外设。USB 定了统一接口，鼠标键盘 U 盘都能插同一个口。MCP 定了"工具怎么描述、怎么调用、怎么返回"的统一协议，任何 MCP server 提供的工具都能被任何 MCP 客户端使用。这样生态里的工具能互通，不用为每个客户端各写一遍。

核心代码：客户端库 packages/mcp-client/、宿主集成 src/services/mcp/。

L02

先厘清：客户端 vs 服务端（易混）

Claude Code 在 MCP 里有两个身份，别搞混：

src/entrypoints/mcp.ts

Claude Code 作为 MCP Server（claude mcp serve）——把自己的内置工具暴露给别的 MCP 客户端用。这不是本节重点。

packages/mcp-client/ + src/services/mcp/

Claude Code 作为 MCP 客户端——连接外部 MCP server、用它们的工具。这才是今天讲的。

为什么一个程序既是客户端又是服务端？ 作为客户端：Claude Code 用你配的外部工具（如查数据库）。作为服务端：别的 AI 应用可以把 Claude Code 的能力（读写文件、跑命令）当工具来用。两个方向独立。今天只关心"Claude Code 怎么用外部工具"，即客户端方向。
L03

支持的传输方式

"传输（transport）"= Claude Code 和 MCP server 之间怎么通信。配置类型枚举（src/services/mcp/types.ts:24）：stdio / sse / http / ws / sdk / ...。建连在 src/services/mcp/client.ts：

传输怎么连适合
stdio（默认）启动一个子进程，通过标准输入输出通信（:959）本地工具（最常用）
sseServer-Sent Events（:674）远程 HTTP 服务
httpStreamable HTTP（:862）远程 HTTP 服务
wsWebSocket（:735）需要双向实时
sdk进程内直连（:918）Chrome/Computer-Use 等内建
stdio 为什么最常用？ 本地 MCP server 就是一个可执行程序（比如 npx some-mcp-server）。stdio 传输就是"启动这个程序，往它的标准输入写 JSON-RPC 请求、从标准输出读响应"——像管道一样。不需要网络端口、不需要认证，最简单。你在 .mcp.json 里写 command + args 的就是 stdio 型。JSON-RPC 是 MCP 底层用的消息格式（一种基于 JSON 的远程调用协议）。
L04

.mcp.json 配置

项目级配置文件是仓库根的 .mcp.json（config.ts:89）。一个典型配置：

{
  "mcpServers": {
    "my-db": {                              // 服务器名
      "command": "npx",                     // stdio: 启动命令
      "args": ["-y", "my-db-mcp-server"],
      "env": { "DB_URL": "..." }
    },
    "internal-api": {
      "type": "http",                       // http 型
      "url": "https://mcp.mycompany.com"
    }
  }
}

读取与合并（config.ts）：支持四个作用域——project（.mcp.json）/ user / local / enterprise（managed-mcp.json，企业锁定）。getAllMcpConfigs（:1258）汇总所有来源 + 插件提供的 server。企业可用策略"只允许托管 MCP"（:1486）。

为什么分四个作用域？ 跟 Day 09 权限规则、Day 17 配置一样的分层思路：project 的 .mcp.json 进 git、团队共享；user 是你个人全局的；local 是本机不进 git 的；enterprise 是公司强制的（最高优先级，能锁死"只准用这些")。这样团队协作、个人定制、企业管控三不误。
L05

工具发现流程

连上 server 后，怎么知道它有哪些工具？discoverTools（packages/mcp-client/src/discovery.ts:47）：

连上 server建立传输→ tools/list问它有啥工具→ 清洗 + 映射转成内部 CoreTool→ 重命名加 mcp__ 前缀
  • 发 tools/list 请求拿到工具清单（:57）。
  • 每个 MCP 工具映射成内部 CoreTool（Day 07 的协议层类型！）——所以 MCP 工具和内置工具是同一种接口。
  • 重命名：buildMcpToolName(serverName, tool.name) 生成全限定名，前缀 mcp__（:66）。比如 my-db server 的 query 工具 → mcp__my-db__query。
  • 工具注解（readOnlyHint/destructiveHint）映射成 isReadOnly/isDestructive（:83，接 Day 08 的行为标志）。
为什么加 mcp__server__tool 前缀？ 因为不同 MCP server 可能有同名工具（都叫 query）。加上 server 名前缀就不会冲突，模型也能看出"这个工具来自哪个 server"。而且权限规则可以按前缀批量控制——deny: ["mcp__my-db"] 一下禁掉整个 server 的所有工具（Day 07 讲的前缀级 deny）。发现结果还会做 LRU 缓存（:122），不用每次重新问。
L06

与内置工具无缝并列

MCP 工具怎么和内置工具一起给模型？回忆 Day 07 的 assembleToolPool——它就是干这个的（React 侧入口 src/hooks/useMergedTools.ts）：

// 内置工具 + MCP 工具 合并、去重、排序
assembleToolPool(toolPermissionContext, mcpTools)
//   getTools()（内置）+ mcpTools + MCP deny 过滤 + 去重（内置优先）+ 按名排序
关键：对模型完全透明。因为 MCP 工具在发现时就被映射成了 Day 07 的 CoreTool（同一种接口），到了 assembleToolPool 这里，内置工具和 MCP 工具长得一模一样，合并、排序、转成 API tool 定义（Day 07 的 toolToAPISchema）都走同一套代码。模型看到的工具池里 Read（内置）和 mcp__my-db__query（MCP）并排站着，调用方式也一样。这就是 Day 07"两层接口"设计的回报——协议层统一，扩展工具能无缝并入。唯一区别：MCP 工具的 schema 用它原始的 inputJSONSchema 而非 zod 转换（Day 07 讲过）。
L07

连接韧性：断了怎么办

外部 MCP server 可能崩、可能断网。packages/mcp-client/src/connection.ts 做了不少韧性处理：

  • 连接超时 withConnectionTimeout（默认 30s，:16）——连不上不无限等。
  • 断线监控 + 重连 installConnectionMonitor（:200）：连续 3 次终止性错误就触发重连（MAX_ERRORS_BEFORE_RECONNECT）。
  • 进程清理升级 terminateWithSignalEscalation（:308）：关 stdio 子进程时 SIGINT → SIGTERM → SIGKILL 逐级升压，确保进程真被杀掉。
为什么这么小心？ 因为 MCP server 是"外部的、不受控的"——它可能是第三方写的、质量参差。一个挂掉的 MCP server 不能拖垮整个 Claude Code。超时、重连、强制清理这套，是"和不可靠的外部依赖打交道"的标准韧性套路，跟 gov-agents 教程里的"失败闸门/优雅降级"是同一种防御思想。一个 MCP server 连不上，只是它的工具用不了，Claude Code 其余照常。
