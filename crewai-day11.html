Flow：事件驱动编排

CrewAI 的第二种范式。Crew 是"让 Agent 自主协作"，Flow 是"你精确控制步骤顺序"的确定性事件驱动工作流。今天讲它是什么、与 Crew 的区别、三段式架构。

L01

Flow 是什么

Flow（工作流）是较新的、事件驱动、确定性的编排范式。你用装饰器把一组普通方法连成一张图，引擎按"某方法完成 → 触发监听它的方法"精确推进。Flow 类在 flow/flow.py:33。

先建直觉 Flow 像你画的一张流程图：开始 → 步骤A → (成功?) → 步骤B / 步骤C。你精确规定了"先做什么、哪一步完成后触发哪一步、什么条件走哪条分支"。Flow 本身不需要 LLM 决策——路线是你写死的。但 Flow 的某一步内部可以调用一个 Crew 或 Agent（让 AI 在那一步自主发挥）。一句话：Crew = 让 Agent 自己决定怎么干；Flow = 你决定步骤顺序，把 Crew/Agent 当成其中一步。
L02

Flow vs Crew

👥 Crew

  • 自主 Agent 团队
  • 行为涌现式/非确定
  • 你给目标，AI 决定过程
  • 适合开放、创造性任务

🔀 Flow

  • 事件驱动的方法图
  • 行为确定/可控
  • 你写死步骤和分支
  • 适合流程固定、要精确控制
什么时候用哪个？ 需要"AI 自主完成一个开放任务"（写报告、做研究）→ Crew。需要"精确控制的多步骤流程，某些步骤用 AI"（比如：读邮件 → 分类 → 如果是投诉就用 Crew 生成回复 → 发送）→ Flow。实践中常组合：Flow 控制大流程，某步内嵌 Crew 让 AI 发挥（L06）。
L03

一个最小 Flow

from crewai.flow import Flow, start, listen

class MyFlow(Flow):
    @start()                          # 入口点
    def fetch_data(self):
        return "原始数据"

    @listen(fetch_data)               # 监听：fetch_data 完成后触发
    def process(self, data):          # data 就是 fetch_data 的返回值
        return f"处理后的：{data}"

result = MyFlow().kickoff()           # 开工
读法：@start() 标记入口方法，@listen(fetch_data) 标记"fetch_data 完成后我就执行"。上游方法的返回值作为参数传给下游（data）。你不用手写"调完 fetch_data 再调 process"——装饰器声明了这个"接线"，引擎自动按事件推进。
和 Crew 写法的直观区别 Crew 里你定义 Agent 和 Task，然后"放手让它们协作"。Flow 里你写普通的 Python 方法，用装饰器声明它们的触发关系——更像写代码控制流程，只是"调用关系"由装饰器声明、引擎驱动。Flow 让你用熟悉的"方法 + 装饰器"精确编排，把不确定性关进每个方法内部。
L04

三段式架构

Flow 被拆成三层（flow.py:1-14 模块 docstring）：

① 编写层 dsl — @start/@listen/@router、or_/and_ 装饰器。你用它们写 Flow。（Day 12）
② 中间表示 flow_definition — 把一个 Flow 静态描述成可序列化的数据（"契约"）。
③ 执行层 runtime — 真正的执行引擎，负责 kickoff、派发监听器。
这个"编写/中间表示/执行"三段式为什么好？ 装饰器只负责"贴元数据"（说明谁触发谁），不含执行逻辑。类定义时，装饰器把触发关系记在方法上；引擎启动时读取这些元数据、构建出一张 FlowDefinition（中间表示）、再驱动执行。好处：同一个 Flow 既能用 Python 类写、也能从 YAML 声明式加载（Flow.from_declaration）——因为中间表示是纯数据。"声明与执行分离"是编译器/工作流引擎的经典架构（呼应 eino 的 compile）。
L05

事件驱动的执行

kickoff()（runtime/__init__.py:1920）→ kickoff_async（:1985）。执行主线：

  • 发 FlowStartedEvent，找到所有 @start 方法，并行执行（asyncio.gather）。
  • 每个方法执行完，发 MethodExecutionFinishedEvent，然后 _execute_listeners（:2727）触发监听它的方法。
  • 被触发的监听器也并行执行；如此推进，直到没有监听器可跑。
  • 最后 method_outputs[-1] 作为最终返回，发 FlowFinishedEvent。
"事件驱动"到底什么意思？ 方法之间不直接互相调用。而是"方法A 完成 → 发出'A 完成了'这个事件 → 引擎查谁监听 A → 触发那些方法"。就像公司里"报告写完了 → 通知相关人 → 他们各自开始下一步"。解耦：A 不需要知道谁在等它的结果，只管完成、发事件；引擎负责路由。这就是发布-订阅模式。和 OpenHands 的事件流、eino 的图执行异曲同工。
L06

Flow 里内嵌 Crew（两范式合体）

Flow 的某个方法内部可以调用一个 Crew（flow_definition.py 甚至有专门的 FlowCrewActionDefinition、FlowAgentActionDefinition）：

class ContentFlow(Flow):
    @start()
    def get_topic(self):
        return "多智能体"

    @listen(get_topic)
    def research_and_write(self, topic):
        # 在这一步内部调用一个 Crew，让 AI 团队自主完成
        return ResearchCrew().crew().kickoff(inputs={"topic": topic})
读法：Flow 控制"大流程的确定性步骤"，某个步骤内部用 Crew 让 AI 自主发挥——两种范式的完美结合。你既有 Flow 的精确控制（哪步先做、条件分支），又有 Crew 的 AI 自主能力（在某步内）。
这是 CrewAI 的推荐用法 纯 Crew 太"放飞"（不好控制流程），纯 Flow 又失去 AI 的自主智能。组合起来最强：用 Flow 搭确定性骨架（保证流程正确、可控），在需要 AI 智能的步骤内嵌 Crew（发挥创造力）。这也是为什么 Flow 是较新推出的——它解决了"纯 Crew 难以精确控制复杂流程"的痛点。
L07

防死循环

Flow 支持循环流（方法可从"已完成集合"里被移除以便重跑，做迭代/重试）。但循环有失控风险，所以有 max_method_calls（默认 100），超限抛 RecursionError（runtime/__init__.py:2928）。

常见死循环原因：@listen 标签误写成方法自身的名字——方法完成触发自己、无限循环。max_method_calls 就是防这个的熔断。和 Crew 的 max_iter、eino 的 MaxRunSteps、OpenHands 的 max_iterations 一样——凡是能循环的地方，必配次数上限。这是 Agent/工作流系统的铁律。
