Day 09 / 共 20 天 · 第 2 周 核心引擎

权限系统

Agent 能动手改你的电脑，凭什么信它？权限系统就是那道闸。今天讲清 5 种模式、判定顺序，以及"哪些操作再高的权限也拦不住"。

L01

为什么需要权限

模型会自主决定调 Bash 跑命令、调 Edit 改文件。但模型可能判断错、也可能被恶意输入诱导。权限系统就是"在工具真执行前踩一脚刹车"——高风险操作停下来问你，低风险的放行，还能按规则批量允许/禁止。

Day 07 讲过：执行管线里"权限检查"在 tool.call() 之前（第 6 关）。今天钻进那关。核心文件 src/utils/permissions/permissions.ts，文件系统相关在 filesystem.ts，Bash 在 bashPermissions.ts。

L02

5 种权限模式

外部可选模式（src/types/permissions.ts:15）。你用 Shift+Tab 切换的就是它们：

default

正常询问：高风险操作弹窗确认

acceptEdits

工作目录内的编辑自动放行，其它照常问

plan

只读规划，不动手；ExitPlanMode 提交方案后才开工

bypassPermissions

几乎全放行——但 deny 规则、ask 规则、safetyCheck 仍免疫

dontAsk

把所有 ask 直接转成 deny（宁可不做也不问）

另有内部模式 auto（不弹窗，用 AI 分类器自动判，L07 讲）和 bubble。

怎么理解这几个模式？ 想象一个"信任滑杆"：plan（只看不动）→ default（动手要问）→ acceptEdits（改文件不用问）→ bypassPermissions（基本全放）。越往右越省心但越危险。dontAsk 是另类——它不是"更信任"，而是"别烦我，拿不准的就别做"。实际用时最常在 default 和 acceptEdits 之间切。
L03

权限规则从哪来

除了模式，还有规则——三种行为 allow/deny/ask，可精确到工具甚至工具的参数：

// settings.json 里配的规则示例
{
  "permissions": {
    "allow": ["Read", "Bash(git status)"],   // 整工具 或 参数级
    "deny":  ["Bash(rm *)", "Edit(/etc/**)"],
    "ask":   ["Bash(git push*)"]
  }
}

规则来源有优先级（permissions.ts:57）：userSettings / projectSettings / localSettings / flagSettings / policySettings / cliArg / command / session。它们最终落到权限上下文的 alwaysAllowRules/alwaysDenyRules/alwaysAskRules。

整工具规则 vs 参数级规则：Bash 是"整个 Bash 工具"；Bash(git status) 是"只有跑 git status 时"。参数级规则让你能精细控制——比如"允许 git status，但 git push 要问"。你在弹窗里点"始终允许 Bash(git status)"，就是往 session 级规则里加一条参数级 allow。policySettings（企业策略）优先级最高，用来做组织级强制管控。
L04

判定顺序：一步步过闸（核心）

入口 hasPermissionsToUseTool（permissions.ts:473）→ hasPermissionsToUseToolInner（:1179）。代码里就用 step 编号标注了顺序，逐条过：

1a

整工具 deny 规则 → deny（最先，最硬）

1b

整工具 ask 规则 → ask

1c

调工具自己的 checkPermissions（Day 07/08，如 Read 的"工作目录内放行"）

1d

工具返回 deny → deny

1e

需要用户交互 + ask → 即使 bypass 也 ask

1f

内容级 ask 规则 → ask（bypass 免疫）

1g

safetyCheck 类 ask（.git/.claude 等，Day 08）→ ask（bypass 免疫）

2a

模式放行：bypassPermissions → allow

2b

整工具 allow 规则 → allow

3

passthrough 转 ask（工具没明确表态，交给用户）

顺序的智慧：deny 和 ask 排在 allow 前面——先看"有没有理由拒绝/询问"，再看"有没有理由放行"。而且 1e/1f/1g（几种 ask）排在 2a（bypass 放行）前面，所以它们能"免疫"bypass。这个顺序编排就是安全策略的核心：禁止 > 询问 > 允许，且某些询问不可被跳过。
L05

哪些能被 bypass、哪些不能

很多人以为 bypassPermissions 是"全放行"。不对。由 L04 的顺序可知，即使在 bypass 模式，这几类仍然拦得住：

  • deny 规则（1a/1d）：明确禁止的永远禁止。
  • ask 规则（1b/1f）：明确要求确认的仍会问。
  • safetyCheck（1g）：动 .git/.claude/.bashrc/.mcp.json 这类危险文件仍会问（Day 08）。
  • 需要用户交互的工具（1e）：如 AskUserQuestion。
为什么 bypass 也留这几道闸？ 因为"绕过权限"是为了省去常规确认的烦扰，不是为了让 Agent 能干灾难级操作。deny 是你明说"绝不许"的红线；safetyCheck 是"改这个可能毁掉环境"的雷区。这些无论多信任都该留一道人工闸——否则一次幻觉就能删库、改坏 shell 配置。"最大放行模式也保留最小安全底线"是这个系统最值得学的设计。
L06

审批弹窗 = await 一个 Promise

判定出 ask 后，怎么变成你看到的那张权限卡？hasPermissionsToUseTool 只产出决策，真正弹 UI 的是 useCanUseTool（src/hooks/useCanUseTool.tsx:46）。它用了一个优雅的模式：

// useCanUseTool.tsx:52 —— 把"等用户点击"变成一个可 await 的 Promise
return new Promise((resolve) => {
  setToolUseConfirmQueue(q => [...q, {
    tool, input,
    onAllow: () => resolve({ behavior: 'allow', ... }),   // 用户点"允许"
    onReject: () => resolve({ behavior: 'deny', ... }),   // 用户点"拒绝"
  }])
})
// 工具执行在这里"挂起"，直到用户点了按钮，Promise 才 resolve、继续往下
这个模式太妙了：工具执行是异步的（await canUseTool(...)）。当需要用户确认时，代码创建一个 Promise 但先不 resolve，把它的 resolve 函数塞进 UI 的确认队列。界面渲染出权限卡（Day 04 讲的队列渲染），你点"允许"就调 onAllow()→resolve('allow')，那个 await 才继续。于是"等一个人类决定"被表达成了"await 一个 Promise"——异步代码里等用户交互的经典写法。工具执行天然地在这一步挂起，不用轮询、不用回调地狱。

权限卡组件是 PermissionRequest（components/permissions/），内部按工具类型分派到 BashPermissionRequest / FileEditPermissionRequest 等具体样式。

L07

auto 模式：用 AI 分类器代替弹窗

auto 模式（permissions.ts:519）不弹窗，改用一个 AI 分类器（yolo classifier）自动判断这次操作安不安全。判定路径：

  1. 先试 acceptEdits 快速路径（:599，工作目录内编辑直接过）。
  2. 查"安全工具白名单" isAutoModeAllowlistedTool（:659，如只读工具）。
  3. 都不满足 → 调 classifyYoloAction（:695）让一个小模型判"这个操作危险吗"，据此 allow/deny。
auto 模式解决什么？ default 太烦（每步都问），bypass 太险（全放）。auto 是折中——用一个便宜的 AI 分类器替你做"这操作要不要拦"的判断：只读/编辑这类明显安全的直接放，可疑的（删文件、改系统配置）才拦。相当于给你配了个"自动审批助理"。这是本 fork 的特色能力之一。headless/后台代理（没有人能点弹窗）则走另一条：先跑 PermissionRequest hook，没决策就自动 deny（:953）——无人值守时"拿不准就拒绝"。
