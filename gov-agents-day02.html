环境搭建 & 跑通第一个 Agent

昨天(Day 01)我们在脑子里建好了「盖楼」这张地图：地基→可信底座→各户业务 Agent→物业前台。今天动手把这栋楼真正通水通电住进去——搞懂 uv workspace 怎么把几十个包串成一个整体，把整个平台在本地跑起来，用浏览器调用你的第一个 Agent。跑通了，Day 03 才好钻进一户人家（一个 Agent）里看它内部怎么运转。

📍 你在 20 天里的位置（第 1 周：建立心智）
D01 全景架构→ D02 跑起来→ D03 LangGraph 基础→ D05 一个 Agent 结构→ D06-11 可信底座→ D14 旗舰精读
💡 用一个类比先兜住今天（延续昨天的「盖楼/物业」世界观） 如果说 Day 01 是拿到楼盘的设计图纸，今天就是交房入住的那一天：uv sync = 物业一次性把全楼水电煤气一起开通（一条命令装好 31 户）；configs/ 配置 profile = 物业的一份「公共守则 + 各单元特批」（公共默认 + 本环境覆盖）；启动 server = 打开楼下大门总闸；调用一个 Agent = 你按了某一户的门铃，看它开门应答。记住这条主线，下面 9 讲就是这四步。
L01

今天的目标

Day 01 我们建立了"地图"。今天把地图落到能跑的环境上。学完你能：

  • 解释 monorepo（单一大仓）和 uv workspace 是什么、为什么用它；
  • 用一条命令把整个平台的几十个包装好；
  • 看懂 configs/ 里的分环境配置是怎么"叠加合并"的；
  • 把 gov-agents-server 跑起来，打开浏览器首页，调用一个 Agent 拿到返回。
没有环境也没关系：今天所有命令我都会把"预期输出"写出来，你光看也能理解。真机操作是加分项，不是必须。
L02

monorepo 与 uv workspace

monorepo（单体仓库）就是"把很多相关的包放在同一个 git 仓库里"。本项目就是——一个仓库里同时住着 toolkit、20 多个 agent、server、cli、前端门户……它们互相依赖。

问题来了：这么多互相依赖的 Python 包，怎么装才能"改一个包的源码，依赖它的其它包立刻生效、而且大家版本一致"？答案就是 uv workspace。

🤔 痛点：没有 workspace 你会怎样？你得进 ai-trust-toolkit 目录 pip install .，再进 gov-agents-server 装一遍，再进 20 多个 agent 各装一遍……而且改了 toolkit 一行源码，还得把它重新打包、其它包重新安装才生效。31 个包手动 pip install，装到怀疑人生，还极易装出「A 包要 pydantic 2.5、B 包锁死 2.7」这种打架版本。
💡 本质：workspace = 物业统一开通全楼水电workspace 就像入住时物业一次性给全楼所有单元同时通水通电：你不用挨家挨户开阀门。而且用的是同一套管网（一个 uv.lock），保证 3 楼和 18 楼水压一致（版本一致）；哪户想换个灯泡（改某个包源码），全楼立刻亮的是新灯——因为是 editable 安装，装的是「指向源码的软链」而不是拷贝。
根 pyproject.toml · [tool.uv.workspace]
packages/ai-trust-toolkit可信底座
packages/gov-agents-server运行时
packages/gov-agents-cli命令行
apps/sre-rca-agent业务 agent
apps/... ×20业务 agent
gov-agents-portal/backend门户后端

根 pyproject.toml:7-42 里的 [tool.uv.workspace] 列出了全部 31 个成员。再配合 [tool.uv.sources]（pyproject.toml:44-53）把内部包标记为"从 workspace 取，而不是从 PyPI 下载"：

[tool.uv.workspace]
members = [
    "packages/ai-trust-toolkit",
    "packages/gov-agents-server",
    "apps/sre-rca-agent",
    # ... 共 31 条
]

[tool.uv.sources]
ai-trust-toolkit = { workspace = true }   # ← 从本地 workspace 取，不去 PyPI
图注：一个根 pyproject 管着 31 个成员，共享一个 uv.lock；业务包都依赖同一份本地 toolkit。
📝 举个例子：editable 安装到底省了什么 你在 ai-trust-toolkit 里把预算校验的报错文案从 "over budget" 改成 "预算超限"，不用重装任何东西 → 直接 uv run pytest → 依赖它的 sre-rca-agent 立刻用上新文案。若是传统 pip install .（拷贝安装），你得把 toolkit 重新打包 + 21 个 agent 逐个重装才生效。
一句话记住：workspace = "把整个大仓当成一个项目来装依赖"。一个 uv.lock 文件锁死所有包的精确版本组合，保证你机器上和同事机器上、和 CI 上装出来的东西一模一样。
L03

一条命令装好全仓

装好 uv 后（curl -LsSf https://astral.sh/uv/install.sh | sh），在仓库根目录只需要一条命令：

terminal
uv sync --all-extras --all-packages
Resolved 400+ packages in 1.2s
Installed ai-trust-toolkit (editable)
Installed gov-agents-server (editable)
Installed sre-rca-agent (editable) ...
✓ 全部 31 个 workspace 包 + 依赖 + dev 工具装好了

参数解释：--all-packages = 装所有 workspace 成员；--all-extras = 连每个包的可选依赖（如 observability、rag）也一起装。装完你可以直接 uv run pytest 跑全套测试——因为测试全部走 FakeLLM（假大模型），不联网、不花钱、几秒钟跑完。

为什么测试不用真大模型？ 这是本框架的一个核心设计（Day 11 细讲）：测试要可复现、零成本、不依赖外网。所以业务代码从不直接 import anthropic，而是走 get_llm()——测试时把它换成返回固定答案的 FakeLLM 即可。
L04

配置 profile 系统：base + 环境 = 最终配置

平台要在本地、测试、预发、生产等不同环境跑，每个环境的数据库地址、预算上限都不同。它用一套"基础配置 + 环境覆盖"的 profile 系统解决，文件在 configs/：

💡 本质：配置合并 = 公司的报销制度base.yaml 就像公司统一的报销总则（默认所有人单次上限 1 美元、限速 60 次/分）；<APP_ENV>.yaml 就像某部门的特批文件，只写"和总则不一样的那几条"（比如预发部门月度额度 500 美元）。你实际能报多少，是总则打底、部门特批覆盖同名条目后的结果——这正是 _deep_merge() 在做的事。没写特批的字段，一律沿用总则。
base.yaml（公共默认）
cost.per_invoke_usd_cap: 1.0quota.ratelimit_rpm: 60redis.host: ...
+
<APP_ENV>.yaml（只写差异）
# 比如 staging.yamlmonthly_usd_cap: 500.0
=
最终配置（深度合并）
per_invoke_usd_cap: 1.0monthly_usd_cap: 500.0ratelimit_rpm: 60

加载器是 ai_trust_toolkit.config.load_config()（config.py:291），它做 5 步：

1

读环境变量 APP_ENV

默认 dev。决定加载哪个 profile。

2

找到 configs/ 目录

从当前目录往上找 configs/base.yaml。

3

展开 ${VAR} 变量

${DB_PASSWORD} 从环境变量取值，${VAR:-默认} 支持默认值——secret 不硬编码进 yaml。

4

深度合并 base + env

_deep_merge() 递归覆盖，env 里写了的字段盖掉 base。

5

Pydantic 校验

extra="forbid"——拼错一个 key 直接报错，绝不静默吞掉。校验过才返回。

把它当调试器单步走一遍：设 APP_ENV=staging，跟踪 cost 这一段字段最后取到什么值——

步骤此刻发生什么cost.per_invoke_usd_capcost.monthly_usd_cap
① 读 APP_ENV取到 staging，决定叠加 staging.yaml——
② 载入 base.yaml公共默认打底1.0(base 未设)
③ 展开 ${VAR}把 ${...} 替换成环境变量真值1.0—
④ deep_merge(base, staging)staging 只写了 monthly，覆盖/新增该字段；没写的 per_invoke 保持 base1.0（沿用）500.0（被覆盖）
⑤ Pydantic 校验字段名合法、类型对 → 通过，返回最终 Config1.0500.0
⚠️ 小白常误以为「加载 staging 会把 base 整个替换掉」。其实不是替换而是逐字段深度合并：base 里 staging 没提到的字段全部保留，只有同名字段才被盖。这就是 _deep_merge()（config.py:255）递归下钻的意义。
profile用途关键差异
base.yaml公共默认值所有 section 的兜底
dev.yaml本地开发redis 指向 127.0.0.1
staging.yaml预发（隔离）月度预算上限 500 美元
prod.yaml生产真 RDS/Redis，secret 走 vault
test.yamlpytest/CIllm.provider: mock、redis 关闭、预算拉满不卡测试

🚨 反面教材提醒：base.yaml 开头自己声明了"secret 不硬编码、走 ${VAR}"，但实际 dev/prod/test.yaml 里硬编码了明文数据库密码和真实 API key——违反了自己的规范。这在真实项目里很常见，学习时要能识别出"这是不该学的写法"。

L05

配 .env 与 API key

要真调大模型，得给平台一个 Anthropic API key。仓库提供了模板 .env.example，复制成 .env 填上即可：

cp .env.example .env
# 编辑 .env，至少填：
# ANTHROPIC_API_KEY=sk-ant-xxxxx
# APP_ENV=dev

配置加载器有个贴心设计（config.py:39 的 load_dotenv_if_present）：它会沿目录树向上最多找 5 级来定位 .env，而且已经设过的环境变量不会被覆盖（config.py:92）——方便 K8s / Vault 在生产用真环境变量盖掉文件里的值。

只想先跑通、不想花钱？ 把 APP_ENV=test，配置里 llm.provider: mock，平台就用假大模型，不需要真 key 也能启动、能看首页。真调用才需要真 key。
L06

启动平台 server

平台的主进程是 gov-agents-server，它是一个 FastAPI 服务，按环境变量 ENABLED_AGENTS 决定挂载哪些 agent。有两种起法：

方式 A：脚本一键起

./scripts/start_server.sh          # 默认 8080 端口，启动前自检防冲突
# 或后台运行：
./scripts/restart_server.sh --detach   # 日志写 logs/server.log

方式 B：直接 uvicorn（看清底层）

ENABLED_AGENTS=sre-rca,doc-checker \
  uv run uvicorn gov_agents_server.main:app --host 0.0.0.0 --port 8080

ENABLED_AGENTS 是逗号分隔的 agent 名列表；不设的话默认挂全部。写了不存在的名字会立刻报错退出（fail-fast）。启动成功后你会看到 uvicorn 监听 8080。

它是怎么找到 agent 的？ 靠 main.py:62-81 一张写死的注册表 AGENT_REGISTRY（{agent名: (模块路径, 工厂函数名)}），启动时按名字 importlib.import_module 懒加载对应模块的 build_router。不是自动扫描文件夹——加新 agent 必须手动往这张表加一行。Day 12 会细讲这套机制。
L07

调用第一个 Agent

server 起来后，打开浏览器访问 http://localhost:8080/，会看到一个自带的首页：列出所有已启用的 agent 卡片 + 一个"Invoke Playground"（网页上填 key 直接调）+ 最近 10 条调用记录。

也可以用命令行直接打 HTTP。每个 agent 都有一个统一的调用端点 POST /v1/agent/<name>/invoke：

调用 doc-checker
curl -s http://localhost:8080/v1/agent/doc-check/invoke \
-H 'X-Anthropic-Api-Key: sk-ant-xxx' \
-H 'Content-Type: application/json' \
-d '{"content": "# 上线方案\n本次变更..."}'
 
{ "case_id": "01HXXX...", "agent": "doc-check",
  "status": "success", "result": {...},
  "metrics": {"elapsed_ms": 3200, "estimated_cost_usd": 0.04},
  "trace_id": "..." }

注意这个返回结构——所有 agent 返回的格式都长一样，叫"统一 envelope（信封）"：

case_id这次调用的唯一 ID (ULID)
statussuccess / critic_end / failed
resultagent 的业务结果
metrics耗时 / token / 花了多少钱

这套统一 envelope + 鉴权 header + case 落库 + 指标上报，是 toolkit 的 build_v1_router() 自动给每个 agent 装上的（Day 12 精讲）。你现在只要感受到：无论调哪个 agent，请求和返回的"外壳"都一致。

👶 小白：为什么每个 agent 都要长成一样的信封？直接各写各的返回不省事吗？

👨‍🏫 老师：还记得昨天「盖楼」里的物业前台吗？统一 envelope 就是全楼共用的一套「访客登记表」——不管你按哪户门铃，前台都能用同一张表记下「谁来的(case_id)、有没有成功(status)、花了多少钱(metrics)」。如果每户格式不同，前台就没法统一做计费、审计、限流了。

👶 小白：那 doc-checker 这个名字，为什么调用路径却是 /v1/agent/doc-check/invoke？

👨‍🏫 老师：好眼力。ENABLED_AGENTS 里用的注册名是 doc-checker，而挂载的 URL 前缀是 doc-check——这个映射写死在 main.py:62 的 AGENT_REGISTRY 里（比如 sre-rca 也映射到 /v1/agent/rca/）。两者不一定同名，以那张表为准。

L08

docker-compose 一键全栈

不想在本机装 Python 依赖？用 Docker。仓库根的 docker-compose.yml 定义了本地全栈：

服务是什么说明
redisredis:7-alpine，端口 6379Working Memory 断点续跑的后端
platformbuild: .，端口 8080平台主进程，依赖 redis 健康后才起
 
APP_ENV=dev docker compose up -d      # 本地全栈起来
# 生产形态：
APP_ENV=prod docker compose up -d

关键点：docker-compose.yml 里 APP_ENV: ${APP_ENV:-dev} 把 compose 和 L04 的 config profile 系统打通了——同一个镜像，靠环境变量切换配置。ENABLED_AGENTS 里写死了 16 个 agent 的列表。

又一个文档漂移：README 说 compose 有 "PG + Redis + Ollama + platform" 四个服务，但实际 docker-compose.yml 只有 redis + platform 两个。再次印证 Day 01 的原则：以文件为准。
