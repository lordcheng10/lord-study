环境搭建与启动链

从 ccb 命令到终端里出现交互界面，这一路代码怎么跑？今天追一遍完整启动链，并把项目在本地跑起来。

L01

今天的目标

Day 01 我们知道了真正的入口是 src/entrypoints/cli.tsx。今天沿着这条线一路追到"REPL 界面渲染出来"，你会看清：

  • 怎么装 Bun、怎么 build、怎么用 dev 模式带源码跑；
  • cli.tsx 里那个"按优先级短路"的快速分发器——为什么 --version 能零额外加载；
  • main() → init() → setup() → launchRepl() 这条启动主链；
  • 为什么构建要拆成几百个 chunk（内存原因）。
L02

装 Bun 与跑起来

这个项目跑在 Bun 上（.tool-versions 锁 bun 1.3.13，package.json:24 要求 bun >= 1.3.0）。三步跑起来：

# 1. 装 Bun（若没有）
curl -fsSL https://bun.sh/install | bash

# 2. 装依赖（monorepo 一次装全部 workspace）
cd claude-code
bun install

# 3. 构建，产出 dist/cli.js + 几个 bin
bun run build          # = bun run build.ts

# 4. 跑
./dist/cli-node.js     # 或 node dist/cli-node.js
# 也可用 bin 名（若 link 了）：ccb
为什么用 Bun 不用 Node？ Bun 是一个更快、自带打包/测试/包管理的 JS 运行时。这个项目大量用 Bun 特有 API（如 Bun.build、bun:ffi）。但它构建时会"打补丁"让产物node/bun 都能跑（L08 讲），所以 ccb（node）和 ccb-bun（bun）两个入口都可用。
L03

dev 模式：不构建直接跑源码

读源码调试时，不用每次 build。bun run dev（scripts/dev.ts）用 Bun 的 -d flag 注入编译期常量后直接跑 src/entrypoints/cli.tsx：

bun run dev            # 直接跑源码，全部 feature 默认开启，版本号显示 888
bun run dev:inspect    # 带调试器
为什么 dev 模式版本号是 888？ 因为正式版本号（如 2.8.3）是构建时通过"宏（MACRO）"从 package.json 注入的常量。dev 模式没走构建，就用一个占位值 888 提醒你"这是开发态"。看到 888 就知道自己在跑源码。

另外有一堆脚本：bun test（跑测试）、biome check（lint+格式）、bun run typecheck（类型检查）、bun run precheck（提交前三合一）。

L04

入口 cli.tsx：最先跑的几行

打开 src/entrypoints/cli.tsx，最顶上几行有讲究（cli.tsx:5-40）：

  • 第一行必须是 performance shim（cli.tsx:5）：替换 globalThis.performance，防止 Bun 底层的 JSC 引擎里某个 C++ Vector 无限增长。顺序敏感，必须最先执行。
  • MACRO 运行时兜底（cli.tsx:11）：dev 模式下没有构建注入的 VERSION 等常量，这里给个兜底。
  • 设若干环境变量（cli.tsx:40）。
细节里藏着工程经验：为什么一个 CLI 的第一行要 patch performance？因为作者在真实运行中发现了内存泄漏，定位到运行时底层。读源码时遇到这种"莫名其妙必须放最前面"的代码，往往背后是一个踩过的坑——留意注释。
L05

fast-path 分发器：能短路就不加载

cli.tsx 的 main()（cli.tsx:76-360）是一个"按优先级短路"的巨型分发器。它的设计目标：用最少的模块加载处理简单命令。几乎每个分支都用动态 import——用到才加载。

// cli.tsx:80 —— --version 零额外模块加载，直接打印
if (arg === '--version' || arg === '-v') { console.log(MACRO.VERSION); return }

// 各种子命令都在加载 5640 行的 main.tsx 之前就短路：
// --dump-system-prompt / --acp / --daemon-worker /
// remote-control|rc / daemon / --bg / job / weixin ...

// cli.tsx:352 —— 默认路径：才真正加载重量级的 main.tsx
const { startCapturingEarlyInput } = await import('../utils/earlyInput.js');
startCapturingEarlyInput();
const { main: cliMain } = await import('../main.jsx');   // = src/main.tsx
await cliMain();
为什么这么设计？ main.tsx 有 5640 行，加载它很"重"。但用户可能只是想看个版本号、或跑个后台子命令——没必要为此加载整个交互式 UI 的代码。动态 import + fast-path 短路让常见轻量操作的冷启动几乎零开销。这是 CLI 冷启动优化的经典手法，值得学。
L06

main() 与 init()：一次性初始化

默认路径进入 src/main.tsx 的 main()（main.tsx:743）。它用 Commander 构建命令行程序（main.tsx:1082），并在真正执行命令前跑一个 preAction 钩子（main.tsx:1087）做初始化：

main.tsx:749

进程级防护

设 Windows PATH 劫持防护、warning handler、注册 process.on('exit')（含 workflow 关闭）和 SIGINT。

main.tsx:1096

await init()

调 src/entrypoints/init.ts:66 的 init（用 memoize 包着，只跑一次）：启用配置、注册 Ink 主题、telemetry/Sentry、优雅关闭、证书/代理、仓库检测……全是一次性初始化。

main.tsx:1100+

迁移与远程设置

设 process.title='claude'、runMigrations()（配置格式升级）、异步加载企业托管设置/策略。

setup.ts:57

setup()

校验 Node ≥18、设置工作目录、抓取 hooks 配置快照、初始化 SessionMemory / SkillLearning、发启动 beacon。

memoize 是什么？ "记忆化"——把一个函数的结果缓存起来，第二次调用直接返回缓存、不重复执行。init() 被 memoize 包着，保证无论被调几次，那些一次性初始化只真正跑一次。
L07

REPL 挂载：Ink 接管终端

初始化完，默认命令的 .action()（main.tsx:1434）处理权限模式、MCP、会话恢复后，交互式会话会挂载 React/Ink 应用：

// main.tsx:2749 —— 创建 Ink 渲染根
const { createRoot } = await import('@anthropic/ink');
root = await createRoot(ctx.renderOptions);

// replLauncher.tsx:14 —— 组装元素树
<SentryErrorBoundary name="RootREPLBoundary">
  <App {...appProps}>
    <REPL {...replProps} />      // ← 真正的交互界面
  </App>
</SentryErrorBoundary>

// interactiveHelpers.tsx:124 —— 渲染并等待退出
export async function renderAndRun(root, element) {
  root.render(element);
  startDeferredPrefetches();
  await root.waitUntilExit();      // ← 阻塞在这，直到用户退出
  await gracefulShutdown(0);
}
REPL = Read-Eval-Print-Loop（读取-求值-打印-循环）——就是那个能反复输入、看输出的交互式界面。root.render(element) 之后，Ink 就接管了终端，你看到的所有消息、输入框、进度都是这个 React 树在渲染。waitUntilExit() 让进程一直挂在交互界面，直到你退出（Day 04 讲 Ink，Day 18 讲界面细节）。

完整启动链一句话：ccb → dist/cli-node.js → cli.tsx（fast-path 分发）→ main.tsx main()（Commander + init + setup）→ createRoot + launchRepl → Ink 渲染 REPL → 等待交互。

L08

构建双管线：为什么要拆几百个 chunk

项目有两条并行构建管线（package.json:44）：

Bun.build（默认）
bun run build → build.ts。用 Bun.build 打包 cli.tsx，splitting: true 拆分代码，产出后处理成 node/bun 双兼容，最后生成 cli-bun.js/cli-node.js 两个 shim。
Vite / Rollup
bun run build:vite → vite.config.ts。发布用；内联依赖、minify、拆 chunk 到 chunks/。
为什么必须拆 chunk（关键内存教训）：Bun 底层的 JSC 引擎会急切地全量解析单个大文件。一个 17MB 的单文件 bundle 会让内存（RSS）飙到约 1GB！拆成几百个小 chunk 后，Bun 按需加载，--version 的内存从 966MB 降到 35MB。（Node 的 V8 因为懒解析没这问题，但为兼容 Bun 必须拆。）这是"打包策略直接影响运行时内存"的真实案例。

另一个巧思：产物通过正则打补丁（build.ts:44）把 Bun 专有的 import.meta.require 换成 Node 兼容写法、给裸 globalThis.Bun 加 typeof 守卫——于是同一份 dist/cli.js node 和 bun 都能跑。

版本号、feature flag 都是构建时用"宏（MACRO）"注入的编译期常量（scripts/defines.ts），运行时通过 import { feature } from 'bun:bundle' 消费——关掉某个 feature，相关代码会被死代码消除掉。
