Day 13 / 共 20 天 · 第 3 周 检索与查询

响应合成 Synthesizer

检索到的片段可能很多、可能塞不下 LLM 上下文——怎么把它们"攒"成一个答案？这就是响应合成。今天看几种合成模式：refine、compact、tree_summarize，它们决定答案的质量和成本。

L01

合成的难题

"片段太多，一次塞不下"怎么办 检索可能返回很多相关片段（top_k=10、每块 1000 token = 上万 token），加上 LLM 上下文有限——不能无脑全塞进一个提示词。而且要"综合"多个片段得出连贯答案，不是简单拼接。响应合成器（Synthesizer）解决这个：用不同策略把 N 个片段"合成"成一个答案——有的逐个精炼、有的压缩填满、有的树形汇总。合成模式直接影响答案质量、LLM 调用次数（成本）、延迟。
L02

ResponseMode

response_synthesizers/type.py:4-51 的 ResponseMode：

class ResponseMode(str, Enum):
    REFINE = "refine"                  # 逐个片段精炼答案
    COMPACT = "compact"                # 压缩填满上下文再精炼（默认）
    SIMPLE_SUMMARIZE = "simple_summarize"  # 全拼一起总结（塞不下就截断）
    TREE_SUMMARIZE = "tree_summarize"  # 树形两两汇总
    ACCUMULATE / COMPACT_ACCUMULATE    # 每片段独立答再累积
    NO_TEXT / CONTEXT_ONLY / GENERATION  # 特殊模式
读法：response_synthesizers/ 每个模式一个文件（refine.py/compact_and_refine.py/tree_summarize.py…）。factory.py 的 get_response_synthesizer 按 mode 造对应合成器（Day 12 默认用 COMPACT）。下面拆三个最重要的。
L03

refine 逐个精炼

response_synthesizers/refine.py：

1. 用片段1 + 问题 → LLM 生成初版答案
2. 用片段2 + 初版答案 + 问题 → LLM "在已有答案基础上，结合片段2 精炼"
3. 用片段3 + 上版答案 → 继续精炼
... 每个片段调一次 LLM，答案层层完善
"滚雪球"式完善答案 refine 一个片段一个片段地过：先用第一个片段答一版，再拿第二个片段"补充/修正"这版答案，如此叠加。每个片段都被完整看到（不会因塞不下被截断）。优点：不丢信息、答案精细。缺点：N 个片段 = N 次 LLM 调用（慢、贵）。适合片段多、要精确综合的场景。
L04

compact 压缩（默认）

response_synthesizers/compact_and_refine.py：先把多个片段"塞满"一个提示词（尽量填满上下文窗口），塞不下的再走 refine。

compact = refine 的省钱版 refine 每片段调一次 LLM 太贵。compact 先"打包":把能塞进一个上下文的片段合并成一次调用（少调 LLM），塞不下的剩余部分再 refine。比如 10 个片段，若 3 个能塞满一次，就 3+3+4 三次调用（而非 refine 的 10 次）。这是 LlamaIndex 的默认模式——在"信息完整"和"少调 LLM"间取平衡。大多数场景用它就好。
L05

tree_summarize 树形汇总

response_synthesizers/tree_summarize.py：把片段两两（或成组）用 LLM 汇总成中间摘要，中间摘要再汇总，层层向上直到一个最终答案（树形归并）。

适合"总结大量内容" tree_summarize 像"淘汰赛"：一堆片段 → 分组各自汇总 → 得到几个中间摘要 → 再汇总 → 最终一个。优点：能处理超多片段（层级归并，每层并行），特别适合"总结整份长文档"。因为每层可并行调 LLM，比 refine 快。缺点：中间汇总可能丢细节。问"总结这本书讲了什么"用它；问"退款政策的具体条款"用 compact/refine（要精确细节）。
L06

PromptHelper 装填

indices/prompt_helper.py 的 PromptHelper：负责"把多少片段塞进一个提示词"的计算——根据 LLM 的上下文窗口、留给答案的空间，算出每次能装多少 Node 文本。

读法：合成器背后靠 PromptHelper 做"装箱":它知道 LLM 上下文有多大、要留多少给输出，算出提示词里能塞多少检索内容、需要分几批。compact 的"尽量塞满"、refine 的"每次一个"都靠它计算边界。它防止"塞爆上下文"报错——自动分批。这是 RAG 工程化的关键细节（不同 LLM 上下文大小不同，要动态适配）。
L07

流式与结构化

合成器支持 streaming=True（答案边生成边返回，改善体验）和结构化输出（output_cls，让 LLM 返回 Pydantic 对象而非纯文本）。

流式：让用户"立刻看到答案在打字" LLM 生成答案要几秒——流式让答案"一个字一个字"实时显示（像 ChatGPT 那样），不用干等。合成器把 LLM 的流式输出透传出来。结构化输出则让答案变成程序能用的对象（如 {"answer": ..., "confidence": ...}），适合要把 RAG 结果接入下游程序的场景。这些是生产 RAG 的体验/集成能力。
