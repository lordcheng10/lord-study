Memory 记忆系统

让 Agent"记住"东西。今天讲 CrewAI 的记忆系统——注意它已从经典"四类记忆"重构为统一记忆，用 scope + categories + importance 组织，靠 embedding + RAG 检索。

L01

重要变迁：统一记忆（先澄清）

🤔 场景：Agent 像"每天失忆的员工" 第一轮你告诉客服 Agent"我叫小明，用的是企业版套餐"。第二轮你问"我的套餐能加几个座席？"——它却完全不记得你是谁、用什么套餐，因为大模型每次调用都是"一张白纸"，不会自动记住上一轮说过的话。怎么让它记住？
💡 一句话本质：Memory = 给 Agent 一个"长期笔记本" 大模型本身没有记忆，Memory 就是外挂的笔记本：把对话/任务里值得记的事编码写入（存成向量），下次遇到相关问题时召回相关几条、拼进 prompt 一起喂给模型。写进去 + 查出来，Agent 就"记住"了往事。
⚠️ 版本变迁：CrewAI 已废弃经典的四类记忆（ShortTermMemory / LongTermMemory / EntityMemory / ContextualMemory）。如果你看旧文档找 ShortTermMemory 这些类，在新源码里找不到了。取而代之的是统一智能记忆（unified memory）：一个 Memory 类，用 scope（作用域）+ categories（类别）+ importance（重要度）这些维度组织记忆。
怎么理解这个变迁？ 旧设计把记忆按类型分成四个类（短期、长期、实体、上下文），各管各的。新设计用一个统一 Memory，靠"维度标签"组织——一条记忆可以标注它的作用域（是团队级还是个人级）、类别、重要度。这更灵活：不用硬分类，而是给每条记忆打标签，检索时按这些维度综合排序。你可以用这些新维度去类比旧的"短期/长期"帮助理解迁移。
上排=写入：把值得记的事编码成向量存进 LanceDB；下排=召回：新问题来了，按语义找回相关记忆、拼进 prompt 一起喂给 LLM——Agent 就"记住"了。
L02

MemoryRecord 数据模型

MemoryRecord（memory/types.py:20）——单条记忆：

content: str          # 记忆内容
scope: str            # 作用域，如 /company/team/user（层级）
categories: list      # 类别标签
importance: float     # 重要度 0-1
embedding: list       # 向量（用于语义检索）
private: bool
读法：一条记忆不只是"一段文字"，还带 scope（属于哪个层级）、categories（分类）、importance（多重要）、embedding（语义向量）。这些维度让记忆能被精准地组织和检索——比如"只召回团队级、重要度高、和当前问题语义相关的记忆"。
L03

综合打分公式（检索排序的核心）

检索时，每条候选记忆按 compute_composite_score（types.py:345）综合打分：

composite = semantic_weight * similarity      # 语义相似度
          + recency_weight  * decay           # 时间新鲜度（越近越高）
          + importance_weight * importance     # 重要度
# decay = 0.5^(age_days / half_life_days)   ← 半衰期衰减
# 默认权重：semantic=0.5 / recency=0.3 / importance=0.2
为什么综合三个维度打分？ 只看"语义相似"不够好——一条很相关但很久以前、无关紧要的记忆，可能不如一条较相关但很新、很重要的记忆有用。所以综合三项：① 语义相似（和当前问题相关吗）② 新鲜度（多久以前的，用半衰期衰减——越老权重越低）③ 重要度（这条记忆本身重不重要）。加权求和 = 模拟人类记忆的检索：既看相关性，也看"最近发生的"和"印象深刻的"。这比单纯的向量相似度检索聪明得多。

读法：保存不是简单地"存一行文字"——_encode_batch 会构造一个 EncodingFlow（一条 Flow 流水线，L06）来处理：嵌入向量化、去重、找相似、LLM 分析字段、批量入库。所以"记住一件事"背后是一套智能的编码流程。
注意这里用到了 Flow（Day 11-13）！记忆的保存和检索都用 Flow 流水线实现——CrewAI 用自己的 Flow 能力来搭内部功能。这说明 Flow 不只是给用户用的，框架自己也用它来组织复杂的多步逻辑。吃自己的狗粮（dogfooding）——好设计的标志。
L05

recall：检索记忆（RAG）

recall()（unified_memory.py:681）——按查询召回相关记忆。分两种深度：

  • shallow：直接 embed 查询 + storage.search 向量检索（快）。
  • deep（默认）：走 RecallFlow（L06）——自适应深度检索，能递归深挖。
RAG 检索是什么（记忆的核心机制） RAG = 检索增强。把记忆内容变成向量存起来，检索时把"当前问题"也变成向量，找语义最接近的记忆。底层用 LanceDB（向量库）：search（lancedb_storage.py:371）做向量搜索 + scope LIKE 'prefix%' 前缀过滤（只搜相关作用域）+ 距离转分数。找回的记忆再按 L03 的综合分排序。这就是让 Agent"想起相关往事"的技术——语义检索，而非关键词匹配。
L06

两条 Flow 流水线

  • EncodingFlow（encoding_flow.py:75）：5 步保存流水线——批量嵌入 → 批内去重 → 并发找相似 → LLM 分析（推断字段/是否合并）→ 批量 insert/update/delete → 存库。
  • RecallFlow（recall_flow.py:58）：自适应检索流水线——分析查询 → 选候选 scope → 向量搜索 → @router 按置信度决定要不要深挖 → 可递归探索 → 综合结果。
为什么保存也要这么复杂（去重、合并）？ 因为如果每次都无脑追加，记忆库会塞满重复、矛盾的内容——"用户喜欢咖啡"存 10 遍，或者新记忆和旧记忆冲突。EncodingFlow 在存之前先去重、找相似的旧记忆、用 LLM 判断"该新增还是更新合并"——保持记忆库干净、一致。好的记忆系统不只是"存"，更是"智能地维护"。RecallFlow 的 @router 自适应深挖（Day 12 的 router）则让"简单问题浅查、复杂问题深挖"，省 token。
L07

Agent/Crew 怎么用记忆

  • Crew：memory=True 时 create_crew_memory()（crew.py:627）建一个 Memory(root_scope="/crew/<name>")，并给 agent 注入 recall/remember 工具（_add_memory_tools，crew.py:1751）。
  • Agent：任务执行前 _retrieve_memory_context（agent/core.py:537）召回相关记忆、拼进 prompt：
# agent/core.py:537（概念）
matches = unified_memory.recall(query, limit=5)      # 召回 top5 相关记忆
memory = "Relevant memories:\n" + "\n".join(m.format() for m in matches)
task_prompt += memory   # 拼进任务提示
读法：记忆通过两种方式起作用：① 自动召回相关记忆拼进 prompt（被动）；② 作为工具让 Agent 主动 recall/remember（主动）。被动召回让 Agent "自然想起相关往事"，主动工具让它能"特意记住某事"或"特意查某记忆"。
📝 最小例子：memory=True 开启后，第二轮记得第一轮 建 Crew 时开一行：Crew(agents=[...], tasks=[...], memory=True)。
第一轮任务里出现信息："客户小明用的是企业版套餐" → 被 remember 编码入库。
第二轮问："他的套餐能加几个座席？" → _retrieve_memory_context 先 recall("套餐 座席") 召回第一轮那条记忆，拼进 prompt。
于是 LLM 看到的是：Relevant memories: 客户小明用的是企业版套餐\n\n他的套餐能加几个座席？ → 能接着答，而不是反问"你是谁、用什么套餐"。（对比：memory=False 时第二轮完全失忆。）
