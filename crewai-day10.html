L01

本日主题

Day 03 快速过了 Task，今天补齐三个进阶点：结构化输出（让 AI 吐规范数据）、上下文链（任务间数据传递，源码级）、guardrail（输出质检）。这三个决定了"任务产出能不能被程序可靠地用"。

为什么这三个很关键？ 把 AI 接进真实软件系统，最怕"AI 的输出不靠谱"——格式乱、内容错、缺关键项。结构化输出解决"格式规范"、上下文链解决"任务间正确传递"、guardrail 解决"内容质检"。这三个是"让 AI 产出可用于生产"的工程保障。
L02

结构化输出：三选一

🤔 痛点：LLM 的输出是一坨自由文本，格式乱、字段还常缺 你想让 Agent 提取"公司名 + 成立年份 + 主营业务"，结果它一会儿返回一段话、一会儿返回 markdown 列表，成立年份有时还漏掉。程序想拿这个结果做后续处理，根本没法可靠地解析。怎么逼它吐出规整、字段齐全的结构化数据？

Task 有三种约束输出格式的方式（互斥，task.py）：

  • output_pydantic=Model（:179）：输出解析成 Pydantic 对象。
  • output_json=Model（:169）：输出为 JSON（符合该 schema）。
  • response_model=Model（:189）：走 LLM 原生结构化输出（最可靠）。
读法：校验器 check_output（task.py:548）保证 output_json 和 output_pydantic 不同时设。产出后 _export_output 把结果转成对应形态，封进 TaskOutput 的 pydantic/json_dict 字段（Day 03）。
📝 用 expected_output + output_pydantic 拿到结构化对象 
from pydantic import BaseModel

class Company(BaseModel):        # 这就是"模具"
    name: str
    founded_year: int
    business: str

task = Task(
    description="提取这段文字里的公司信息",
    expected_output="公司名、成立年份、主营业务",   # 告诉 LLM 要什么
    output_pydantic=Company,                        # 用模具把输出塑形成对象
)
result = crew.kickoff()
result.pydantic.founded_year   # → 2021（直接当对象字段用，不用手动解析！）
输入：一段杂乱的公司介绍文字 → 输出：一个字段齐全的 Company 对象。程序拿 .founded_year 直接用。
💡 一句话本质：output_pydantic = 给输出套一个"模具" 就像工厂做月饼：面团（LLM 的自由输出）本身软趴趴、形状随机；套上月饼模具一压，个个规整统一、能装盒发货。output_pydantic/output_json 就是这个模具，把 LLM 的自由文本塑形成规整结构；expected_output 则是"用文字说明我要什么口味"。模具在手，字段齐全、类型正确、程序可直接用。
❌ 错误驱动：不用模具，你得手写多少"擦屁股"代码？ 简化版（没有模具，自己解析）——很快就被 LLM 的花式输出逼疯： 
raw = agent_output            # "公司叫 Acme，2021 年成立，做 SaaS"（这次是句子）
# 下次可能是 markdown：- 名称：Acme\n- 年份：2021 …
# 你得写正则/split/try-except 应付无穷格式，年份还常是字符串 "2021"
import re
year = int(re.search(r'(\d{4})', raw).group(1))  # 😰 换个措辞就崩
真实版（用模具，一行搞定）： 
task = Task(..., output_pydantic=Company)   # 模具在此
result.pydantic.founded_year                # → 2021（int，稳）
"能让模型原生塑形，就别自己写解析代码"——省下的正是那堆脆弱的正则。
response_model 为什么最可靠？ output_pydantic 是"让模型自由输出，再由框架解析成对象"（解析可能失败）；response_model 用模型的原生结构化输出能力——模型在生成时就被约束必须符合 schema（约束解码），几乎不会格式错。现代模型优先用 response_model。这和 Day 07 讲的"原生函数调用 > 文本解析"是同一个道理——能让模型原生结构化就别自己解析。
L03

上下文链三态（源码复习）

Day 03/05 讲过，这里看源码 _get_context（crew.py:1827）：

def _get_context(task, task_outputs):
    if not task.context:                    # context=[] 空列表 → 隔离，不看上文
        return ""
    return (aggregate_raw_outputs_from_task_outputs(task_outputs)  # NOT_SPECIFIED → 前面所有
            if task.context is NOT_SPECIFIED
            else aggregate_raw_outputs_from_tasks(task.context))   # 指定列表 → 只这些
读法：三态用一个字段的三种取值优雅表达：默认（NOT_SPECIFIED）拼前面所有任务、指定列表只拼那些、空列表谁都不看。这是"合理默认 + 精确控制"的 API 平衡艺术（Day 03 baby box 讲过）。
还有个安全校验 validate_context_no_future_tasks（crew.py:839，Day 04 见过）——context 不能依赖后面的任务，防止"任务 1 依赖任务 3 输出"的时间悖论。依赖必须指向过去，这个约束在建 Crew 时就检查。
L04

guardrail：输出的"质检员"

护栏（guardrail）= 任务产出后，先"质检"是否合格，不合格就带着反馈重跑。Task 的 guardrail（task.py:246）有两种：

  • 函数护栏：你写个函数校验（如"检查输出是否包含至少 5 个要点"）。
  • 字符串护栏：写自然语言描述（如"确保输出是专业、正式的语气"），框架用一个 LLM 来判断合不合规。
💡 一句话本质：guardrail = 出厂前的"质检员" output_pydantic（模具）管"格式对不对"，guardrail 管"内容合不合格"——像流水线尽头的质检员：合格放行、不合格贴上问题标签打回重做。模具保证形状规整，质检员保证内容达标，两道关卡一起把住"AI 产出能否用于生产"。
质检为什么重要？ AI 有时会产出"看起来完成了但不合要求"的结果——比如你要 5 个要点它给了 3 个，或语气不对。如果不检查就直接用，质量没保障。guardrail 在任务产出和"交付"之间加一道关卡：不合格打回重做。这让最终输出的质量可控——尤其对生产系统重要。
Task 输出全链路：LLM 原始输出 → 结构化(模具塑形) → guardrail 校验(失败带反馈重跑) → 合格的 TaskOutput。
L05

校验 + 带反馈重试

护栏执行 _invoke_guardrail_function（task.py:1246）的核心是一个重试循环：

任务产出→ 跑护栏校验→ 通过 → 交付 / 失败 → 把原因当反馈重跑↺ 
# task.py:1264（精简）
for attempt in range(max_attempts):
    result = process_guardrail(output=task_output, guardrail=guardrail)
    if result.success:
        return task_output          # 通过（结果可能被护栏改写）
    if attempt >= self.guardrail_max_retries:
        raise Exception("failed guardrail validation after retries")
    context = 把失败原因格式化成反馈
    result = agent.execute_task(task=self, context=context, ...)  # 带反馈重跑
读法：护栏失败不是直接报错，而是把"失败原因"作为反馈重新喂给 Agent，让它改进后重跑，最多 guardrail_max_retries 次（默认 3）。这是"带反馈的自我修正"——和 Day 07 的解析自愈一个思路。支持多护栏串联，每个独立计数。
L06

LLM 校验 LLM

字符串护栏由 LLMGuardrail（tasks/llm_guardrail.py:49）实现——它内部临时建一个"Guardrail Agent"，让另一个 LLM来判断输出是否符合描述：

# llm_guardrail.py:98 __call__ 返回 (True, 原文) 或 (False, 反馈)
# 内部：一个"质检 Agent"判断输出合不合规，返回 LLMGuardrailResult(valid, feedback)
"用 LLM 校验 LLM" 是什么套路？ 干活的 Agent 产出结果 → 另一个专门的"质检 Agent"读这个结果，对照你的要求（"是否专业正式"）判断合不合格、给反馈。这是当下很流行的模式（也叫 LLM-as-a-judge）。好处：质检标准可以用自然语言写（灵活），不用写死代码规则。坏处：多一次 LLM 调用（成本）。所以简单规则用函数护栏（免费、确定），主观/复杂标准用字符串护栏（LLM 判断，灵活）。
L07

签名校验前移

validate_guardrail_function（task.py:302）在你创建 Task 时就校验函数护栏的签名——必须恰好一个参数，返回类型若标注必须是 Tuple[bool, Any]。

为什么创建时就检查函数签名？ 护栏函数必须符合约定格式（收一个参数、返回 (是否通过, 结果/反馈)）。如果你写错了（比如返回单个值），运行到护栏那步才崩就晚了。创建 Task 时就检查签名，写错立刻报错——又是"fail-fast、错误前移"（Day 04 的声明式校验、eino 的编译期检查，同一哲学，本教程第 N 次出现）。你会发现优秀框架都痴迷于"尽早暴露错误"。
