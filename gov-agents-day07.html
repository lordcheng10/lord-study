Critic 双层防幻觉

大模型会一本正经地编造证据、过度自信。Critic 是专门给结论"挑刺"的评审员——用"先 0 成本代码规则、再便宜 LLM"两层把幻觉拦下来。

L01

什么是"幻觉"，为什么必须防

幻觉（hallucination）指大模型生成了"看起来很合理、其实是编造"的内容。在本框架的场景里，典型幻觉有：

  • 引用了一个根本不存在的证据 ID（比如凭空捏造一条 trace_id）；
  • 结论过度自信（明明证据不足却说"确定就是它"）；
  • 只引 1 个证据就下大结论、忽略反例；
  • 对高风险动作（重启、回滚）不加"先验证"的提示。

对一个要给 SRE 做故障根因的 Agent 来说，幻觉是致命的——你不能让它把运维人员带到错误方向。所以框架专门设了 Critic 节点：在综合出结论后、返回给用户前，先自我审查一遍。代码在 packages/ai-trust-toolkit/src/ai_trust_toolkit/critic/。

L02

双层拦截总图：先便宜后贵

Critic 的核心巧思是分两层，按"成本递增"顺序拦截——能用 0 成本代码解决的，绝不浪费 LLM 调用：

L1

代码层：纯 Python 规则检查

机械性错误（编造 ID、置信度非法、专家数不够）用确定性代码就能 100% 拦下。先跑这层，不过直接返回，根本不调 LLM。

0 成本
毫秒级
100% 准确
L2

LLM 层：Haiku 语义审查

L1 过了，才用便宜的 Haiku 做"语义级"审查：结论和证据逻辑一致吗？有没有过度外推？教学性够不够？

约 ¥0.04/次
Haiku
✓

两层都过 → 结论可信，放行

否则打回重做（见 L05 三态路由）。

继续 writeback
为什么这个顺序省钱又快？ 因为大量幻觉是"机械错误"（编造 ID 这种），L1 用代码毫秒级就拦了，压根不用花钱调 LLM。只有通过 L1 的"看起来没硬伤"的结论，才值得花 ¥0.04 让 Haiku 做语义审查。这是"用最便宜的手段解决最多的问题"的典型。
L03

L1 代码层：4 项确定性检查

代码在 critic/layer1.py。汇总入口 run_layer1_checks()（layer1.py:135）跑 4 项检查，返回 (是否通过, 违规列表, 详情)：

① check_evidence_ids

结论里引用的证据 ID，必须都在"合法 ID 集合"里。fabricated = 引用的 - 合法的，只要有编造的就挂（layer1.py:75）。

② check_min_specialists

至少 N 个（默认 2）专家真的产出了 finding（排除 fallback 降级的），防止只凭一个证据下结论（layer1.py:88）。

③ check_schema

置信度必须 ∈ {高,中,低}，风险等级 ∈ {high,medium,low}——格式非法直接拦（layer1.py:101）。

④ check_high_risk_verify_first

高风险动作（重启/回滚等）必须带 verify_first 提示，不能让 Agent 直接叫人干危险操作（layer1.py:121）。

"合法 ID 集合"从哪来？collect_valid_evidence_ids(state)（layer1.py:44）会把 4 个专家 finding 里的真实证据 ID 全部收集起来。所以只要结论引用了不在这个集合里的 ID，就一定是编造的——这是用代码 100% 抓幻觉的关键机制。

L04

L2 LLM 层 & 短路优化

代码在 critic/layer2.py。build_critic_node(config)（layer2.py:51）返回一个 async 节点。它的执行逻辑最能体现"双层"设计——先跑 L1，L1 不过直接返回、根本不烧 LLM：

async def critic_node(state):
    valid_ids = collect_valid_evidence_ids(state)
    l1 = run_layer1_checks(state, valid_ids)      # 先跑代码层
    if not l1.passed:
        return {"critique_passed": False,
                "critique_layer": 1,               # ← 标记：被代码层拦下
                "retry_count": 1, ...}             # 不调 LLM，直接返回
    # 只有 L1 通过，才调 Haiku 做语义审查（6 项铁律）
    llm = config.llm_factory()                    # 通常 get_llm("haiku")
    response = await llm.ainvoke([system, user])
    ...                                            # critique_layer=2 表示 LLM 层结果

配置项 CriticConfig（layer2.py:30）业务需要提供：system_prompt（审查用的 prompt，就是 Day 05 见过的 critic-v1.md）、llm_factory、conclusion_field（结论存在 state 哪个字段）、soft_fail（默认 True）。

critique_layer 这个字段很妙：它记录"是被哪一层拦下的"——0=通过、1=代码层拦下、2=LLM 层拦下。回忆 Day 05，sre-rca 的 State 里就有这个字段。它让你事后能分析"我们的幻觉大多是机械错误(1)还是语义错误(2)"，从而针对性优化。
L05

三态路由：形成重试循环

Critic 审完，怎么决定下一步？回忆 Day 03 的"条件边"和 Day 05 builder 里那句 build_critic_router(...)。它就是把 Critic 结果翻译成三种走向（代码在 failsafe/retry_router.py:12，属于失败闸门，Day 08 会再提）：

✓ 通过

critique_passed=True
→ 去 writeback 沉淀经验，正常结束

↻ 不过 & 没超次数

回 synthesizer 重新综合
（把 Critic 的意见带回去改）

■ 不过 & 超 2 次

→ END
诚实输出"信息不足，无法给出可靠结论"

def critic_router(state):                    # retry_router.py:12
    if state.get("critique_passed"):
        return "writeback"                   # 通过
    if state.get("retry_count", 0) >= max_retries:
        return END                           # 触顶，诚实收尾
    return "synthesizer"                     # 打回重做
"触顶诚实收尾"是可信设计的点睛之笔：如果重试了 2 次还是过不了 Critic，框架不会硬憋出一个结论，而是老实说"我信息不足"。宁可承认不知道，也不给一个可能误导人的答案——这正是"可信"二字的分量。retry_count 用 Day 05 讲的累加 Reducer 计数，所以能可靠判断是否触顶。
L06

业务规则 L1：不调 LLM 的轻量 Critic

有些高频、低延迟的 agent（比如 alert-triage 告警治理，要求 P99 < 5 秒）连 Haiku 都嫌慢。于是 v0.3 抽出了纯规则版的 business_layer1.py——用几条业务规则做校验，0 成本、< 1 毫秒、不调任何 LLM。

核心是 Rule（business_layer1.py:34）+ build_business_critic_l1(rules)（business_layer1.py:51）。业务用几个 helper 声明规则即可：

critic_l1 = build_business_critic_l1([
    # 决策必须在允许集合内
    rule_in_allowed_set("routing_decision", ALLOWED_DECISIONS),
    # 如果决定"立即呼叫"，就必须填了业务影响字段
    rule_conditional_field(
        when=lambda s: s["routing_decision"] == "page_immediately",
        require_field="business_impact"),
])
builder.add_node("critic", critic_l1)

提供的 helper 有：rule_in_allowed_set（值在枚举内）、rule_field_not_empty（非空）、rule_conditional_field（条件必填）、rule_field_in_range（数值范围）、rule_list_min_length（列表最短长度）。规则本身崩了也视为违规（business_layer1.py:86），绝不放过。

L07

三档 Critic 强度：按场景取舍

框架并不强制每个 agent 都上"双层完整 Critic"。它按场景提供三档强度，这本身就是一个很好的"权衡"教学案例：

档位代表 agent配置为什么
满配sre-rcaL1 + L2 + 三态重试根因分析责任重，值得花时间反复审
仅 L1alert-triage只跑代码规则，不调 LLM高频在线，P99<5s，延迟敏感
无 Criticrisk-reviewer不设 Critic 节点刻意验证"toolkit 在无 Critic 场景也可复用"
设计智慧：可信不等于"处处堆满最重的防护"，而是按场景选择合适的防护强度。责任重的多审、延迟敏感的用轻量、有些故意做减法来验证框架弹性。这种"因地制宜"比"一刀切"更成熟。
