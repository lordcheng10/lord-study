Day 12 / 共 20 天 · 第 3 周 插件系统

插件运行 run_plugin

昨天 filter 选好了插件，今天看它们怎么被"跑起来"——run_plugin（plugin.lua:1161）在每个阶段遍历插件、调方法、处理"插件想提前结束请求"（拦截）。这是插件链执行的心脏。

L01

run_plugin 总览

plugin.lua:1161：run_plugin(phase, plugins, api_ctx)——给定阶段名，遍历 plugins，调每个插件该阶段的方法。Day 04 里 run_plugin("rewrite"/"access")、Day 02 里 common_phase 调 run_plugin("header_filter"/"log")——都是它。

读法：一个函数处理所有阶段，靠 phase 参数区分。它把"插件链在某阶段的执行"统一收口——这是 APISIX 请求处理的执行引擎。Day 04 的整个 access 处理，本质就是几次 run_plugin 调用。
L02

成对遍历

plugin.lua:1178+：用 for i = 1, #plugins, 2 每次跳 2（回收 Day 11 的"成对存"）：

for i = 1, #plugins, 2 do
    local phase_func = plugins[i][phase]   -- plugins[i] 是插件对象，取它的阶段方法
    local conf = plugins[i + 1]            -- plugins[i+1] 是该插件的配置
    if phase_func then
        local code, body = phase_func(conf, api_ctx)  -- 调用！传配置和上下文
        -- ... 处理返回值（下一节）
    end
end
为什么步长是 2？ 因为 filter 把插件存成 {对象, 配置, 对象, 配置...}。步长 2 遍历，每轮拿到一对：plugins[i] 对象、plugins[i+1] 配置。调 plugins[i][phase]（比如 limit-count.access）时传入 conf（这条路由给 limit-count 的配置）和 api_ctx。插件方法签名永远是 (conf, ctx)——配置 + 上下文，够用了。
L03

提前结束（拦截）

plugin.lua:1196-1219：插件方法返回 code, body 表示"我要直接返回响应，别往下跑了":

local code, body = phase_func(conf, api_ctx)
if code or body then
    if code >= 400 then
        core.log.warn(plugins[i].name, " exits with http status code ", code)
        if conf._meta and conf._meta.error_response then
            body = conf._meta.error_response   -- 用配置的错误消息，不泄露真实原因
        end
    end
    core.response.exit(code, body)   -- 直接返回，终止后续插件和转发
end
插件怎么"拦截"请求？ 鉴权插件发现 key 无效、限流插件发现超限——它们 return 401 或 return 429, "rate limit"。run_plugin 看到返回了 code，就 core.response.exit 直接把响应发回客户端，不再跑后面的插件、不转发上游。这就是"拦截"。error_response 那段是安全设计：可以用配置的通用错误消息覆盖真实原因，不让攻击者从错误里探测系统。回想 Day 02 的 request-block（wasm-go）——同样是"返回响应即拦截"。
L04

两类阶段的差异

run_plugin 里分两段（:1173 和 :1224）：

  • 决策阶段（rewrite/access…）：插件能返回 code/body 提前结束（拦截）。
  • 响应/日志阶段（header_filter/body_filter/log）：插件不能拦截（响应已在发送/请求已结束），只处理不中断。
读法：为什么日志阶段不能拦截？因为请求已经处理完了，"拦"没意义。决策阶段（access 等）才有"放不放行"的语义。所以 run_plugin 对这两类阶段用不同的遍历逻辑——决策阶段检查返回值，响应/日志阶段只调方法不管返回。细致的区分。
L05

rewrite_in_consumer

plugin.lua:1180-1184：处理 Day 04 那个"consumer 二次 rewrite":

if phase == "rewrite_in_consumer" and plugins[i + 1]._skip_rewrite_in_consumer then
    goto CONTINUE   -- 跳过已经在第一轮 rewrite 跑过的插件
end
local phase_func = phase == "rewrite_in_consumer" and plugins[i]["rewrite"]
                   or plugins[i][phase]  -- consumer 轮实际调的还是 rewrite 方法
回收 Day 04 的伏笔 Day 04 说过：先跑一轮 rewrite（含鉴权识别 consumer）→ 合并 consumer 配置 → 补跑 rewrite_in_consumer。但已经跑过 rewrite 的插件不能再跑一遍（会重复执行副作用）。所以 filter 里给已跑过的打了 _skip_rewrite_in_consumer 标记（Day 11 的 :507），这里跳过它们，只跑"consumer 新引入的插件"的 rewrite。这个细节保证了两轮 rewrite 不重复执行。
L06

meta_filter 条件执行

plugin.lua:1187, 1233：每个插件跑之前先过 meta_filter——插件配置可带一个 _meta.filter 表达式，只有当前请求满足条件才跑这个插件。

"按条件跑插件" 比如"只对 POST 请求限流""只对某个 header 的请求跑这个插件"。_meta.filter 是个 vars 表达式，meta_filter 求值——真才跑、假就跳过。这让一个插件配置能"条件生效",更灵活。run_meta_pre_function 还能在插件跑前执行元函数。这些 _meta.* 机制（disable/priority/filter/error_response）是 APISIX 给所有插件的通用增强。
L07

run_global_rules

plugin.lua:1266 的 run_global_rules：跑"全局规则"（Day 08 的 Global Rule）里的插件——它们对所有请求生效，不绑路由。Day 04 里"匹配路由前后都跑 global_rules"就是它。

读法：全局插件（如全站 prometheus、全站限流）通过 global_rules 运行，独立于路由级插件。它在路由匹配前（未匹配也要跑）和匹配后各跑一次相关阶段。机制和 run_plugin 类似，只是插件来源是 global_rules 而非路由。
