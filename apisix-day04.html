Day 04 / 共 20 天 · 第 1 周 全景与请求生命周期

请求生命周期总览

全课最核心的一天。精读 http_access_phase（init.lua:602-758）——一个请求进来后，APISIX 逐步做的所有决策。读懂这一个函数，就掌握了 APISIX 处理请求的主干。

L01

入口总览

http_access_phase（init.lua:602）的骨架（对应 Nginx access 阶段）：

1
创建 api_ctx（请求上下文）+ 设变量元表
2
校验 HTTPS 客户端（mTLS）+ uri 归一化
3
router.router_http.match(api_ctx) 匹配路由
4
合并 plugin_config / service / consumer 配置
5
plugin.filter 选插件 → run_plugin("rewrite"/"access")
6
handle_upstream 交给上游
下面 L02-L07 逐段拆。
L02

创建 api_ctx

init.lua:608-614：

-- always fetch table from the table pool
local api_ctx = core.tablepool.fetch("api_ctx", 0, 32)
ngx_ctx.api_ctx = api_ctx
core.ctx.set_vars_meta(api_ctx)
为什么从"table 池"取，不直接 new？ Lua 频繁创建/丢弃 table 会给 GC（垃圾回收）造成压力，拖慢性能。APISIX 用"对象池"（tablepool）：请求开始时从池里 fetch 一个 table 当 api_ctx，请求结束（log 阶段）release 回池复用。每秒几万请求下，这个优化很关键——避免了海量 table 的分配和回收。api_ctx 就是这个请求的"上下文袋子",后面所有阶段共享它（Day 05 细讲）。
L03

uri 归一化

init.lua:622-651：按配置删末尾斜杠、servlet 风格归一化，并做安全处理：

-- 防止被不可信 request_uri 攻击：记录归一化后的 uri
api_ctx.var.real_request_uri = api_ctx.var.request_uri
api_ctx.var.request_uri = api_ctx.var.uri .. api_ctx.var.is_args .. (api_ctx.var.args or "")
为什么要归一化 uri？ 同一个资源可能有多种 uri 写法（结尾带不带 /、含 ..、编码变体）。如果不归一化，攻击者能用畸形 uri 绕过路由/鉴权。APISIX 先把 uri 归一化成标准形式再匹配路由——既保证路由准确，又防"路径穿越"类攻击。保留 real_request_uri 是为了需要时还能拿到原始值。安全细节体现在这些不起眼的地方。
L04

路由匹配

init.lua:654-664：

router.router_http.match(api_ctx)     -- radixtree 匹配，结果放进 api_ctx.matched_route
local route = api_ctx.matched_route
if not route then
    -- 没匹配到路由：跑全局规则后返回 404
    local global_rules = apisix_global_rules.global_rules()
    plugin.run_global_rules(api_ctx, global_rules, nil)
    return core.response.exit(404, {error_msg = "404 Route Not Found"})
end
读法：match 用 radixtree（前缀树，Day 06）按 uri/host/method 等条件找出匹配的路由，放进 api_ctx.matched_route。没匹配到也不是直接 404——先跑"全局规则"插件（比如全局日志/指标要记录未匹配请求），再返回 404。细致。
L05

合并 service / plugin_config

init.lua:670-706：路由可能引用可复用的 plugin_config 和 service，要合并进来：

if route.value.plugin_config_id then
    local conf = plugin_config.get(route.value.plugin_config_id)
    route = plugin_config.merge(route, conf)       -- 合并插件配置
end
if route.value.service_id then
    local service = service_fetch(route.value.service_id)
    route = plugin.merge_service_route(service, route)  -- 合并 service（插件+上游）
    api_ctx.conf_type = "route&service"
    api_ctx.service_id = service.value.id
end
为什么要"合并"？ Day 01 说 Service/Plugin Config 是"可复用零件"。一条路由可以只写"我用 service X",X 里定义了插件和上游——运行时把 X 的配置"合并"进这条路由，得到完整配置。这样 100 条路由共享一个 service，改 service 一处生效。合并有优先级：路由自己的配置覆盖 service 的（Day 13 详讲合并规则）。合并后 route 就是这个请求最终生效的完整配置。
L06

选插件 + consumer

init.lua:716-753：选出该跑的插件，跑 rewrite/access 阶段：

local plugins = plugin.filter(api_ctx, route)   -- 选出该路由启用的插件
api_ctx.plugins = plugins
plugin.run_plugin("rewrite", plugins, api_ctx)  -- 跑 rewrite 阶段插件（含鉴权）
if api_ctx.consumer then                          -- 鉴权插件识别出了 consumer
    -- 合并 consumer 的专属配置，可能改变插件集
    route, changed = plugin.merge_consumer_route(route, api_ctx.consumer, group_conf, api_ctx)
    if changed then
        api_ctx.plugins = plugin.filter(api_ctx, route, api_ctx.plugins, nil, "rewrite_in_consumer")
        plugin.run_plugin("rewrite_in_consumer", api_ctx.plugins, api_ctx)
    end
end
plugin.run_plugin("access", plugins, api_ctx)    -- 跑 access 阶段插件
consumer 的"二次合并"很巧妙 鉴权插件（如 key-auth）在 rewrite 阶段识别出"这是消费者 Alice",此时才知道 Alice 有没有专属配置（比如给她单独的限流）。所以识别 consumer 后要重新合并配置、重新选插件、补跑 rewrite。这就是为什么有 rewrite 和 rewrite_in_consumer 两轮——"先鉴权识别身份、再按身份定制处理"。Day 14 讲 consumer 细节。
L07

交给上游

access 阶段最后 handle_upstream(api_ctx, route, enable_websocket)（init.lua:756）——确定上游、设置转发。之后 Nginx 进入 balancer 阶段（Day 02）选实例转发，再 header_filter/body_filter/log。

读法：至此 access 阶段结束，请求进入"转发 + 响应处理"环节。整个请求生命周期：access（决策，最重）→ balancer（选实例）→ filter（改响应）→ log（收尾释放 ctx）。其中 access 里的"匹配路由→合并配置→选插件→跑插件"是精华，值得反复看。
