Task：任务定义与输出

第二个核心概念。Agent 是员工，Task 是工单。今天读 task.py：任务怎么定义、怎么产出结构化结果、以及任务间"上下文链"这个编排精髓。

📍 你在整条链的位置（昨天认识了"员工"Agent，今天看你派给员工的那张"工单"Task）
Day1 全景→ Day2 Agent 员工→ Day3 Task 工单（要干的活）→ Day4 Crew 组队→ Day5 kickoff 旅程
L01

Task 是"工单"

🤔 只说"做什么"、不说"要成什么样"，会怎样？ 你给同事派活："帮我调研一下竞品。"——没说要几家、要哪些维度、交 PPT 还是一句话。结果他交回一份 30 页的报告，而你只想要一张对比表。没有明确的验收标准，产出十有八九跑偏，来回返工。对 AI 更是如此：它会自由发挥，你拿到的东西可能完全不是你要的。
💡 一句话本质 Task = description（做什么）+ expected_output（做成什么样）。类比一张正规工单：光写"处理这个问题"不够，必须写清"验收标准"。expected_output 就是那把验收的尺子——它同时也是喂给 AI 的方向指引。

Task(BaseModel)（task.py:114）。两个必填字段就是一张工单的核心：

# task.py:146-149
description: str        # 任务描述：要做什么
expected_output: str    # 期望输出：做成什么样
一张工单（左）交给 agent 执行（中），结果统一封进 TaskOutput（右）——想要文本读 raw，想要结构化读 pydantic/json_dict。这是本日 L05 会细讲的结构。
为什么 expected_output 是必填的？ 因为不说清"要什么样的结果"，AI 就会自由发挥、可能跑偏。expected_output="一份 5 条要点的清单"这种明确要求，等于给 AI 一个验收标准，它会朝这个方向产出。这是提示词工程的关键——明确的期望产出 = 更可控的结果。CrewAI 把它设为必填，逼你想清楚"我到底要什么"。

L03

结构化输出

默认任务输出是文本。但你常想要结构化数据（好让程序后续处理）。用 output_pydantic 或 output_json：

from pydantic import BaseModel
class Report(BaseModel):
    title: str
    key_points: list[str]

task = Task(
    description="研究并总结 {topic}",
    expected_output="标题 + 要点列表",
    output_pydantic=Report,     # ★ 输出会被约束成 Report 对象
)
读法：指定 output_pydantic=Report，任务产出就会被解析成一个 Report 对象——你能 result.pydantic.key_points 直接取字段，而不是从一坨文本里正则抠。校验器 check_output（task.py:548）保证 output_json 和 output_pydantic 不能同时设。
📝 一个 Task 输入 → 结构化输出 输入：description="研究 CrewAI"，expected_output="标题+要点"，output_pydantic=Report
产出（不再是一坨文本，而是一个 Report 对象）：
result.pydantic.title → "CrewAI 多智能体框架速览"
result.pydantic.key_points → ["组队协作", "角色扮演", "两种范式Crew/Flow"]
→ 下游代码直接 for p in result.pydantic.key_points: 遍历，不用正则从文本里抠。
为什么结构化输出很重要？ 如果 AI 只吐文本，你想用其中的"要点列表"就得写脆弱的文本解析。让 AI 直接吐一个符合 Report 模型的结构化对象，下游程序能可靠地按字段取值——这是把 AI 接进真实软件系统的关键。response_model（task.py:189）则走 LLM 原生结构化输出（更可靠）。
L04

_execute_core：任务如何产出

同步入口 execute_sync（task.py:572）→ 核心 _execute_core（task.py:762）：

# task.py:772-794（精简）
agent = agent or self.agent
if not agent: raise Exception("...no agent assigned...")   # 没 agent 不能跑
crewai_event_bus.emit(self, TaskStartedEvent(...))          # 发"任务开始"事件
result = agent.execute_task(task=self, context=context, tools=tools)  # ★ 交给 agent 干
读法：Task 自己不干活——它把活儿交给 agent.execute_task（Day 02 学的），自己负责"发事件、组装 TaskOutput、跑护栏、写文件、回调"这些编排。注意 Task 必须有 agent 才能执行（自己没有就用 Crew 分派的）。整个方法用 try/except/finally 包裹，失败发 TaskFailedEvent。
职责分清：Agent = "怎么想怎么做"（ReAct 循环），Task = "这件活的定义 + 产出的封装"。Task 把 agent 的原始结果加工成规范的 TaskOutput（L05），并处理输出格式、护栏、文件、回调、事件。Agent 管执行，Task 管定义与产出规范化——各司其职。
L05

TaskOutput：三形态统一输出

任务结果封装成 TaskOutput（tasks/task_output.py:14），同时容纳三种形态：

raw: str                    # 原始文本（永远有）
pydantic: BaseModel | None  # Pydantic 对象（若设了 output_pydantic）
json_dict: dict | None      # JSON 字典（若设了 output_json）
output_format: OutputFormat # 标记当前是 RAW / JSON / PYDANTIC
读法：无论任务是文本还是结构化输出，都统一封进 TaskOutput，三个字段按需填。__str__（task_output.py:99）优先返回 pydantic、其次 json、最后 raw——所以你 print(output) 总能拿到最有用的形态。
为什么要"三形态统一"？ 因为不同任务输出类型不同，但下游希望用统一的方式拿结果。TaskOutput 就是这个统一容器：想要文本读 .raw、想要对象读 .pydantic、想要字典读 .json_dict。统一的输出抽象，让编排代码不用为每种输出类型写分支。
L06

上下文链：一个任务的输出喂给下一个（编排精髓）

这是 CrewAI 流水线的核心。串联在 Crew 层 _get_context（crew.py:1827），根据 task.context 的三种状态：

Task A研究输出→context→ Task B分析输出→context→ Task C成文 
# crew.py:1827 三态语义
# context = NOT_SPECIFIED（默认）→ 自动拼进"前面所有任务"的输出
# context = [task_a, task_b]      → 只拼这两个任务的输出（精确依赖）
# context = []（空列表）          → 不看任何上文（隔离）
读法：三态设计极其优雅——默认串联（前面所有）、指定列表（精确依赖）、空列表（隔离）。拼好的上下文通过 agent.execute_task(task, context=...) 传进去，成为下一个任务的输入。这样"任务 A 的产出"就变成"任务 B 的输入"，形成流水线。
三态为什么这么设计？ 真实工作流有三种依赖情况：① 默认——大多数任务需要看到前面所有产出（写手要看研究和分析的全部）；② 精确——某任务只依赖特定几个前置（润色只需看初稿，不用看原始资料）；③ 隔离——某任务独立起头，不看任何上文。用一个 context 字段的三种取值优雅表达这三种，比强制你手动传数据方便多了。好的默认值（自动串联）+ 精确控制的能力（指定列表），是 API 设计的平衡艺术。
L07

条件任务与安全

ConditionalTask（tasks/conditional_task.py:14）——带一个 condition 函数，根据上一个任务的输出决定要不要跑：

# conditional_task.py:41 should_execute
def should_execute(self, context: TaskOutput) -> bool:
    return bool(self.condition(context))   # 用上一任务的输出判断
# 条件不满足 → get_skipped_task_output 返回空 TaskOutput（raw=""）
读法：条件任务实现了简单的 if/else 分支——比如"如果研究结果里发现了风险，就跑风险评估任务，否则跳过"。约束：条件任务不能是唯一任务、也不能是第一个（因为需要前置任务的输出来判断条件）。
护栏（guardrail）预告（Day 10 细讲）：Task 还能配 guardrail——任务产出后先"质检"，不合格就带着反馈重跑（最多 guardrail_max_retries 次）。字符串护栏会用一个 LLM 来判断输出合不合规（"用 LLM 校验 LLM"）。这让任务输出质量有保障。
