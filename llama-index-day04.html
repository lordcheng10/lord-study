切块 NodeParser

Document 太大不能直接用——要切成小块（Node）。切块质量直接决定检索质量，是 RAG 里最影响效果的一环。今天精读 SentenceSplitter：怎么按 chunk_size 切、为什么要 overlap、为什么按句子边界。

L01

为什么要切块

切块是 RAG 效果的关键 为什么不能整篇文档直接用？① 大模型上下文有限——塞不下整本书。② 检索精度——用户问"退款政策"，检索应返回"退款那一段",而不是整份 100 页的手册。③ 嵌入质量——一小段主题集中的文本，向量更能代表其语义；一整篇混杂多主题的，向量"糊"了。所以要把 Document 切成"大小合适、主题集中"的 Node。切得太大→检索不精准、塞不下；切得太小→丢失上下文、语义不完整。切块策略是 RAG 调优的重点。
L02

NodeParser 家族

node_parser/：interface.py（基类 NodeParser/TextSplitter）+ text/（各种文本切分器）+ relational/（层级切分）+ file/（按文件结构，如 Markdown/HTML/JSON）。text/ 下有：sentence.py、token.py、sentence_window.py、semantic_splitter.py、code.py。

读法：切分器都继承 TransformComponent（schema.py:191）——统一的"转换"接口（输入 Node 列表、输出 Node 列表）。这让切块能像流水线一样和其他转换（Day 05 的 ingestion）串起来。最常用的是 SentenceSplitter（默认）。
L03

SentenceSplitter

node_parser/text/sentence.py:34：

class SentenceSplitter(MetadataAwareTextSplitter):
    chunk_size: int = Field(default=DEFAULT_CHUNK_SIZE)      # 默认 1024（token）
    chunk_overlap: int = Field(default=SENTENCE_CHUNK_OVERLAP) # 默认 200
    def __init__(self, chunk_size=1024, chunk_overlap=200, ...):
        if chunk_overlap > chunk_size:
            raise ValueError("overlap 不能大于 chunk_size")   # :83 校验
默认切分器，兼顾大小和句子完整 SentenceSplitter 的目标：每块尽量接近 chunk_size（默认 1024 token），但尽量在句子边界切（不把一句话拦腰砍断）。它是"MetadataAware"的——切分时会考虑 metadata 占用的空间（回想 Day 02：metadata 会拼进文本给 LLM/嵌入），确保"文本 + metadata"不超 chunk_size。这比"每 1024 字符硬切"聪明得多——硬切会把句子切碎，语义受损。
L04

chunk_size / overlap

两个最关键的调优参数 chunk_size（块大小）：每块多大。太大→检索不精准、塞不下；太小→上下文不足。默认 1024 token 是通用折中，实际按你的文档调（技术文档可小些、叙述性文本可大些）。
chunk_overlap（重叠）：相邻块重叠多少。默认 200 token。为什么要重叠？因为切块可能把"一个完整意思"切在两块边界上。让相邻块重叠一部分，保证边界处的信息不丢——即使答案跨块，至少有一块包含完整上下文。好比裁纸时每页留点重叠，接缝处的字不会丢。overlap 太大浪费存储、太小丢上下文——200 是常用值。
L05

按边界切（层层降级）

SentenceSplitter 用一组分隔符按优先级切：先按段落（\n\n）、再按句子（. ! ? 等）、再按单词、最后按字符。

"尽量在自然边界切"的层层降级 理想是每块正好一个完整意思。SentenceSplitter 先试着按段落分——如果段落太长超过 chunk_size，就在段落内按句子分；句子还太长（罕见）就按词、按字符。层层降级，尽量在"越自然的边界"切。这样每个 Node 都是"完整的句子/段落集合",语义完整、检索准。底层用 tokenizer 数 token（因为大模型按 token 计费和限长，不是字符）。semantic_splitter（更高级）甚至用嵌入相似度找"语义断点"来切。
L06

切完设关系

切分后，node_parser/node_utils.py 的 build_nodes_from_splits 给每个新 Node 设置 metadata 和关系（Day 02）：SOURCE 指向原 Document、PREV/NEXT 串起同文档的块顺序、记录 start/end_char_idx。

读法：回收 Day 02 的关系——切块时自动建立 SOURCE/PREV/NEXT。这样检索到某块时，能追溯原文档（SOURCE）、取相邻块补充上下文（PREV/NEXT）。切块不只是"切碎",还要"记住每块从哪来、和谁相邻"——这些关系是后续高级检索（sentence-window、auto-merging）的基础。
L07

其他 splitter

  • TokenTextSplitter（token.py）：纯按 token 数切（不管句子边界，最简单）。
  • SentenceWindowNodeParser（sentence_window.py）：每句一个 Node，但 metadata 存"前后几句窗口"——检索命中一句、给 LLM 时带上窗口。
  • SemanticSplitter（semantic_splitter.py）：用嵌入相似度找语义断点切（相邻句子语义突变处切）。
  • CodeSplitter（code.py）：按代码结构（函数/类）切。
  • HierarchicalNodeParser（relational/）：切成多层级（大块+小块，配 auto-merging 检索）。
切块策略要按数据类型选 普通文本用 SentenceSplitter；想"精准命中 + 丰富上下文"用 SentenceWindow；追求语义完整用 Semantic；切代码用 CodeSplitter；要层级检索用 Hierarchical。没有万能切法——切块策略是 RAG 调优最该实验的地方。它们都是 TransformComponent，可插进 ingestion 管道（明天）。
