Checkpoint 检查点

Day 08 那行"每个超步存检查点"存的到底是什么？今天拆开 libs/checkpoint/ 的 Checkpoint 数据结构——它是持久执行、时间旅行、人在环的共同根基。

📍 你在整门课的位置
节点·并行→Checkpoint→Saver·threads→时间旅行
L01

检查点是什么

🤔 痛点：没有检查点会怎样？一个 Agent 跑了半小时、调了十几次工具，进程突然崩了——内存里的 State 全没了，只能从头再来一遍。长流程、要人工审批的流程、可能中断的流程，全都无从谈起。
💡 本质：每个超步后存一份"整份 State 快照"LangGraph 的解法极其朴素：每跑完一个超步，就把此刻所有通道的值（channels 快照）+ 进度信息打包存一份。崩溃后加载最近一份快照就能续跑。持久执行、时间旅行、人在环，全都是这一个机制的衍生品。

检查点（checkpoint）= 某个超步结束时，整个图状态的一份完整快照。有了它，程序重启后能"回到那一刻继续"。

像游戏存档 打游戏时每过一关自动存档。LangGraph 每跑完一个超步就"存档"一次——把此刻所有通道的值、进度信息打包保存。下次即使进程崩了、机器重启了，加载存档就能从那一步继续，不用从头打。更妙的是：因为每步都存，你还能"读档到任意一关"（时间旅行，Day 13），或"在某关暂停等玩家操作"（人在环，Day 14）。这一整周的能力，全靠"每步存档"这一个机制。
L02

Checkpoint 结构

每个超步产出一份 checkpoint，靠 id/parents 串成可回溯的历史链

Checkpoint（libs/checkpoint/langgraph/checkpoint/base/__init__.py，class Checkpoint L92）是个 TypedDict：

class Checkpoint(TypedDict):
    v: int                              # 版本号（格式版本）
    id: str                             # 检查点 ID（单调递增，可排序）
    ts: str                             # 时间戳
    channel_values: dict[str, Any]      # ★ 所有通道当前值（状态本体）
    channel_versions: dict[str, str]    # 每个通道的版本号
    versions_seen: dict[str, dict]      # 每个节点"见过"的通道版本（触发去重）
    updated_channels: list[str] | None  # 本步更新了哪些通道
读法：一个检查点 = 状态本体（channel_values）+ 进度元信息（各种 versions）。id 单调递增，所以检查点天然可排序 → 能构成一条历史时间线（Day 13 时间旅行的基础）。
⚠️ 常见误解：小白常以为检查点只是"把 messages 存一下"。其实它还存了一堆进度元信息（versions_seen 等），少了它们恢复就会重复执行——数据和进度必须一起存。
💬 小白 vs 老师：为什么不直接 pickle 整个对象？ 👶 小白：存档嘛，我直接 pickle.dumps(整个图) 一股脑存下来不就完了？
👨‍🏫 老师：pickle 整个图有三个坑——① 图里有函数、锁、连接等存不了/不该存的东西；② 存成一坨二进制没法排序、没法只读某一步，时间旅行就废了；③ 换个代码版本可能就反序列化失败。所以 LangGraph 只存"纯数据 + 进度"这种结构化的 Checkpoint，而不是整个运行时对象。
L03

channel_values（状态本体）

channel_values 是所有通道当前值的字典——就是你的 State 此刻的完整内容（Day 07 通道值的集合）。恢复时把它灌回各通道，状态就"活"过来了。

📝 例子：一个 channel_values 长什么样假设 State 有 messages 和 count 两个字段，聊了两轮后某个检查点里的 channel_values 大致是： 
channel_values = {
    "messages": [HumanMessage("我叫小明"), AIMessage("你好小明"),
                 HumanMessage("我叫啥?")],   # add_messages 累加的历史
    "count": 2,                              # 走了两个超步
}
# 恢复时：把这份 dict 灌回各通道 → State 瞬间回到"聊了两轮"那一刻

另外几个字段（class CheckpointTuple L139 把 checkpoint、metadata、pending_writes 打包在一起）都是"怎么正确恢复和继续"的元信息。

读法：这是存档的"主体数据"。你的 messages 历史、count、任何 State 字段，都在这里。其余字段都是"怎么正确恢复和继续"的元信息。
L04

versions_seen（触发去重）

versions_seen[node] 记录"节点 node 上次执行时，见过的各触发通道版本号"。Day 06/08 讲的触发判断就靠它：通道当前版本 > 节点见过的版本 → 触发；相等 → 不重复触发。

为什么恢复也要存它？ 如果只存 channel_values（数据）不存 versions_seen（进度），恢复后引擎不知道"哪些节点已经处理过当前数据了"，会重复执行。versions_seen 就是"每个节点的已读回执"——存下它，恢复后引擎才能准确判断"接下来该触发谁、谁已经跑过了"，做到精确续跑而非从头重跑。
L05

pending_writes（半完成保护）

检查点还伴随存储 pending writes（put_writes，Day 08）——本超步中已完成节点的写入。若单步执行到一半崩溃，恢复时这些已完成的写入不用重算。

读法：粒度比"整步"更细的保护：一个超步里 A 跑完、B 还没跑就崩了——A 的结果（pending write）已落盘，恢复后只需重跑 B。避免"因为 B 挂了，把已成功的 A 也重跑一遍"（A 可能有副作用，如已扣款）。
L06

CheckpointMetadata

每个检查点还带一份元数据 CheckpointMetadata：

字段含义
source来源：input（首次输入）/ loop（超步间，Day 08）/ update（手动改状态）
step第几步（-1=输入前，0,1,2...）
parents父检查点（构成历史链）
读法：元数据回答"这个存档是怎么产生的、在时间线的第几步"。step + parents 让检查点串成一条可回溯的链——Day 13 时间旅行遍历的就是这条链。
L07

恢复过程

带 checkpointer 的图再次 invoke 时（同一 thread_id），_loop.py 启动阶段会通过 BaseCheckpointSaver（同文件 class BaseCheckpointSaver L176，Day 12 细讲）读回检查点：

# 1. 从 saver 读最新检查点（Day 12）
# 2. channel_values → 灌回各通道（状态复活）
# 3. versions_seen → 恢复触发进度
# 4. pending_writes → 应用未提交的已完成写入
# 5. 从下一超步继续 tick 循环（Day 08）
📝 简化版 → 真实版：如果让你自己写"存档器"朴素做法可能就一个字典： 
# 极简版：内存里存最新一份
store = {}
def save(thread_id, state):   store[thread_id] = state   # 只存"整步"结果
def load(thread_id):          return store.get(thread_id)
对照真实的 BaseCheckpointSaver，会发现它多出几个方法，每个都在补朴素版的漏洞： 
put(config, checkpoint, metadata)  # 存整步：但会保留历史多份（时间旅行），不是覆盖
put_writes(config, writes, ...)    # 多出来：存"半步"里已完成节点的写入 → 单步崩了不重算
get_tuple(config)                  # 读：能按 checkpoint_id 精确读某一份，不只是"最新"
list(config)                       # 多出来：列出该 thread 所有历史 → 时间旅行遍历用
一句话：真实接口比"一个字典"多出来的，全是为了历史可回溯和半步保护。
"继续"而不是"重来" 这就是"持久执行"（durable execution）的完整闭环：存档时保存了数据+进度+半完成保护，恢复时逐一还原，然后从断点的下一步继续跑。用户视角：一个跑了半小时、中途崩溃的长流程，重启后几乎无缝续上。这是 LangGraph 区别于"一个大 while 循环"式 Agent 的核心工程能力，也是它能支撑生产级长运行 Agent 的原因。
