Day 07 / 共 20 天 · 第 2 周 索引/嵌入/存储

索引 Index

嵌入好的 Node 要组织成可检索的"索引"。今天精读最核心的 VectorStoreIndex：from_documents 怎么一键把文档变索引、build_index_from_nodes 怎么把 Node 嵌入并存进向量库。这是 Day 01 "5 行 RAG"第二行的真相。

L01

索引是什么

索引 = 组织好、能快速检索的数据结构 "索引"就像书末的索引页——把内容组织成"能快速查找"的结构。LlamaIndex 的 Index 把一堆 Node 组织起来，让你能高效检索。不同索引用不同的组织方式：VectorStoreIndex（最常用）按向量组织（语义检索）；SummaryIndex 按列表组织（遍历所有）；KeywordTableIndex 按关键词组织；PropertyGraphIndex 按知识图谱组织（Day 10 概览）。今天聚焦 VectorStoreIndex——RAG 的默认选择。
L02

BaseIndex

indices/base.py 的 BaseIndex 是所有索引的基类，核心：from_documents(documents)（类方法，最常用的建索引入口）、index_struct（索引的元结构）、as_retriever()（转成检索器）、as_query_engine()（转成查询引擎）、insert/delete（增删 Node）。

读法：所有索引统一接口：from_documents 建、as_retriever/as_query_engine 用、insert/delete 维护。换索引类型只需换类名，用法不变。索引依赖 StorageContext（Day 08）存数据。
L03

VectorStoreIndex

indices/vector_store/base.py:36：class VectorStoreIndex(BaseIndex[IndexDict])——把 Node 嵌入成向量存进 vector_store，检索时按向量相似度找。

最主流的 RAG 索引 VectorStoreIndex 就是"向量检索"的索引：建库时把每个 Node 嵌入（Day 06）存进向量库（Day 09），查询时把问题嵌入、在向量库里找最相似的 Node。90% 的 RAG 应用用它。它的"索引结构"很轻（主要是 Node 到向量库的映射），真正的向量存在 vector_store 里。下面看它怎么建。
L04

from_documents

Day 01 第二行 VectorStoreIndex.from_documents(documents) 的内部（BaseIndex.from_documents）：

# 简化流程：
# 1. 用 transformations（默认含 SentenceSplitter）把 documents 切成 nodes（Day 04）
# 2. build_index_from_nodes(nodes) → 嵌入 + 存向量库（下一节）
# 3. 返回 index 对象
一行代码 = 切块 + 嵌入 + 建库 回想 Day 01：from_documents 这一行其实做了前面好几天的事——切块（Day 04）、嵌入（Day 06）、存向量库（Day 09）。它内部就是跑一个隐式的 ingestion（Day 05 的转换链）+ 建索引。所以你现在能看穿这一行了：Documents 进去，一个"可检索的索引"出来。想精细控制就显式用 IngestionPipeline，想省事就 from_documents。
L05

build_index_from_nodes

indices/vector_store/base.py:260-283：

def _build_index_from_nodes(self, nodes, **insert_kwargs) -> IndexDict:
    index_struct = self.index_struct_cls()
    if self._use_async:
        run_async_tasks([self._async_add_nodes_to_index(index_struct, nodes, ...)])
    else:
        self._add_nodes_to_index(index_struct, nodes, ...)   # 核心
    return index_struct

_add_nodes_to_index（:219）：给没有 embedding 的 Node 嵌入（调 embed_model），然后 vector_store.add(nodes) 存进向量库，同时在 index_struct 记录映射。

读法：核心两步：① 嵌入（Node 没向量就现算，Day 06）；② 存向量库（Day 09 的 vector_store.add）。_use_async 时并发嵌入（嵌入调 API，并发快）。大批量时分批处理（避免一次嵌太多）。
L06

index_struct

IndexDict 是 VectorStoreIndex 的"索引结构"——记录 Node id 到向量库的映射等元信息。存在 index_store（Day 08）里。

索引结构 vs 实际数据 要分清：向量本身存在 vector_store（向量库）；Node 的文本/metadata 存在 docstore（文档库）；而"索引结构"（哪些 Node 属于这个索引、id 映射）这个"目录"存在 index_store。三者分开存（Day 08 的 StorageContext）。VectorStoreIndex 的 index_struct 相对轻——重活在 vector_store。（有些索引如 SummaryIndex 的 index_struct 就包含全部 Node id 列表。）
L07

as_retriever / as_query_engine

索引建好后，两个"变身"方法：

retriever = index.as_retriever(similarity_top_k=5)   # → 检索器（Day 11），只检索
query_engine = index.as_query_engine()                # → 查询引擎（Day 12），检索+生成
读法：Day 01 第三行 index.as_query_engine() 就是它——把索引包装成"能问答的引擎"。索引负责"存和检索",query_engine 在检索之上加"用 LLM 生成答案"。参数如 similarity_top_k（检索几个）在这里传。第 3 周会拆 retriever 和 query_engine 的内部。
