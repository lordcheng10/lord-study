Day 05 / 共 20 天 · 第 1 周 RAG 全景与数据摄入

摄入管道 Ingestion

第 1 周收官。前几天的"读→切→嵌"其实可以串成一条可复用、可缓存的流水线——IngestionPipeline。今天看它怎么把一串 transformation 串起来、怎么缓存避免重复处理、怎么增量更新文档。

L01

为什么要管道

把重复的处理步骤"打包" 每次建库都要"切块 → 抽取元数据 → 嵌入"这几步。与其每次手写，不如定义一条"管道"（Pipeline）——列好要做哪些转换，一键跑完。更重要的是缓存：如果 1000 个文档里只改了 1 个，重新跑管道时，没变的 999 个直接用缓存（不重新切块/嵌入，省时省钱——嵌入是要花钱调 API 的！）。IngestionPipeline 把摄入流程工程化：可复用、可缓存、可增量。
L02

TransformComponent

schema.py:191 的 TransformComponent——一切"转换"的统一接口：输入一批 Node、输出一批 Node。

class TransformComponent(BaseComponent, DispatcherSpanMixin):
    def __call__(self, nodes: List[BaseNode], **kwargs) -> List[BaseNode]: ...
"转换"是可组合的乐高块 切块器（SentenceSplitter）、元数据抽取器（TitleExtractor 等）、嵌入模型——它们都是 TransformComponent！都是"输入 Node 列表 → 输出 Node 列表"。因为接口统一，就能像乐高一样任意串联成管道。回想 APISIX/wasm-go 的"统一接口、可组合"——LlamaIndex 用 TransformComponent 实现同样的可组合性。切块、抽元数据、嵌入都是转换，串起来就是摄入流程。
L03

run_transformations

ingestion/pipeline.py:72-113 的 run_transformations：

def run_transformations(nodes, transformations, ...):
    for transform in transformations:      # 依次应用每个转换
        nodes = transform(nodes, **kwargs)  # 上一个的输出 = 下一个的输入
    return nodes
Documents原始→ SentenceSplitter切块→ Extractor抽元数据→ Embedding向量化→ Nodes就绪
读法：就是一个 for 循环——依次跑每个转换，前一个的输出喂给后一个。极简的"流水线"实现，因为每个转换接口统一（TransformComponent）。有 arun_transformations（:115）异步版（嵌入调 API 时并发加速）。
L04

IngestionPipeline

from llama_index.core.ingestion import IngestionPipeline
pipeline = IngestionPipeline(transformations=[
    SentenceSplitter(chunk_size=512),      # 切块（Day 04）
    TitleExtractor(),                       # 抽标题当 metadata
    OpenAIEmbedding(),                      # 嵌入（Day 06）
])
nodes = pipeline.run(documents=documents)   # 一键跑完，得到就绪的 Node
读法：IngestionPipeline 把 transformations 列表 + 缓存 + 向量库封装在一起。run 就是调 run_transformations + 缓存逻辑。Day 01 的 VectorStoreIndex.from_documents 内部就在做类似的摄入。显式用 Pipeline 让你能精细控制每一步 + 复用缓存。
L05

缓存机制

IngestionPipeline 有个 IngestionCache：对每个转换，用"输入 Node 的 hash + 转换的配置"当缓存键，存转换结果。

缓存键 = 内容 hash + 转换配置（又见版本化缓存） 再次跑管道时，某个 Node 经过某个转换前，先算"这个 Node + 这个转换"的 hash，查缓存——命中就直接用结果，不重跑。所以只改了 1 个文档，其余文档的切块/嵌入结果全从缓存拿——嵌入 API 调用大幅减少（省钱！）。回想 APISIX 的 conf_version 缓存、wasm-go 的规则备份——"用内容 hash 做缓存键"是通用手法。Node 的 hash 字段（Day 02，基于内容计算）正是为此。
L06

文档去重更新

IngestionPipeline 配 docstore 后支持 docstore_strategy（如 UPSERTS）——按 Document 的 id_ + hash 判断"这个文档是新的/改了/没变"，只处理变化的。

增量更新：只处理变化的文档 知识库不是一次性建好就不动——文档会新增/修改/删除。每次全量重建太浪费。UPSERTS 策略：对比 docstore 里已有的文档 hash，新文档 → 处理并入库；改过的（hash 变了）→ 重新处理并更新；没变的 → 跳过。这样维护知识库很高效。回想 Day 03 的 filename_as_id——用稳定 id 才能正确判断"是不是同一个文档"。去重更新是生产级 RAG 的必备。
L07

直接存进向量库

IngestionPipeline 可传 vector_store（Day 09）——跑完管道后，嵌入好的 Node 直接写进向量库，不用再手动建索引。

读法：这让 Pipeline 成为"从原始文档到向量库"的完整摄入方案：run 一次 = 读好的 Documents 经切块+嵌入，直接进向量库，随时可检索。Day 07 的 VectorStoreIndex 也能这么用。第 1 周到此形成闭环：Reader（Day 03）→ NodeParser（Day 04）→ Pipeline 串起来 + Embedding + 存向量库——RAG 的"离线建库"阶段完整了。
