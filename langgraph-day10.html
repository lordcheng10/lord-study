Day 10 / 共 20 天 · 第 2 周收官

节点执行与并行

同一超步里多个节点怎么并行跑？为什么并行不会互相踩踏？Send 又怎么实现 map-reduce 动态并发？今天收官 Pregel 引擎。

L01

同步屏障回顾

Day 06 讲过：一个超步内被选中的节点并行执行，但都读同一份"步初快照"，写入攒到步末统一提交。今天看这在代码里怎么落地。

一句话回顾 BSP 同一超步的节点像一排同时起跑的选手：都从同一起跑线（步初状态快照）出发，各跑各的，谁也看不到别人这一步的中途结果；全部到达终点（步末），才统一结算成绩（apply_writes）。这样并行才安全——没有"我读到你写一半的数据"这种竞态。今天看这个"同时起跑、统一结算"在 PregelRunner 里怎么实现。
L02

PregelRunner

PregelRunner（pregel/_runner.py）负责并行跑本超步的所有任务。tick() 内部：为每个任务建一个可等待单元，用 asyncio（异步）或线程池（同步）并发执行，边完成边 yield 结果给外层流式输出（Day 08 的 for _ in runner.tick(...)）。

读法：PregelRunner 是"这一超步的并行执行器"：拿到本步任务列表，并发跑，哪个先完成就先吐结果。同步图用线程池、异步图用 asyncio——同一套调度逻辑两种后端。
L03

Read 读输入

节点执行前，PregelNode 通过 ChannelRead（pregel/_read.py）从步初快照读取它订阅的通道值，组成输入。

读法：节点不直接访问全局状态，而是通过 ChannelRead 从"步初快照"读它声明的 channels（Day 09 编译时定的）。读的是快照 → 本步内别的节点写什么都影响不到我 → 快照隔离（Day 06）。
L04

Write 攒输出

节点跑完，ChannelWrite 不直接改通道，而是把写入交给注入的 write 函数 → 攒进 task.writes（pending writes，Day 08 的 put_writes）。

# 节点返回 {"count": 5} → writers 拆成写入条目 → 交给 write 函数
# write 函数把它 append 到 task.writes，不碰真正的通道
# 超步末 after_tick → apply_writes 才统一提交（Day 08）
读法：写入被"缓冲"起来（task.writes），不立即生效。Read（读步初快照）+ Write（攒到步末）配合，就实现了"读写解耦、快照隔离"。这就是 Day 06 说的"actor 只跟通道打交道、不互相直接调用"的物理实现。
L05

并行为何安全

把 L03/L04 合起来看，同一超步 A、B 两节点并行：

  • A、B 都从同一份步初快照读输入（互不影响）。
  • A、B 的写入各自攒进自己的 pending writes（不直接改通道）。
  • 步末 apply_writes 按确定顺序合并所有写入（reducer 处理"两个都写了 messages"的情况）。
为什么这样就不会出 bug？ 传统并行编程最怕"竞态"：A 读的时候 B 正在改，读到半拉子数据。Pregel 用两招根除竞态：①都读同一份不变的快照（读的时候没人在改）；②写入先攒着、步末按固定顺序统一提交（合并顺序确定 → 结果可复现）。于是你写并行节点时完全不用加锁、不用管线程安全——引擎的 BSP 模型替你保证了正确性。这是 LangGraph 相比"手写 async 编排"最大的安全红利。
L06

Send 动态并发（map-reduce）

Send(node, arg)（Day 04 见过）实现运行时动态并发：一个节点返回一批 Send，下一超步为每个 Send 各起一个任务并行跑同一节点（PUSH 任务，Day 08 L03）。

def fan_out(state):
    # 运行时才知道要拆几路 → 动态生成 N 个并行任务
    return [Send("worker", {"item": x}) for x in state["items"]]
Send = 运行时决定的"分身术" 普通边在编译时就固定了（a→b）。但有时并发数量要运行时才知道——比如"把用户给的 N 个问题各查一遍"，N 是动态的。Send 让你在节点里返回一批 Send，引擎下一步就为每个 Send 起一个并行任务（都跑 worker 节点、各带各的数据）。这就是经典的 map（拆成 N 路并行）→ reduce（结果汇总进通道，用 reducer 合并）。Send 是 LangGraph 做"动态扇出"的唯一正道，比自己在节点里开线程干净得多。
L07

重试与错误

任务可配 RetryPolicy：节点抛异常时按策略重试（指数退避）。若最终失败，异常向上抛出中断整个执行——但因为上一超步的检查点已存（Day 08），修好后可从该检查点恢复，不用从头跑。

读法：节点级重试（RetryPolicy）应对瞬时错误；超步级检查点应对彻底失败——从最近检查点恢复。两层容错。这正是"持久执行"的价值：长流程中途挂了，不用推倒重来。
