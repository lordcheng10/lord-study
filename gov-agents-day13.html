Day 13 / 共 20 天 · 第 3 周 运行时与实战

CLI 与 MCP 接入 IDE

除了 HTTP，agent 还能通过命令行给 CI/运维用、通过 MCP 让 IDE"说人话就调"。今天讲清这两种入口，并厘清最容易混的"两个 MCP"。

L01

四种接入面

同一个 agent 能力，平台通过四种"面（surface）"暴露给不同用户：

接入面给谁用怎么用
HTTP API程序 / 前端 / 集成POST /v1/agent/…（Day 12）
CLI (agentctl)CI/CD / 运维 / 脚本命令行调用
MCPIDE 里的 AI（Cursor/Claude Code）自然语言触发
SkillsIDE 里的人一句话 SOP（Day 19）

关键点：CLI 和 MCP 本身都不含业务逻辑，它们最终都是把请求转成对 Day 12 那个 HTTP server 的调用。二者甚至共用同一个 HTTP 客户端 PlatformClient。

L02

agentctl：命令行封装

packages/gov-agents-cli 提供命令 agentctl（基于 Typer）。入口 gov_agents_cli.main:app。它就是把 Day 12 的 HTTP 端点包成好用的命令行，给 CI/CD、运维脚本、Jupyter 用。

它内部用 PlatformClient（main.py:50）调平台，统一了退出码映射（_run, main.py:58）：0 成功 / 1 HTTP 错 / 2 输入错 / 3 网络错 / 130 Ctrl+C——这对 CI 脚本判断成败很重要。

一个有意思的取舍：CLI 里写死了只认 5 个 canonical agent 名（AGENT_NAMES, main.py:31：biz-link-gov / rca / risk-review / alert-triage / doc-check），而 server 注册表有 18 个。为什么不复用？因为 CLI 要保持极轻——不 import 任何平台业务包（否则会拉进 langgraph/大模型一堆重依赖，启动变慢）。所以它宁可硬编码一小份名单。这又是一处"务实的重复"。
L03

CLI 命令 → HTTP 映射

每个命令对应一个 Day 12 的端点：

命令对应 HTTP
agentctl invoke <agent> --data ...POST /invoke
agentctl stream <agent> --data ...POST /stream（自己解析 SSE）
agentctl cases <agent> [--limit --table]GET /cases
agentctl case <agent> <case_id>GET /cases/{id}
agentctl feedback <agent> <case_id> --verdict ...POST /feedback
agentctl healthGET /v1/healthz
agentctl agents本地列名，不走网络

还有子命令组：agentctl skill（init/validate/index/check，管 L4 skills）、agentctl new agent（脚手架起新 agent，用 6 个 Jinja2 模板，Day 19 用到）。环境变量 PLATFORM_BASE_URL（默认 localhost:8080）指定连哪个平台。

# 例：命令行调 rca，等价于 Day 02 那个 curl
agentctl invoke rca --data '{"user_question": "service-A 超时"}'
agentctl cases rca --limit 10 --table       # 看最近 10 条调用
agentctl feedback rca 01HXXX --verdict approve --score 5
L04

MCP 是什么：让 IDE 的 AI 能调你的 agent

MCP（Model Context Protocol）是一个标准协议，让 IDE 里的 AI 助手（Cursor / Claude Code / Cline / Windsurf）能"调用外部工具"。你在 IDE 里说一句人话，AI 就能触发一个 MCP tool 帮你干活。

IDE 的 AICursor / Claude Code
stdio启动子进程
MCP servergov-agents-mcp
HTTP转发调用
平台 serverDay 12

本框架把 agent 暴露成 MCP tool，于是你在 IDE 里说"帮我分析下 service-A 的超时根因"，AI 就会调 invoke_sre_rca 这个 MCP tool，背后其实是打了平台的 HTTP 接口。

L05

gov-agents-mcp：HTTP 瘦代理

packages/gov-agents-mcp 是一个 MCP stdio 瘦代理：IDE 通过 stdio 启动它，它把平台的 5 个 agent 暴露成 MCP tools，把 case 历史暴露成 MCP resources。零业务逻辑，全部转成对平台的 HTTP 调用。

  • 5 个 tool（schemas.py:68）：invoke_biz_link_gov / invoke_sre_rca / invoke_risk_review / invoke_alert_triage / invoke_doc_check。
  • 每个 tool 的输入 schema 用 Pydantic 模型的 model_json_schema() 自动生成（tools.py:14）——注意这些 schema 是手抄的，不 import agent 包（同样为了轻量）。
  • resources：cases://<agent>（最近 50 条）和 case://<agent>/<id>（单条详情），让 IDE 能直接浏览历史调用。
  • PlatformClient（client.py:49）把 HTTP 状态码归成 4 类友好错误（422→输入错 / 401,403→鉴权 / 500→agent错 / 其它→上游错）。

装到 IDE 就是往 .mcp.json 加一段（README 示例）：

{"mcpServers": {"gov-agents": {
  "command": "uvx", "args": ["gov-agents-mcp"],
  "env": {"PLATFORM_BASE_URL": "http://localhost:8080",
          "MCP_USER_ID": "mcp:alice"}}}}
L06

bmc-agent-mcp：curl 一键装的独立 MCP

README 首页那条 curl ... | bash 一键安装，装的其实是另一个 MCP——apps/bmc-agent-mcp，专做"把 Java 工程的 bmc-parent 升版"。它和 gov-agents-mcp 架构完全不同。

安装脚本 bmc-mcp.sh 做 4 件事：

1

检测 Python ≥ 3.10

从 3.13 往下试到 3.10。

2

建 venv + 从公司 Nexus 装 bmc-agent-mcp

venv 在 ~/.bmc-mcp，shim 落 ~/.local/bin。

3

交互收集 3 项配置

Anthropic key / Maven Home / settings.xml（curl|bash 时把 stdin 切到 /dev/tty 的技巧）。

4

探测 IDE 并安全 merge 写配置

Cursor/Claude Code/Windsurf 的 mcp.json，保留已有配置、叠加新值。

关键区别：bmc-agent-mcp 直接 import 复用 bmc_agent 的图（不走 HTTP！），用 FastMCP 暴露 4 个 tool（scan/diagnose/upgrade/read_report）。它是"独立进程、内嵌 agent"形态。

一个 stdio 小坑值得学：MCP 走 stdio 传 JSON-RPC，如果 agent 里的 rich 库往 stdout 打印会污染协议。bmc-agent-mcp 用 contextlib.redirect_stdout 把这些输出导到 stderr（server.py:20）——这种"保护协议通道"的细节，是做 MCP server 的常见坑。
L07

三个易错点：两个 MCP、两个 supervisor、三层命名

本框架有几组"名字像、其实不同"的东西，一次讲清避免踩坑：

gov-agents-mcp
  • HTTP 瘦代理
  • 暴露平台 5 个 agent
  • 不含业务，转发 HTTP
  • uvx gov-agents-mcp
bmc-agent-mcp
  • 独立进程内嵌 agent
  • 专做 Java BMC 升版
  • 直接 import bmc_agent 的图
  • curl 一键装

另外两组（前面讲过，这里汇总）：

  • 两个 supervisor（Day 04）：图内 supervisor_node（选专家、真跑）vs 跨 agent router（选 agent、只建议）。
  • 三层命名（Day 12）：注册表名(sre-rca) ≠ 路由名(rca) ≠ CLI/MCP canonical 名。
读代码时的自保习惯：遇到 "supervisor" / "mcp" / agent 名，先确认"这是哪一个"——看它在哪个包、import 了什么、agent_name= 传的什么。名字相近但职责不同，是大型项目的常态。
