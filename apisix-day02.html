Day 02 / 共 20 天 · 第 1 周 全景与请求生命周期

OpenResty 与 Nginx 阶段

读懂 APISIX 的前提是理解"Nginx 处理请求的阶段"。APISIX 的所有逻辑，本质就是"在 Nginx 的某个阶段挂一段 Lua"。今天把这套阶段模型讲清，你就有了阅读 init.lua 的地图。

L01

为什么要懂阶段

Nginx 把处理一个请求切成"阶段" Nginx 处理一个 HTTP 请求不是"一口气跑完",而是分成有序的"阶段"（phase）：先读请求、再决定权限（access）、再选后端（balancer）、再改响应头（header filter）、再改响应体（body filter）、最后记日志（log）。OpenResty 让你在每个阶段挂一段 Lua 代码（access_by_lua、header_filter_by_lua、log_by_lua…）。APISIX 就是把它的网关逻辑分派到这些阶段的 Lua 里——所以 init.lua 里那一堆 http_xxx_phase 函数，就是各阶段的入口。懂了阶段，就懂了 APISIX 的骨架。
L02

请求处理的阶段序

init（master 启动一次）+ init_worker（每 worker 启动一次）— 加载配置、起后台任务
ssl（握手时）— 动态选证书
access / rewrite（每请求）— 路由匹配、鉴权、限流，决定"放不放行、怎么改"
balancer（选后端）— 负载均衡挑一个上游实例，失败可重试
header_filter — 改响应头
body_filter — 改响应体（可能多次，流式）
log — 记录日志、上报指标、清理资源
读法：对照 Day 01 的数据流：access 阶段干了最多活（路由+插件），balancer 选上游，filter 改响应，log 收尾。这个顺序是 Nginx 定死的，APISIX 顺着它编排。和上一站 wasm-go 的"六阶段钩子"异曲同工——都是"请求生命周期分段处理"。
L03

init 与 init_worker

init.lua 里对应两个函数（Day 03 细讲）：

  • _M.http_init(args)（:85）：master 进程启动时跑一次——初始化 resolver、id、env、配置。
  • _M.http_init_worker()（:107）：每个 worker 进程启动跑一次——起服务发现、balancer、admin、router、plugin、consumer 等的 worker 初始化。
master vs worker Nginx 是"1 个 master + N 个 worker"进程模型：master 管理、worker 真正处理请求（对应 CPU 核数）。http_init 在 master 跑（全局一次性初始化），http_init_worker 在每个 worker 跑（每个 worker 要自己的 etcd 连接、自己的定时器）。这和 Envoy 的"1 主 + N worker"线程模型很像——高性能服务器的通用套路。
L04

access 阶段（重头戏）

_M.http_access_phase()（init.lua:602）是每个请求的主处理入口，Day 04 会逐行读。它干的事：创建 api_ctx → 校验 TLS → 匹配路由 → 合并 service/consumer 配置 → 选插件 → 跑 rewrite/access 阶段插件 → 交给 handle_upstream。

读法：为什么最重的逻辑在 access 阶段？因为 access 是"请求已读完、还没转发上游"的时机——正好在这里做所有"决策"（能不能过、走哪个后端、要不要改）。APISIX 90% 的请求处理逻辑集中在这一个阶段函数里。
L05

balancer 阶段

_M.http_balancer_phase()（init.lua:993）：

function _M.http_balancer_phase()
    local api_ctx = ngx.ctx.api_ctx
    if not api_ctx then
        return core.response.exit(500)
    end
    load_balancer.run(api_ctx.matched_route, api_ctx, common_phase)
end
balancer 为什么是单独阶段？ Nginx 的 balancer 阶段特殊：它可能被调用多次——第一次选的上游实例连不上，Nginx 会重试，再次进入 balancer 选下一个实例。所以负载均衡（挑哪个后端）+ 失败重试的逻辑放这里。load_balancer.run 用 api_ctx.matched_route（access 阶段匹配好的路由）里的上游配置来选实例。Day 10 详讲负载均衡算法。
L06

filter 与 log

响应阶段和收尾（都通过 common_phase 统一跑插件，init.lua:470）：

function _M.http_header_filter_phase()   -- :810 改响应头
    core.response.set_header("Server", ver_header)
    common_phase("header_filter")
end
function _M.http_body_filter_phase()     -- :836 改响应体
    common_phase("body_filter")
    common_phase("delayed_body_filter")
end
function _M.http_log_phase()             -- :959 收尾
    local api_ctx = common_phase("log")
    healthcheck_passive(api_ctx)         -- 被动健康检查
    core.ctx.release_vars(api_ctx)       -- 释放上下文（回收 table）
    core.tablepool.release("api_ctx", api_ctx)
end
读法：common_phase(name) 是各阶段的通用套路——跑全局规则 + 跑该阶段的插件。log 阶段还负责"释放 api_ctx 到 table 池"——这是 APISIX 性能优化的关键（复用 table 减少 GC，Day 05 讲）。被动健康检查也在 log 阶段（根据这次请求的成败标记上游健康度）。
L07

_M 与阶段绑定

init.lua 里的 _M.http_xxx_phase 函数怎么和 Nginx 阶段绑定？答案在生成的 nginx.conf（Day 03 讲）里，类似：

access_by_lua_block { apisix.http_access_phase() }
header_filter_by_lua_block { apisix.http_header_filter_phase() }
body_filter_by_lua_block { apisix.http_body_filter_phase() }
log_by_lua_block { apisix.http_log_phase() }
balancer_by_lua_block { apisix.http_balancer_phase() }
Lua 里的 _M 是什么？ Lua 的模块惯例：local _M = {} 是模块的"导出表",最后 return _M。_M.http_access_phase 就是这个模块对外提供的一个函数。nginx.conf 里的 access_by_lua_block 调用它——这就是"Lua 函数挂到 Nginx 阶段"的绑定。所以读 APISIX，就是读这些 _M.http_xxx_phase 函数在各阶段做了什么。
