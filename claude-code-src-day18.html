Day 18 / 共 20 天 · 第 4 周 平台化进阶

TUI 深入

Day 04 讲了 TUI 骨架，今天钻输入框细节——多行编辑、粘贴、自动补全、键位、vim 模式、对话框浮层怎么"仲裁"。终端交互的精华都在这。

L01

输入框的分层

输入框 PromptInput.tsx（2650 行）本身不处理按键——它是"编排层"，负责拼装模式/建议/粘贴/历史/渲染。真正逐键编辑在 useTextInput（src/hooks/useTextInput.ts）。分层：

层管什么
PromptInput.tsx编排：模式（bash !）、自动补全、粘贴、历史、提交分流
useTextInput.ts逐键编辑：光标、emacs 键位、换行/提交判定
useVimInput.ts在 useTextInput 外套一层 vim 状态机
Cursor.ts不可变的文本+光标模型
为什么分这么细？ 输入框看着简单，其实要处理：多行、粘贴大段文本、@文件补全、/命令补全、↑历史、emacs 快捷键、vim 模式、bash 模式……全塞一个组件会乱成一团。分层后：Cursor 管"文本和光标的纯数据"、useTextInput 管"按键怎么改光标"、useVimInput 加 vim、PromptInput 管"上层业务"。每层只干一件事，组合起来才是完整输入框。
L02

Cursor：不可变的编辑模型

底层编辑用不可变的 Cursor 对象（src/utils/Cursor.ts）。每次按键产出一个新 Cursor，而不是改旧的：

// useTextInput.ts:478 —— 受控编辑回写
const nextCursor = mapKey(key)(cursor)      // 按键 → 新 Cursor
if (cursor.text !== nextCursor.text)
  onChange(nextCursor.text)                 // 文本变了才通知上层
setOffset(nextCursor.offset)                // 更新光标位置
为什么用"不可变 Cursor"？ 文本编辑涉及一堆操作（插入、删除、移动光标、删词），如果直接改一个可变对象，很容易状态错乱、也难做撤销。用"每次操作返回新 Cursor"（不可变），每个操作都是纯函数 旧Cursor → 新Cursor——清晰、可测、天然支持撤销（保存历史 Cursor 即可）。这跟 Day 06 讲的 queryLoop"整体替换 State"是同一种"用不可变数据避免状态错乱"的思想。useTextInput 还内置整套 emacs 键位（Ctrl+A/E/K/U/W、kill-ring/yank）。
L03

换行 vs 提交（点睛代码）

输入框最微妙的判断：按回车是"换行"还是"提交"？useTextInput.ts:248 的 handleEnter：

function handleEnter(key) {
  // 反斜杠 + Enter → 换行（删掉反斜杠）
  if (multiline && cursor.text[cursor.offset-1] === '\\')
    return cursor.backspace().insert('\n')
  // Shift/Option(Meta) + Enter → 换行
  if (key.meta || key.shift) return cursor.insert('\n')
  // 普通 Enter → 提交
  onSubmit?.(value)
}

三种换行方式（\+Enter、Shift+Enter、Option+Enter），普通 Enter 才提交。而且 case key.return 特意排在 case key.meta 之前，保证 Option+Return 走换行。粘贴过程中的 Enter 被抑制（防误提交）。

为什么这么讲究？ 因为在终端里既要能多行输入（写长 prompt/贴代码），又要能快速提交。约定俗成：普通回车提交、修饰键+回车换行。但不同终端对修饰键+回车的支持不一，所以提供了三种换行法（连纯 \+回车都支持）兼容各种终端。这种"照顾各种终端怪癖"的细节，是终端应用体验好坏的关键。撤销栈由 useInputBuffer 单管（防抖 1000ms、最多 50 条）。
L04

自动补全：/ @ # 触发

由 useTypeahead（PromptInput.tsx:1281）驱动。输入变化时判断触发字符：

  • / 开头 → 斜杠命令补全（generateCommandSuggestions，Day 11 的命令列表）。
  • @ → 文件/agent 补全。
  • # → slack 频道等。

建议列表存进 state，渲染在页脚下拉。接受方式：Tab/→ 接受、↑↓ 选择、Esc 关闭。护栏：有建议显示时，普通 Enter 不提交（而是接受当前建议，PromptInput.tsx:1229）。

"有建议时 Enter 不提交"为什么重要？ 你敲 /mod，下拉出现 /model，你按回车——期望是"选中 /model"，不是"把 /mod 这半截提交出去"。所以补全下拉可见时，回车的语义变成"接受建议"。这种"根据当前 UI 状态改变按键含义"的上下文敏感，是好交互的细节。Fuse.js（Day 01 依赖表提过）用来做模糊搜索——你敲 /mdl 也能匹配到 /model。
L05

粘贴：三层处理

往终端粘贴（尤其大段文本/图片）要特殊处理，分三层：

  1. 检测层 usePasteHandler：靠按键事件的 isPasted 标志（括号粘贴模式）判定，分块累积 + 100ms 超时合并；拖入的图片路径 → 读图。
  2. 业务层 onTextPaste（PromptInput.tsx:1374）：清理 ANSI、\r→\n；超过阈值就不塞全文，而是存进 pastedContents、只在输入框插一个占位引用（:1398）。
  3. 截断层 inputPaste.ts：>10000 字保留首尾各 500 字、中间折叠。
为什么大段粘贴要"占位引用"而非直接显示？ 你粘了 500 行代码进去——如果全显示在输入框里，输入框撑爆、界面卡、你也看不清自己在打什么。所以大段内容被折叠成一个 [Pasted 500 lines] 占位，实际内容存在 pastedContents 里，提交时才展开发给模型。图片同理插一个图片引用占位。这是"输入框只显示摘要、内容另存"的体验优化——既不卡界面又不丢内容。括号粘贴模式（bracketed paste）是终端的一个特性，让程序能区分"用户逐字敲的"和"粘贴进来的"。
L06

键位系统与 vim 模式

键位系统核心在 @anthropic/ink，仓库侧 src/keybindings/ 多为再导出。默认绑定表 defaultBindings.ts:32 按上下文分组：

  • Ctrl+O → 切 transcript 视图；Ctrl+R → 历史搜索；Shift+Tab → 切权限模式（Day 09）。
  • 用户可用 ~/.claude/keybindings.json 覆盖默认。
  • Ctrl+C/Ctrl+D 登记但不可重绑（走时间敏感的双击处理）。

vim 模式（src/vim/ + useVimInput.ts）：完整实现了 NORMAL/INSERT 模式、移动（motions）、操作符（d/c/y）、文本对象（iw/ap）、. 重复上次修改（dot-repeat）。INSERT 模式几乎透传给 useTextInput，NORMAL 模式把按键交给状态机 transition（useVimInput.ts:273）。

vim 模式怎么套在普通编辑之上？ useVimInput 包在 useTextInput 外面：INSERT 模式时基本"放行"给底层的普通编辑；NORMAL 模式时拦截按键、走 vim 状态机（d+w = 删一个词……）解析成对 Cursor 的操作。因为底层是不可变 Cursor（L02），vim 的各种操作都能表达成"旧 Cursor → 新 Cursor"，dot-repeat 也只是"重放上次那串操作"。分层设计让 vim 这种复杂模式能干净地叠加上去，而不用改动底层编辑。Esc 退出 INSERT 是固定不可配的。
L07

对话框浮层：优先级仲裁

权限卡、模型选择、成本确认……这些浮层怎么管？不是"组件栈"，而是"队列 + 一个优先级仲裁函数"。核心是 getFocusedInputDialog()（REPL.tsx:2414）：

// REPL.tsx:2414 —— 按固定优先级返回"当前唯一活跃"的对话框
function getFocusedInputDialog() {
  if (退出态) return 'exit'              // 最高
  if (messageSelector) return 'message-selector'
  if (用户正在打字 && 距上次输入 < 1500ms)
    return null                          // ★ 抑制打断式弹窗
  if (toolPermissionQueue.length) return 'tool-permission'
  // ... 各类对话框按优先级
}
"优先级仲裁"而非"弹窗堆栈"的好处：同一时刻只显示一个最该显示的对话框，避免弹窗打架/叠一堆。而且有个体贴设计——你正在打字时（1500ms 内）抑制打断式弹窗（PROMPT_SUPPRESSION_MS），不会你打一半突然蹦个框把你打断。各类请求存在各自队列（toolUseConfirmQueue 等），永远渲染队头 [0]，处理完出队。权限卡还作为 FullscreenLayout 的 overlay 渲染（Day 04），数据由 Day 09 的"await Promise"模式产生。另一类对话框在 dialogLaunchers.tsx——那些 REPL 之外、启动期的一次性对话框（快照更新、resume 选择器）。
