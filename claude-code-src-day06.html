QueryEngine 深入

从宏观进入微观。Day 03 讲了循环"是什么"，今天钻进 QueryEngine.ts 和 query.ts 源码，看那个驱动 turn 的生成器到底怎么写的。

L01

三层再定位

复习 Day 03 的三层（今天聚焦前两层）：

层文件职责
会话层QueryEngine.ts一会话一实例，跨 turn 保持状态，产出对外 SDK 消息
循环层query.tsqueryLoop 的 while(true)，真正的 agent loop
API 层services/api/claude.ts打 Anthropic API、流式累积（Day 03 讲过）
还有个便捷入口 ask()（QueryEngine.ts:1256）：它只是 QueryEngine 的一次性包装——new QueryEngine(...) 然后 yield* engine.submitMessage(...)。适合"问一句拿一次结果"的场景（比如 headless 模式）。交互式 REPL 则复用同一个 QueryEngine 实例跨多轮对话。
L02

一会话一实例：状态跨 turn 保持

类定义在 QueryEngine.ts:192。它的注释点明了设计哲学（:188）："One QueryEngine per conversation. Each submitMessage() call starts a new turn... State persists across turns."

class QueryEngine {
  mutableMessages: Message[]        // 跨 turn 持久的完整消息历史
  abortController: AbortController  // 用于中断（Esc/Ctrl+C）
  totalUsage: Usage                 // 累计 token 用量
  readFileState: ...                // 读过哪些文件（去重用）
  // ...
}
为什么"一会话一实例"？ 因为一次对话里，多个 turn 要共享同一份消息历史、同一个中断控制器、累计的 token 统计。把这些做成实例字段，submitMessage() 每次调用就是"在同一个 engine 上开一个新 turn"，状态自然延续。这比"每次都传一大堆参数"干净得多。AbortController 是 JS 标准的"取消信号"——你按 Esc，它 abort()，正在进行的 API 请求和工具就被取消。
L03

submitMessage：驱动一个 turn 的主生成器

async *submitMessage(prompt, options)（QueryEngine.ts:217）是核心。开头做准备，然后进入消费循环层的 for-await：

async *submitMessage(prompt, options) {
  // 1. 处理 slash 命令/附件，push 进 mutableMessages
  const messages = await processUserInput(prompt, ...)   // QueryEngine.ts:426
  this.mutableMessages.push(...)                          // :441
  yield { type: 'system', subtype: 'init', ... }          // :551 先吐一条 init

  // 2. ★ 消费循环层的全部产出
  for await (const message of query({                     // :688
    messages, systemPrompt, canUseTool: wrappedCanUseTool,
    maxTurns, taskBudget, ...
  })) {
    switch (message.type) { ... }   // 见 L04
  }

  // 3. 循环结束，产出最终 result
  yield { type: 'result', subtype: 'success', ... }       // :1194
}
async function*（异步生成器）：能"边算边一个个吐结果、且中间可以 await"的函数。submitMessage 是异步生成器，所以 UI 能用 for await (const msg of engine.submitMessage(...)) 实时拿到每条消息更新界面——不用等整个 turn 跑完。这是"流式"能从最底层 API 一路传到界面的根本机制。

注意 wrappedCanUseTool（:253）——它包装了权限回调（Day 09），顺便记录被拒绝的工具到 permissionDenials，最终进 result。这就是权限系统接进循环的地方。

L04

消息类型 switch：把内部消息转成对外消息

循环体是一个大 switch(message.type)（QueryEngine.ts:772）。它的核心工作是把循环层产出的"内部 Message"分类，转成对外的 SDK 消息，并顺手维护统计：

assistant

捕获 stop_reason、push 进 mutableMessages、yield* normalizeMessage(msg) 转成对外 SDK 消息（:776）

stream_event

维护 usage/成本：message_start 重置、message_delta 累加、message_stop 累进 totalUsage；仅当调用方要"打字机"才透传原始事件（:813）

user

turnCount++（:768）——数这是第几轮

attachment

提取结构化输出；处理 max_turns_reached → 产出 error_max_turns result（:886）

system

处理 compact_boundary（上下文压缩边界，Day 10）、api_error → api_retry（:939）

为什么要"内部消息 → 对外 SDK 消息"这层转换？ 循环层内部的 Message 格式是干活用的（带各种中间状态）；而对外（给 UI、给 SDK 调用方）需要一个稳定、干净的格式。normalizeMessage 做这个翻译。这种"内外格式分离"让内部实现能自由演进而不破坏外部契约——是好 API 设计的通例。
L05

queryLoop 的 State：每轮整体替换

钻进循环层 query.ts。queryLoop 的 while(true)（:460）每轮迭代维护一个可变的 State（query.ts:261）。一个值得学的写法——每次 continue 用整体替换而非分散赋值：

// query.ts:2043 —— 构造下一轮完整 state，整体替换
const next: State = {
  messages: messagesForQuery.concat(assistantMessages, toolResults),
  turnCount: nextTurnCount,
  // ... 所有字段一次性给全
}
state = next   // 而不是 state.messages = ...; state.turnCount = ...（9 处分散赋值）
continue
为什么整体替换？ 循环里有 7 个不同的 continue 点（对应 7 种"继续"原因，见 transitions.ts 的 Continue 类型）。如果每处都去改 state 的 9 个字段，很容易漏改一个、留下上一轮的脏值。改成"每处都构造一个完整的新 state 整体赋值"，就不可能漏——要么全给、要么编译报错。这是用"不可变整体替换"消除"部分更新遗漏"这类 bug 的典型手法。

Day 03 讲的检测 tool_use（:1090）、跑工具（:1671）、停止判断（:1349 的 !needsFollowUp）都在这个 while 体里。今天你能把它们和 State 的流转对上了。

L06

依赖注入：为什么可测试

query.ts 没把"调模型""压缩上下文"这些写死，而是抽成可注入的依赖 QueryDeps（src/query/deps.ts:21）：

// deps.ts:21
interface QueryDeps {
  callModel: ...      // 生产实现 = queryModelWithStreaming
  microcompact: ...   // 微压缩
  autocompact: ...    // 大摘要
  uuid: ...
}
// deps.ts:33
function productionDeps(): QueryDeps { return { callModel: queryModelWithStreaming, ... } }

// query.ts:416
const deps = params.deps ?? productionDeps()   // 没传就用生产实现
依赖注入（DI）：不在函数内部直接创建它依赖的东西，而是"从外面传进来"。这里 query 默认用 productionDeps()（真调 API），但测试时可以传一个假的 callModel（返回预设响应）——于是能测整个循环逻辑而不真调 Anthropic API、不花钱、结果可复现。同理 QueryConfig（config.ts）把各种 feature gate 在入口快照成不可变配置。这跟 gov-agents 教程里的 get_llm/FakeLLM 是同一种"为可测试性做依赖注入"的思想。
L07

usage / 成本统计怎么攒起来

你退出时看到的"本次花了 $0.03"是怎么算的？靠流式事件里的 usage 一路累加（Day 17 细讲，这里看在 QueryEngine 的接线）：

  • 每条 assistant 消息的 message_start 重置本条 usage、message_delta 累加、message_stop 把本条累进 this.totalUsage（QueryEngine.ts:817-848）。
  • 累加函数 updateUsage / accumulateUsage 在 claude.ts。
  • 实时计费发生在流式增量处：calculateUSDCost(model, usage) → addToTotalSessionCost（claude.ts:2357）。
为什么在流式过程中就算成本，而不是等结束？ 因为如果 turn 中途被中断（你按了 Esc），已经消耗的 token 也得算钱。边流边累加保证"消耗多少就记多少"，中断也不丢账。usage 指 API 返回的 token 用量（输入/输出/缓存读写各多少 token），乘以单价就是花费——Day 17 讲定价表。

QueryEngine 还有几个"硬停"：USD 预算超限 → error_max_budget_usd（:1023）、结构化输出重试超限 → error_max_structured_output_retries（:1058，默认 5 次）。这些是会话层独有的保护，循环层管不到。
