Channels 通道

状态存在通道里，节点通过通道通信。今天读 channels/：BaseChannel 接口、几种具体通道，以及"reducer 其实就是通道的 update()"这个真相。

📍 你在整门课的位置
Pregel引擎→Channels→super-step→编译图
L01

通道是"带合并逻辑的状态格子"

🤔 痛点State 里有的字段想"新值覆盖旧值"（比如 当前用户），有的想"新值追加到列表"（比如 messages 越攒越多）。如果所有字段都用同一种合并方式，就没法同时满足这两种需求。怎么让每个字段各有各的合并规则？
💡 本质LangGraph 让 State 的每个 key 底层都是一个独立的 channel（通道），而你写的 reducer 其实就是这个 channel 的 update() 合并逻辑。想覆盖就用 LastValue 通道，想追加就用 BinaryOperatorAggregate 通道。"字段各有合并规则"= "字段各配一种通道类型"。
通道就像公司里的公告栏/信箱：节点之间从不当面对话，都是往公告栏贴、从公告栏读。而"新内容怎么上墙"每块栏各有规矩——有的擦了重写（LastValue 覆盖），有的像留言本一条条往下记（BinaryOperatorAggregate 追加）。

Day 03 说 State 的每个字段编译成一个 channel。channel 就是"一个带自定义合并逻辑的状态格子"——存一个值，并定义"新写入怎么合并进来"。

State 字段 ↔ channel 你写的 class State(TypedDict): messages: ...; count: ...，编译后每个字段（messages、count）都变成一个 channel。节点写状态 = 往对应 channel 写；节点读状态 = 从 channel 读。不同字段可以用不同类型的 channel（Day 03 的 reducer 选择就是选 channel 类型）——覆盖用 LastValue、追加用 BinaryOperatorAggregate。"状态"这个抽象，底层就是一组 channel。
reducer 决定通道类型：messages 用累加通道，count/user 用覆盖通道
L02

BaseChannel 接口

BaseChannel（channels/base.py:19）泛型 [Value, Update, Checkpoint]，核心方法：

方法作用
update(values) :90★ reducer 落地点——把新写入合并进来，返回是否被更新
get() :70读当前值（空则抛 EmptyChannelError）
is_available() :75通道是否有值——只有 available 才能触发节点
checkpoint()取出当前值用于存档（Day 11）
读法：三个泛型参数：存储值类型、接收更新类型、序列化类型。update 是最重要的——它定义"合并策略"。docstring 明说 update "由 Pregel 在每个超步结束时对所有通道调用"（呼应 Day 06 的 Update 阶段）。
L03

update 返回 True = 被更新

update(values) -> bool 返回 True 表示"本通道被更新了"——这个布尔值决定下一步谁被触发（Day 06 的版本号 +1）。

update 的返回值串起了整个引擎 超步末，Pregel 对所有通道调 update(这步收到的写入)。返回 True 的通道 → 版本号 +1 → 触发订阅它的节点在下一步跑（Day 06 的 _triggers）。返回 False（没收到写入）→ 版本不变 → 不触发下游。"通道被更新 → 触发下游"这条 Day 04/06 反复提的机制，落地就在 update 的返回值上。通道是引擎的"神经"——它的 update 既合并数据，又通过返回值决定数据流向。
L04

LastValue（覆盖）

LastValue（last_value.py:56）——默认通道，"存最后一个值、每步最多一个"（Day 03 已看过）：

def update(self, values):
    if len(values) == 0: return False
    if len(values) != 1:
        raise InvalidUpdateError("Can receive only one value per step...")
    self.value = values[-1]; return True
读法：没标 reducer 的 State 字段编译成 LastValue——覆盖语义、每步只准一个写入。两个节点同步写就报错（Day 03 讲过）。
⚠️ 小白常误以为 LastValue 会"默默用后写的盖掉先写的"；其实它一步收到 2 个写入会直接抛 InvalidUpdateError——宁可报错也不猜你想要哪个，逼你显式选 reducer。
💬 小白 vs 老师 👶 小白：为什么覆盖型字段一步只准写一个，追加型却能写好几个？
👨‍🏫 老师：因为"覆盖"遇到两个值就不知道该听谁的（会丢数据），干脆报错；"追加"天生能容纳多个，全记下来即可。就像公告栏：只能贴一张的"今日通知"栏贴两张就冲突了，而"意见留言本"想写几条写几条。
L05

BinaryOperatorAggregate（合并）

BinaryOperatorAggregate（binop.py:65）——用二元操作符折叠（Day 03 的 Annotated[list, operator.add]）：

for value in values:
    self.value = self.operator(self.value, value)   # 逐个折叠合并
💥 错误驱动：用错通道会出什么事故 如果给 messages 用了覆盖型的 LastValue：两个并行节点这一步各写了一条消息，引擎发现"一步收到 2 个写入"直接报错崩溃；就算不报错（勉强取一个），也会丢掉另一条消息。这正是"追加型通道"存在的理由——对话历史这种只增不减的东西，必须用能容纳多写入的通道。
📝 例子：覆盖 vs 追加 同一步收到两个写入 ["a"] 和 ["b"]：
· LastValue：len(values)!=1 → 直接 报 InvalidUpdateError（一步只准一个写入）。
· BinaryOperatorAggregate(operator.add)：[] + ["a"] + ["b"] = ["a","b"]（两个并行节点的写入都被追加，不冲突）。
这就是为什么 messages 要用 Annotated[list, operator.add]——多个节点同步写才不会打架。
读法：把这步收到的多个写入依次用 operator 合并进当前值。这就是"追加型状态"（多个节点并行写 messages 全被累加）的实现。add_messages（Day 03）是这类的一个特化 reducer。
L06

Topic 与 barrier（更多通道类型）

  • Topic（topic.py:23）：PubSub 多值通道，accumulate 决定是否跨步累积。保留通道 TASKS 就是 Topic[Send]（承载动态并发的 Send，map-reduce）。
  • NamedBarrierValue：栅栏通道——等齐多个上游才放行（实现 Day 04 的汇合 fan-in）。
  • EphemeralValue：只活一步（节点的触发通道 branch:to:* 用它）。
  • LastValueAfterFinish（last_value.py:81）：只在 finish 后可读（defer 节点用）。
不同通道 = 不同"通信语义"：LastValue（一对一覆盖）、BinaryOperatorAggregate（累加）、Topic（一对多广播/累积）、NamedBarrierValue（多对一汇合等齐）、EphemeralValue（一次性触发信号）。LangGraph 用不同通道类型表达不同的数据流模式——这套通道体系是 Pregel 引擎的"通信基础设施"。你平时只写 State + reducer，框架帮你选对通道。
L07

reducer 就是 update（真相揭示）

现在可以点破 Day 03 的真相：你写的 reducer（如 add_messages、operator.add），在底层就是被塞进某个 channel 的 update() 逻辑。

reducer 不是挂在图上的东西，是通道的行为 Day 03 你以为 reducer 是"State 字段的合并函数"。真相：它被内建进 channel 的 update()。Annotated[list, operator.add] → 编译成 BinaryOperatorAggregate（operator 就是 add）→ 它的 update 用 operator 折叠。add_messages → 编译成对应通道 → update 执行追加/替换逻辑。所以"reducer 决定合并策略"= "通道的 update 决定合并策略"——同一件事的两个视角。理解了通道，你就彻底懂了 State/reducer 的底层。这是 LangGraph 最优雅的设计之一：把"状态合并"统一成"通道的 update 行为"。
