Day 09 / 共 20 天 · 第 2 周 Pregel 引擎

编译：StateGraph → Pregel

你写的高层 StateGraph 怎么变成底层 Pregel？今天看 compile() 做的翻译：状态键→通道、节点→PregelNode、边→写触发通道。前两周在这里合流。

📍 你在整门课的位置
super-step→编译图→节点·并行→Checkpoint
L01

编译干什么

🤔 痛点你写图时用的是"友好"的概念：add_node、add_edge、State 字段。但 Pregel 引擎（Day 06/08）只认"通道、PregelNode、触发通道"这套底层词汇。两套语言对不上——中间少了一步翻译，用户的图根本没法在引擎上跑。
💡 本质compile() 就是那个翻译器：把用户友好的 StateGraph 逐项翻译成引擎能执行的 Pregel 结构——State 字段→通道、节点→PregelNode、边→"往下游触发通道写一下"。好比源码编译成机器码。用户端保持简单，复杂度全压进这一次编译里。

compile()（state.py:1164）把 StateGraph（图纸）翻译成 CompiledStateGraph（state.py:1391，继承 Pregel，Day 02）。核心两件翻译：状态键 → 通道、节点 → PregelNode。

"编译"= 从用户语言翻译成引擎语言 你用 StateGraph 的语言写图（State 字段、add_node、add_edge）——直观、面向业务。但引擎（Pregel）的语言是"通道、PregelNode、触发"。compile 就是翻译器：把你的高层描述翻译成引擎能执行的低层结构。好比源代码编译成机器码。compile 就像生活中把顾客的菜单翻译成后厨工单：顾客写"一份番茄炒蛋"（友好、面向人），后厨拿到的却是"取鸡蛋3个→打散→热油→…"这种可执行的步骤单（面向操作）。同一个后厨（Pregel 引擎），能照任何翻译好的工单出菜。一套 Pregel 引擎，能执行任何编译好的图——你的 StateGraph、预制 create_react_agent、甚至函数式 API，最终都编译成 Pregel。
字段→通道、节点→PregelNode、边→写触发通道，编译一次得到可执行的 Pregel
L02

状态键 → 通道

_get_channel（state.py:1836，Day 03 看过）为每个 State 字段选一个通道类型：

字段标注→ 通道
无 reducer（如 count: int）LastValue（覆盖）
Annotated[list, operator.add]BinaryOperatorAggregate（累加）
Annotated[..., 某 Channel]直接用那个通道
读法：每个 State 字段变成一个通道，reducer 决定通道类型（Day 07）。_add_schema（state.py:342）把 State schema 展开成 self.channels。这就是"State 底层是一组通道"的实现。
L03

节点 → PregelNode

每个用户节点编译成一个 PregelNode（state.py:1518），关键字段：

self.nodes[key] = PregelNode(
    triggers=[branch_channel],       # 订阅的触发通道（branch:to:自己）
    channels=input_channels,          # 读哪些 state 键（通道）
    writers=[ChannelWrite(...)],      # 跑完把返回值写回哪些 state 键
    bound=用户节点函数,
)
读法：PregelNode（_read.py:97）= actor 的运行时容器。三要素：triggers（订阅哪些通道 → 被触发）、channels（读哪些通道 → 输入）、writers（写哪些通道 → 输出）。这正是 Day 06 的"actor 读通道→算→写通道"三段式。
L04

触发通道

每个节点被分配一个专属触发通道 branch:to:<节点名>（state.py:1512），节点订阅它作为触发条件：

branch_channel = _CHANNEL_BRANCH_TO.format(key)   # branch:to:
self.channels[branch_channel] = EphemeralValue(Any, guard=False)  # 一次性触发信号
# PregelNode(triggers=[branch_channel], ...)
触发通道 = 节点的"门铃" 每个节点有一个专属的"门铃通道"（branch:to:自己）。别的节点想启动它，就往它的门铃通道写一下（按门铃）——下一超步引擎发现门铃响了（通道被更新），就跑这个节点。门铃通道用 EphemeralValue（只活一步）——响过就清，不会一直触发。这就是 Day 04/06 讲的"通道触发"的编译实现：把"边"翻译成"按门铃"的动作。节点之间不直接调用，靠按彼此的门铃解耦。
📝 例子：一条边 a→b 编译成什么 你写 graph.add_edge("a", "b")。编译后（attach_edge，state.py:1537）：
· 给 b 建一个门铃通道 branch:to:b（EphemeralValue，只活一步）；
· b 的 PregelNode.triggers = ["branch:to:b"]（订阅自己的门铃）；
· 给 a 追加一个 writer：a 跑完就往 branch:to:b 写一下（按门铃）。
运行时：a 跑完 → 门铃被写 → 版本 +1 → 下一超步 Plan 发现 b 的 triggers 更新了 → b 被选中执行。"边"就这样变成了"按门铃"。
L05

writers 写回状态

节点的 writers 是 ChannelWrite(write_entries)——用 _get_updates 把节点返回的 dict 拆成"对各 State 键通道的写入"（state.py:1482）。

读法：节点函数返回 {"messages": [...], "count": 5}，writers 负责把它拆成"往 messages 通道写 [...]、往 count 通道写 5"。这些写入在超步末被 apply_writes（Day 08）用 reducer 合并。_control_branch 处理 Command/条件边跳转（写触发通道）。
节点的"输出"怎么变成"状态更新" 节点只返回一个普通 dict（{"count": 5}）。writers 把这个 dict 翻译成"往 count 这个通道写 5"的通道写入操作。于是节点函数保持简单（只返回 dict），框架负责把它落到正确的通道、走对的 reducer。writers 是"节点返回值"和"通道写入"之间的桥。
L06

边 = 写触发通道

边怎么翻译？attach_edge（state.py:1537）：让起点节点跑完后往终点的 branch:to:* 通道写一下：

# 普通边 a→b：给 a 节点加一个 writer，往 branch:to:b 写
self.nodes[starts].writers.append(
    ChannelWrite((ChannelWriteEntry(_CHANNEL_BRANCH_TO.format(end), None),)))
🛠️ 如果让你自己实现"边"：极简版 → 真实版 朴素想法：把边存成一张邻接表 {"a": ["b"]}，a 跑完就直接 run("b")。 
# 极简版：a 跑完直接调用 b
edges = {"a": ["b"]}
for nxt in edges[cur]:
    run(nxt)          # 直接调用 → a 和 b 耦合死了
真实版不直接调 b，而是让 a 往 branch:to:b 通道写一下（按门铃）。多这一层"通道"换来三件事：① a 不用知道 b 是谁（解耦）；② 多个上游能一起按同一个门铃、由通道 reducer 合并（并行/汇合）；③ 门铃动作是可存档的状态（可持久化/可重放）。真实版 = 邻接表 + "改成写通道"这一层解耦。
读法：普通边 a→b 编译成"给 a 加一个 writer——跑完往 b 的触发通道写"（按 b 的门铃）。
⚠️ 小白常误以为编译后 a 会"调用"b；其实a 只是往 b 的门铃通道写个信号，跑不跑 b 由引擎下一超步统一决定——a 和 b 从不直接见面。
条件边 attach_branch（state.py:1563）则把路由函数的输出翻译成"往哪些 branch:to:* 写"。多起点汇合边用 NamedBarrierValue（等齐才放行）。
💥 错误驱动：不编译会出什么事故 假设直接把用户的 StateGraph 塞给 Pregel 引擎跑——引擎只认"通道/PregelNode/触发通道"，它根本看不懂 add_edge("a","b") 是什么：不知道该建哪些通道、a 跑完谁被触发、返回的 dict 往哪写。结果就是引擎空转、状态永远不更新。正因为两套表示对不上，才必须有 compile 这道翻译工序。
至此前两周合流：你写 StateGraph（Day 02-04）→ compile 把状态键翻译成通道（Day 07）、节点翻译成 PregelNode、边翻译成"写触发通道" → 得到 Pregel → 超步执行（Day 06/08）。"边"这个高层概念，底层就是"节点跑完按下游门铃"。理解了编译，你就打通了"用户 API"和"执行引擎"。
L07

反查表

编译后 Pregel 初始化时用 _trigger_to_nodes（main.py:4175）建立"触发通道 → 订阅它的节点"索引（main.py:947）——供 Day 08 的增量调度优化用。

编译期建好、运行期高速用 Day 08 讲的增量调度优化（只看被更新通道的订阅者）需要一张"通道 → 节点"反查表。这张表在编译时一次建好，运行期直接查——不用每步重算。这是"编译期做准备、运行期只管快跑"的又一体现（和 eino 的 compile、AutoGPT 的图编译一个思想）。编译不只是翻译，还顺便做了运行期优化的准备工作。
