Day 05 / 共 20 天 · 第 1 周收官

一个 Agent 的标准解剖

第 1 周收官。前 4 天的概念（图 / State / 节点 / supervisor），今天全部落到"一个真实 Agent 的目录结构"上。以旗舰 sre-rca 为范本，看清每个文件的角色。这是 Day 14 逐行精读的地图，也是第 2 周钻进 toolkit 之前的最后一块拼图。

📍 你在 20 天里的位置（第 1 周：建立心智 · 收官）
D01 全景架构→ D02 跑起来→ D03 LangGraph→ D04 Supervisor→ D05 Agent 解剖
💡 用一个类比先兜住今天（延续「盖楼/装修」世界观） 一个 Agent 的目录，就像一户精装房的施工档案袋，每份文件对应一样东西：state.py=这户的"公告板"定义（Day 03 那块黑板）；builder.py=施工蓝图（工序怎么连，最该先看）；nodes/=各道工序；specialists/=取证师傅；tools/=只读的检测仪器；prompts/=施工作业指导书；server/main.py=两种入户方式（跟着物业总门进 vs 自己单独开门）；BOM=全楼统一的建材采购清单（一处改、全楼版本对齐）。全平台每户档案袋格式都一样——看懂一户就看懂所有户。
L01

标准目录结构：每个 Agent 长一个样

本框架的一大好处是所有 Agent 目录结构统一——看懂一个就看懂全部。以 apps/sre-rca-agent/sre_rca/ 为例：

state.py
定义"共享黑板" RcaState（TypedDict）——全图数据在这里流动
builder.py
★ 装配 LangGraph 图：加节点、连边、条件路由、compile。读 agent 从这里入手
nodes/
普通节点：triage(分诊)/recall(召回)/rag(检索)/synthesizer(综合)/critic(质检)/writeback(沉淀)
specialists/
取证专家：trace/metric/deploy/log 四个，各从一个视角分析，可并行
tools/
只读数据源工具：查 trace/指标/发布记录/日志，全用 @safe_tool_result 包
prompts/
版本化的 prompt 文件（*-v1.md），每份还是带设计说明的工程文档
server.py
build_router()——产出可挂载的 API 路由（给平台 host 用）
main.py
独立部署入口：单独一个 FastAPI + 一行接齐可观测性
pyproject.toml
依赖声明：一行 ai-trust-toolkit-bom 锁死所有版本

回忆 Day 01 的铁律：L3 业务 Agent 只写 State / Specialists / Prompts / DAG(图) 这四类东西，护栏能力全从 toolkit import。上面这个结构正是这条铁律的体现。

L02

state.py — 共享黑板

state.py:15 定义 class RcaState(TypedDict, total=False)。回忆 Day 03：这是整张图的"黑板"，每个节点读它、返回部分字典合并回去。这里重点看 Reducer 的运用：

class RcaState(TypedDict, total=False):
    # ── 输入 ──
    user_question: str
    alert_type: str
    # ── 4 个专家各写各的字段：并行写入零冲突，默认"覆盖"即可 ──
    trace_finding: dict          # state.py:29
    metric_finding: dict
    deploy_finding: dict
    log_finding: dict
    # ── 需要累加的计数器：用 operator.add 做 Reducer（Day 03 学过）──
    retry_count: Annotated[int, add]     # state.py:48
    # ── 单写者字段：覆盖即可 ──
    conclusion: dict
    critique_passed: bool
    critique_layer: int          # 0=通过 1=代码层拦下 2=LLM层拦下
为什么 retry_count 要用累加 Reducer？因为 Critic 打回重做时，可能有并发写入。用 Annotated[int, add] 累加，避免两次 +1 互相覆盖导致计数丢失——这是并发安全的关键，也是判断"重试是否触顶"的依据。
L03

builder.py — 图的装配（最重要）

核心函数 build_rca_graph()（builder.py:42）。它就是 Day 03 学的那套 StateGraph → add_node → add_edge → compile，只是节点更多。整张图长这样：

START→ triage分诊→ recall召回历史⇉ trace专家 metric专家 deploy专家 log专家 ⇉ rag查 SOP→ synth综合→ critic质检⇢ writeback沉淀→ END

关键代码片段（对照 Day 03 的抽象）：

builder = StateGraph(RcaState)                    # builder.py:73
# 10 个节点
builder.add_node("triage", triage_node)           # builder.py:76-85 ...
# 线性入口
builder.add_edge(START, "triage")                 # builder.py:88
builder.add_edge("triage", "recall")
# 并行扇出/扇入：4 个专家都从 recall 出发、都汇入 rag → 自动并行
for sp in ["trace_sp","metric_sp","deploy_sp","log_sp"]:   # builder.py:92
    builder.add_edge("recall", sp)
    builder.add_edge(sp, "rag")
builder.add_edge("rag", "synthesizer")
builder.add_edge("synthesizer", "critic")
# Critic 三态条件路由 —— 直接用 toolkit 封好的，不手写 if/else！
critic_router = build_critic_router(              # builder.py:100
    pass_dest="writeback", retry_dest="synthesizer",
    end_dest=END, max_retries=2)
builder.add_conditional_edges("critic", critic_router, {...})
builder.add_edge("writeback", END)
return builder.compile(checkpointer=checkpointer) # builder.py:116
看出来了吗？ Day 03/04 的每一个抽象（普通边、并行扇出、条件边循环、checkpointer）在这里全部用上了。业务作者没有重新发明轮子——连"Critic 三态路由"都是从 toolkit import 的 build_critic_router。这就是"薄业务 + 厚 toolkit"。
🧍 第一人称请求之旅：现在你是一次「支付超时」故障请求 你带着 {"alert":"支付超时率突增到8%"} 进门 →（triage）门口分诊师傅用关键词把你归到"latency"类，没花一分钱 →（recall）档案员翻出去年 3 条相似旧 case 塞进你口袋 →（4 个专家并行）trace/metric/deploy/log 四位师傅同时给你取证，各自往公告板写 finding →（rag）查出相关 SOP →（synthesizer）请贵师傅 Sonnet 把你手里所有材料综合成结论 →（critic）验收师傅 Haiku 挑刺：编造证据？证据不够？不过就把你打回 synthesizer 重来（最多 2 次）→ 过了就 writeback 把你这次经验存档 → 出门，拿到统一 envelope。你全程只是"数据"，被这张图推着走完了每道工序。
图注：业务只写左边四类东西，右边所有护栏能力都 import 自 toolkit——这就是"薄业务 + 厚 toolkit"。
L04

nodes/ — 6 个普通节点

每个节点是 async def node(state) -> dict，或返回这种函数的"工厂"（把依赖闭包进去）。逐个看它们的角色：

triage规则版分诊，0 成本、不调 LLM：用关键词字典把问题归到 5 类。体现"能用代码就别用 LLM"的省钱哲学（triage.py:27）
recall从"情景记忆"里捞相似的历史故障 case（recall.py:10）。异常吞掉返回空——挂了也不影响主流程
rag检索 SOP/运维手册（rag.py:10）。用 4 个专家的发现拼查询语句
synthesizer综合节点，调 Sonnet（贵但强）：把 4 专家 + 历史 + SOP + 上轮反馈拼成结论（synthesizer.py:49）。外面包了一层 toolkit 的"证据不足就跳过 LLM"护栏
critic质检节点，调 Haiku（便宜）+ prompt 缓存：直接复用 toolkit 的 build_critic_node（critic.py:12）。Day 07 主角
writeback经验沉淀：先用 toolkit 的 should_writeback 守门（只有质检通过且信息充分才写），把这次 case 存回记忆库（writeback.py:12）
省钱三档：triage 用规则（0 元）、critic 用 Haiku（约 ¥0.04）、synthesizer 用 Sonnet（约 ¥0.20）。把贵模型只用在最难的一步，是全框架的成本纪律。Day 11 会看到 get_llm(tier) 怎么支撑这种分档。
L05

specialists/ — 专家工厂消除模板

4 个专家文件（trace/metric/deploy/log）每个都只有约 30 行——因为它们都用 toolkit 的 make_specialist_node(SpecialistConfig(...)) 工厂。以 metric 专家为例（metric_sp.py:13）：

metric_specialist = make_specialist_node(SpecialistConfig(
    name="metric_specialist",
    state_field="metric_finding",              # 结果写进 state 的哪个字段
    system_prompt=load_prompt("metric-specialist-v1.md"),
    fetch_fn=lambda state: get_metrics(...),   # 先抓真实/mock 数据
    fallback_finding={"health": "unknown"},    # 抓取失败时的降级结果
    model_tier="sonnet",
))

工厂把"取数据 → 喂 LLM → 解析 → 写 state 字段 → 失败降级 → 自动包失败闸门"这整套模板收进了 toolkit（specialists/factory.py:84）。业务只填这几个配置项。

📝 举个例子：metric 专家的一次工作 输入：state 里有 alert_type="latency" → 工厂先跑 fetch_fn 抓指标数据（本地是 mock）→ 拼进 prompt 喂 Sonnet → 解析 → 回写 {"metric_finding":{"health":"degraded","evidence_id":"M-2","confidence":"中"}} 到公告板。
若抓数据那步报错 → 自动降级返回 fallback_finding={"health":"unknown"}，图不崩（这层兜底是工厂自动包的，Day 08 讲）。业务作者一行 try/except 都不用写。
活化石：目录里有个 specialists/_factory.py 标着 DEPRECATED，里面只是把 toolkit 的符号重新导出一遍。它见证了"业务里的重复代码被上移进 toolkit"的过程——这正是 Day 06 要讲的"渐进抽象"。
🍼 一句话复述专家之所以每个才 30 行，是因为"取数→喂 LLM→解析→写字段→失败降级→包兜底"这套模板整个搬进了 toolkit 工厂，业务只填 5 个空。
L06

tools/ 与 prompts/

tools/observability.py — 只读数据源

定义 get_trace_by_id / get_metrics / get_deployment_history / search_logs 四个工具。两个要点：

  • 每个都用 @safe_tool_result(fallback=...) 装饰（observability.py:19 等）——工具永不抛异常，失败返回兜底值（Day 11 细讲）。
  • USE_REAL 环境变量开关：默认走 mock 假数据（本地/测试用），生产走真接口（接 SkyWalking / Prometheus 等，目前是占位）。

prompts/*.md — 版本化的工程文档

7 个 *-v1.md。它们不是干巴巴的 prompt，而是带教学说明的工程文档：正文 + 用户模板 + "设计说明"表格（逐段解释为什么这么写）+ Token/成本估算 + 变更记录。例如 critic-v1.md 定义了 6 项检查 + PASS/FAIL/PASS_WITH_NOTES 三态 + few-shot 示例。

带 -v1 版本号是为了 A/B 测试和回滚——想试新 prompt 就加 -v2，评测对比后再切换，老版本随时能退回。这也是把 prompt 当"代码"严肃管理的体现。
L07

server.py / main.py — 两个入口

一个 Agent 有两种被跑起来的方式，对应两个文件：

server.py · build_router()

产出一个 APIRouter，能被平台的 gov-agents-server 多 agent 同进程挂载。核心一句：

router.include_router(build_v1_router(
  agent_name="rca",
  invoke_fn=_invoke,
  stream_fn=_stream,
  case_store=store))

业务只写 _invoke（校验入参→跑图→包成结果），统一的鉴权/envelope/落库/指标全由 build_v1_router 自动装（Day 12 精讲）。

main.py · 独立 FastAPI

单独部署这个 agent 时的入口：一个 FastAPI + include_router + 一行接齐可观测性：

auto_configure(app,
  service_name="sre-rca-agent")
# 接上 observability/cost/critic/
# failsafe/eval/memory 六模块

/healthz 暴露版本等非敏感信息。用 try/except 保旧部署兼容。

还有个宝藏端点 /agents/rca/graph（server.py:142）：它把每个节点的 role/model/purpose/输入/输出以 JSON 返回——相当于这个 Agent 的"自我说明书"，Day 14 会拿它当权威参照。

L08

依赖走 BOM：一行锁死所有版本

看 apps/sre-rca-agent/pyproject.toml:16-21，你会发现它的核心依赖只有一行：

dependencies = [
    "ai-trust-toolkit-bom[core,supervisor,monitor]==0.6.0",
]
BOM = Bill of Materials（物料清单），借用自 Maven。它本身没有代码，只负责"声明一组互相兼容的库的精确版本"。agent 不直接 pin toolkit/langgraph/fastapi 各自的版本，而是引一个 BOM——全平台要升级，只改 BOM 一处，所有 agent 自动对齐。[core,supervisor,monitor] 是"extras"，表示按需勾选能力组。

CI 里甚至有专门的闸门（Day 18 讲）：禁止 agent 绕过 BOM 直接 pin 子模块版本，并校验 BOM 声明与实际锁文件一致。这保证了几十个 agent 的依赖永远不会各自漂移。
