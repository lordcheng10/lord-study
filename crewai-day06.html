Process：顺序 vs 层级

Crew 支持两种执行流程。今天看它们的真实实现——你会发现两者复用同一个执行引擎，只在"谁来执行任务"和"有没有经理"上不同。设计极优雅。

📍 你在整门课的位置（第 2 周 Crew 编排 · 昨天 Day 05 追完一次 kickoff 旅程，今天拆 Process 决定"谁先谁后、谁来做"，明天 Day 07 钻进 Agent 的 ReAct 大脑）
全景 D1· Agent·Task·Crew D2-4· kickoff 旅程 D5· Process D6· ReAct D7· 委派 D8· 规划·护栏 D9-10
L01

Process 只是一个标签

process.py 短得惊人——它只是个字符串枚举，不含任何逻辑：

class Process(str, Enum):
    sequential = "sequential"
    hierarchical = "hierarchical"
    # TODO: consensual = 'consensual'   # 共识制，尚未实现
读法：Process 只是"策略标签"——真正的执行逻辑写在 Crew 里，Crew 在 kickoff 时根据这个标签分发到不同方法。这就是"策略模式"：用枚举选择算法，算法实现与选择分离。继承 str 让它能直接和字符串比较、序列化。
为什么把"策略"和"实现"分开？ 这样加新流程很干净——注释里预留的 consensual（共识制，多个 agent 投票决策）将来实现时，只需加一个枚举值 + 一个 _run_consensual_process 方法，kickoff 里加一个分支，完全不动现有的顺序/层级逻辑。"对扩展开放，对修改封闭"。
L02

两种流程对比

🤔 痛点：一堆任务和 Agent，谁先谁后？谁来做？ 你给 Crew 塞了几个任务和几个 Agent。问题来了：这些任务按什么顺序跑？每个任务该分给哪个 Agent？是写死的流水线，还是有人临场调度？CrewAI 用一个 process 参数，就把这两件事一起定了。

➡️ sequential（顺序）

  • 任务像流水线一个接一个
  • 每个 Task 必须自己指定 agent
  • 数据顺次传递（上下文链）
  • 适合步骤明确、依赖清晰的流程

🏛️ hierarchical（层级）

  • 框架自动创建一个经理 agent
  • Task 可不指定 agent，由经理动态分派
  • 经理通过"委派工具"派活给下属
  • 适合需要动态决策"由谁做"的场景
用团队打比方 顺序 = 一条明确的流水线，每道工序谁负责事先定好（研究员→写手→审稿）。层级 = 有个项目经理，任务来了他看情况分派给哪个下属，下属做完汇报，经理再决定下一步。顺序适合固定流程，层级适合灵活调度。
💡 一句话本质 Process = 团队协作模式的"选择器"。它本身不含任何逻辑（就是个字符串枚举，L01 会看到），只是告诉 Crew：走"流水线串行"（sequential）还是"设个经理动态调度"（hierarchical）。选哪种，就决定了"任务顺序"和"谁来执行"这两件事怎么定。
左：顺序=固定流水线，每步谁做事先定好；右：层级=经理居中，把任务动态派给下属。两者复用同一个 _execute_tasks 引擎（L03/L04）。
📝 例子：同一批任务，两种 process 的差别 3 个任务 + 3 个 Agent。
process=Process.sequential：任务1(agentA)→任务2(agentB)→任务3(agentC)，顺序固定、谁做写死。
process=Process.hierarchical：多出一个经理 Agent，任务先都交给它，它看情况派给 A/B/C，还能来回追问。
只改一个词，整支队伍的协作方式就变了——业务代码一行不动。
L03

顺序执行源码

# crew.py:1475
def _run_sequential_process(self) -> CrewOutput:
    return self._execute_tasks(self.tasks)   # 直接执行任务列表

真正的循环在 _execute_tasks（crew.py:1519，Day 05 见过）：遍历 tasks，用 _get_context 把前序输出拼成上下文，逐个 task.execute_sync，异步任务并发。

读法：顺序流程就是"按列表顺序跑任务 + 上下文链传递"，一句话的事。它把复杂度都交给了通用的 _execute_tasks。
L04

层级执行源码（惊喜：复用同一引擎）

# crew.py:1479
def _run_hierarchical_process(self) -> CrewOutput:
    self._create_manager_agent()          # ★ 唯一的区别：先造一个经理
    return self._execute_tasks(self.tasks)  # 然后……复用同一个 _execute_tasks！
读法：层级和顺序流程复用同一个 _execute_tasks！唯一区别是层级模式先 _create_manager_agent() 创建一个经理。这个设计太漂亮了——两种流程共享执行引擎，差异只在"是否有经理"和"任务分给谁"。
为什么能复用同一引擎？ 因为"遍历任务、传递上下文、收集输出"这套流程两种模式都一样。差异只在一个点：顺序模式下任务分给它自己指定的 agent，层级模式下所有任务名义上都分给经理（经理再委派）。这个"分给谁"的差异被收敛到一个方法 _get_agent_to_use（L06）里。找出共性、把差异隔离到最小的点——这是消除重复代码的高级功夫。
L05

经理 Agent 的创建

_create_manager_agent（crew.py:1484）：

  • 用户提供了 manager_agent：强制 allow_delegation=True，且经理不允许带工具（带了直接抛异常）。
  • 否则自动创建一个经理：角色="Crew Manager"、目标="用最佳方式管理团队完成任务"（取自 i18n 文案），并把 AgentTools(agents=self.agents).tools()（委派工具，Day 08）作为它的工具。
为什么经理不能带（普通）工具？ 因为经理的职责是"管理和分派"，不是"亲自干活"。它的"工具"应该只有"委派工具"（把活派给下属）。如果给经理配了搜索、写文件之类的普通工具，它可能自己动手而不分派，就违背了层级模式的设计。框架用"禁止经理带工具"强制它专注于管理。职责单一原则。
L06

谁来执行任务：差异的唯一落点

# crew.py:1675
def _get_agent_to_use(self, task: Task) -> BaseAgent | None:
    if self.process == Process.hierarchical:
        return self.manager_agent      # 层级：所有任务都先给经理
    return task.agent                  # 顺序：任务给它自己指定的 agent
读法：这一个方法就是两种流程的"唯一实质差异"。层级模式下，_execute_tasks 里每个任务都被交给经理，经理再通过委派工具（Day 08）分派给真正的下属；顺序模式下直接交给任务自己的 agent。整个层级 vs 顺序的复杂性，收敛成了这几行的一个 if。
委派工具的注入（_prepare_tools，crew.py:1606）：allow_delegation=True 的 agent 会被注入"委派工具"——层级模式给经理注入、顺序模式给声明了 delegation 的 agent 注入。这是 Day 08 的主题。
L07

两种流程怎么选

  • 用 sequential：流程明确、依赖清晰、每步谁做很确定。大多数场景够用，简单可控。（默认就是它。）
  • 用 hierarchical：任务多且"谁做哪个"需要动态判断、需要一个协调者统筹全局、任务可能需要来回协商。代价是多一层经理的 LLM 调用（更贵）、行为更不确定。
新手建议 先无脑用 sequential。它简单、可预测、便宜。等你遇到"任务分配需要智能判断"的复杂场景，再上 hierarchical。更复杂的确定性编排，其实该用 Flow（Day 11）——它比 hierarchical 更可控。层级模式是"让 AI 经理自主调度"，Flow 是"你自己精确画流程图"，两种思路。

👶 小白：层级模式有个"经理"统筹全局，听起来更高级，那是不是无脑用它更好？

👨‍🏫 老师：正相反。给团队塞个经理，就多养了一张"嘴"——经理每次分派、追问都要额外调一次大模型，更贵、更慢，而且它临场判断"这活派给谁"也可能派错。就像小作坊三个人干活，本来喊一嗓子就分好了，非要请个经理开会分工，反而拖沓。

👶 小白：那什么时候才值得请这个"经理"？

👨‍🏫 老师：当"哪个活该谁做"本身需要动态判断、任务多到需要有人统筹时，才值这份钱。流程固定就用 sequential（默认），要严格可控的复杂编排就上 Flow（Day 11）——别为了"看起来高级"多花冤枉钱。
