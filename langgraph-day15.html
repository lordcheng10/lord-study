序列化与长期记忆

人在环→记忆·序列化→react_agent→ToolNode
L01

为什么要序列化

🤔 如果让你自己实现：直接 json.dumps 行不行？你可能想：把 State 丢给 json.dumps 存进库不就好了？试一下就崩：TypeError: Object of type HumanMessage is not JSON serializable。datetime、UUID、pydantic 对象……标准 JSON 全都不认。这就是为什么需要一个专门的序列化器。
💡 本质：序列化是"持久化"的前提，就像生活中存游戏序列化就像生活中把游戏进度写成存档文件：内存里活的对象没法直接躺进硬盘，必须先"打包"成一串字节；读档时再"拆包"还原。Day 11-14 反复说的"存检查点"，落到磁盘那一刻靠的全是它——没有序列化，前四天的持久化一步都迈不出去。

Day 12 的 Sqlite/Postgres Saver 要把 Day 11 的 Checkpoint（含 messages、任意 Python 对象）写进数据库——但数据库只认字节/字符串。序列化（serialization）= 把 Python 对象转成可存储的字节；反序列化 = 读回来还原成对象。

序列化 = "打包/拆包" 你的状态里有 HumanMessage、datetime、自定义类等活生生的 Python 对象。数据库存不了"对象"，只能存字节。序列化就是把对象"打包"成字节存进去；下次读出来再"拆包"还原成一模一样的对象。难点在于：不光基础类型（数字、字符串），LangChain 的 Message、时间、甚至你自定义的类都要能正确打包/拆包。这就是需要一个专门 serializer 的原因。
L02

SerializerProtocol

SerializerProtocol（checkpoint/serde/base.py）定义序列化器接口：

class SerializerProtocol(Protocol):
    def dumps_typed(self, obj) -> tuple[str, bytes]: ...   # 对象 → (类型标签, 字节)
    def loads_typed(self, data: tuple[str, bytes]): ...    # (类型标签, 字节) → 对象
读法：又是接口/实现分离（Day 12 老朋友）：Saver 只依赖这个抽象接口，具体怎么序列化交给实现。dumps_typed 返回带类型标签的字节——反序列化时靠标签知道该还原成什么类型。
L03

JsonPlusSerializer

默认实现 JsonPlusSerializer（serde/jsonplus.py）——"JSON 加强版"：

  • 基础类型走标准 JSON。
  • LangChain 对象（Message 等）、dataclass、pydantic、datetime、UUID、Enum 等有专门编解码。
  • 兜底用 pickle（并标记类型），保证几乎任何对象都能存。
读法："JSON 优先、特殊类型特判、pickle 兜底"——既保证常见对象存成可读 JSON，又不会因为遇到怪对象就崩。这是"实用主义序列化"的典型设计。你几乎不用关心它，但知道 messages 能安全落库靠的是它。
💬 小白 vs 老师：那干脆全用 pickle 兜底不就省事了？ 👶 小白：反正 pickle 啥都能存，为啥还要费劲优先走 JSON？
👨‍🏫 老师：因为 JSON 有两个 pickle 给不了的好处——① 可读、可跨语言：存进 Postgres 后你能直接 SQL 查、能用别的语言读；pickle 是一坨只有 Python 认的二进制。② 版本更稳：pickle 对类定义的改动很敏感，改个字段旧存档可能就读不回来了。所以策略是"能 JSON 就 JSON，实在不行才 pickle 兜底"。
L04

短期 vs 长期记忆

短期记忆（Checkpoint）长期记忆（Store）
范围单个 thread（一次会话）跨所有 thread（跨会话）
内容本次对话的完整状态用户画像、事实、偏好
接口BaseCheckpointSaverBaseStore
短期=这次通话记录（按 thread 隔离）；长期=客户档案（跨会话共享）
两种记忆的区别（很关键） 短期记忆（检查点）：像"这次通话的记录"——挂了电话（换 thread）就翻篇。长期记忆（Store）：像"客户档案"——不管打几次电话，"这个用户对花生过敏"永远记着。放回游戏世界观：短期记忆就像单局游戏的存档（这一局的进度，换局清空），长期记忆则像跨存档继承的"账号成就/等级"（不管你重开多少局都还在）。前者按 thread_id 隔离（Day 12），后者刻意跨 thread 共享。一个成熟 Agent 两者都要：用检查点记住"当前在聊什么"，用 Store 记住"这个用户是谁、有什么长期偏好"。
⚠️ 错误驱动：只有短期记忆的 Agent 会怎样？假设你的助手只有 checkpoint、没有 Store：用户今天告诉它"我对花生过敏"，隔了几天开新会话（新 thread）再问"这餐能吃吗"——它完全不记得过敏史，可能推荐花生酱。短期记忆随会话翻篇，救不了跨会话的事实，这正是 Store 存在的理由。
L05

BaseStore

BaseStore（checkpoint/store/base.py）是长期记忆的抽象接口，键值风格：

store.put(namespace, key, value)   # 存
store.get(namespace, key)          # 取
store.search(namespace, query=...) # 搜（可语义检索）
# 编译时传入，节点里通过 get_store() 或注入参数访问
graph = builder.compile(checkpointer=..., store=InMemoryStore())
📝 例子：长期记忆真的"跨会话"了吗 
store = InMemoryStore()
# —— 周一，会话 A（thread_id="A"）——
store.put(("user-42",), "diet", {"allergy": "peanuts"})   # 记下过敏史

# —— 周三，全新会话 B（thread_id="B"，短期记忆早翻篇了）——
info = store.get(("user-42",), "diet")   # → {"allergy": "peanuts"}
# ✅ 换了 thread 也读得到！因为 Store 按 namespace(user-42) 存，跟 thread_id 无关
#    就像游戏账号成就：这一局(thread)重开清空，账号等级(Store)照样在
读法：Store 和 Saver 平行——同样"抽象接口 + 多后端实现（InMemory/Postgres）"，同样 compile 时插入。节点函数可拿到 store，跨会话读写用户级数据。
L06

命名空间（namespace）

Store 用命名空间元组组织数据，天然支持多用户隔离：

namespace = ("user-42", "memories")    # 按用户/类别分层
store.put(namespace, "diet", {"allergy": "peanuts"})
store.get(("user-42", "memories"), "diet")   # → {"allergy": "peanuts"}
读法：namespace 像文件夹路径，把不同用户、不同类别的长期记忆分门别类隔离。和 checkpointer 的 thread_id 是两套独立维度：thread_id 隔离"会话"，namespace 隔离"用户的长期知识"。
L07

语义检索

Store 的 search 可配 embedding，支持语义检索：存记忆时算向量，查询时按相似度返回相关记忆——这就是给 Agent 做"记忆库/RAG"的基础设施。

读法：不只是精确 key 查找，还能"找出和当前问题相关的历史记忆"。Agent 每轮把相关长期记忆检索出来塞进 prompt → 实现"越用越懂你"。Store + 语义检索 = LangGraph 内建的记忆层，不用你自己接向量库。
