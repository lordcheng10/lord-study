Day 19 / 共 20 天 · 第 4 周 Agent/Workflow/生态

可观测与评估

RAG/Agent 是"黑盒"——检索了啥、LLM 想了啥、花了多少 token、答得好不好，都看不见。今天看两套工具：callbacks/instrumentation（追踪内部）+ evaluation（衡量质量）。这是把 RAG 从"能跑"做到"能上线"的关键。

L01

黑盒问题

"答错了，但不知道错在哪" RAG 答错了——是检索没找到对的内容？还是找到了但 LLM 没用好？花了多少钱（token）？延迟多少？Agent 到底调了哪些工具、想了什么？不观测就是抓瞎。而且怎么客观衡量"这个 RAG 系统好不好"？改了参数是变好还是变差？可观测（看内部）+ 评估（打分）解决这两个问题——它们是 RAG 从 demo 走向生产的必经之路。
L02

callbacks 回调

callbacks/：CallbackManager + 各种 handler（LlamaDebugHandler、TokenCountingHandler）。schema.py 的 CBEventType 定义事件类型（RETRIEVE/LLM/EMBEDDING/QUERY/…）。

读法：回想前几天代码里到处的 callback_manager.event(CBEventType.RETRIEVE, ...)（Day 11/12）——那就是埋点。CallbackManager 在每个关键步骤（检索、调 LLM、嵌入）发事件，handler 接收后可以打印/计时/统计。LlamaDebugHandler 打印每步详情（调试神器），TokenCountingHandler 数 token。
L03

instrumentation

instrumentation/（较新，逐步取代 callbacks）：基于 dispatcher 的事件系统——回想 Day 11 dispatcher.event(RetrievalStartEvent(...))、@dispatcher.span。更细粒度、更结构化的追踪。

新一代可观测：span + event instrumentation 引入了"span"（一段操作的时间区间，如"这次检索耗时 200ms"）和结构化 event。你注册一个 handler，就能收到框架各处发的事件（检索开始/结束、LLM 调用、Agent 每步）。这套更接近现代 APM（应用性能监控）的模型——回想 Envoy/Istio 的追踪、langgraph 的流式事件。基于它能实现完整的链路追踪：一次 query 内部所有步骤的时间线。
L04

token 计数

callbacks/token_counting.py 的 TokenCountingHandler：统计嵌入 token、LLM 提示 token、LLM 生成 token。

token = 钱，必须盯 LLM 和嵌入都按 token 收费。一次 RAG query 可能：嵌入问题（几十 token）+ 检索的内容塞进提示（几千 token）+ LLM 生成答案（几百 token）。TokenCountingHandler 帮你算清每部分用了多少。生产环境这直接关系成本——比如发现"检索塞了太多内容导致提示 token 爆炸",就调小 top_k。回想 wasm-go/Higress 的 tokenusage——AI 应用都要盯 token。
L05

第三方追踪

通过 instrumentation/callbacks，LlamaIndex 能接入第三方可观测平台：Arize Phoenix、LangSmith、Langfuse、OpenTelemetry 等（integrations）。set_global_handler("arize_phoenix") 一行开启。

读法：这些平台提供"可视化链路追踪 UI"——一次 query 的每步（检索了哪些 Node、每个的分数、LLM 的完整提示和输出、耗时）都能在界面上看。调试复杂 RAG/Agent 时，可视化追踪比看日志高效得多。Phoenix 还能做评估（下面）。这是生产 RAG 的标配——线上出问题能快速定位。
L06

evaluation 评估

evaluation/：一批 Evaluator（FaithfulnessEvaluator、RelevancyEvaluator、CorrectnessEvaluator、RetrieverEvaluator…），多用 LLM-as-judge（用一个 LLM 给答案打分）。

怎么给"答案质量"打分？ RAG 答案好不好难量化（不像分类有标准答案）。LlamaIndex 用"LLM 当裁判"：
• Faithfulness（忠实度）：答案是不是真的基于检索的资料（没瞎编）？
• Relevancy（相关性）：答案和检索内容跟问题相关吗？
• Correctness（正确性）：对比参考答案，答对了吗？让一个强 LLM 读"问题+资料+答案",打分 + 给理由。这样能批量、客观地衡量 RAG 质量——改了参数跑一批评估，看分数升降。
L07

检索 vs 生成评估

RAG 评估分两段：

  • 检索评估（RetrieverEvaluator）：检索出的 Node 里有没有正确答案所在的（hit rate、MRR 等指标）。
  • 生成评估（Faithfulness/Relevancy/Correctness）：基于检索内容，答案生成得好不好。
分段评估才能定位问题 RAG 答错了，是"没检索到对的"（检索问题）还是"检索到了但没答好"（生成问题）？分段评估告诉你。检索评估分低 → 改切块/嵌入/检索策略（第 1-2 周、Day 11/14）；生成评估分低 → 改提示词/合成模式/LLM（Day 13-15）。这让 RAG 调优有的放矢——先测哪段弱、再针对性优化。回想 Day 09/14 说的"检索质量决定一切"——评估帮你验证。
