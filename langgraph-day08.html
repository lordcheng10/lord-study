Day 08 / 共 20 天 · 第 2 周 Pregel 引擎

super-step 执行循环

Day 06 的三阶段超步，代码里怎么实现？读 pregel/_loop.py + _algo.py：tick（Plan）→ runner（执行）→ after_tick（Update + 检查点）。

L01

驱动循环

核心驱动循环在 main.py:2964——三阶段清晰对应：

while loop.tick():                    # Plan：选出本步任务（无任务→返回 False→退出）
    for _ in runner.tick(tasks, ...): # Execution：并行跑任务
        yield from _output(...)        # 流式输出
    loop.after_tick()                  # Update：apply_writes + 存检查点
读法：while loop.tick() 是超步循环——tick()=Plan（选节点）、runner.tick()=Execution（并行跑）、after_tick()=Update（写回+检查点）。直到 tick() 返回 False（没节点可跑）循环结束（Day 06）。
L02

tick = Plan 阶段

tick()（_loop.py:599）：

# 超步数超限 → status="out_of_steps" 返回 False（防无限循环）
# 调 prepare_next_tasks（L03）选出本步任务
# 没有任务 → status="done" 返回 False（图执行结束！）
# 有任务 → 可选 interrupt_before 检查 → 返回 True 进入执行
读法：tick 负责"这步该跑哪些节点"。没任务了就返回 False 结束循环（Day 06 的"无节点可跑即停"）。还有超步上限（recursion_limit）防死循环、interrupt_before（Day 14 的断点）。
L03

prepare_next_tasks（选谁跑）

prepare_next_tasks（_algo.py:392）计算下一超步要执行的任务集。两类：

  • PUSH 任务：来自 TASKS 通道的 Send（动态并发，map-reduce）。
  • PULL 任务：被边触发的普通节点。

每个候选节点经 _triggers（Day 06 的版本号触发）复核，通过则用 _proc_input 读输入、生成 PregelExecutableTask。

读法：Plan 阶段选出"触发通道被更新过的节点"作为本步任务，读好它们的输入。PULL（边触发的普通节点）+ PUSH（Send 动态派发的任务）两类。
L04

runner 执行（并行）

runner.tick(tasks, ...) 用 PregelRunner 并行执行本步的所有任务。节点执行时通过注入的 write 函数把输出攒进 pending writes（put_writes，_loop.py:415），并不立即改通道（快照隔离，Day 06）。

"并行执行 + 攒写入" 本步选中的多个节点并行跑（Day 10 详讲）。关键：它们的输出不直接写通道，而是攒进"待写入"（pending writes）——因为快照隔离要求"一步之内通道不变"。所有节点跑完，才在 after_tick 统一把 pending writes 应用到通道。"执行时只攒不写、步末统一提交"——这正是 BSP 让并行安全的机制（Day 06 的快照隔离在代码里的落地）。pending writes 还会被后台持久化，保证单步中途崩溃已完成的结果不丢。
L05

after_tick = Update 阶段

after_tick()（_loop.py:683）：

writes = [w for t in self.tasks.values() for w in t.writes]   # 收集所有节点的写入
self.updated_channels = apply_writes(...)   # 应用写入，得到"本步更新了哪些通道"
self.checkpoint_pending_writes.clear()
self._put_checkpoint({"source": "loop"})    # ★ 步间存检查点
读法：Update 阶段：把所有节点攒的写入用 apply_writes（L06）统一应用到通道，得到 updated_channels（喂给下一步的 Plan），然后存一个检查点。updated_channels 传递了步与步之间的依赖。
"每个超步之间存检查点"（Day 11 的根基） _put_checkpoint 在每个超步之间存一次状态快照。这就是 LangGraph 持久执行、时间旅行、人在环的物理基础——因为超步边界是天然的"稳定点"（此刻状态一致、无半完成的写入）。Day 11-14 讲的检查点能力全建立在这一行上。Day 06 说"BSP 的超步边界给了天然的存档点"，这里就是那个存档动作。
L06

apply_writes（真正应用写入）

apply_writes（_algo.py:232）——Update 的核心，返回"被更新的通道集合"：

# 1. 排序任务保证确定性
# 2. 更新 versions_seen（记录每个任务见过的触发通道版本，防重复触发）
# 3. 按通道分组写入
# 4. 逐通道调用 channels[chan].update(vals)  ← reducer 真正执行处（Day 07）
#    返回 True 且通道 available → 加入 updated_channels、版本号 +1
读法：把这步所有写入按通道分组，逐个调 channel.update()（Day 07 的 reducer）合并。返回 True 的通道版本 +1、加入 updated_channels。updated_channels → 下一步 Plan 用它选节点（Day 06 的版本号触发）。闭环：本步写入 → apply_writes 合并 → updated_channels → 下步触发下游。
L07

增量调度优化

prepare_next_tasks（_algo.py:468）有个性能优化：用"上一步更新了哪些通道（updated_channels）"+"通道→节点反查表（trigger_to_nodes）"，只检查这些通道对应的候选节点，不用遍历所有节点：

if updated_channels and trigger_to_nodes:
    for channel in updated_channels:
        if node_ids := trigger_to_nodes.get(channel):
            triggered_nodes.update(node_ids)   # 只看被更新通道的订阅者
为什么要这个优化？ 朴素做法：每步遍历所有节点、逐个检查"你的触发通道被更新了吗"。图大时慢。优化：预先建"通道 → 订阅它的节点"反查表（trigger_to_nodes）。这步只有几个通道被更新（updated_channels），直接查表得到"哪些节点该被触发"，不扫全图。从"遍历所有节点"降到"只看被更新通道的订阅者"——大图上快很多。反查表在编译时建好（Day 09），是"增量调度"的关键。
