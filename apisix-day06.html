Day 06 / 共 20 天 · 第 2 周 路由/配置/数据面

路由 router

第 2 周开始拆数据面。路由是"请求进来后第一个大决策":这个 uri/host/method 该走哪条配置？今天看 router.lua 怎么用 radixtree（前缀树）高效匹配，以及路由的可插拔设计。

L01

路由要解决什么

从"一堆规则"里快速找到匹配的那条 你可能配了几千条路由（/api/user/* 走服务 A、/api/order/* 走服务 B、host=a.com 走 C…）。请求进来，要在几千条里快速找到匹配的那条。如果逐条比对（O(n)），路由多了就慢。APISIX 用 radixtree（基数树/前缀树）——把路径组织成树，匹配是 O(路径长度) 而非 O(路由数)，几千条路由也能微秒级匹配。这就是路由子系统的核心任务：又快又准地"选路"。
L02

可插拔路由

router.lua:74-93 的 http_init_worker 按配置选路由实现：

local router_http_name = "radixtree_uri"     -- 默认
if conf.apisix.router then
    router_http_name = conf.apisix.router.http or router_http_name
end
local router_http = require("apisix.http.router." .. router_http_name)
路由算法可以换 APISIX 支持多种路由实现：radixtree_uri（按 uri）、radixtree_host_uri（按 host+uri）、radixtree_uri_with_parameter 等，在 apisix/http/router/ 目录下。你在 config.yaml 里选用哪个。这是"策略模式"——路由核心逻辑不变，具体匹配算法可插拔。SSL 路由（按 SNI 选证书）也一样可插拔（radixtree_sni）。
L03

radixtree

radixtree 是一个独立的 C 库（lua-resty-radixtree，通过 FFI 调用），APISIX 把路由规则喂给它建树。

前缀树为什么快？ 想象一本字典：找 "apple" 不用翻遍所有词，而是先翻 a、再 ap、再 app…按前缀逐层缩小。radixtree 就是这个思想——把所有路由路径按公共前缀组织成树，匹配时顺着树走，走到哪算到哪。路由再多，匹配代价只跟"路径有多长"有关，跟"有多少条路由"无关。而且它是 C 实现 + FFI 调用，比纯 Lua 快得多。这是 APISIX 路由高性能的核心。除了 uri，还能按 host、method、header、参数、优先级等组合匹配。
L04

http_init_worker

router.lua:74-96 完整初始化：装 router_http（uri 路由）、router_ssl（SNI 证书路由）、api（内部 API 路由）。attach_http_router_common_methods（:54-72）给路由实现补上通用方法（routes() 返回路由列表、init_worker 建 watch）。

读法：http_route.init_worker(filter) 建立对 etcd /routes 的 watch（Day 07）——路由配置变了，重新喂给 radixtree 建树。filter 是每条路由存入前的预处理函数（下一节）。三个路由器：http（业务路由）、ssl（证书）、api（内部管理 API）。
L05

filter 预处理

router.lua:29-50 的 filter(route)——每条路由存入前的预处理：

local function filter(route)
    route.orig_modifiedIndex = route.modifiedIndex
    route.has_domain = false
    set_plugins_meta_parent(route.value.plugins, route)
    if route.value.host then
        route.value.host = str_lower(route.value.host)      -- host 转小写
    elseif route.value.hosts then
        for i, v in ipairs(route.value.hosts) do
            route.value.hosts[i] = str_lower(v)
        end
    end
    apisix_upstream.filter_upstream(route.value.upstream, route)  -- 预处理上游
end
"存入时预处理"是优化 host 转小写、上游预解析这些活，如果每次请求都做就浪费。放在"路由存入内存时"做一次，之后每次匹配直接用处理好的结果。这是"把重复计算前移到配置变更时"——配置不常变、请求很频繁，所以在配置变更时多算点、请求时省点，划算。
L06

match 匹配

回到 Day 04：init.lua:654 调 router.router_http.match(api_ctx)。match 把当前请求的 uri/host/method/args 等喂给 radixtree，radixtree 返回匹配的路由，放进 api_ctx.matched_route。

读法：匹配还会考虑优先级（多条路由都匹配时选 priority 高的）和各种条件（vars 表达式、自定义匹配函数）。radixtree 支持这些高级匹配。匹配到的路由对象里就有插件配置、上游引用——供后续步骤（Day 04 的合并、选插件）使用。
L07

router_ssl 与 api

  • router_ssl（radixtree_sni）：TLS 握手时按 SNI（客户端请求的域名）选对应证书——在 ssl_phase（Day 19）用。
  • api（api_router）：APISIX 内部 API 的路由（比如插件暴露的 /apisix/* 接口），和业务路由分开。
为什么证书路由也用 radixtree？ 你可能有几百张证书，每张对应一个/一批域名。TLS 握手时客户端说"我要访问 a.com"（SNI），网关要快速找到 a.com 的证书。这也是"从一堆规则里按名字快速找"——正好用 radixtree（按 SNI 匹配）。APISIX 把"路由匹配"这个能力复用到了证书选择上。
