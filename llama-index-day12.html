Day 12 / 共 20 天 · 第 3 周 检索与查询

查询引擎 QueryEngine

检索器只"找内容"，查询引擎把"找 + 后处理 + 生成答案"串成端到端问答。今天精读 RetrieverQueryEngine——这就是 Day 01 第四行 query_engine.query(...) 的真相。

L01

QueryEngine 定位

query_engine/retriever_query_engine.py:25：class RetrieverQueryEngine(BaseQueryEngine)——最常用的查询引擎。对外方法 query(str)（基类 BaseQueryEngine 提供），子类实现 _query。

QueryEngine = 检索器 + 合成器的组装 检索器只返回相关 Node（Day 11），但用户要的是"一句答案"。QueryEngine 在检索之上加"用 LLM 把 Node 合成答案"——它是"问答"的完整封装。Day 07 index.as_query_engine() 造的就是它。输入问题字符串，输出 Response（答案 + 引用的源 Node）。
L02

三个零件

retriever_query_engine.py:39-52 构造：

def __init__(self, retriever, response_synthesizer=None, node_postprocessors=None, ...):
    self._retriever = retriever                   # 检索器（Day 11）
    self._response_synthesizer = response_synthesizer or get_response_synthesizer(...)  # 合成器（Day 13）
    self._node_postprocessors = node_postprocessors or []   # 后处理器（Day 14）
读法：三个可插拔零件：retriever（找）+ node_postprocessors（筛/重排）+ response_synthesizer（合成答案）。合成器不传就用默认（get_response_synthesizer）。这三样正好对应第 3 周 Day 11/14/13——QueryEngine 是它们的"组装厂"。
L03

_query 三步

retriever_query_engine.py:202-210 的 _query（问答核心）：

def _query(self, query_bundle: QueryBundle) -> RESPONSE_TYPE:
    with self.callback_manager.event(CBEventType.QUERY, ...) as query_event:
        nodes = self.retrieve(query_bundle)              # ① 检索（含后处理）
        response = self._response_synthesizer.synthesize( # ② 合成答案
            query=query_bundle, nodes=nodes)
        query_event.on_end(payload={EventPayload.RESPONSE: response})
    return response
问题QueryBundle→ retrieve找 Node→ postprocess重排/过滤→ synthesizeLLM 生成→ Response答案
RAG 在线查询的心脏就这两行 _query 就干两件事：retrieve（找相关 Node，含后处理）+ synthesize（喂 LLM 生成答案）。Day 01 的 query_engine.query("...") 最终跑的就是这里。整个 RAG 的"检索增强生成"——检索（Retrieval）+ 生成（Generation）——就浓缩在这两行。简洁得惊人，因为复杂性都封在 retriever 和 synthesizer 里。
L04

retrieve + 后处理

retriever_query_engine.py:160-166 的 retrieve：

def retrieve(self, query_bundle: QueryBundle) -> List[NodeWithScore]:
    nodes = self._retriever.retrieve(query_bundle)         # 检索器找（Day 11）
    return self._apply_node_postprocessors(nodes, query_bundle=query_bundle)  # 后处理（Day 14）
读法：QueryEngine 的 retrieve = 检索器检索 + 依次应用后处理器。后处理器（Day 14）对检索结果重排、过滤、去噪——比如"只留 score>0.7 的""用 rerank 模型重新排序"。处理完的 Node 才交给合成器。这一层让"检索"和"精修检索结果"解耦。
L05

synthesize

retriever_query_engine.py:178-188 的 synthesize：委托给 response_synthesizer.synthesize(query, nodes)（Day 13 精读）。

合成 = 把 Node 和问题喂给 LLM 生成答案 检索到的几个 Node（相关片段）+ 用户问题，一起塞进提示词，让 LLM 生成一句连贯的答案。这就是"生成"（Generation）。但如果片段太多塞不下上下文怎么办？如果要综合多个片段呢？——这些由 Synthesizer 的不同模式（refine/tree_summarize，Day 13）处理。QueryEngine 只管"把 Node 交给 Synthesizer",怎么合成是 Day 13 的事。
L06

Response 对象

query 返回 Response（response/）：含 response（答案文本）、source_nodes（生成答案所依据的 Node）、metadata。

source_nodes = 可溯源（RAG 的关键卖点） Response 不只给答案，还带 source_nodes——"这个答案是基于这几个片段生成的"。这实现了 Day 01 说的"可溯源":用户能看到答案的依据、点进原文档核实。这是 RAG 相对纯 LLM 的重要优势（能追责、能验证）。print(response) 显示答案，response.source_nodes 拿依据。
L07

各种查询引擎

query_engine/ 下还有很多：

  • RouterQueryEngine：多个引擎，LLM 选一个（Day 10 提过的路由）。
  • SubQuestionQueryEngine：把复杂问题拆成子问题，分别查再汇总。
  • CitationQueryEngine：答案带引用编号。
  • SQLQueryEngine：把问题转成 SQL 查数据库。
  • RetrieverQueryEngine：本课主角（通用 RAG）。
查询引擎 = 不同的"问答策略" 简单问答用 RetrieverQueryEngine；复杂问题（"对比 A 和 B 的财报")用 SubQuestion 拆解；多数据源用 Router 分派。它们都是 BaseQueryEngine（统一 query 接口），能互换、能嵌套。第 4 周会看到 Agent 把 QueryEngine 当"工具"用——RAG 成为智能体的一种能力。
