Day 05 / 共 20 天 · 第 1 周 全景与请求生命周期

core.ctx 与 api_ctx

第 1 周收官。昨天贯穿全程的 api_ctx 到底是什么？今天拆 core/ctx.lua——尤其是 api_ctx.var 那个用 Lua 元表实现的"惰性求值 + 缓存"魔法，以及 tablepool 复用机制。这是理解 APISIX 性能的钥匙。

L01

api_ctx 是什么

api_ctx 是"一个请求的上下文袋子"——从 access 阶段创建（tablepool.fetch("api_ctx")），贯穿 balancer/filter/log，装着这个请求的一切：匹配的路由、consumer、plugins、上游配置、各种变量。

为什么需要"上下文"？ 一个请求要经过多个 Nginx 阶段（access → balancer → filter → log），每个阶段是独立的 Lua 函数调用。它们怎么共享"这个请求的信息"（匹配了哪条路由、识别出哪个 consumer）？答案就是 api_ctx——存进 ngx.ctx，所有阶段都能取到同一个。好比一个请求随身带的"档案袋",各阶段往里放东西、取东西。这跟上一站 wasm-go 的 HttpContext 是同一个概念。
L02

ngx.ctx vs api_ctx

init.lua:608-610：ngx_ctx.api_ctx = api_ctx。

两层容器 ngx.ctx 是 OpenResty 提供的"每请求 Lua 表"——同一请求的各阶段共享。APISIX 在 ngx.ctx.api_ctx 里放自己的上下文。为什么不直接用 ngx.ctx？因为 ngx.ctx 有些跨阶段的坑（子请求、内部跳转时行为微妙），而且 APISIX 想用 tablepool 精细管理自己的上下文对象。所以：ngx.ctx 是 OpenResty 的通用容器，api_ctx 是 APISIX 自己的、可池化复用的上下文。各阶段开头都 local api_ctx = ngx.ctx.api_ctx 取出来用。
L03

api_ctx.var 元表

core/ctx.lua:447-457 的 set_vars_meta 给 api_ctx 装上一个特殊的 var 表：

function _M.set_vars_meta(ctx)
    local var = tablepool.fetch("ctx_var", 0, 32)
    if not var._cache then var._cache = {} end
    var._request = get_request()
    var._ctx = ctx
    setmetatable(var, mt)     -- ★ 关键：装上元表 mt
    ctx.var = var
end
什么是"元表"（metatable）？ Lua 的元表能"拦截"对一个表的操作。给 var 装上元表 mt 后，当你写 api_ctx.var.uri——如果 var 里没有 uri 这个键，Lua 会调用元表的 __index 函数来"临时计算"这个值。这就是下一节的"惰性求值"魔法的基础。元表是 Lua 实现"面向对象""动态属性"的核心机制。
L04

惰性求值 + 缓存

core/ctx.lua:277-300 的 __index（读 var.xxx 时触发）：

__index = function(t, key)
    local cached = t._cache[key]
    if cached ~= nil then return cached end    -- ① 缓存命中直接返回
    local val
    local method = var_methods[key]
    if method then val = method()               -- ② 自定义变量（如 cookie/graphql）
    elseif has_prefix(key, "cookie_") then ...  -- ③ cookie_xxx
    else val = get_var(key, t._request) end     -- ④ 兜底：问 Nginx 要（ngx.var.xxx）
    if val ~= nil then t._cache[key] = val end   -- 存进缓存
    return val
end
"惰性求值"省了什么？ 一个请求有几十个变量（uri/host/remote_addr/args/各种 header），但一次请求可能只用到其中几个。如果启动时全算出来就浪费。惰性求值 = "用到 var.uri 时才去算 uri，算完缓存起来，下次直接取缓存"。没用到的变量根本不计算。加上缓存，同一个变量在多个插件里被读也只算一次。这是"按需 + 缓存"的经典优化——对每秒几万请求的网关，省下的计算很可观。你在插件里写 ctx.var.uri 就享受了这套机制，无感。
L05

register_var

core/ctx.lua:433 的 register_var(name, getter, opts)：让插件能注册"自定义变量"。

-- 例：注册 a6_labels_zone 变量
core.ctx.register_var("a6_labels_zone", function(ctx)
    return ctx.route and ctx.route.value.labels and ctx.route.value.labels.zone
end)
-- 之后就能在配置里用 $a6_labels_zone（比如日志格式）
读法：APISIX 把 Nginx 变量系统扩展了——插件能注册新变量，之后在路由/日志配置里像内置变量一样用。getter 在变量被读时惰性调用。这让插件能优雅地"暴露自己算出的值"给配置系统。
L06

tablepool 复用

回顾 Day 04：api_ctx 和 var 都从 tablepool fetch。tablepool 是"table 对象池"——预先攒一批空 table，用完还回去复用，而不是丢给 GC。

GC 是性能的隐形杀手 Lua 每创建一个 table 都要分配内存，用完了 GC 要回收。每秒几万请求 × 每请求几个 table = 海量分配/回收，GC 会周期性"停顿"拖慢延迟。tablepool 让这些 table "循环使用"——请求 A 用完的 api_ctx 清空后给请求 B 用，几乎不产生新分配。这是 APISIX（和很多高性能 Lua 程序）压榨性能的关键手段。代价是要小心"用完必须清空归还",否则会串数据（下一节）。
L07

release 回收

请求结束（log 阶段，init.lua:981-990）回收：

core.ctx.release_vars(api_ctx)                     -- 清空 var 并归还 ctx_var 池
if api_ctx.plugins then core.tablepool.release("plugins", api_ctx.plugins) end
core.tablepool.release("api_ctx", api_ctx)         -- 归还 api_ctx 池

release_vars（ctx.lua:459-467）：core_tab.clear(ctx.var._cache) 清空缓存 → 归还 table 池。

读法：归还前必须 clear（清空内容）——否则下个请求 fetch 到这个 table，会看到上个请求的残留数据（严重 bug/安全问题）。log 阶段是请求的最后一站，负责把所有池化对象清空归还。"fetch → 用 → clear → release"这个循环是 tablepool 正确性的核心。
