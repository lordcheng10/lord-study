Flow 状态与持久化

Flow 的各步骤如何共享数据、如何把进度存下来断点续跑、如何在关键步骤等人工反馈。今天收官 Flow 三部曲。

📍 你在整门课的位置（第 3 周 Flow / 工具 / LLM 主线）
Flow 编排· Flow 装饰器· Flow 状态持久化（今天）· 工具体系· LLM 抽象· Memory
L01

状态是共享字段 self.state

🤔 场景：一个跑了半小时的 Flow，第 8 步崩了 你写了个 10 步的数据处理 Flow，跑到第 8 步机器断电/进程被杀。前 7 步辛辛苦苦算出来的中间结果，全没了？重启后又得从第 1 步从头再跑一遍？
💡 一句话本质：状态 = 共享白板，持久化 = 存档点 各步骤要传数据，靠一块公共"白板"（self.state）读写；要防崩溃丢进度，就把这块白板定期拍照存盘（@persist）——像游戏的"存档点"，崩了从最近存档继续，而不是回到开局。今天就讲这块白板和它的存档机制。

Flow 的状态就是 self.state（runtime/__init__.py:1659）。所有步骤方法通过 self.state 读写同一个对象——状态在所有步骤间天然共享。

class MyFlow(Flow):
    @start()
    def step1(self):
        self.state["count"] = 1        # 写状态

    @listen(step1)
    def step2(self):
        self.state["count"] += 1       # 读+写同一个状态（现在是 2）
状态 = Flow 的"共享白板" 想象 Flow 的各步骤围着一块白板工作：step1 在白板写"count=1"，step2 能看到并改成"count=2"。self.state 就是这块所有步骤共享的白板。这和 eino Graph 的 State（Day 09）、OpenHands 的 Session 是同一个概念——跨步骤共享的可变状态。
🎮 生活类比：State 就像游戏的"存档数据" 打游戏时你的金币数、关卡进度、背包物品就是一份"存档数据"，全程跟着你走、随时能改。Flow 的 self.state 就是这份存档数据——每个步骤都能读它、改它。今天整节课的世界观就是"打游戏"：这一节是"存档里有啥"，后面 L05 讲"随时按下存盘键"，L06 讲"崩溃后读档续玩"。
L02

结构化 vs 非结构化 state

非结构化（dict）

  • Flow[dict] 或不指定
  • 状态是普通字典，随意加字段
  • 灵活，但无类型检查、易打错字段名

结构化（Pydantic）

  • Flow[MyState]，MyState 是 BaseModel
  • 有类型校验、IDE 补全
  • 规范、安全，推荐用于复杂 Flow
class MyState(BaseModel):
    count: int = 0
    results: list[str] = []

class MyFlow(Flow[MyState]):    # ★ 结构化状态
    @start()
    def step1(self):
        self.state.count = 1     # 有类型、IDE 能补全、拼错字段会报错
怎么选？和 Task 的结构化输出一个道理 简单 Flow 用 dict（省事）；复杂 Flow 用 Pydantic 模型（self.state.count 有类型检查，拼错字段名 IDE 立刻飘红，比 dict 的 self.state["cuont"] 悄悄出 bug 强）。状态越复杂越该结构化——这和 Day 03 的 output_pydantic、Day 10 的 response_model 是同一哲学：能强类型就强类型。
L03

强制 id 字段

所有状态都强制带一个唯一 id。基类 FlowState（runtime/__init__.py:360）就是给结构化状态注入 id 用的；若你的 model 没继承 FlowState，引擎会动态合成 class StateWithId(FlowState, 你的model)（:213）。

为什么每个状态要有 id？ 因为持久化（L05）需要一个"钥匙"来标识"这是哪次 Flow 运行的状态"。id 就是这把钥匙——存状态时用它当 key，之后 kickoff(inputs={"id": ...}) 就能按 id 加载回来（断点续跑）。没有唯一 id，就没法区分和恢复不同的运行。框架强制注入 id，让持久化和恢复成为可能。
L04

状态如何在步骤间传递

两种数据传递方式并存：

  • 共享状态：self.state 所有步骤都能读写（L01）——适合"贯穿整个 Flow 的数据"。
  • 返回值传参：上游方法的返回值，作为参数传给下游监听器（_execute_single_listener，runtime/__init__.py:2965）——适合"直接的上下游数据"。
# :2965 —— 检查监听器方法有没有参数，有就把上游结果传入
method_params = [p for p in sig.parameters.values() if p.name != "self"]
if method_params:
    result = await self._execute_method(listener_name, method, upstream_result)  # 传参
else:
    result = await self._execute_method(listener_name, method)                    # 不传
读法：引擎看下游方法的签名——有参数就把上游返回值传进去，没参数就不传。所以你写 def process(self, data)，data 就是上游的返回值；写 def process(self) 就只靠 self.state。共享状态适合"全局数据"，返回值传参适合"直接的上下游数据"，两者按需混用。
L05

@persist 持久化

@persist（persistence/decorators.py:147）同样是"纯元数据盖章器"——不含逻辑，只标记"这个方法/这个类的状态要存盘"。真正落盘由引擎在方法完成后 _persist_method_completion（runtime/__init__.py:2668）驱动。默认后端是 SQLite。

@persist   # 类级：所有方法完成后都存状态
class MyFlow(Flow[MyState]):
    @start()
    def step1(self): ...   # 完成后自动把 state 存进 SQLite
紫色：状态随步骤流转（同一块 self.state）；绿色：每步完成 @persist 把状态存进 SQLite；蓝色：崩溃后按 id 读回存档、从断点续跑。
📝 最小例子：改 state → 存盘 → 重启恢复 第一次跑：MyFlow().kickoff() → step1 令 state.count=1（存盘）→ step2 令 =2（存盘）→ step3 崩溃。
重启：MyFlow().kickoff(inputs={"id":"abc"}) → 引擎从 SQLite 读回 {count:2} → 直接从 step3 开始，前两步不再重算。
输出：最终 state.count 从 2 接着往下走，而不是从 0 重来。（钥匙就是 L03 的 id）
持久化解决什么？（🎮 = 游戏的"存盘键"） 长 Flow 可能跑很久、中途可能崩溃或需要暂停（比如等人工反馈，L07）。@persist 把每步完成后的状态存盘——就像游戏里每过一关自动按一次存盘键，万一进程挂了、重启后能从存档恢复，不用从头重打。取 state.id 当 key（L03 的 id 在这派上用场）。这和 OpenHands 的 CheckPoint、eino 的中断恢复是同一需求——让长任务能断点续跑。
❌ 错误驱动：不加 @persist 会怎样？ 假设你的 Flow 有 10 步、每步调一次付费 LLM，跑到第 8 步机器 OOM 崩了。没有 @persist：前 7 步的钱和时间全白花，重启只能从 step1 从头再来（还得再花一遍钱）。加了 @persist：每步存盘，重启读回 step7 的存档、直接从 step8 续跑。先感受"没有它的痛"，才明白这行装饰器为什么值。
🔍 走查这段"崩溃→读档"过程（trace table，跟着一行行看状态怎么变）： 
时刻          动作                     self.state         SQLite 存档
─────────────────────────────────────────────────────────────────
T1  首次跑    step1 令 count=1          {count:1}          {id:abc,count:1}  ← 存
T2            step2 令 count=2          {count:2}          {id:abc,count:2}  ← 存
T3            step3 执行中 💥崩溃        (内存清空)          {id:abc,count:2}  ← 存档还在
─────────────────────────────────────────────────────────────────
T4  重启      kickoff(id=abc) 读档       {count:2}          {id:abc,count:2}  ← 读回
T5            从 step3 续跑(不重跑1、2)   {count:3}          {id:abc,count:3}  ← 存
关键：崩溃只清空内存里的 self.state，SQLite 存档不受影响；重启靠 id 把最近一次存档读回内存，从断点继续。

👶 小白：崩溃后 self.state 里的数据不就没了吗？重启怎么可能"记得" count=2？

👨‍🏫 老师：分清两个地方。self.state 是内存里的白板，一断电就擦干净；但 @persist 每步都把白板拍照存进 SQLite 这块硬盘，硬盘上的存档断电不丢。重启时游戏（Flow）先去硬盘读回最近那张照片，白板就"恢复"成 count=2 了——和你关机重开游戏、进度还在是一模一样的道理。

👶 小白：那每一步都存盘，不会又慢又占地方吗？

👨‍🏫 老师：存的只是那块白板的当前快照（几个字段），一次写入很轻。相比"崩了要把前 7 步、每步一次付费大模型全重跑一遍"的代价，这点存盘开销几乎可以忽略——拿几毫秒的存盘，换掉重跑几分钟加一大笔 token 费，非常划算。

L06

恢复与检查点

配套的恢复能力：

  • kickoff(inputs={"id": ...})：按 id 加载已存状态继续（runtime:2132）。
  • from_pending(id)（:1168）：恢复"因等人工反馈而暂停"的 Flow。
  • from_checkpoint / fork（:585/:635）：从检查点恢复，或分叉出新分支。
fork（分叉）是个有意思的能力 fork = 从某个检查点复制一份状态，开出一条新的执行分支。用途：比如你想"从第 3 步的状态出发，试两种不同的后续方案"——fork 两份分别跑，对比结果。像 git 分支，但针对 Flow 的执行状态。fork 就像游戏里"读同一个存档，但从这里开始走两条不同剧情线"。注意：checkpoint 和 @persist 是两套独立系统，不能同用（:1949 会报错）。
📢 一句话复述（合上网页也能背出来） "self.state 是全程带着的游戏存档；@persist 是每步按一下存盘键；崩溃后靠 id 读档，从断点续玩、不从头重来。"
L07

@human_feedback：人在环

@human_feedback（dsl/_human_feedback.py:23）标记某步需要人工反馈。引擎执行该方法后调 _run_human_feedback_step（runtime:3197）。反馈可异步：

# 抛 HumanFeedbackPending 暂停 Flow、存 pending 状态、发 FlowPausedEvent
# 之后：MyFlow.from_pending(id).resume(feedback) 继续（runtime:1254）
又见 Human-in-the-loop（Day 09 也提过） 某些步骤需要人拍板——比如"生成了营销文案，等人审核批准才发布"。@human_feedback 让 Flow 在这一步暂停、存现场、等人反馈、再从断点继续。这和 OpenHands 的 confirmation mode、eino 的 Interrupt/Resume 完全同构。"能自主行动的 AI 系统，必须能在关键点停下等人"——本系列第 N 次强调，因为它是敢部署 AI 的底线。若配了多个可能结局（emit），该步会被规范化成 router，用人类反馈经 LLM"坍缩"成一个结局标签来路由。
