Day 04 / 共 20 天 · 第 1 周 建立心智

Ink 终端 UI 入门

循环的"大脑"清楚了，今天看"脸"——用 React 写终端界面是什么体验、REPL 的组件树长什么样、流式消息怎么变成你看到的样子。不懂 React 也能跟上。

L01

Ink 是什么：用 React 写终端界面

Ink = "把 React 渲染到终端"。你写的还是 React 组件、JSX、Hooks 那一套，但它渲染出来的不是网页 DOM，而是终端里的字符。对照理解：

浏览器 <div>
≈
Ink <Box>（flexbox 布局）
浏览器 <span>
≈
Ink <Text color=... dimColor>
onKeyDown 事件
≈
useInput(handler) Hook
requestAnimationFrame
≈
useAnimationFrame(ms)（spinner 靠它）
React 一句话：一个"数据变了、界面自动重画"的库。你把界面拆成一个个组件，每个组件根据它的"状态(state)"渲染；状态一变，React 自动重新渲染那部分。Hook 是 React 里以 use 开头的函数（如 useState），用来在组件里"挂"状态和副作用。这就是为什么一个终端 CLI 里有 700+ 个 .tsx 组件文件。

本项目用的是自研 fork 的 Ink——工作区包 packages/@ant/ink，通过别名 @anthropic/ink 引用（package.json:91）。键位系统、useTerminalSize、ScrollBox、全屏备用缓冲区等基础设施都在这个包里；src/ 下很多同名文件只是再导出（比如 src/hooks/useTerminalSize.ts 全文就一行 export { useTerminalSize } from '@anthropic/ink'）。

L02

根组件树：4 层 Provider 包着 REPL

Day 02 见过 replLauncher.tsx 挂载的元素树。展开看根部结构（replLauncher.tsx:20 + App.tsx:22）：

SentryErrorBoundary # 错误边界，崩了不白屏 └─ App # 只做 Provider 包裹，App.tsx:22 ├─ FpsMetricsProvider # 帧率统计 ├─ StatsProvider # 运行统计 ├─ AppStateProvider # ★ 全局状态 store（类 Zustand） └─ ThemeProvider # 主题（来自 @anthropic/ink） └─ REPL # ★ 真正的交互界面，screens/REPL.tsx
Provider 是什么？ React 里"往下传全局数据"的机制——包在外面的 Provider 提供数据，里面任何深度的组件都能直接取用，不用一层层传参。这里 AppStateProvider 提供全局状态（设置、模型、任务、权限上下文等），ThemeProvider 提供配色主题。ErrorBoundary 是"错误边界"——里面组件崩了，它兜住不让整个界面白屏。
L03

REPL 组件树全貌

screens/REPL.tsx（6000+ 行）是主界面。它挂了一串"零高度"的键位处理器 + 一个三区布局。简化版：

REPL └─ KeybindingSetup # 键位环境 ├─ GlobalKeybindingHandlers # 全局快捷键（零渲染） ├─ CancelRequestHandler # Ctrl+C 打断 └─ FullscreenLayout # 三个具名插槽 ├─ overlay: 权限弹窗 # toolPermissionOverlay ├─ scrollable(消息滚动区): │ ├─ ★ Messages # 消息历史列表 REPL.tsx:5906 │ ├─ toolJSX # 工具/本地命令注入的 UI │ └─ ★ SpinnerWithVerb # 转圈"动词…"REPL.tsx:5950 └─ bottom(底部固定区): ├─ 各类对话框 ├─ ★ PromptInput # 输入框 REPL.tsx:6482 └─ MessageSelector # 历史回溯选择器

三个核心组件：Messages（消息历史，L04 讲）、PromptInput（输入框，Day 18 讲）、SpinnerWithVerb（那个转圈 + "Thinking…"）。整个界面只有两种屏 'prompt' | 'transcript'（Ctrl+O 切换，REPL.tsx:814）。

为什么有一堆"零高度处理器组件"？ 像 GlobalKeybindingHandlers 这种组件不渲染任何可见内容，只是"挂载时注册一批快捷键、卸载时注销"。用组件而非普通函数来做，是为了借用 React 的生命周期自动管理注册/清理——这是 Ink/React 应用里管理键盘绑定的常见技巧。
L04

消息渲染循环：数组 → 一条条组件

你看到的对话记录，就是一个消息数组被渲染成一条条组件。链路是 REPL → Messages → MessageRow → Message：

  • REPL 不自己 map，把数组交给 <Messages>（REPL.tsx:5906）。
  • Messages.tsx 归一化/分组/折叠后，用 renderMessageRow（Messages.tsx:787）把每条转成一个带唯一 key 的 <MessageRow>（memo 化，避免无谓重渲染）。消息多时走虚拟滚动 VirtualMessageList（Messages.tsx:928）。
  • 单条消息由 Message.tsx 的 switch(message.type)（Message.tsx:103）分派：assistant / user / system / tool_use / … assistant 内部再按 block 类型（text / thinking / tool_use）分派到 components/messages/ 下的组件。
虚拟滚动 & memo：对话可能有几百条消息。虚拟滚动只渲染"当前可视区域"的那几条，其余不渲染，省性能。React.memo 让一个组件在"props 没变"时跳过重渲染。终端渲染比浏览器还敏感（每次重画都要重写字符），所以这里到处用 memo + 虚拟滚动。
L05

流式文本怎么"逐行冒出来"

Day 03 讲了 API 层流式吐字。到了界面这层，有个巧妙处理——已定稿的消息走列表，正在流式的文本作为列表后面一个"独立兄弟节点"实时渲染（Messages.tsx:954）：

// Messages.tsx:954 —— streamingText 不进消息列表，单独渲染
{streamingText && (
  <Box><StreamingMarkdown>{streamingText}</StreamingMarkdown></Box>
)}
● 已定稿的消息（在 Messages 列表里）
● 我正在分析这段代码，发现
↑ 这行是 streamingText，独立渲染、逐行更新

而且 visibleStreamingText 只截到"最后一个换行"为止（REPL.tsx:1803）——所以你看到的是"逐行"平滑冒出，而不是"逐字"抖动。定稿后这条才并入正式消息列表。

为什么要分开渲染？ 如果每来一个 token 就更新整个消息列表，几百条消息的树会被反复重画，卡到不行。把"正在流式的那一小段"单独拎出来实时更新、定稿后再并入列表，就只有一小块在高频重画，列表本身不动。这是"隔离高频更新区域"的经典性能手法。
L06

ref 当真值源、state 当渲染投影

REPL 里一个值得学的模式（REPL.tsx:1502）——消息数组的"真值"存在 ref 里，state 只是给渲染看的投影：

// REPL.tsx:1486 —— 消息数组
const [messages, rawSetMessages] = useState(initialMessages ?? []);
const messagesRef = useRef(messages);
// setMessages 包装器：先同步写 ref，再触发 state 更新
function setMessages(next) {
  messagesRef.current = next;    // ← 立刻可读（同步）
  rawSetMessages(next);          // ← 触发重渲染（异步提交）
}
为什么要这样？ React 的 setState 是异步的——你刚 setMessages(...)，紧接着读 messages 还是旧值（React 还没提交）。但 Agent 循环里经常需要"刚追加完消息立刻读到最新的"。于是用 ref（messagesRef.current，同步可读可写）当真正的数据源，state 只负责触发界面重画。ref 是 React 里一个"不触发重渲染、可随时读写"的盒子。

同样地，流式文本长度用 responseLengthRef（REPL.tsx:1752）——每个 text delta 只更新 ref、不触发重渲染，spinner 靠动画帧去读它显示进度。这样几千个 token 增量不会引发几千次重画。

L07

性能：终端 UI 为什么处处小心

把今天的性能手法串一下——它们都在解决同一个问题：终端重画很贵，必须把"高频变化"和"大而稳定"的部分隔离开。

手法解决什么
虚拟滚动几百条消息只渲染可视区那几条
React.memo（MessageRow）props 没变的消息行跳过重渲染
流式文本独立兄弟节点高频更新区域只有一小块，列表不动
ref 当真值源token 增量不触发整树重画
useDeferredValue（deferredMessages）长列表重渲染降优先级，保输入流畅（REPL.tsx:1625）
spinner 共享时间基准所有动画同步，避免各自定时器
useDeferredValue：React 18 的 API，把某个值的更新标记为"低优先级"。这里对消息列表用它——当你在打字（高优先级）时，庞大消息列表的重渲染会被延后，保证输入不卡。输入永远比历史刷新重要，这是交互体验的取舍。
这些手法看着琐碎，但正是它们让一个"跑在终端、用 React、还要实时流式"的界面能顺滑不卡。读 UI 代码时看到 memo / ref / deferred，别当噪音——它们是作者跟"终端重画开销"斗争的痕迹。
