Day 06 / 共 20 天 · 第 2 周 可信底座

ai-trust-toolkit 总览 & 渐进抽象

第 1 周你摸清了地图和一户人家的骨架；从今天起进入框架的灵魂——ai-trust-toolkit。先鸟瞰它的 10 个模块、公开 API、内部依赖规则，以及全仓最值得学的方法论——"渐进抽象"。后面 Day 07-11 逐个拆它的核心能力。

📍 你在 20 天里的位置（第 2 周：可信底座）
D06 toolkit 总览→ D07 Critic→ D08 失败闸门→ D09 Memory→ D10 评测
💡 用一个类比先兜住今天（延续「盖楼/物业」世界观） toolkit 就是整栋楼的公共设备机房 + 承重结构：消防、水泵、配电、电梯全在这——每一户(业务 Agent)不用自己装，接根管子就用。今天讲三件事：① 机房里有哪 10 台设备（10 个模块）；② 机房内部的管线也分层（叶子设备不反向依赖别人）；③ 这机房不是一天建成的——它遵循"渐进抽象"：第一户要什么先在户内凑合搭，等第二户也要一模一样的，才把它挪进公共机房。这句"第二次重复才抽"是全仓最值钱的一句话。
L01

toolkit 的定位：横切能力的公共底座

packages/ai-trust-toolkit（版本 0.6.0）是本仓自研的核心库。它不是"某个 agent 的代码"，而是所有 agent 都能用的横切能力——防幻觉、闸门、评测、记忆、成本治理。

回忆 Day 02 的"薄业务 + 厚 toolkit"：一个业务 agent（如 sre-rca）真正自己写的代码可能就几百行，剩下的"可信/可观测/成本/记忆"全是从这个库 import 来的。所以吃透了 toolkit，你就吃透了整个平台。

权威参照文档：packages/ai-trust-toolkit/ARCHITECTURE.md——它的 §0 有分层图、§3 逐模块讲"为什么这么设计"、§8 有 v0.1→v0.6 的抽象演进时间线。本周的讲解都以它和源码为准。

L03

公开 API 地图：从哪 import 什么

一个有意思的设计：这个库顶层几乎不暴露符号。__init__.py 只 re-export 了 handoff 和 effect 两组，其余全部要从子包按需 import。为什么？保持解耦、避免 import 时触发一堆副作用和慢加载。

__init__.py 开头的 docstring 就是一张"API 地图"，把常用 import 路径列全了——这是你日后查 API 的最佳索引页：

from ai_trust_toolkit.tools import safe_tool_result
from ai_trust_toolkit.failsafe import wrap_with_fallback, build_critic_router
from ai_trust_toolkit.critic import collect_valid_evidence_ids, build_critic_node
from ai_trust_toolkit.eval import EvalSample, FiveDimScorer, run_eval
from ai_trust_toolkit.memory import Embedder, VectorStore, PgVectorStore, InMemoryVectorStore
from ai_trust_toolkit.api import build_v1_router, CostTracker, check_or_raise
from ai_trust_toolkit.llm import set_llm_factory, get_llm
from ai_trust_toolkit.testing import FakeLLM, SystemAwareFake, install_fakes
📝 举个例子：按"我想要什么能力"查 import 路径 想给结论加防幻觉 → from ai_trust_toolkit.critic import build_critic_node
想让某个节点挂了不崩 → from ai_trust_toolkit.failsafe import wrap_with_fallback
想给 HTTP 入口套统一 envelope → from ai_trust_toolkit.api import build_v1_router
想在测试里不联网 → from ai_trust_toolkit.testing import FakeLLM。先想"要哪台设备"，再去对应子包接管子。
阅读顺序建议：每读一个子包前，先看它自己的 __init__.py——里面的 __all__ 和 docstring 就是这个模块的"能力清单"。本周每一天都会先看对应子包的 __init__.py。
⚠️ 小白常误以为"顶层 __init__ 不 re-export，是没写完/偷懒"。恰恰相反，这是刻意的解耦：如果顶层 from ai_trust_toolkit import * 就把 critic/memory/api 全拉起来，会触发一堆副作用和慢加载（有的模块要连 DB）。让你"用哪个从哪个子包 import"，是为了按需加载、彼此不牵连。
🍼 记忆口诀（本周地图）toolkit 核心能力五连：「批(critic防幻觉)、兜(failsafe闸门)、记(memory记忆)、评(eval评测)、算(cost成本)」——对应 Day 07→08→09→10→11。外壳治理另算一档 api/（Day 12）。
L04

内部依赖铁律：叶子不依赖任何人

Day 01 讲了"层与层之间"的依赖铁律。toolkit 内部模块之间也有一套依赖规则，保证它自己不会变成一团乱麻：

eval/ — 站最高，可以依赖下面所有模块（评测要串起全链路）
failsafe/ — 只依赖叶子模块，不依赖 critic/eval
llm.py · tools/ · testing/ · memory/ — 叶子模块，不 import 任何 toolkit 内部模块

另外还有几条"红线"约束，是为了安全和可测试：

  • sensitivity/ 模块绝不 import anthropic / langchain——它是纯规则的敏感度分类，必须极轻、无外部依赖（classifier.py:10）。
  • 许多函数刻意做成"没有依赖时静默降级"：比如 budget_gate 没有 tracker 时静默放行、get_llm 遇到不支持缓存参数的 FakeLLM 时自动退化——都是为了让测试和独立调用不崩。
为什么这么较真？ 因为 toolkit 是被 20+ 个 agent 共同依赖的地基。地基里模块乱依赖，会导致：改一个模块牵连一片、循环 import、测试要拉起一堆无关组件。这套"分层 + 叶子 + 红线"的自律，是它能被这么多 agent 放心依赖的原因。
L05

渐进抽象：全仓最值得学的方法论

这是整个项目最核心的工程思想，AGENTS.md 和 CHANGELOG 反复强调。一句话：

🌱 "1 个 Agent 时不抽象，第 2 个 Agent 出现重复了才抽。"

意思是：不要在只有一个用例时就急着设计"通用框架"。等到第二个、第三个 agent 出现真实重复，你才真正知道哪些该抽、抽成什么样。过早抽象往往抽错，反而成为负担。

🤔 如果让你自己来，你会怎么做？假设你在写第一个 agent sre-rca，需要 4 个专家节点。朴素做法：直接复制粘贴 4 段"取数→喂 LLM→解析→兜底"的相似代码。这时候你会不会立刻抽个 make_specialist 函数？——渐进抽象说先别：你只有这一个 agent，猜不准通用形态，抽早了大概率抽错。等 risk-reviewer 也要几乎一样的专家节点（真实重复出现），你才把它上移到 toolkit 成 make_specialist_node。这就是"忍住不过早抽象"的价值。
图注：一份代码，第二次重复出现时才提取到公共机房，两户再各自 import——CHANGELOG 会记下这次"触发原因"。

🚫 过早抽象的坑

  • 只有 1 个用例，猜不准通用形态
  • 为"可能的未来"过度设计
  • 抽象错了，改起来比不抽还贵

✅ 渐进抽象的做法

  • 第 1 个 agent 允许"写死、重复"
  • 第 2 个出现同样代码 → 才提取到 toolkit
  • 每次抽象在 CHANGELOG 写清"触发原因"

Day 05 见过的那个 DEPRECATED 的 specialists/_factory.py，就是这个过程的"化石"——专家工厂最初写在业务里，第二个 agent 也需要时才被上移进 toolkit，旧路径留个空壳保持兼容。

L06

抽象演进时间线（CHANGELOG 是活教材）

docs/CHANGELOG.md 完整记录了每一次抽象的"何时抽、为什么抽、为什么之前不抽"。这是一部难得的"抽象决策史"：

v0.2

抽出 Specialist 工厂

触发：risk-reviewer 出现和 sre-rca 95% 重复的专家节点代码 → 提取 make_specialist_node。

v0.3

抽出 business_critic_l1

触发：第 3 个 agent（alert-triage）需要纯规则的轻量 Critic（不调 LLM、省延迟）→ 提取规则式 L1。

v0.5

抽出 reporter 工厂

触发：末端渲染节点第 3 次重复 → 提取 make_reporter_node。

v0.6

加入 budget_gate + 成本感知路由

成本治理成熟：失败闸门从 5 道扩到 6 道，get_llm("auto") 支持预算紧张时自动降级。

怎么用这份 CHANGELOG？ 当你想理解"这个抽象为什么长这样"，去 CHANGELOG 找它被引入的那一版，读它的触发故事——比读代码本身更能理解设计意图。这也是读任何成熟开源项目的通用技巧。
L07

两类使用者：agent-facing 与 api

toolkit 内部按"谁来用"分成两大类，理解这个划分能帮你快速定位代码：

agent-facing 八件套

给 LangGraph 图里的节点用的：critic / failsafe / eval / memory / specialists / tools / llm / testing。你在 agent 的 nodes/、builder.py 里 import 的就是这些。

wrapper-facing 子包 api/

给 HTTP 入口（server/mcp/cli/门户）用的：build_v1_router / envelope / auth / cases / cost / quota / ratelimit / budget。它把一次调用的"外壳治理"全包了。Day 12 精讲。

一句话：图内节点用左边，HTTP 外壳用右边。 分清这个，你就知道一段代码大概在解决"业务推理"还是"服务治理"的问题。
