Day 15 / 共 20 天 · 第 3 周收官

Agent 全家福 + 元 Agent

读透了一个满配 agent，今天横向扫全部 20+ 个：各干什么、结构上有哪些变体，以及最精彩的"用 Agent 造 Agent"。

L01

20+ agent 分类速览

apps/ 下实际有 21 个 agent（文档常说 9/12，Day 01 讲过的漂移）。按用途大致分四类：

业务/运维执行类

直接解决具体业务问题：故障、风控、文档、告警、安全、知识……

元 Agent（造东西的 Agent）

agent-creator（造 agent）、skiller-creator（造 skill）。

自我开发流水线

requirement-discoverer → spec-author → spec-executor → release-coordinator，让平台"自己开发自己"。

调度/载体类

supervisor-router（跨 agent 路由）、bmc-agent-mcp（MCP 形态）等。

怎么快速读懂任意一个？ 用 Day 05/14 的方法：打开它的 builder.py 看图骨架 → 看它有几个专家、有没有 Critic → 看 prompts。因为结构统一，10 分钟就能摸清一个陌生 agent。
L03

结构变体谱系：一套框架，多种裁剪

所有 agent 共用同一套 toolkit，但按需裁剪出不同"形态"。理解这些变体，能体会框架的弹性：

① Critic 强度分层（Day 07 讲过）

形态代表原因
L1+L2 三态sre-rca责任重，值得反复审
仅 L1（不调 LLM）alert-triage高频在线，延迟敏感
无 Criticrisk-reviewer刻意验证"无 Critic 也能复用 toolkit"

② 载体形态分层（Day 12/13 讲过）

FastAPI pod（默认）/ CLI / MCP。如 bmc-agent（pod）vs bmc-agent-mcp（MCP 内嵌）、supervisor-router 的 CLI+MCP 双入口。

③ 专家数量

从 0（纯路由的 supervisor-router）、2（risk-reviewer）、4（sre-rca）到 5（security-audit）。make_specialist_node 让加减专家几乎零成本。

为什么故意留"无 Critic""仅 L1"这些变体？ 一方面真实场景确实需要（延迟/成本权衡），另一方面这些变体是对 toolkit 的压力测试——如果 toolkit 只在"满配"下好用、一裁剪就散架，说明抽象没做好。能优雅支持各种裁剪，才证明底座真的通用。这是"渐进抽象"的验收标准。
L04

什么是"元 Agent"

元 Agent（meta-agent）= 造 Agent/组件的 Agent。它的输出不是"业务分析结果"，而是"另一段代码/一个新组件"。本框架有两个：

  • agent-creator：一句自然语言描述 → 生成一个符合规范、可直接跑的新 agent 代码骨架。
  • skiller-creator：生成并注册新的 Skill 组件，带自动评测-修订的迭代闭环。

它们本身也是标准的 LangGraph agent（有 State、builder、节点、Critic），只是节点干的活是"分析需求、渲染模板、生成文件"而非"查日志、算指标"。这是"框架用自己造自己"的第一层体现。

L05

agent-creator：造 Agent 的 Agent

图是串行的（agent_creator/builder.py:40）：

需求分析Sonnet 解析→ 架构设计architect→ 脚手架渲染文件→ 评测设计golden 样本→ critic_l1硬错误检查→ assemble产出

几个关键设计（agent_creator/specialists.py）：

  • 三态 mode：dry_run（只预览不落盘）/ write（真写文件）/ bundle（打 zip）——用状态控制"副作用"大小（呼应 Day 04 的 scope guard 思想）。
  • 模板渲染：scaffolder 用 Haiku 出计划，再渲染 templates/base/**（builder.py.tpl 等）+ 白名单 fragments/（critic_l1/memory 等预置片段，防 LLM 编造）。
  • 可选 MCP 工具：需求分析节点能 opt-in 绑定 brave-search MCP 工具（环境变量开关，失败静默）——这是 toolkit MCP 客户端能力的活 demo。
防编造的巧思：生成 Critic、记忆这些"标准件"时，agent-creator 不让 LLM 自由发挥，而是用白名单 fragments（预先写好的正确片段）拼装。因为这些代码有标准写法，让 LLM 编反而容易出错。"该用模板的用模板，该用 LLM 的用 LLM"——又一个"能用确定性手段就别用 LLM"的例子。
L06

skiller-creator：带 RLHF 自迭代的造 Skill

skiller-creator 比 agent-creator 多了一个自我评测-修订循环（类似 RLHF 思想）。它的图有两条路径（skiller_creator/builder.py:83）：

skill_writer→ scaffolder→ critic_l1→ 生成测试问句→ evaluator 评分→ reviser 修订↺ assemble

两个条件函数是精髓：_after_critic（builder.py:40）决定过了 L1 后去评测还是直接组装；_after_eval（builder.py:65）——评测达标或预算用尽 → 组装产出；不达标且还有预算 → 修订后回 scaffolder 重新组装再评测，用 iteration vs max_iterations 控制循环上限。

这是一个"自我改进"的闭环：生成 → 评测 → 不满意就自己改 → 再评测，直到达标或预算耗尽。它把 Day 10 学的评测能力用在了"生成质量把关"上——生成的东西自己先考一遍，不及格自己重写。对比 agent-creator 的"一次成型"，skiller-creator 是"迭代打磨"。
L07

自我开发流水线：平台开发自己

最精彩的部分——4 个 agent 串成一条"平台自己给自己提需求、写规格、改代码、评审发布"的流水线（就是 Day 04 route_chain 那条链）：

requirement-
discoverer发现需求→ spec-author写 OpenSpec 规格→ spec-executor改代码+测试→ release-
coordinator5 道 gate 评审
agent做什么安全约束
requirement-discoverer3 专家扫 cases/prom/静态代码，产出 IssueDraft不自动起 spec，人工把关起点
spec-authorissue 文本 → OpenSpec change 4 文件safe_change_write 只能写本次 change 目录（禁改 specs/apps/自身）
spec-executor读 change → 改代码 → 跑测 → commitgit_commit 只能提到 agent/* 分支（不碰 main）；测试失败自动 revert
release-coordinator编排 ruff/mypy/pytest/arch/risk 5 道 gate出 PR decision，不自动合并
处处 scope guard（Day 04）：发现需求的不自动起 spec、写 spec 的只能写自己那块、改代码的只能提到临时分支不碰 main、评审的只出决策不自动合。每一环都"只做自己该做的、把关键决策留给人"——这是让"AI 自我开发"变得安全可控的关键。Day 20 会结合 OpenSpec 再讲这条闭环。
