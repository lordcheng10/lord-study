Day 16 / 共 20 天 · 第 4 周 Agent/Workflow/生态

Workflow 引擎

前三周把 RAG 全链路拆透了。第 4 周超越 RAG——LlamaIndex 用 Workflow（事件驱动引擎）作为 Agent 的底座。今天看 Workflow 的核心：@step、Event、Context，理解"事件驱动编排"这个新范式。

L01

超越 RAG

从"一问一答"到"多步自主" RAG（前三周）是"检索→生成"的固定流程。但复杂任务需要"多步、有分支、能循环"——比如 Agent："先想想要用什么工具 → 调工具 → 看结果 → 再决定下一步 → 直到解决"。这不是固定流程，而是动态的、可能循环的。LlamaIndex 用 Workflow 表达这种复杂控制流——一个事件驱动的编排引擎。Agent（Day 17）、复杂 RAG（多步查询）都建在 Workflow 上。（注意：Workflow 核心已抽成独立包 workflows，core 的 workflow/ 主要是 re-export + LlamaIndex 特定事件。）
L02

事件驱动

workflow/：workflow.py（Workflow 基类）、decorators.py（@step）、events.py（Event）、context.py（Context）、handler.py。

"步骤发事件、事件触发步骤" Workflow 的核心模型：一堆"步骤"（step），每个步骤接收某种事件、处理后发出另一种事件；发出的事件又触发下一个步骤。就像多米诺骨牌——A 步骤发出 EventX，接收 EventX 的 B 步骤被触发，B 发出 EventY 触发 C……直到发出 StopEvent 结束。这种"事件驱动"比"写死的函数调用链"灵活得多：能分支（发不同事件走不同步骤）、能循环（步骤发出的事件又回到自己）、能并发。
L03

@step 装饰器

workflow/decorators.py:7：step 装饰器（委托给上游 workflows 包的 upstream_step）。用法：

from workflows import Workflow, step
from workflows.events import StartEvent, StopEvent, Event

class MyFlow(Workflow):
    @step
    async def step_one(self, ev: StartEvent) -> MiddleEvent:   # 接收 Start，发出 Middle
        return MiddleEvent(data="...")
    @step
    async def step_two(self, ev: MiddleEvent) -> StopEvent:    # 接收 Middle，发出 Stop
        return StopEvent(result="done")
用"类型注解"声明事件流 关键设计：步骤的参数类型声明"我接收什么事件"，返回类型声明"我发出什么事件"。step_one(ev: StartEvent) -> MiddleEvent 就是"收 Start、发 Middle"。Workflow 引擎读这些类型注解，自动把步骤连成事件流——不用手写"谁调谁"。你只写步骤 + 声明输入输出事件，引擎自动编排。这比手写调用链优雅（回想 wasm-go 的类型驱动、langgraph 的图）。
L04

Event 连接步骤

自定义 Event 继承 Event（Pydantic 模型，装数据）。步骤间通过 Event 传递数据。一个步骤可以返回不同 Event 实现分支，或返回自己接收的 Event 类型实现循环。

Event 既是"信号"也是"数据载体" Event 不只触发下一步，还带着数据（Pydantic 字段）。MiddleEvent(data="...") 把 data 传给接收它的步骤。分支：一个步骤根据情况返回 EventA 或 EventB——走不同的后续步骤。循环：步骤 X 返回一个最终又会触发 X 的事件——实现"反复执行直到条件满足"（Agent 的"想-做-看"循环就靠它）。Event 类型 = 控制流的"路标"。
L05

Start / Stop Event

两个特殊事件：StartEvent（Workflow 启动时自动发，携带输入）、StopEvent（发出它就结束，result 是最终结果）。

flow = MyFlow()
result = await flow.run(input="...")   # 触发 StartEvent → ... → StopEvent → 返回 result
读法：run 发出 StartEvent 启动流程，引擎按事件流跑各步骤，直到某步骤返回 StopEvent 结束、返回其 result。接收 StartEvent 的步骤是"入口",返回 StopEvent 的步骤是"出口"。中间可以有任意多步骤、分支、循环。
L06

Context 状态

workflow/context.py 的 Context：跨步骤共享状态。步骤可以 await ctx.store.set/get 存取数据、ctx.write_event_to_stream 发流式事件（进度）、ctx.collect_events 等待多个事件（并发汇合）。

Context = Workflow 的"共享内存 + 流式通道" 步骤间除了用 Event 传数据，还能用 Context 存"全局状态"（整个流程共享，如累积的中间结果）。collect_events 支持"扇入"（等几个并发步骤都完成再继续）。write_event_to_stream 让流程"边跑边报告进度"（前端能实时看到 Agent 在干嘛）。回想 langgraph 的 State/Channels、wasm-go 的 Context——都是"跨步骤共享状态"的机制。Workflow 的 Context 是 LlamaIndex 版。
L07

和 langgraph 对比

两种"编排范式" 你学过的 langgraph 用"图"（节点 + 边 + 状态通道，Pregel 超步）编排；LlamaIndex Workflow 用"事件驱动"（步骤 + 事件）编排。本质都是"表达复杂控制流（分支/循环/并发）"，风格不同：langgraph 显式画图（节点边）；Workflow 用类型注解隐式连接（收什么事件、发什么事件）。Workflow 的事件模型对"动态、涌现式"的流程更自然（不用预先画全图）。两者都比"写死的 if-else 链"强——都是 Agent 时代的编排基础设施。
