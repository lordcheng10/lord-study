CheckpointSaver 与 threads

检查点存哪里、怎么存？读 BaseCheckpointSaver 抽象接口和它的三种实现，理解 thread_id 怎么把多个独立会话隔离开。

L01

Saver 是什么

Day 11 讲了检查点是什么，今天讲它存哪儿。CheckpointSaver（检查点存储器）负责把检查点写入/读出某种后端（内存、SQLite、Postgres……）。编译时传入：

from langgraph.checkpoint.memory import InMemorySaver
graph = builder.compile(checkpointer=InMemorySaver())   # 插上"存档器"
graph.invoke(input, {"configurable": {"thread_id": "user-42"}})  # 指定存档槽位
读法：compile 时插上 checkpointer，图就获得了"存档能力"；invoke 时用 thread_id 指定"存到哪个会话"。不传 checkpointer → 图无记忆，每次从头（Day 01-10 的默认）。
L02

抽象接口

BaseCheckpointSaver（checkpoint/base/__init__.py）定义了统一接口，所有后端实现它：

方法作用
put存一个检查点（Day 08 after_tick 调）
put_writes存 pending writes（Day 11 半完成保护）
get_tuple读某检查点（恢复用）
list列出某 thread 的所有检查点（时间旅行用，Day 13）
又是"接口/实现分离"（老朋友了） 和 eino 的 ChatModel、AutoGPT 的 Block、crewAI 的 LLM 一样：Pregel 引擎只依赖 BaseCheckpointSaver 这个抽象接口（put/get/list），完全不关心底层是内存还是数据库。换存储后端 = 换一个实现类，引擎代码一行不改。开发时用 InMemory、生产用 Postgres，图逻辑完全一样——这就是抽象接口的价值。贯穿所有框架的同一设计哲学。
L03

thread_id 隔离

检查点按 thread_id 分组存储。每个 thread_id 是一条独立的检查点时间线——互不干扰。

thread = 一个独立的对话/会话 想象一个客服机器人同时服务 1000 个用户。每个用户一个 thread_id——他们的对话历史（检查点）各存各的，绝不串台。用户 A 发消息用 thread_id="A"，图自动加载 A 的历史、接着聊；用户 B 用 "B"，是全新的另一条线。这就是 LangGraph 做"多用户记忆"的方式：不用你手动管理会话字典，thread_id + checkpointer 自动搞定持久化和隔离。换个 thread_id 就是换个记忆空间。
L04

InMemorySaver

InMemorySaver（checkpoint/memory/）把检查点存进内存字典（按 thread_id → checkpoint_id 嵌套）。进程结束即丢——适合开发、测试、单元测试。

读法：最简单的实现，零依赖、零配置，验证逻辑用。它证明了接口的完整性：连纯内存字典都能撑起完整的持久化/时间旅行 API。生产别用（重启就没了）。
L05

Sqlite / Postgres

生产级实现在独立包：

包后端适用
langgraph-checkpoint-sqliteSQLite 文件单机、本地持久化
langgraph-checkpoint-postgresPostgres生产、多实例共享

它们把 Day 11 的 Checkpoint 结构序列化（Day 15 讲 serde）后存进表；list/get_tuple 用 SQL 查询实现。API 与 InMemory 完全一致。

读法：同一套接口的持久化后端。生产用 Postgres——多个服务实例连同一个库，Agent 状态天然共享、可水平扩展。切换只需换 checkpointer 那一行。
L06

get_state / get_state_history

Pregel 在 Saver 之上包了用户友好的 API（main.py）：

cfg = {"configurable": {"thread_id": "user-42"}}
snap = graph.get_state(cfg)              # 当前状态快照（StateSnapshot）
for s in graph.get_state_history(cfg):   # 历史所有检查点（新→旧）
    print(s.config, s.values, s.next)    # next = 接下来该跑的节点
读法：get_state=读当前存档；get_state_history=列出这个 thread 的所有历史存档（底层调 saver.list）。StateSnapshot 带 next（下一步跑谁）和 config（含 checkpoint_id）——Day 13 时间旅行就用这个 config 精确定位到某一步。
L07

多会话实战

graph = builder.compile(checkpointer=InMemorySaver())

# 会话 A：连续两轮，自动记住上一轮
graph.invoke({"messages":[HumanMessage("我叫小明")]}, {"configurable":{"thread_id":"A"}})
graph.invoke({"messages":[HumanMessage("我叫啥?")]}, {"configurable":{"thread_id":"A"}})
# → 第二轮能答"小明"，因为 add_messages 累加了 A 的历史（Day 03 + Day 11）

# 会话 B：全新记忆，不知道小明
graph.invoke({"messages":[HumanMessage("我叫啥?")]}, {"configurable":{"thread_id":"B"}})
# → 答不上来，B 是独立时间线
读法：这就是"聊天机器人记住上下文"的完整机制：checkpointer 存历史 + add_messages 累加 + thread_id 隔离。三者合起来，你几乎不用写记忆管理代码。
