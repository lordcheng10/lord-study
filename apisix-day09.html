Day 09 / 共 20 天 · 第 2 周 路由/配置/数据面

schema 校验

昨天的对象存入前必须校验（不能存一条 uri 是数字的路由）。今天看 core/schema.lua 怎么用 JSON Schema 校验，以及 schema 在 Admin API 和插件配置里的统一作用。这是 APISIX 配置健壮性的保障。

L01

为什么要校验

垃圾进 → 垃圾出 配置是运维手写/程序生成的，难免出错：uri 写成数字、端口填了字符串、必填字段漏了。如果不校验就存进 etcd，等请求处理时才崩——难排查、影响线上。所以 APISIX 在配置写入时（Admin API）就用 schema 严格校验，不合法直接拒绝、返回清晰错误。"在源头挡住坏配置"比"运行时才发现"好一万倍。（回想上一站 Higress Console 的后端校验是空 TODO——APISIX 这里是真校验。）
L02

JSON Schema

APISIX 用 JSON Schema 描述"合法配置长什么样"。schema_def.lua 里的对象定义就是 JSON Schema：

_M.route = {
    type = "object",
    properties = {
        uri = {type = "string"},
        methods = method_schema,
        priority = {type = "integer", default = 0},
        plugins = _M.plugins,
        -- ...
    },
    -- oneOf / required / dependencies 等约束
}
JSON Schema 是"数据的合同" JSON Schema 是一套标准，用来声明"一个 JSON 对象允许有哪些字段、什么类型、哪些必填、取值范围"。比如 uri 必须是 string、priority 是 integer 默认 0。校验器拿配置对照 schema 检查，不符就报错。好处：声明式（不用写一堆 if 校验代码）、标准化（前后端/文档共用）、自带默认值填充。上一站 wasm-go/Higress Console 的插件配置也用 JSON Schema——网关界的通用语言。
L03

core.schema.check

core/schema.lua:59 的 check(schema, json) 是校验入口：拿 schema 和数据，返回是否合法 + 错误信息。底层用 jsonschema 库（Lua 的 JSON Schema 实现，会把 schema"编译"成校验函数）。

读法：check 被到处调用：Admin API 存对象前校验、插件加载配置时校验（plugin.check_schema）、consumer 凭据校验……一个统一的校验函数，配上各处的 schema 定义,覆盖了整个配置系统。
L04

schema_def 复用片段

schema_def.lua 定义了很多可复用的 schema 片段：host_def（:50）、ip_def（:69）、uri_def（:72，带正则 pattern）、label_value_def、health_checker（:300）、method_schema…

schema 也讲 DRY "合法的 host""合法的 IP""合法的健康检查配置"这些片段被 route/service/upstream 反复用到。定义一次（如 host_def），到处引用——改一处全生效。比如 uri_def（:72）用一个正则严格限制 uri 格式，所有用到 uri 的地方共享这个约束。schema 片段化让配置校验既严格又不重复。
L05

插件的 schema

每个插件（apisix/plugins/*.lua）都定义自己的 schema（该插件接受哪些配置）。插件加载/配置时用 core.schema.check 校验用户填的插件配置。

-- 插件文件里（如 limit-count.lua）
local schema = {
    type = "object",
    properties = {
        count = {type = "integer", exclusiveMinimum = 0},
        time_window = {type = "integer", exclusiveMinimum = 0},
    },
    required = {"count", "time_window"},
}
读法：插件自带 schema，让"配 limit-count 但漏填 count"这种错误在配置阶段就被拒。Day 11 会看到 plugin.check_schema 怎么用它。这套 schema 还能自动生成插件文档/前端表单（呼应上一站 Console 的动态表单）。
L06

Admin 校验

Admin API（Day 17）在把对象写进 etcd 前，用对应 schema 校验。apisix/admin/ 下每种资源（routes/services/upstreams…）都有校验逻辑，不合法返回 400 + 具体哪个字段错。

"写入时校验"是关键位置 校验放在 Admin API（写入端），而不是读取端（请求处理）——因为 etcd 里的配置应该永远是合法的。守住写入这道门，读取时就不用再校验，省性能。好比"入库时质检合格，出库时直接用"。所以你调 Admin API 建一条非法路由会立刻被拒，坏配置进不了 etcd。
L07

编译缓存

jsonschema 库会把 schema"编译"成一个 Lua 校验函数（比每次解释 schema 快）。APISIX 缓存这些编译结果，同一个 schema 只编译一次。

读法：schema 校验虽然主要在写入时（不那么频繁），但插件配置变更、consumer 校验也会用到，编译缓存避免重复编译开销。这又是 APISIX "把重复计算缓存起来"的一贯风格（对比 Day 05 的变量缓存、Day 06 的路由预处理）。
