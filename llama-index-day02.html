核心数据结构 Node

LlamaIndex 里流动的一切数据都是 Document/Node。今天精读 schema.py——BaseNode/TextNode/Document 的字段、metadata 的巧妙设计、以及 Node 之间的"关系"。这是全框架的数据基石。

L01

一切皆 Node

schema.py 定义了继承链：BaseComponent（:81）→ BaseNode（:264）→ Node（:638）/TextNode（:765）→ ImageNode/IndexNode/Document（:1097）。

Document 和 Node 的关系 Document = 一份完整的原始文档（一个 PDF、一个网页）。Node = 从 Document 切出来的一小块（一段话）。有趣的是 Document 其实继承自 Node（:1097 class Document(Node)）——它就是"一个特殊的大 Node"。整个 RAG 流程就是"Document → 切成一堆 Node → Node 向量化存储 → 检索出 Node → 喂给 LLM"。所以理解 Node 就是理解数据怎么流动。
L02

BaseNode 字段

schema.py:264-302：

class BaseNode(BaseComponent):
    id_: str = Field(default_factory=lambda: str(uuid.uuid4()))  # 唯一 ID
    embedding: Optional[List[float]] = None      # 向量（嵌入后填充）
    metadata: Dict[str, Any] = Field(default_factory=dict, alias="extra_info")  # 元数据
    excluded_embed_metadata_keys: List[str] = []  # 嵌入时排除的元数据键
    excluded_llm_metadata_keys: List[str] = []     # 给 LLM 时排除的元数据键
    relationships: Dict[NodeRelationship, RelatedNodeType] = {}  # 与其他 Node 的关系
读法：核心四样：id_（唯一标识）、embedding（向量，Day 06 填）、metadata（元数据，如来源文件名/页码）、relationships（Node 间关系，L06）。用 Pydantic（BaseModel）定义——类型安全、能序列化存储。
L03

metadata 三种视图（精妙）

那两个 excluded_*_metadata_keys 和 MetadataMode（schema.py:242：ALL/EMBED/LLM/NONE）配合，实现"同一份 metadata、不同场景看到不同内容"：

class MetadataMode(str, Enum):
    ALL = "all"; EMBED = "embed"; LLM = "llm"; NONE = "none"
# node.get_content(metadata_mode=MetadataMode.EMBED)  → 嵌入时看到的文本（含部分 metadata）
# node.get_content(metadata_mode=MetadataMode.LLM)    → 给 LLM 时看到的文本
为什么 metadata 要分场景？ 一个 Node 的 metadata 里有很多字段（文件名、页码、创建时间、URL…）。但不同场景需要的不一样：嵌入（算向量）时可能只想带"标题"（帮助语义匹配），不想带"创建时间"（干扰）；给 LLM 时想带"文件名"（好溯源），不想带内部 ID。所以用 excluded_embed_metadata_keys/excluded_llm_metadata_keys 分别排除。get_content(metadata_mode=...) 按场景生成"该看到的文本"——同一个 Node，嵌入模型、LLM、纯文本各看到不同版本。这是 LlamaIndex 对 metadata 的精细控制，直接影响检索质量。
L04

TextNode

schema.py:765-800：最常用的 Node 类型，装文本：

class TextNode(BaseNode):
    text: str = ""                          # 文本内容
    mimetype: str = "text/plain"
    start_char_idx / end_char_idx           # 在原文档里的字符位置（切块后记录）
    text_template: str = DEFAULT_TEXT_NODE_TMPL  # {metadata_str} + {content} 模板
start/end_char_idx 有什么用？ 切块时记录"这块文本来自原文档的第几到第几个字符"。这样检索到某个 Node 后，能精确定位它在原文的位置——用于溯源、高亮、或取上下文。text_template 定义"文本怎么和 metadata 拼在一起"（给 LLM 看的格式）。注意新版把内容存进 text_resource（MediaResource），TextNode 保留 text 属性做兼容（:768-776）——支持多模态（文本/图片/音频）的演进。
L05

Document

schema.py:1097 class Document(Node)——一份原始文档。构造函数（:1104+）做了大量向后兼容：doc_id→id_、extra_info→metadata、text→text_resource。

为什么这么多兼容代码？ LlamaIndex 迭代很快，早期用 doc_id/extra_info/text，新版改成 id_/metadata/text_resource（支持多模态）。但不能破坏老用户的代码——所以构造函数里"如果你传老字段名，自动转成新的 + 警告"。这是成熟框架的向后兼容责任（回想 wasm-go 的新旧 API、APISIX 的 v3_adapter）。Document 就是"你用 Reader 读进来的东西",接下来要被切成 Node。
L06

Node 之间的关系

schema.py:207-224 的 NodeRelationship：

class NodeRelationship(str, Enum):
    SOURCE    # 这个 Node 来自哪个 Document（溯源）
    PREVIOUS  # 上一个 Node（同文档里的顺序）
    NEXT      # 下一个 Node
    PARENT    # 父 Node（层级结构）
    CHILD     # 子 Node

BaseNode 提供 source_node/prev_node/next_node/parent_node/child_nodes 属性（:398-445）访问。

关系让 Node 不是"孤岛" 切块后，Node 之间要保留联系：SOURCE 记住"我来自哪份文档"（溯源）；PREV/NEXT 记住"我在原文的前后块"（检索到一块时能取相邻块补充上下文，如 sentence-window 检索）；PARENT/CHILD 支持层级（大块套小块，如 auto-merging 检索）。这些关系用 RelatedNodeInfo（:249，存 node_id + type + hash）表达。高级检索策略（取上下文窗口、层级合并）全靠这些关系。
L07

NodeWithScore

schema.py:1035 的 NodeWithScore：一个 Node + 一个相似度分数。检索器返回的就是它。

读法：检索（Day 11）不只返回 Node，还带"这个 Node 和查询有多相关"的分数（相似度）。NodeWithScore = {node, score}。后处理（Day 14 重排/过滤）就是操作这些分数——比如"只保留 score > 0.7 的"、"按分数重新排序"。它是检索结果的标准载体。
