03

Higress 与 Istio 的血缘

Higress 是"瘦身魔改版"的 Istiod

Higress 控制面本质是一个改造过的 Istio Pilot：去掉 mTLS、CA、Sidecar Injector 等不必要模块，专心做 xDS 配置生成。它通过 vendoring（内嵌依赖）的方式把 Istio 关键代码拷贝到 istio/ 目录，再用 go.mod 的 replace 指令重定向。

证据 1：bootstrap 大量 import istio

// pkg/bootstrap/server.go
import (
    "istio.io/istio/pilot/pkg/config/aggregate"
    "istio.io/istio/pilot/pkg/model"
    "istio.io/istio/pilot/pkg/server"
    kubecontroller "istio.io/istio/pilot/pkg/serviceregistry/kube/controller"
    "istio.io/istio/pilot/pkg/xds"            // ← Istio 的 xDS 服务端，直接复用
    ...
)

证据 2：go.mod replace 指向本地 istio/

查看根目录 go.mod，会看到大量类似 replace istio.io/istio => ./istio/istio 的指令，意思是"虽然 import 路径写的是 istio.io/istio，但实际编译用我本地裁剪过的副本"。这让 Higress 可以小步快跑地修改 Pilot 而不必等上游合并。

三方分工示意

┌─────────────────────────────────────────────────────────────┐
│                    Higress 控制面 (this repo)               │
│  pkg/ingress  →  生成 VirtualService / DestinationRule …    │
│         │                                                   │
│         ▼                                                   │
│  istio/istio (vendored Pilot)                               │
│  ├─ pilot/pkg/config         配置聚合                       │
│  ├─ pilot/pkg/xds            ADS gRPC server                │
│  └─ pilot/pkg/model          ServiceRegistry / Push 模型     │
│         │   gRPC ADS                                        │
│         ▼                                                   │
│  Envoy 数据面 (envoy/)  ←─── 加载 Wasm plugin (plugins/)    │
└─────────────────────────────────────────────────────────────┘

对阅读者的影响

  • 读源时遇到 istio.io/istio/... import 不要跳走，IDE 会跳到 ./istio/istio/... 本地副本。
  • 不需要先看完整本 Istio 源码——Higress 用到的核心 5 个包：pilot/pkg/{config,xds,model,server,serviceregistry}。
  • Higress 自己定义的 CRD（Ingress 注解扩展、McpBridge、WasmPlugin）通过自己的 ConfigStore 注入到 Pilot Push 流程里。
04

数据面 Envoy 与 xDS

数据面长什么样

Higress 数据面是一个 定制化 Envoy：基于上游 Envoy，加入了几个自研 HTTP Filter 与扩展（部分写在 envoy/envoy 子模块、部分编译进官方镜像）。运行时它通过 gRPC 连到控制面，按 ADS (Aggregated Discovery Service) 增量拉取配置。

xDS 资源四件套

资源对应 K8s 概念由谁生成
LDS · ListenerHTTPS:443 / HTTP:80 监听Gateway / Listener 配置
RDS · RouteIngress rules + 注解VirtualService（由 IngressConfig 翻译）
CDS · ClusterK8s Service / 注册中心服务DestinationRule + ServiceEntry
EDS · EndpointPod IP 列表kube ServiceRegistry / registry/*

配置下发链路

K8s API Server      Nacos / ZK / Consul
      │                     │
      ▼                     ▼
 kube Informer        registry/*.watcher
      │                     │
      └────────┬────────────┘
               ▼
  pkg/ingress/config.IngressConfig     ← 这是核心翻译器
               │ (生成 VirtualService / DestinationRule / EnvoyFilter)
               ▼
  istio pilot ConfigStoreCache
               │
               ▼
  pilot/pkg/xds Server （ADS gRPC）
               │
               ▼
        Envoy 数据面

Envoy 侧的特殊扩展

  • Wasm HTTP Filter：标准上游能力，用来加载 plugins/wasm-go/extensions/* 编译出的 .wasm。
  • Higress 自研 Go Filter：plugins/golang-filter，走 Envoy Go Extension 路线（非 Wasm，性能更好但需重编 Envoy）。
  • External Processing / ext-authz：标准 Envoy filter，被 ext-auth 插件复用。
05

main.go 启动入口

整个 main.go 只有 32 行

// cmd/higress/main.go
package main

import (
    "fmt"
    "os"

    "istio.io/pkg/log"
    "github.com/alibaba/higress/v2/pkg/cmd"
)

func main() {
    log.EnableKlogWithCobra()
    if err := cmd.GetRootCommand().Execute(); err != nil {
        _, _ = fmt.Fprintln(os.Stderr, err)
        os.Exit(1)
    }
}

三个关键点

  1. log.EnableKlogWithCobra()：把 K8s 客户端的 klog 接入 Istio 的日志库 + Cobra 的 flag 系统，从而 --log_output_level=debug 这类 flag 能透传到 client-go。
  2. cmd.GetRootCommand()：所有真正逻辑都在 pkg/cmd，main 只是一个 thin shell——这是 Go 项目的常见做法（参考 kubectl / istioctl）。
  3. 错误返回 → 退出码：标准 12-factor 实践，所有 fatal 错误统一从 Execute() 冒泡。

思考题

为什么 main.go 不直接 import pkg/bootstrap？把启动逻辑放进 pkg/cmd 而不是 main 包带来了哪些好处？（提示：可测试性 / 多子命令复用）

Cobra 命令体系

命令树

查看 pkg/cmd，根命令下挂了若干子命令（不同版本略有差异）：

higress
├── serve            # 启动控制面 (主用)
├── version          # 输出版本信息
└── ...              # debug / completion 等

真正驱动控制面运行的是 higress serve，它的 RunE 最终调用 bootstrap.NewServer(args).Start(stop)。

flag 设计哲学

Higress 沿用了 Istio Pilot 的 ServerArgs 结构体：把所有可配置项收敛到几个 Options 结构体里（XdsOptions、RegistryOptions 等），命令层只负责把 Cobra flag 写到这些结构体里。这种"参数对象模式" 让 server 包可被库式调用（也方便单元测试）。

type ServerArgs struct {
    XdsOptions      XdsOptions
    RegistryOptions RegistryOptions
    KeepaliveOptions *keepalive.Options
    HTTPAddr        string
    GRPCAddr        string
    Namespace       string
    GatewaySelectorKey   string
    GatewaySelectorValue string
    // ...
}

读源动作

  1. 在 IDE 里搜 GetRootCommand()，向下读 3 层。
  2. 找到 serve 子命令的 RunE，定位到 bootstrap.NewServer。
  3. 记住 ServerArgs 的字段——后面 Server 初始化都围绕它展开。
07

Server 初始化全景（pkg/bootstrap/server.go）

主线 6 步（NewServer / Start）

  1. kube client 初始化：基于 in-cluster 或 kubeconfig 创建 istiokube.Client。
  2. Mesh Config Watcher：复用 Istio 的 meshwatcher，监听 mesh config 变化。
  3. ConfigController 聚合：用 configaggregate 把多个 ConfigStore（K8s CRD + Ingress + WasmPlugin + McpBridge）合并成一个。
  4. ServiceRegistry 聚合：aggregate.Controller + kube + registry/* 多注册中心。
  5. Discovery Server（xDS）：构造 xds.NewDiscoveryServer，注册到 gRPC server。
  6. 启动一组 goroutine：HTTP debug、gRPC ADS、Cert manager、Ingress translator 等。

关键代码定位

// pkg/bootstrap/server.go
type Server struct {
    server.Instance              // 复用 Istio server.Instance 做 lifecycle
    XDSServer       *xds.DiscoveryServer
    kubeClient      kube.Client
    environment     *model.Environment
    configController model.ConfigStoreController
    serviceEntryController serviceregistry.Instance
    // ...
}

func NewServer(args *ServerArgs) (*Server, error) {
    s := &Server{...}
    if err := s.initKubeClient(args); err != nil { return nil, err }
    if err := s.initConfigController(args); err != nil { return nil, err }
    if err := s.initRegistryEventHandlers(args); err != nil { return nil, err }
    if err := s.initDiscoveryService(args); err != nil { return nil, err }
    if err := s.initCertManager(args); err != nil { return nil, err }
    // ...
    return s, nil
}

初学者的阅读顺序

  • 先看 NewServer 的整体骨架（约 80 行），把每个 init 函数当黑盒。
  • 再展开 initConfigController——这是 Higress 自己的 IngressConfig 注入点（第 10 讲）。
  • 最后看 Start(stop) 怎么把所有 controller 拉起来：s.server.RunComponent。

易踩坑

不要被 krt（Kubernetes Resource Tracker）相关 import 吓到——这是 Istio 1.20+ 引入的新式 Informer 框架。Higress 部分代码已用 krt，部分仍是老式 Informer，混用时要看具体 controller。

08

K8s Client 封装（pkg/kube/client.go）

为什么要再封装一层

Higress 的客户端需要同时访问：

  • 原生资源（Service、Endpoints、Ingress、Secret、ConfigMap）
  • Knative kingress
  • Higress 自定义 CRD：McpBridge、WasmPlugin、Http2Rpc、McpServer 等
  • Istio CRD：VirtualService、DestinationRule、EnvoyFilter

所以 pkg/kube/client.go 在 istiokube.Client 之上又包了一层，统一管理多 CRD 客户端。

client/ 目录

所有 Higress 自定义 CRD 的 typed client / lister / informer 都通过 code-generator 自动生成在 client/ 目录下，规范跟 K8s 官方一样：

client/
├── clientset/versioned/        # typed clientset
├── informers/externalversions/ # SharedInformer 工厂
└── listers/                    # 各资源 Lister

这些代码是不需要读的，会用 NewForConfig / NewSharedInformerFactory 即可。

读源建议

记住一句话："controller 拿数据 → 走 Lister，监听变化 → 走 Informer.AddEventHandler"。这是后面所有 ingress / wasmplugin / mcpbridge controller 的统一姿势。

09

Ingress Controller 模型

多版本兼容

pkg/ingress/kube/ 下针对不同 K8s Ingress 版本各有一个 controller：

  • ingress/：extensions/v1beta1（老集群兼容）
  • ingressv1/：networking.k8s.io/v1（主流）
  • kingress/：Knative Ingress
  • gateway/：Gateway API（HTTPRoute 等）

它们对外暴露统一的 common.IngressController 接口（见 kube/common），上层翻译器对接口编程。

典型 controller 骨架

type controller struct {
    informer cache.SharedIndexInformer
    lister   networkinglister.IngressLister
    queue    workqueue.RateLimitingInterface
    handlers []common.IngressHandler   // 上游回调
}

func (c *controller) Run(stop <-chan struct{}) {
    go c.informer.Run(stop)
    if !cache.WaitForCacheSync(stop, c.informer.HasSynced) { return }
    wait.Until(c.worker, time.Second, stop)
}

func (c *controller) worker() {
    for c.processNextItem() {}
}

标准的 K8s Controller "Informer + Workqueue + Reconcile" 三件套，没有惊喜。重点是 handlers 列表——IngressConfig 会注册回调，把 K8s 资源事件转成内部翻译动作。

多集群支持

Higress 支持 multi-cluster：每个集群一个 controller 实例，由 common.AggregateController 聚合。这就是为什么很多接口签名里都有 clusterId 这个参数。

IngressConfig 主转换器（2085 行）

位置与定位

pkg/ingress/config/ingress_config.go，Higress 控制面最复杂的一个文件，2000 多行。它实现了 Istio 的 model.ConfigStoreController 接口，对外伪装成一个普通的 ConfigStore：Pilot 想要 VirtualService，它就当场基于 Ingress + 注解 + 注册中心数据合成一份。

核心方法

// 简化后的接口
type IngressConfig struct {
    remoteIngressControllers map[string]common.IngressController
    mcpbridgeController       mcpbridge.McpBridgeController
    wasmPluginController      wasmplugin.WasmPluginController
    http2rpcController        http2rpc.Http2RpcController
    annotationHandler         annotations.AnnotationHandler
    namespace                 string
    // ...
}

func (m *IngressConfig) List(typ config.GroupVersionKind, namespace string)
    ([]config.Config, error)

func (m *IngressConfig) RegisterEventHandler(
    kind config.GroupVersionKind,
    handler model.EventHandler)

当 Pilot xDS 推送时，会调用 List(VirtualService)、List(DestinationRule)、List(EnvoyFilter)。IngressConfig 在这三个回调里实时合成结果。

合成 VirtualService 的关键步骤

  1. 遍历所有 IngressController 拿到 IngressV1 列表。
  2. 对每条 Ingress：
    • 调用 annotationHandler.Parse(ingress) 解析注解 → 得到 Ingress.Annotations 对象。
    • 对每条 rule + path 生成一条 HTTPRoute。
    • 把注解里的灰度 / 重写 / 限流 / CORS 等转成 HTTPRoute 字段或额外的 EnvoyFilter。
  3. 按 host 合并多条 Ingress 生成的 HTTPRoute → 一份完整 VirtualService。
  4. 把结果缓存，并通过 EventHandler 通知 xDS 触发 Push。

设计精髓

这种"把 K8s 资源动态翻译成 Istio API"的做法，避免了让用户手写 VirtualService，又复用了整套 Istio Pilot 推送链路——这是 Higress 架构上最聪明的一步。

阅读建议

  • 不要顺序读完，按需要按方法读：List → 找到 case 分支 → 跳到对应合成函数。
  • 结合 ingress_config_test.go 里的 case 输入输出对照理解最快。

Annotation 解析器框架

30+ 注解，统一接口

位于 pkg/ingress/kube/annotations/，每个能力（canary、cors、ip 黑白名单、限流、重写、JWT、负载均衡、destination …）一个文件，都实现 interface.go 里的 Parser 与 Handler 接口。

// 简化
type AnnotationsParser interface {
    Parse(annotations Annotations, config *Ingress, globalContext *GlobalContext) error
}

type Annotations map[string]string

// 中心入口
type AnnotationHandler interface {
    Parse(meta metav1.ObjectMeta) (*Ingress, error)
    ApplyRoute(route *networking.HTTPRoute, ingress *Ingress)
    ApplyCluster(cluster *networking.DestinationRule, ingress *Ingress)
    ApplyGateway(gw *networking.Gateway, ingress *Ingress)
}

责任链 + 访问者

核心数据结构是 Ingress（解析结果聚合体），各 Parser 把自己的字段填进去；之后调用 Apply 系列把内容写入对应的 Istio 资源。"Parser 写入 / Applier 输出" 两阶段，清晰隔离了"读注解"和"产配置"。

典型例子：canary

annotations/canary.go 解析 higress.io/canary、canary-weight、canary-by-header 等注解；最后由 ApplyRoute 把它转成 HTTPRoute.Route[*].Weight 或 Match.Headers。

扩展思路

若要支持一个新注解，只需：
① 新建 annotations/myfeat.go 实现 Parser；
② 在 annotations.go 的注册列表中添加；
③ 决定它影响 Route / Cluster / Gateway 中的哪一个，在对应 Apply 处补一行。
整个扩展过程不需要碰 IngressConfig。

McpBridge 与 registry/

McpBridge 是什么

K8s Ingress 默认只能路由到 K8s Service。但企业里大量服务注册在 Nacos / ZK / Consul / Eureka 上。McpBridge 是 Higress 自定义的 CRD，描述"从某个注册中心拉服务，注入到 ServiceRegistry"。一个集群通常只有一个 McpBridge 单例（namespace 内）。

CRD 示例

apiVersion: networking.higress.io/v1
kind: McpBridge
metadata:
  name: default
  namespace: higress-system
spec:
  registries:
    - name: my-nacos
      type: nacos2
      domain: nacos.example.com
      port: 8848
      nacosNamespaceId: public
      nacosGroups: [DEFAULT_GROUP]

代码路径

pkg/ingress/kube/mcpbridge/controller.go    # 监听 McpBridge CRD
registry/                                   # 真正的协议实现
├── reconcile/                              # ★ 总协调器
├── memory/                                 # 内存版 ServiceRegistry
├── nacos/、consul/、zookeeper/、eureka/、direct/

工作流

  1. McpBridge controller 监听 CRD 变更。
  2. 把 spec.registries 列表交给 registry/reconcile。
  3. Reconcile 对每个 registry 创建/销毁对应 watcher（Nacos / ZK / …）。
  4. 各 watcher 拉到的服务实例写入共享的 memory.ServiceRegistry。
  5. 这个 ServiceRegistry 被注册到 bootstrap 的 aggregate.Controller，最终通过 EDS 推给 Envoy。
14

Nacos / ZK / Consul 接入

统一接口：Watcher

registry/watcher.go 定义了所有注册中心适配器的统一接口：

type Watcher interface {
    Run()
    Stop()
    IsHealthy() bool
    GetRegistryType() string
    ReadyHandler(func(bool))
    AppendServiceUpdateHandler(func(*v1.ServiceEntry, model.Event))
}

每种实现都把"注册中心事件 → Istio ServiceEntry"作为统一输出，这样上游不关心后端是 Nacos 还是 ZK。

Nacos 实现要点

  • registry/nacos/ 同时支持 Nacos 1.x / 2.x（两套 SDK）。
  • 核心动作：登录 → 订阅 Service / Instance 变更 → 把 instance list 组装成 ServiceEntry.Spec.Endpoints。
  • 关注 namespace、group、cluster 的多维度过滤。

ZK 实现要点

  • 位于 registry/zookeeper/，主要适配 Dubbo 的路径协议（如 /dubbo/{serviceName}/providers/{url}）。
  • 需要把 Dubbo URL 解析成 host:port + metadata，然后写入 ServiceEntry。

扩展提示

想新增一种注册中心：在 registry/ 下新建包，实现 Watcher，并在 reconcile/ 工厂里注册即可，不必触碰任何 ingress 代码。这是"开闭原则"的典型应用。

WasmPlugin CRD 加载链路

从 YAML 到 Envoy

Higress 的 WasmPlugin CRD 设计借鉴并扩展了 Istio 同名 CRD。完整链路：

用户 kubectl apply 一份 WasmPlugin YAML
            │
            ▼
pkg/ingress/kube/wasmplugin/controller.go   # Informer 监听
            │
            ▼
pkg/ingress/config/ingress_config.go        # 合并到 EnvoyFilter / WasmPlugin 输出
            │
            ▼
istio pilot xds  →  ADS 推到 Envoy
            │
            ▼
Envoy HTTP Wasm Filter 加载 .wasm 镜像 (OCI / HTTP / local)
            │
            ▼
ai-proxy / ai-cache / ... 真正执行业务逻辑

关键字段

字段含义
spec.url.wasm 镜像地址（支持 oci:// / http:// / file://）
spec.imagePullSecretOCI 拉取凭证
spec.phase插入位置：AUTHN / AUTHZ / STATS / UNSPECIFIED
spec.priority同 phase 内的执行顺序
spec.defaultConfig插件全局配置
spec.matchRules按域名 / 路由覆盖配置（Higress 扩展）

动态加载

Envoy 端会异步从 url 拉取 .wasm，拉到后用 proxy-wasm ABI 加载。运行时插件被沙箱化在 V8/WAVM 里，崩溃不影响 Envoy 主进程——这就是 Wasm 相对 native filter 的最大价值。

16

wasm-go SDK 设计

分层

开发一个 Higress Wasm 插件，依赖的 SDK 分两层：

  • 下层：proxy-wasm-go-sdk（上游 tetratelabs 维护），实现 proxy-wasm ABI。
  • 上层：plugins/wasm-go/pkg/wrapper（Higress 自己写），把生命周期抽象成 OnHttpRequestHeaders / OnHttpRequestBody / OnHttpResponseHeaders / OnHttpResponseBody 等高层回调，并自带 JSON / gjson 配置解析。

典型插件骨架

type MyConfig struct {
    Key string `json:"key"`
}

func main() {
    wrapper.SetCtx(
        "my-plugin",
        wrapper.ParseConfig(parseConfig),
        wrapper.ProcessRequestHeaders(onHttpRequestHeaders),
    )
}

func parseConfig(json gjson.Result, config *MyConfig, log wrapper.Log) error {
    config.Key = json.Get("key").String()
    return nil
}

func onHttpRequestHeaders(ctx wrapper.HttpContext, config MyConfig, log wrapper.Log) types.Action {
    proxywasm.AddHttpRequestHeader("x-my-plugin", config.Key)
    return types.ActionContinue
}

极简：插件作者只需关心配置 schema + 回调函数。SDK 完成所有与 Envoy 的 ABI 交互。

调用第三方服务的能力

SDK 提供 wrapper.HttpCall / wrapper.RedisCall 等异步外呼接口（Envoy 通过 Cluster 转发），这让插件可以做 ext-auth、ai-rag 等需要回查后端的业务，而不阻塞主请求线程。

ai-proxy 多模型代理

定位

plugins/wasm-go/extensions/ai-proxy 是 Higress AI 网关最核心的插件：把任意 LLM 的"原生 API"统一抽象成 OpenAI 兼容协议对外暴露；对内根据 provider 类型转发到对应大模型供应商（OpenAI / Azure / 通义千问 / 文心 / Claude / DeepSeek / Gemini / Moonshot …）。

目录结构

extensions/ai-proxy/
├── main.go                # 注册插件回调
├── config.go              # provider 配置 schema
├── provider/              # 各厂商适配器
│   ├── provider.go        # 接口定义 + 工厂
│   ├── openai.go
│   ├── azure.go
│   ├── qwen.go
│   ├── claude.go
│   ├── gemini.go
│   ├── deepseek.go
│   └── ...
└── README.md

核心接口

type Provider interface {
    GetProviderType() string
    OnRequestHeaders(ctx, apiName, log) error
    OnRequestBody(ctx, apiName, body, log) (types.Action, error)
    OnResponseHeaders(ctx, apiName, log) (types.Action, error)
    OnStreamingResponseBody(ctx, apiName, chunk, isLastChunk, log) ([]byte, error)
    OnResponseBody(ctx, apiName, body, log) (types.Action, error)
}

每个厂商一个 provider 实现，负责：① 改写 path / host（路由到对应 upstream Cluster）；② 转换请求体（OpenAI schema → 厂商 schema）；③ 转换响应体（含 SSE 流式）；④ 处理 token 计数、错误归一化。

典型流

  1. 客户端发 POST /v1/chat/completions（OpenAI 协议）。
  2. ai-proxy 在 OnRequestHeaders 阶段根据 model 字段或显式 provider 选择 Provider 实例。
  3. OnRequestBody 把请求体改写成目标厂商需要的格式，并通过 proxywasm.SetRouteName / 改写 cluster 让 Envoy 转发到正确 upstream。
  4. 响应回来后再反向转换成 OpenAI SSE 格式。

与其它 AI 插件协同

ai-proxy 只做协议转换。配合：

  • ai-token-ratelimit：按 token 限流
  • ai-cache：语义/精确缓存
  • ai-rag：召回 + 注入上下文
  • ai-security-guard：内容安全审核

这些插件通过 spec.phase 与 priority 串成一条 AI 处理流水线，相互独立、可独立启用。

MCP Server 托管

背景

Model Context Protocol（MCP）由 Anthropic 推出，定义了一套"工具/资源"对 LLM 暴露的协议。Higress 把 MCP Server 当作一等公民：用户可以在网关里直接挂载 MCP Server，让任意 LLM 客户端通过 Higress 调用工具。

双线实现

位置用途
pkg/ingress/kube/mcpserver/K8s 侧 CRD 控制器，监听 McpServer 资源
pkg/ingress/mcp/MCP（Mesh Config Protocol，注意名字撞车）配置下发
plugins/wasm-go/extensions/mcp-routerWasm 插件，请求级路由到对应 MCP Server
plugins/wasm-go/mcp-servers/内建 MCP Server 实现（高德 / Notion / GitHub 等）

请求链路

LLM Client (SSE)
   │
   ▼
Higress Envoy  ← mcp-router(Wasm) 解析 jsonrpc method/params
                 → 选择目标 MCP Server upstream
   │
   ▼
mcp-server (Wasm) 或外部 MCP server 服务
   │
   ▼
后端工具（数据库 / API / 内部服务）

读源建议

MCP 这部分迭代最快，以 plugins/wasm-go/mcp-servers/ 下的具体实现为锚点反推 SDK 抽象 是最快的方式，不要先啃协议规范。

证书管理 pkg/cert

能力

  • 自签 CA：测试场景一键签发。
  • ACME（Let's Encrypt）：基于 HTTP-01 自动签发与续签。
  • Secret 存储：证书最终落到 K8s Secret（被 Envoy SDS / Istio 引用）。

主要文件

文件职责
certmgr.go对外的 CertManager，调度续签
config.goACME / 自签配置 schema
controller.go监听 Ingress / Secret 变化，触发签发
server.goACME HTTP-01 挑战 server
storage.go证书持久化到 ConfigMap / Secret
ingress.go把证书 binding 注入到 Ingress / Gateway

触发链路

  1. 用户写 Ingress 时指定 host。
  2. CertController 检测到该 host 没有对应 Secret。
  3. CertManager 起 ACME flow：注册账号 → 申请 order → HTTP-01 挑战 server.go 响应 token → 拿到证书 → 写入 Secret。
  4. Higress Gateway 通过 SDS 加载该 Secret，自动启用 HTTPS。

学习路线复盘

回答开篇 3 问

  1. Higress 与 Istio 的关系：Higress 是基于 Istio Pilot 的"瘦身魔改版"，通过 vendoring + replace 让自己拥有完全控制权，专注于 Ingress / Gateway / AI 网关场景。
  2. 一条 Ingress 怎么变 Envoy 配置：Ingress Informer → IngressConfig（含 Annotation 解析、注册中心数据合并）→ 合成 Istio VirtualService / DestinationRule / EnvoyFilter → 被 Pilot ConfigStoreCache 消费 → xDS ADS 推到 Envoy。
  3. AI 网关能力的位置：核心写在 plugins/wasm-go/extensions/ai-*，全部以 Wasm 插件形态挂在 Envoy HTTP Filter 链路上；控制面只负责 WasmPlugin CRD 的下发与配置覆盖。

能力对应讲次验证方法

下一步可以做什么

  • 给 ai-proxy 加一个新模型 provider（参考已有的 deepseek.go / moonshot.go）。

  • 研读 e2e 测试 test/e2e 的搭建方式，理解 Higress 是怎么自我验证端到端行为的。
