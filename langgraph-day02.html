Day 02 / 共 20 天 · 第 1 周 核心概念

StateGraph：节点 + 边 + 状态

第一个核心概念。读 graph/state.py：StateGraph 的三件套（State/Node/Edge）、add_node/add_edge、Builder 模式、compile 产出什么。

L01

三件套（源码 docstring 说得最清楚）

StateGraph（state.py:130）的 docstring 一句话定义："A graph whose nodes communicate by reading and writing to a shared state. The signature of each node is State -> Partial<State>."

  • State（共享状态）：一个带类型的字典（TypedDict），整张图的"共享白板"，所有节点读它、往它写。
  • Node（节点）= 一个函数：签名 State → Partial<State>——读状态、返回"要更新哪些字段"的局部字典。
  • Edge（边）= 控制流：只决定"下一个轮到谁"，本身不搬运数据（数据都在共享 State 里）。
状态与控制流分离（核心设计） 传统写 Agent 是一堆 if/else + 手工传参，难中断、难重放、难可视化。LangGraph 把"状态"和"控制流"分开——状态集中在一个可序列化的 dict，控制流是显式的图。于是天然支持 checkpoint（存档）、断点续跑、并发、可视化。这个"数据在共享状态、边只管顺序"的分离是理解 LangGraph 的钥匙。
L02

节点 = 函数（返回局部更新）

# state.py:426 官方示例
def my_node(state: State, config: RunnableConfig) -> State:
    return {"x": state["x"] + 1}      # 只返回要改的键，不是完整状态
读法：节点读 state、返回 {"x": ...}——只更新 x 这一个键（partial state update），框架负责合并进完整状态（Day 03 的 reducer）。节点除了 state，还能按需接收 config/writer/store/runtime 等参数（_node.py:16 用 Protocol 穷举定义可选签名）。
"只返回局部更新"为什么好？ 节点只关心"我要改什么"，不用管整个状态怎么组装。比如聊天节点只返回 {"messages": [新回复]}，不用重建整段对话历史。框架用 reducer 把局部更新合并进全局状态（Day 03）。这让节点函数简单、聚焦、可复用——只做自己的事，合并交给框架。
L03

START / END 特殊节点

# constants.py:28
END = sys.intern("__end__")
START = sys.intern("__start__")
读法：START/END 不是真节点，是两个保留字符串常量。START="图的入口，用户输入从这灌进来"，END="到此停机"。不能把它们当普通节点名（state.py:794 会报 "Node is reserved"）。
L04

add_node

add_node（state.py:662）加一个节点。智能之处：

  • 节点名推断（:768）：直接传函数则取 __name__；也可 add_node("name", fn) 显式命名。
  • 输入 schema 推断（:803）：读函数第一个参数的类型注解作为该节点输入 schema。
  • 从返回类型推断出边（:826）：若返回类型标注 Command[Literal["a","b"]]，自动把 a/b 记为可能的目标（用于可视化/路由）。
节点最终被包装成 StateNodeSpec（_node.py:84）存进 self.nodes 字典。"约定优于配置"——节点名从函数名推断、出边从返回注解推断，少写样板。
L05

add_edge

add_edge（state.py:915）加普通边，两种形态：

builder.add_edge("a", "b")           # 直连：a 跑完就跑 b
builder.add_edge(["a", "b"], "c")    # 汇合：a 和 b 都跑完才跑 c（fan-in）
# 语法糖：
builder.set_entry_point("a")  # = add_edge(START, "a")
builder.set_finish_point("z") # = add_edge("z", END)
读法：单起点 = 直连边；多起点 add_edge(["a","b"], "c") = "等 a、b 都跑完才执行 c"（汇合/fan-in，存进 waiting_edges）。边只表达"顺序/依赖"，不传数据（数据在 State）。
边只管顺序、不传数据（再强调） 注意 add_edge("a", "b") 没有指定"a 的什么输出给 b"——因为数据不通过边传，而是都在共享 State 里。a 更新了 State 的某些键，b 直接从 State 读。边只是"a 跑完轮到 b"的控制信号。这和 eino/AutoGPT 的"边传数据"不同——LangGraph 是"共享状态 + 边只管顺序"。理解这点很关键。
L06

Builder 模式

StateGraph 只是"图纸"——不能直接跑（state.py:139 docstring 警告：必须先 .compile()）。所有 add_* 方法都 return self（:913），支持链式调用。

"图纸"vs"可执行" StateGraph 是可变的图纸——你往上加节点、加边。compile() 产出不可变的 CompiledStateGraph（真正能跑的）。分离"定义期"（可随意改图纸）和"运行期"（图定型、优化好、可反复高速执行）。这和 eino 的 Compile、AutoGPT 的图编译一个思想——建图时灵活、编译后高效不可变。return self 让你能 builder.add_node(...).add_edge(...).add_edge(...) 链式写。
L07

compile：图纸变可执行

compile()（state.py:1164）做几件事：

  1. validate()（:1116）：检查边指向的节点都存在、必须有从 START 出发的入口。
  2. 把每个 State 字段变成一个 channel（通道）（Day 07）。
  3. 构造 CompiledStateGraph，把节点/边"焊接"成 Pregel 计算图。
# state.py:1391 —— 关键类型关系
class CompiledStateGraph(Pregel[...], ...):   # ★ 编译产物就是一个 Pregel！
读法：CompiledStateGraph 继承自 Pregel——LangGraph 的执行引擎（Day 06）。Pregel 实现了 LangChain 的 Runnable 接口，所以编译后的图能 .invoke()/.stream()/.ainvoke()。你写的高层 StateGraph，编译后变成通用的底层 Pregel——一套引擎支撑多种上层 API。Day 09 会详看这个编译过程。
