流式输出

聊天界面里 AI 逐字蹦字、工具进度实时刷新——怎么做到的？读 stream_mode（types.py:120）的五种模式，理解 Day 08 驱动循环里的 yield 怎么变成用户看到的流。

L01

为什么要流式

🤔 痛点：invoke 要等全跑完，用户对着空屏干等 一个 Agent 可能想好几轮、调好几个工具，几十秒起步。用 invoke() 期间界面一片空白，用户以为卡死了。可我们明明每一步都已经算出了中间结果——为什么不能边算边给？

invoke() 要等整个图跑完才返回——长任务用户干等几十秒，体验差。stream() 让你边跑边拿中间结果：token 逐个出、每个节点完成即推送。

流式 = "边做边报告"，不是"做完才交卷" 想象点外卖：invoke 像"做好了一次性端上来"（中间你啥也看不到）；stream 像"下单成功→开始备餐→骑手取货→即将送达"实时推送。对 Agent 尤其重要——它可能要想好几轮、调好几个工具，几十秒起步。流式让用户看到"AI 正在查天气""正在计算"，甚至答案逐字蹦出，体验天差地别。这就是所有 AI 聊天产品都用流式的原因。
💡 本质：图执行是超步驱动，天然能在每步 yield 中间结果 Day 08 那个驱动循环本来就是"跑一个超步 → 产出 → 再跑下一个超步"。流式不是额外加的功能，而是把这些本就存在的中间产出按需 yield 出来。invoke 其实就是"把 stream 的产出收集起来、只返回最后一份"。
流式就像餐厅里厨师边炒边上菜：invoke 是"满汉全席全做完再一起端上桌"，你饿着等半天；stream 是"凉菜先上、热菜一道一道端"，你边吃边等，体感快得多。而厨房（引擎）本来就是一道道做出来的——流式只是把每做好一道就先端出去，而不是全压在最后。
L02

stream() API

for chunk in graph.stream(input, config, stream_mode="updates"):
    print(chunk)   # 每个超步/每个节点完成就吐一块，不用等全跑完

stream_mode（types.py:120-134）决定"吐什么粒度"，可传单个或列表（多模式混合）。

💬 小白 vs 老师 👶 小白：stream 比 invoke 快吗？总耗时是不是更短？
👨‍🏫 老师：总耗时几乎一样——图要跑的活没变少。stream 快的是"首次看到东西"的时间：invoke 要等全跑完（比如 20 秒）才有输出，stream 可能第 1 秒就开始蹦字。
👶 小白：那 invoke 是不是就没用了？
👨‍🏫 老师：不是。后台批处理、不需要给人看进度的场景，invoke 更省事。其实 invoke 内部就是把 stream 的产出收集起来只返回最后一份——它俩同源。
读法：stream() 返回一个生成器，用 for 循环边跑边收。stream_mode 是关键参数——同一次执行，选不同模式看到的"流"完全不同。下面逐个看五种模式。
图：values=整份状态 / updates=增量事件 / messages=LLM token，一次执行按需选
📝 例子：只想看"哪个节点在动" for chunk in graph.stream(inp, stream_mode="updates"): 每个节点跑完就吐一块 {节点名: 它的返回值}，用来做进度条或调试最直观——不像 values 每次都把整个 state 全量重发。
L03

values 模式

stream_mode="values"：每个超步后吐出完整的当前状态。

读法：每步给你"此刻整个 state 长啥样"。适合"我只关心最新完整状态"的场景（如每步都想渲染完整对话历史）。代价：数据量大（每次全量）。
L04

updates 模式

stream_mode="updates"：每个节点执行后，只吐出该节点做的增量更新（{节点名: 它的返回值}）。

for chunk in graph.stream(input, stream_mode="updates"):
    # {"agent": {"messages": [AIMessage(...)]}}   ← 谁更新了什么
    for node, update in chunk.items():
        print(f"{node} 更新了: {update}")
读法：values 给"全量状态"，updates 给"这步谁改了啥"（增量）。updates 更省、更能反映"哪个节点在动"——调试和进度展示的首选。values vs updates = 全量快照 vs 增量事件，按需选。
L05

messages 模式（逐 token）

stream_mode="messages"：吐出 LLM 生成的每个 token（配元数据），实现打字机效果：

for token, metadata in graph.stream(input, stream_mode="messages"):
    print(token.content, end="", flush=True)   # 逐字打印，像 ChatGPT 那样蹦字
读法：这就是聊天界面"逐字蹦字"的来源——它深入到 LLM 的 token 流。metadata 带节点名等信息（可区分是哪个节点的输出）。三种主力模式分工：values(全量)/updates(节点增量)/messages(token 级)。

单步走查：同一次执行（agent → tools → agent），三种模式每步各 yield 什么：

超步values（全量状态）updates（增量）messages（token）
agent①{messages:[Human, AI]}{"agent":{messages:[AI]}}"我" "去" "查"…逐字
tools{messages:[Human, AI, Tool]}{"tools":{messages:[Tool]}}（工具无 token，不吐）
agent②{messages:[…, AI2]}{"agent":{messages:[AI2]}}"北" "京" "晴"…逐字
⚠️ 小白常误以为 "messages 模式能拿到工具的输出 token"；其实 messages 只流 LLM 生成的 token，工具执行没有 token（看上表 tools 行为空）。想看工具进度得用 updates 或 custom。
L06

custom / debug 模式

模式吐什么
custom节点内用 get_stream_writer() 主动推送的自定义进度（如"已处理 30/100"）
debug最详尽的调试事件（任务开始/结束、检查点等）
custom = 你自己往流里塞消息 有时你想推送的不是状态、不是 token，而是你自定义的进度信息——比如工具在处理一个大文件，你想每处理 10% 就告诉前端。custom 模式让你在节点里用 get_stream_writer()("已完成 30%") 主动往流里塞任何东西。五种模式可以组合（传 list），一次 stream 同时拿到 token + 节点更新 + 自定义进度。
L07

yield 从何而来

回到 Day 08 的驱动循环：

while loop.tick():
    for _ in runner.tick(tasks, ...):
        yield from _output(...)     # ★ 这里！执行中的产出被 yield 出来
    loop.after_tick()
闭环回到引擎：你在 Day 08 见过这个 yield from _output(...) 却没深究。现在明白了：正是它把执行过程中的产出（按 stream_mode 过滤成 token/更新/状态）一块块 yield 给外层的 for chunk in graph.stream(...)。流式不是额外功能，而是驱动循环本来就在边跑边 yield——invoke 其实是"把 stream 的产出收集起来只返回最后一个"。理解引擎，流式就是顺理成章的产物。
