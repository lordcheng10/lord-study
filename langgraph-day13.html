时间旅行与断点

既然每步都存了检查点、还能 list 出历史（Day 12），那就能"读档到任意一步重新出发"。今天看时间旅行（time travel）和执行断点（breakpoint）。

📍 你在整门课的位置
Saver·threads→时间旅行→人在环→记忆·序列化
L01

时间旅行是什么

🤔 痛点：想调试"如果那步换个决定会怎样"Agent 在第 3 步做了个糟糕决策，后面全跑歪了。普通程序你只能改代码、从头再跑一遍——但 LLM 有随机性，重跑未必复现同一场景。你真正想要的是：回到第 3 步那一刻、只改那一个决定、其余不变地往下看。
💡 本质：checkpoint 链让"回到过去 + 重放"成为可能因为每步都存了完整快照、还靠 parents 串成链（Day 11），任意一个历史检查点都能被精确定位并加载。时间旅行 = 挑一个历史 checkpoint 当起点重新 tick；改写状态再重放就 fork 出一条"平行宇宙"，原历史不受影响。

时间旅行 = 回到某个历史检查点，从那里重新执行（可选：改一下状态再重跑）。用途：调试、"如果当时选另一条路会怎样"、从错误决策点纠偏。

游戏读档 + 改档重打 Day 11 说检查点像游戏存档。时间旅行就是"读取第 3 关的存档，重新从第 3 关打"——不是从头，也不是接着最新进度。更强的是：读档后你还能修改存档里的数据（比如给自己加满血）再重打（改写状态）。对 Agent 来说：LLM 在第 3 步做了个糟糕决策 → 回到第 3 步、手动改掉那个决策 → 让它从这里重新往下跑。这在传统"一次性跑完"的程序里根本做不到，是 LangGraph 检查点机制的独特红利。
L02

定位历史点

用 Day 12 的 get_state_history 列出所有历史检查点，每个 StateSnapshot（langgraph/types.py class StateSnapshot L643）的 config 里带一个 checkpoint_id——这就是"存档编号"：

回到 ckpt1、改写、再重放 → fork 出一条不影响原历史的新分支
history = list(graph.get_state_history(cfg))   # 新→旧
target = history[3]        # 想回到的那一步
target_cfg = target.config # {"configurable": {"thread_id":..., "checkpoint_id":"xxx"}}
读法：每个历史检查点都有唯一 checkpoint_id；带着它的 config 就是"指向那一步的地址"。Day 11 说过 checkpoint_id 单调递增可排序，所以历史是有序时间线。
L03

从历史点重跑

把带 checkpoint_id 的 config 传给 invoke，图就从那一步的状态继续（而不是从最新）：

graph.invoke(None, target_cfg)   # input=None：不给新输入，纯从该检查点续跑
读法：invoke 时 config 带了 checkpoint_id → 恢复阶段（Day 11 L07）加载的是那一个检查点而非最新 → 从那步的下一步开始跑。input 传 None 表示"不加新输入，就从存档点继续"。
🎮 第一人称之旅：假如"你"是一次被时间旅行的运行 ① 我本来一路跑到了 ckpt3（最新），停在那儿。
② 主人翻出历史，说"回到 ckpt1 那一刻"——他拿着我 ckpt1 的存档编号（checkpoint_id）叫 invoke(None, 那个config)。
③ 引擎没读最新的 ckpt3，而是把 ckpt1 的整份状态灌回我身上——我瞬间"失忆"回到第 1 关刚打完的样子。
④ 然后我从 ckpt1 的下一步重新往下跑。就像生活中读取旧存档重打这一关——ckpt3 那条线还在硬盘上，没被我抹掉。
L04

update_state 改写状态

update_state（main.py）在恢复前手动修改状态——本质是写一个 source="update" 的新检查点（Day 11 metadata）：

graph.update_state(target_cfg, {"messages": [AIMessage("改后的决策")]})
# 走的是 reducer！所以 add_messages 是追加，不是覆盖（Day 03）
graph.invoke(None, new_cfg)   # 从改写后的状态继续
改写也走 reducer（重要细节） update_state 提供的更新不是简单粗暴地覆盖，而是像节点返回值一样经过 apply_writes → reducer 合并（Day 08）。所以对 messages（用 add_messages）来说，update_state 是追加一条，不是替换整个历史。要理解这点才不会踩坑：想替换就得用支持覆盖的 reducer 或专门手段。这保证了手动改写和正常执行的语义一致。
L05

fork 分叉

从历史检查点 update_state 会产生一个新分支：原时间线保留，新检查点的 parents 指向那个历史点。于是同一 thread 下可以有多条"平行宇宙"。

📝 例子：把整套时间旅行串起来跑一遍 
cfg = {"configurable": {"thread_id": "debug-1"}}
graph.invoke(input, cfg)                       # 正常跑完，留下一串检查点

hist = list(graph.get_state_history(cfg))      # 列出历史（新→旧）
bad  = hist[3]                                 # 定位到"决策变糟"那一步

# 从那一步改写决策 → fork 出新分支（不动原历史）
forked_cfg = graph.update_state(bad.config,
                {"messages": [AIMessage("换个更好的决策")]})
graph.invoke(None, forked_cfg)                 # 从分叉点继续，看新结果
# 原 hist[3] 那条线依然在，可随时对比两条宇宙
💬 小白 vs 老师：回到过去改一下，会不会把"未来"删掉？ 👶 小白：我回到 ckpt1 改了决策，那原来 ckpt2、ckpt3 是不是就没了？
👨‍🏫 老师：不会！时间旅行不销毁历史。改写会新生成一份 ckpt2'，它的 parents 指向 ckpt1，于是分叉出一条新线；原来的 ckpt2→ckpt3 那条线原封不动还在。就像生活中的游戏——读旧档改个选择重打，会开出一条新剧情线，但老存档并没被覆盖，你随时能切回去对比两个结局。
读法：时间旅行不销毁历史——从旧点出发会 fork 出新分支（Day 11 的 parents 链记录父子关系）。可以对比"原路线"和"改写后路线"的不同结果。适合 A/B 探索、Agent 决策对比。
⚠️ 常见误解：小白常以为 update_state 是"覆盖式改状态"。其实它走 reducer（Day 08）——对 messages 这种用 add_messages 的字段是追加而非替换（Day 04 已强调过一次，这里再踩一遍坑）。
L06

断点 interrupt_before / after

编译时可设静态断点，让图在某节点前/后暂停（Day 08 tick 里的 interrupt 检查）：

graph = builder.compile(
    checkpointer=InMemorySaver(),
    interrupt_before=["tools"],   # 执行 tools 节点前暂停
)
graph.invoke(input, cfg)   # 跑到 tools 前停下、返回；状态已存检查点
断点 = 让程序在指定地方"停下等你" 和调试器打断点一个意思：图跑到 tools 节点前会自动暂停、把控制权交还给你（invoke 返回，此刻状态已存进检查点）。你可以检查状态、审批、甚至 update_state 改点东西，再让它继续。最经典的用途：工具调用前让人类审批（"AI 要执行删库操作，批准吗？"）。断点靠的还是检查点机制——能停能存能续，全是一套东西。
L07

断点恢复

暂停后，再次 invoke(None, cfg) 即从断点继续（可先 update_state 改状态）：

state = graph.get_state(cfg)          # 看看停在哪、state.next 是啥
# ...（人类审批 / 修改）...
graph.invoke(None, cfg)               # 继续执行
读法：断点暂停 → 检查/干预 → invoke(None) 续跑，是"人在环"的静态版本。Day 14 讲的 interrupt() 是更灵活的动态版本（在节点内部任意位置暂停并向人类要输入）。二者都建立在检查点之上。
