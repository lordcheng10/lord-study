ToolNode 与 tools_condition

Day 16 的 tools 节点里到底发生了什么？ToolNode 怎么并行跑多个工具、处理报错、把结果包成 ToolMessage；tools_condition 怎么做通用路由。

📍 你在整门课的位置
react_agent→ToolNode→流式→部署
L01

ToolNode 是什么

🤔 痛点：模型只会"说"要调工具，谁真的去执行？ agent 节点里模型返回的 AIMessage 只是一句"我想调 search，参数是北京"——它并不会真的运行你的 Python 函数。那么"根据模型的请求、找到函数、传参、执行、拿回结果"这堆脏活谁干？

ToolNode（libs/prebuilt/tool_node.py，class ToolNode:622）是一个预制节点：拿到 LLM 产生的 tool_calls，找到对应工具、执行、把结果包成 ToolMessage 追加回 messages。

ToolNode = "工具执行车间" Day 16 里 agent 节点（模型）只是说"我要调 search，参数是北京"——它不真的执行。真正干活的是 ToolNode：它读懂模型的调用请求，去调对应的 Python 函数，拿到返回值，再包装好塞回对话历史，让模型下一轮能看到结果。模型负责"决策调什么"，ToolNode 负责"实际执行并回填结果"——分工明确。
💡 本质：ToolNode 是"tool_calls → ToolMessage"的翻译执行器 它把模型输出的结构化调用请求（tool_calls）逐个执行，再把每个返回值包成带 tool_call_id 的 ToolMessage 写回历史，让模型下一轮"看到"结果。这一进一出，就是 ReAct 里"Acting"那一步的落地。
ToolNode 就像公司前台的派单员：模型（老板）喊一句"派人去查北京天气、再算一笔账"，前台派单员照着工单找到对应的人（函数）去办，办完把回执（ToolMessage）贴回工作群，老板下一眼就看到结果。老板只管"派什么活"，派单员管"真去办、办完回话"。
图：模型说要调工具 → ToolNode 真执行 → 结果包成 ToolMessage 回填给模型
L02

读 tool_calls

ToolNode 从 state 里最后一条 AIMessage 取出 tool_calls（模型可能一次要调多个工具）：

last = state["messages"][-1]
for call in last.tool_calls:
    # call = {"name": "search", "args": {"q": "北京"}, "id": "call_1"}
    tool = self.tools_by_name[call["name"]]   # 按名字找到工具
读法：ToolNode 内部维护 tools_by_name（名字→工具的字典），按模型给的 name 精确找到要执行的工具。每个 tool_call 有唯一 id——结果 ToolMessage 用它对应回去。
L03

并行执行

若模型一次要调多个工具，ToolNode 并行执行它们（异步 gather / 线程池），不逐个串行等。

一次调多个，同时跑 模型可能一口气说"帮我查北京天气 + 上海天气 + 算个数"。ToolNode 不会一个查完再查下一个，而是三个同时发出去——总耗时约等于最慢那一个，而不是三者相加。对有网络 IO 的工具（查天气、搜索）提速明显。这和 Day 10 的节点并行是同一种"能并则并"的思路，只是这里并行的是工具调用。
就像生活中点三份外卖：你不会等第一家送到再下第二单，而是三单一起下——三个平台同时备餐配送。假设每个工具要 2 秒，串行 3 个要 6 秒，并行只要约 2 秒（最慢那个），差 3 倍。
L04

ToolMessage

每个工具的返回值被包成 ToolMessage（带 tool_call_id 对应上请求），追加进 messages：

return {"messages": [
    ToolMessage(content=str(result), tool_call_id=call["id"], name=call["name"])
]}   # add_messages 追加（Day 03）→ 下一轮模型能看到工具结果
读法：tool_call_id 是关键——它把"结果"和模型发出的"请求"配对。模型下一轮（回到 agent 节点）看到 ToolMessage，就知道"我上次要的 search 结果是这个"，据此继续推理。这是 ReAct 闭环的"结果回填"步。
🎬 第一人称：我是一个"查天气"工单的一生 ① 我出生：模型在 agent 节点想了想，把我写进 AIMessage 的 tool_calls：{name:"天气", args:{city:"北京"}, id:"call_1"}。
② 我被派单：进了 ToolNode，派单员按 name 在 tools_by_name 里找到"天气"函数，把 args 传进去执行。
③ 我变成回执：函数返回"晴 28℃"，被包成 ToolMessage(content="晴 28℃", tool_call_id="call_1")——注意 id 还是 call_1，这样模型认得出"这是我点的那单"。
④ 我回炉：追加进 messages，回到 agent 节点，模型看到我就接着往下答。我的一生走完了。
L05

错误处理

ToolNode 有 handle_tool_errors 参数：工具抛异常时，默认捕获错误、包成 ToolMessage 返回给模型（而不是崩掉整个图），让模型看到报错、自行重试或换方案。

让 AI 自己看到错误、自己纠正 传统程序里函数报错就崩了。但 Agent 场景更聪明：工具报错（比如参数写错了）→ 把错误信息当成"工具结果"喂回给模型 → 模型看到"哦参数格式不对"→ 下一轮自己改对再调。这让 Agent 有了"试错-纠正"的韧性。当然可配置成严格模式（报错就抛），生产中按需选择。这是 Agent 工程里"把错误也当上下文"的典型设计。
💬 小白 vs 老师 👶 小白：工具报错了，整个图会崩掉吗？
👨‍🏫 老师：默认不会。ToolNode（handle_tool_errors=True）会捕获异常，把报错信息包成 ToolMessage 喂回模型。
👶 小白：那模型看到报错能干嘛？
👨‍🏫 老师：它像人一样"哦参数写错了"，下一轮自己改对再调——Agent 因此有了试错-纠正的韧性。
👶 小白：那要是我就想让它报错立刻停呢？
👨‍🏫 老师：把 handle_tool_errors=False，就恢复成"报错即抛"的严格模式，生产里按需选。
L06

tools_condition

tools_condition（tool_node.py，def tools_condition:1582）是 Day 16 should_continue 的官方通用版——一个开箱即用的条件边函数：

from langgraph.prebuilt import tools_condition
# 最后一条 AIMessage 有 tool_calls → 返回 "tools"，否则 → END
builder.add_conditional_edges("agent", tools_condition)
读法：你自己搭 ReAct 图时（不用 create_react_agent），直接用 ToolNode + tools_condition 两个预制件就能拼出核心循环。它们是"比 create_react_agent 低一层、比手搓高一层"的中间层积木。
💥 错误驱动：不用 tools_condition，直接无脑连 agent→tools 会怎样？ 假设你把边写死成 add_edge("agent", "tools")——不判断就每轮都进 ToolNode。结果：当模型已经想好、给出最终答案（AIMessage 没有 tool_calls）时，还是被拽进 tools 节点，ToolNode 拿到一个空的 tool_calls 列表，要么空转、要么报错，图永远停不下来（撞 recursion_limit 才崩）。tools_condition 的意义就是当这个"该不该继续"的开关——有工单才派单，没工单就收工（END）。
📝 例子：两个预制件拼出 ReAct 核心循环 builder.add_node("tools", ToolNode(tools)) 加执行节点，再 builder.add_conditional_edges("agent", tools_condition) 加路由——一行判定"最后一条消息有 tool_calls 就去 tools，否则 END"。想自定义流程但又不想重写路由逻辑时，这套组合最顺手。
L07

注入状态 / Store

工具可通过 InjectedState / InjectedStore 注解拿到图状态或长期记忆（Day 15），而这些参数不暴露给模型（模型不该填它们）：

from langgraph.prebuilt import InjectedState

def my_tool(query: str, state: Annotated[dict, InjectedState]):
    # query 由模型填；state 由框架注入（模型看不到这个参数）
    ...
读法：InjectedState/Store 让工具能读到"当前对话状态/用户长期记忆"，但对模型透明——模型只需填业务参数（query）。框架在执行时把 state/store 悄悄注入。这解决了"工具需要上下文但又不能让模型乱填"的矛盾。
