项目脚手架与 YAML 配置

真实项目怎么组织。前面都是编程式写法，生产项目更常用 @CrewBase + YAML 的声明式写法。今天讲这套标准结构。

L01

两种写法

定义 Crew 有两种写法：

  • 编程式（前面一直用的）：手动 Agent(...) → Task(...) → Crew(...) → kickoff()。适合快速实验。
  • 声明式（@CrewBase + YAML）：agents/tasks 的配置写在 config/*.yaml，Python 里用装饰器组装。官方推荐用于真实项目。
为什么真实项目用声明式？ 编程式把"配置（角色、目标、任务描述）"和"代码逻辑"混在一起，改个提示词要动 Python 代码。声明式把配置抽到 YAML 文件——产品经理/非程序员也能改角色和任务描述、能 code review 配置变更、能给不同环境用不同 YAML。"配置与代码分离"是工程化的标志。这是本日的核心。
L02

CLI 脚手架

CrewAI 提供命令行脚手架快速建项目（lib/cli）：

crewai create crew my_project    # 生成标准项目结构
# 生成：
# my_project/
#   src/my_project/
#     config/agents.yaml   ← agent 配置
#     config/tasks.yaml    ← task 配置
#     crew.py              ← @CrewBase 组装
#     main.py              ← 入口
crewai run                       # 运行
读法：crewai create 生成一套标准目录结构——配置在 config/ 的 YAML、组装逻辑在 crew.py。这是 CrewAI 项目的"标准姿势"，团队协作、部署都基于它。
L03

YAML 定义 agents/tasks

# config/agents.yaml
researcher:
  role: "{topic} 行业资深研究员"
  goal: "找到关于 {topic} 的最新可靠资料"
  backstory: "你深耕这个行业十年……"

# config/tasks.yaml
research_task:
  description: "研究 {topic} 的最新进展"
  expected_output: "5 条要点的资料清单"
  agent: researcher
读法：Agent 的 role/goal/backstory（Day 02）、Task 的 description/expected_output（Day 03）全写在 YAML 里，用名字（researcher、research_task）标识。{topic} 占位符照样能用（Day 02 的插值）。这些 YAML 就是"配置"，纯文本、易读易改。
L04

@CrewBase 装饰器

Python 里用 @CrewBase（project/crew_base.py，元类 CrewBaseMeta :193）把 YAML 和代码粘起来：

@CrewBase
class MyProjectCrew:
    agents: List[BaseAgent]     # 会被自动填充
    tasks: List[Task]

    @agent
    def researcher(self) -> Agent:
        return Agent(config=self.agents_config['researcher'],   # ← 读 YAML 配置
                     tools=[SerperDevTool()])
    @task
    def research_task(self) -> Task:
        return Task(config=self.tasks_config['research_task'])
    @crew
    def crew(self) -> Crew:
        return Crew(agents=self.agents, tasks=self.tasks, process=Process.sequential)
读法：@CrewBase 让类自动从 config/agents.yaml、config/tasks.yaml 加载配置到 self.agents_config/self.tasks_config。你在 @agent 方法里用 config=self.agents_config['researcher'] 引用 YAML 里的配置，再补上代码里才能给的东西（如 tools）。
分工：YAML 管"文字配置"，Python 管"代码对象" YAML 放"能用文字表达的"（角色、目标、任务描述）——非程序员也能改。Python 放"必须是代码的"（工具实例、自定义逻辑、流程）。config=... 把两者拼起来。各放各的位置，改配置不碰代码、改逻辑不碰配置。
L05

@agent / @task / @crew 装饰器

这些装饰器（project/annotations.py）标记方法的角色：

  • @agent（:78）：标记"这是一个 agent 定义方法"，返回的 Agent 被收集进 self.agents。
  • @task（:66）：同理收集进 self.tasks。
  • @crew（:180）：标记组装 Crew 的方法。
  • @before_kickoff/@after_kickoff（:42/:54）：开工前/后的钩子。
  • 还有 @llm/@tool/@callback 等。
又见"装饰器贴元数据"（呼应 Day 12 Flow） 和 Flow 的装饰器一样，这些 @agent/@task 也是"贴标签"——标记方法的身份，让 @CrewBase 元类在类创建时自动收集所有 @agent 方法的返回值填进 self.agents。你不用手动维护一个 agents 列表，装饰器帮你收集。声明式（贴标签）比命令式（手动 append）更省心、更不易出错。
L06

自动加载配置

@CrewBase 的元类 CrewBaseMeta 在类创建时调 load_configurations（crew_base.py:368）自动读取 config/agents.yaml 和 config/tasks.yaml，并把 @agent/@task 方法收集进 self.agents/self.tasks。

元类（metaclass）是什么？ "类的类"——控制类怎么被创建。普通装饰器作用于函数/方法，元类作用于整个类的创建过程。CrewBaseMeta 在你的 Crew 类被定义时就介入：读 YAML、扫描 @agent/@task 方法、准备好一切。这是 Python 的高级特性，让 @CrewBase 能"魔法般"地把 YAML 和方法自动组装。你不用懂元类也能用，但知道"背后是元类在自动加载"就不觉得神秘了。
L07

为什么 YAML 分离（工程价值）

  • 非程序员可改：产品/运营能直接改 agent 的角色、任务描述，不碰代码。
  • 提示词迭代快：调 prompt 是 Agent 开发的核心工作，YAML 里改比在 Python 字符串里改清爽得多。
  • 可 review、可版本管理：配置变更在 git 里一目了然。
  • 多环境：不同环境（测试/生产）可用不同 YAML。
这和 OpenHands 的 skills/microagents（Day 18）、eino 的配置化异曲同工——都是"把 AI 行为的可变部分（提示词、配置）从代码里抽出来"，让迭代更快、协作更容易。Agent 开发的一大工作量是调提示词，把提示词放 YAML 是工程化的必然选择。
