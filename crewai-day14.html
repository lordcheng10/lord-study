工具体系

工具是 Agent 的"双手"。今天读 tools/base_tool.py：工具怎么定义、参数 schema 如何从函数签名自动生成、@tool 装饰器、以及工具被 Agent 调用的两条路径。

L01

BaseTool 抽象基类

BaseTool(BaseModel, ABC)（tools/base_tool.py:103）是所有工具的父类，核心字段（:139-191）：

name: str              # 工具名
description: str        # 告诉 LLM 何时/为何用它
args_schema            # 参数的 Pydantic schema
result_as_answer: bool  # 结果是否直接作为最终答案
max_usage_count: int    # 用量上限
# 子类必须实现抽象方法 _run（base_tool.py:375）
读法：一个工具 = 名字 + 描述 + 参数 schema + 执行逻辑（_run）。这和 OpenHands Day 12 讲的"工具三件套"一模一样——name/description 给 LLM 看，args_schema 定参数，_run 真正干活。天下工具一个样。
L02

args_schema 自动从函数签名生成

你没提供 args_schema 时，_default_args_schema（base_tool.py:200）用 inspect.signature(cls._run) 读取 _run 的参数类型注解，自动 create_model 生成 Pydantic schema。

"从函数签名自动生成 schema"是什么魔法？ 你写 def _run(self, city: str, days: int) -> str:，框架用 Python 的反射（inspect）读出"有两个参数：city 是字符串、days 是整数"，自动生成对应的参数 schema。你不用手写一份重复的参数定义——函数签名就是唯一的真相来源。（呼应 eino 的 InferTool、OpenHands 工具从类型推断——同一招。）这个 schema 最终会告诉 LLM"调这个工具要填哪些参数"。
L03

@tool 装饰器：快速造工具

@tool（base_tool.py:676）让你把普通函数一键变工具：

@tool
def greet(name: str) -> str:
    '''Greet someone.'''      # ← docstring 成为工具 description
    return f"Hello, {name}!"
# 参数 name: str → 自动生成 args_schema
读法：_make_tool（base_tool.py:708）强制要求函数有 docstring（当描述）和类型注解，再从签名生成 args_schema。支持 @tool、@tool("名字")、@tool(result_as_answer=True) 三种写法。
为什么强制要 docstring 和类型注解？ 因为 docstring 会变成"给 LLM 的工具说明"、类型注解会变成"参数 schema"。没有它们，LLM 就不知道这工具干嘛、参数怎么填。框架强制你写，其实是逼你把工具描述清楚——这直接影响 LLM 用好这个工具的能力（Day 12 OpenHands 讲过 description 写好坏很关键）。好的约束引导你写出 LLM 友好的工具。
L04

run 与用量上限

对外统一入口是 run（base_tool.py:314），它先校验参数、检查用量、再调 _run：

def run(self, *args, **kwargs):
    if not args:
        kwargs = self._validate_kwargs(kwargs)   # 用 args_schema 校验参数
    limit_error = self._claim_usage()            # 原子计数，超 max_usage_count 返回错误
    if limit_error: return limit_error
    result = self._run(*args, **kwargs)          # 真正执行
    return result
读法：run 是"带护栏的执行"——先校验参数合法、再检查没超用量上限、才真正 _run。max_usage_count 防止 Agent 反复滥用同一个工具（比如无限调搜索）。参数校验则保证 LLM 传的参数符合 schema。
为什么要 max_usage_count？ Agent 可能陷入"反复调同一工具却不推进"的循环。用量上限是针对单个工具的"刹车"——补充了 Day 07 的 max_iter（整体循环上限）。多层限制，防失控。
L05

描述重写：把 schema 喂给 LLM

_generate_description（base_tool.py:482）把工具描述重写成带 JSON schema 的格式：

self.description = (
    f"Tool Name: {sanitize_tool_name(self.name)}\n"
    f"Tool Arguments: {args_json}\n"         # ← 参数结构
    f"Tool Description: {self.description}")
读法：工具最终给 LLM 看的描述里，包含了参数的 JSON schema——这样 LLM 就知道"这工具叫什么、参数有哪些、什么类型"，才能正确地调用它。这份描述会进 Agent 的系统提示（文本 ReAct 模式）或转成 OpenAI function schema（原生模式，L06）。
L06

两条调用路径（呼应 Day 07）

Day 07 讲过 Agent 执行有两种模式，工具调用也对应两条路径：

  • 路径 A（原生 function-calling）：convert_tools_to_openai_schema（utilities/agent_utils.py:154）把工具转成 OpenAI schema、建立"函数名→tool.run"映射（available_functions）。LLM 返回 tool_call 后，LLM._handle_tool_call（llm.py:1734）从映射取函数、json.loads 参数、调用。
  • 路径 B（文本解析 ReAct）：ToolUsage 类（tools/tool_usage.py:76）负责——parse_tool_calling 解析文本、_use（:469）执行（先查缓存、可重试解析）。
统一转换 CrewStructuredTool：BaseTool.to_structured_tool()（:393）把工具转成内部统一执行的 CrewStructuredTool（替代 langchain 的 StructuredTool）。无论哪条路径，最终都执行到工具的 run。两条路径同一个工具定义——现代模型走 A（可靠），老模型走 B（兜底），和 Day 07 一致。
L07

用量记录与缓存

ToolsHandler（agents/tools_handler.py:15）是工具使用的回调处理器。on_tool_use（:26）记录 last_used_tool，并按 cache_function 决定是否缓存 (工具名, 输入)→输出：

if self.cache and should_cache and calling.tool_name != CacheTools().name:
    self.cache.add(tool=calling.tool_name, input=input_str, output=output)
工具缓存为什么有用？ Agent 可能在推理中用相同参数重复调同一个工具（比如反复查同一个网址）。缓存后，第二次直接返回上次的结果——省时间、省钱（尤其工具调用花钱时，如付费 API）、结果也一致。cache_function 让你自定义"什么情况该缓存"（有些实时数据不该缓存）。这是 Crew 的 cache=True（Day 04）在工具层的落地。
