Day 10 / 共 20 天 · 第 2 周 路由/配置/数据面

upstream 与 balancer

第 2 周收官。请求处理完决策，最后要转发给某个后端实例——从上游的一组 nodes 里挑一个。今天看 balancer.lua：五种负载均衡算法、健康检查如何剔除坏节点、失败如何重试。

L01

balancer 阶段回顾

Day 02 见过 http_balancer_phase（init.lua:993）调 load_balancer.run(route, ctx, common_phase)。balancer.lua:343 的 run 里核心是 pick_server（:361）——选一个上游实例。

balancer 阶段的特殊性（重申 Day 02） Nginx 会在这个阶段"重试"——第一个实例连不上，重新进 balancer 选下一个。所以 run 里有重试计数 balancer_try_count（:218）,第一次选一个、失败了第二次选另一个。负载均衡不只是"挑一个",还包含"挑失败了换一个"的容错。
L02

五种负载均衡

apisix/balancer/ 目录，upstream 的 type 字段选用哪个：

算法怎么选
roundrobin轮流（按 weight 加权轮询），默认
chash一致性哈希（按 key 如 IP/uri 固定映射到某实例）
least_conn最少连接（选当前连接数最少的）
ewma指数加权移动平均（选响应最快的，动态感知）
priority优先级（先用高优先级组，挂了降级到低优先级）
为什么要这么多算法？ 不同场景要不同策略：roundrobin 最公平通用；chash 让同一用户总打到同一实例（有本地缓存时有用）；least_conn 适合长连接不均的场景；ewma 自动避开慢节点；priority 做主备/多机房降级。APISIX 把每种做成一个可插拔模块（balancer/roundrobin.lua 等），upstream 配 type 选用。又是"策略模式"——和路由、配置中心一脉相承。
L03

create_server_picker

balancer.lua:99-134：按 upstream.type 加载对应算法模块，用健康的节点建一个"picker"（选择器）：

local function create_server_picker(upstream, checker)
    local picker = pickers[upstream.type]
    if not picker then
        pickers[upstream.type] = require("apisix.balancer." .. upstream.type)  -- 按名加载
        picker = pickers[upstream.type]
    end
    local up_nodes = fetch_health_nodes(upstream, checker)   -- 只用健康节点（L05）
    if #up_nodes._priority_index > 1 then                     -- 有多个优先级组
        return priority_balancer.new(up_nodes, upstream, picker)
    end
    return picker.new(up_nodes[up_nodes._priority_index[1]], upstream)  -- 单组直接建
end
读法：require("apisix.balancer." .. upstream.type) 按配置的算法名动态加载模块——加新算法就加个文件。picker.new(nodes, upstream) 用节点建一个选择器对象，之后每次请求调它的 get() 选一个。picker 会缓存（pickers[type]），upstream 配置不变就复用。
L04

pick_server

balancer.lua:195-280：

local function pick_server(route, ctx)
    local up_conf = ctx.upstream_conf
    local nodes_count = #up_conf.nodes
    if nodes_count == 1 then                    -- 只有一个节点，直接返回
        local node = up_conf.nodes[1]
        ctx.balancer_ip = node.host
        ctx.balancer_port = node.port
        return node
    end
    -- 多节点：用 server_picker（按算法）选一个
    ctx.balancer_try_count = (ctx.balancer_try_count or 0) + 1
    -- ... 建/取 server_picker → picker:get(ctx) 选一个 → 设 balancer_ip/port
end
单节点快路径 如果上游只有一个实例，根本不用跑负载均衡算法——直接返回它。这是常见情况的快路径优化。多节点才走 picker。选中的实例 IP/端口存进 ctx.balancer_ip/balancer_port，Nginx 据此转发。ipv6 地址还会补上 []（:200-203）。
L05

健康节点过滤

balancer.lua:64-97 的 fetch_health_nodes：结合健康检查器（checker），只把"健康的"节点交给 picker——挂了的节点不参与负载均衡。

健康检查：主动 + 被动 主动健康检查（active）：后台定时探测每个节点（发心跳请求），不通就标记不健康。被动健康检查（passive）：根据真实请求的成败判断——回想 Day 02 log 阶段的 healthcheck_passive，这次请求 5xx 了就给这个节点记一笔。两者结合，坏节点被自动剔除，请求只发给健康节点。这就是"上游一台挂了，网关自动不给它发流量"的实现。健康检查配置在 upstream 的 checks 字段（Day 08）。
L06

priority 优先级

balancer.lua:117-122：节点可以分优先级组（_priority_index）。priority_balancer 先用最高优先级组的健康节点；全挂了才降到下一级。

主备 / 多机房降级 给主机房节点 priority=10、备机房 priority=0。正常只用主机房；主机房全挂了才切到备机房。这实现了"主备切换""多机房容灾"。priority_balancer 在优先级组之间做降级，每个组内部再用你配的算法（roundrobin 等）选实例。两层选择：先选组（按优先级+健康），再组内选实例（按算法）。
L07

失败重试

balancer.lua:343 的 run 配合 set_current_peer（:288）和 balancer_try_count：某个实例连不上，Nginx 重新进 balancer，pick_server 排除已试过的、选下一个，直到成功或超过 retries 次。

读法：重试次数来自 upstream 的 retries（Day 08）。"选一个 → 失败 → 排除它 → 选下一个"直到成功或用尽重试——这让单个实例的临时故障不影响用户（自动切到其他实例）。run 里还调 plugin_funcs("before_proxy")（:378）——转发前给插件最后改请求的机会。
