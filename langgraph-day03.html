State 与 reducers

全书最重要的概念。节点返回"局部更新"，reducer 决定这些更新怎么合并进状态（覆盖 vs 追加）。精读 add_messages。

📍 你在整门课的位置（第 1 周主线）
全景→StateGraph→State+reducer→条件边→invoke旅程
L01

为什么需要 reducer

节点返回的是"局部更新"（Day 02）。问题：更新怎么合并进旧状态？两种典型情况：

  • 同一步里多个节点并发给同一个键写值，怎么办？
  • 一个"消息列表"，新消息应该追加还是覆盖整个列表？
🤔 痛点：节点只会"报差异"，那"旧值 + 差异"谁来算？ Day 02 说节点只返回局部更新，比如聊天节点返回 {"messages": [新回复]}。可 State 里本来已经有一串历史消息了——新回复是接到历史后面（追加），还是把整串历史换成只剩这一条（覆盖）？框架没法猜，这个"怎么合并"的规则必须由你指定。
💡 本质：reducer 就是每个字段的"合并规则" (旧, 新) → 结果 LangGraph 的答案是：给每个 State 字段配一个 reducer——一个二元函数 (旧值, 新值) → 合并后的值。计数器用"覆盖"（LastValue，直接取新值）；消息列表用"追加"（add_messages）。节点永远只管报差异，"旧 + 新 = 什么"由字段的 reducer 一锤定音。这就是 LangGraph 状态管理的全部秘密。
这就像生活中的记账本："追加"reducer = 记流水账（每笔收支都记一行，历史全留）；"覆盖"reducer = 只写当前余额（新数字一写，旧的就没了）。同一本账，不同的字段用不同记法——这正是 reducer 的活。
reducer = "合并策略" 答案就是 reducer：每个 State 字段背后是一个 channel（通道），channel 的 update() 方法决定合并策略。reducer 签名 (旧值, 新值) → 合并后的值。比如聊天历史用"追加"reducer（新消息接到末尾），计数器用"覆盖"（新值替换旧值）。节点无需关心合并——只管返回局部更新，reducer 负责合并。这是 LangGraph 状态管理的精髓。
L02

字段 → 通道

compile 时，_get_channel（state.py:1836）为每个 State 字段挑一个 channel：

def _get_channel(name, annotation, ...):
    if channel := _is_field_channel(annotation): ...    # Annotated[..., 某 Channel]
    elif channel := _is_field_binop(annotation): ...     # Annotated[..., reducer 函数]
    fallback: LastValue = LastValue(annotation)          # 没标注 → 默认 LastValue（覆盖）
    return fallback
读法：每个 State 字段变成一个 channel。看字段的类型注解决定用哪种：没 reducer 注解 → LastValue（覆盖）；有 reducer 函数 → BinaryOperatorAggregate（合并）。reducer 不是挂在图上的额外概念，而是内建在 channel 的 update() 里（Day 07 深入）。
L03

无 reducer = 覆盖（LastValue）

字段没标 reducer（如 count: int）→ LastValue channel（last_value.py:56）：

def update(self, values):
    if len(values) == 0: return False
    if len(values) != 1:
        raise InvalidUpdateError("Can receive only one value per step. Use an Annotated key ...")
    self.value = values[-1]   # 直接覆盖
读法：LastValue = "存最后一个值、每步最多接收一个"。关键：没有 reducer 的字段，同一步被两个节点同时写就报错（"Can receive only one value per step"）——这就是新手常见的报错来源。所以并发写必须用 reducer（L07）。
📝 简化版 → 真实版：如果让你自己写"合并" 如果让你写，你八成会这样： 
state["messages"] = new_messages   # 直接赋值：新的一写，历史全没了（= 覆盖）
这对计数器没问题，但聊天历史会被"清空只剩最新一条"。LangGraph 的真实做法（last_value.py:20 的 LastValue.update）也确实是"取最后一个值"——但它多做了一件事：发现一步里来了 2 个值就直接报错，逼你为这个字段想清楚合并策略，而不是静默丢数据。这行"多出来的报错"，就是真实版比朴素版更靠谱的地方。
L04

有 reducer = 合并（BinaryOperatorAggregate）

Annotated[类型, 二元函数] → BinaryOperatorAggregate（binop.py:123）：

class State(TypedDict):
    items: Annotated[list, operator.add]   # reducer = operator.add（列表拼接）

# update() 逐个折叠：
for value in values:
    self.value = self.operator(self.value, value)   # 用 operator 合并
读法：Annotated[list, operator.add] 让多次写入逐个用 + 累加（列表拼接），而非覆盖。于是多个节点并行往 items 写，全部被 operator.add 累加，不冲突。reducer 就是那个二元合并函数。
reducer 是什么（数学直觉） reducer 来自函数式编程的"归约"——把一串值用一个二元操作"折叠"成一个。[1,2,3] 用 + 归约 = ((0+1)+2)+3 = 6。LangGraph 用它合并状态更新：旧状态 + 新更新 → 新状态。覆盖（LastValue）其实是"取最后一个"的特殊 reducer。
这就像生活中的购物车：operator.add 就是"往车里再放几件"（原有的都还在，新的加进去）；而覆盖则像"清空车、只留刚拿的这件"。多个人（并行节点）同时往同一辆车放东西也不冲突——这正是聚合型 reducer 的价值。把"如何合并状态"抽象成 reducer——灵活（你能自定义任意合并逻辑）、统一（所有字段都走这套机制）。
L05

add_messages 精读（最常用的 reducer）

add_messages（message.py:60）是 chat/agent 最常用的 reducer——默认追加，ID 相同则替换（:216）：

merged = left.copy()
merged_by_id = {m.id: i for i, m in enumerate(merged)}
for m in right:
    if (existing_idx := merged_by_id.get(m.id)) is not None:
        merged[existing_idx] = m       # 同 ID → 替换
    else:
        merged.append(m)                # 新 ID → 追加
# RemoveMessage(id=REMOVE_ALL_MESSAGES) 可清空所有
读法：新消息 ID 已存在 → 替换那条（改写）；新 ID → 追加到末尾。还给缺 ID 的消息补 UUID、支持 RemoveMessage 删消息。
为什么聊天用 add_messages？ 聊天机器人每轮，节点只需 return {"messages": [ai_回复]}，add_messages 自动把新回复追加到历史里，而不是覆盖整段对话。如果用默认的 LastValue（覆盖），每轮就把历史丢了、只剩最新一条——聊天就"失忆"了。"同 ID 替换"则支持流式更新（同一条消息边生成边更新）。这个 reducer 是 LangGraph 聊天记忆的基础。
这就像生活中的微信聊天记录：新消息永远接在下面（追加），你不会因为发了句"在吗"就把整段历史清空——聊天框用的正是"追加"。若换成覆盖，每发一句就"失忆"只剩最新一条。
同样一次"返回 B"，覆盖 reducer 丢了 A，追加 reducer 两条都留 —— 差别全在字段配了哪个 reducer
⚠️ 小白常误以为 reducer 要自己在节点函数里手动调用（merged = add_messages(old, new)）。其实你只在 State 的类型注解里写一次 Annotated[list, add_messages]，框架就在每一步自动帮你合并——节点里永远只写 return {"messages": [新消息]}。
L06

MessagesState（开箱即用）

# message.py:372
class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
读法：LangGraph 预置了 MessagesState——一个带 messages 键 + add_messages reducer 的 State。绝大多数教程/agent 直接继承它，不用自己写。约定优于配置——最常见的 State（聊天消息）现成给你。
v1.0 变化提示：老的 MessageGraph 已废弃（message.py:312），官方建议用带 messages 键的 StateGraph（即 MessagesState 风格）。写新代码用新 API。
L07

并发写为什么必须 reducer

回到 L03 的报错："Can receive only one value per step"。这是因为 LangGraph 支持同一超步多个节点并行执行（Day 06）——它们可能都往同一个键写。

并发 + 无 reducer = 冲突 想象两个节点并行都往 results 写。用 LastValue（覆盖）：一步收到两个值，它不知道该留哪个——报错（避免静默丢数据）。用 reducer（如 operator.add）：两个值被合并（拼接）——各自的贡献都保留。所以"会被多个节点并发写的字段"必须配 reducer。这是 LangGraph 并行安全的机制：reducer 定义了"多个并发写怎么合并"。没 reducer 的字段只能单节点写——框架用报错强制你为并发字段想清楚合并策略。
