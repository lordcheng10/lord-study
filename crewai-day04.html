Crew：把 Agent 和 Task 组队

第三个核心概念，也是"指挥中心"。Crew 把员工（Agent）和活儿（Task）组织起来、按流程调度。今天读 crew.py（2400 行）的骨架。

📍 你在整条链的位置（前两天有了"员工"和"工单"，今天把它们组队交给"项目经理"Crew）
Day1 全景→ Day2 Agent 员工→ Day3 Task 工单→ Day4 Crew 组队（项目经理）→ Day5 kickoff 旅程
L01

Crew 是指挥中心

🤔 有了一堆 Agent 和一堆 Task，谁来调度？ 你手上现在有 3 个员工（研究员、分析师、写手）和 3 张工单。但工单该谁接？先做哪张、后做哪张？上一张的产出怎么传给下一张？跑完怎么汇总？——总不能让员工们自己在群里吵吧。缺一个"项目经理"来统筹。
💡 一句话本质 Crew = 把 agents[] 和 tasks[] 装进来、按 Process 决定执行顺序、一声 kickoff() 开工、最后汇总结果的"项目经理/编排器"。它自己不干活，只负责"排活、传料、收尾"。类比：项目经理不写代码，但决定谁做什么、按什么顺序、成果怎么交付。

Crew（crew.py:159，继承 FlowTrackable, BaseModel）本身不干活——它是编排器/指挥中心，把 agents（干活的人）和 tasks（要干的活）组织起来，按 process 策略调度，调 kickoff() 开工。

Crew 收进"人"(agents) 和"活"(tasks)，按 Process 排出执行顺序，kickoff() 一触发，任务链依次跑完，归总成一个 CrewOutput 交付。
Agent/Task/Crew 三者的关系（复习 + 深化） Agent 是员工，Task 是工单，Crew 是把人和活儿凑成一个项目组并负责调度的"项目"。Crew 决定：这些活儿按什么顺序做（Process，Day 06）、谁做哪个、要不要开记忆/规划、跑完怎么汇总结果。它是三个核心概念里的"总指挥"——前两天学的 Agent 和 Task 都在这里被组织起来运转。

👶 小白：那真正"动脑子调大模型"的是 Crew 吗？感觉它最像老大。

👨‍🏫 老师：不是。Crew 就像项目经理——他自己一行代码不写，只负责排活、把上一步的产出传给下一步、最后把成品收齐交付。真正"动脑子"（调大模型思考）的永远是员工 Agent 的执行器（Day 07）。经理再能干，也不替员工干活。

👶 小白：既然最后只返回最后一个任务的产出，中间那些任务不是白跑了？

👨‍🏫 老师：不白跑。就像写报告：研究、分析都是为最终成文铺垫的半成品——你交付的是那篇报告，但中间的调研笔记框架都留在 tasks_output 里备查。最终交付物只有一个，但每道工序的产出都被记着。

L03

声明式校验：开工前就抓错

Crew 用 Pydantic 的 model_validator 做大量声明式校验，在 kickoff 之前就把配置错误暴露出来：

  • check_manager_llm（crew.py:696）：层级模式必须给 manager_llm 或 manager_agent，且经理不能出现在 agents 列表里。
  • validate_tasks（crew.py:741）：顺序模式下每个 task 必须有 agent。
  • validate_context_no_future_tasks（crew.py:839）：任务的 context 不能依赖后面的任务（防止"时间悖论"）。
为什么"开工前校验"这么重要？ 想象你配错了（比如层级模式忘了给经理），如果不校验，可能跑到一半、烧了不少 token 才崩。声明式校验在你构造 Crew 对象的那一刻就检查所有规则，配置不对立刻报错——根本跑不起来。把错误"前移"到最早的时刻（fail-fast），省时间省钱省心。这和 eino 教程的"编译期类型检查"是同一哲学。validate_context_no_future_tasks 尤其巧妙——防止你让"任务 1 依赖任务 3 的输出"这种逻辑上不可能的配置。
L04

kickoff：开工入口

主入口 kickoff()（crew.py:966）。核心分发逻辑（crew.py:1021）：

inputs = prepare_kickoff(self, inputs, input_files)   # 准备：插值、规划等
if self.process == Process.sequential:
    result = self._run_sequential_process()           # 顺序执行
elif self.process == Process.hierarchical:
    result = self._run_hierarchical_process()          # 层级执行
# 之后：after_kickoff_callbacks、计算 token 用量、返回 CrewOutput
📝 组队 kickoff → 结果 crew = Crew(agents=[研究员, 写手], tasks=[研究任务, 写作任务])
result = crew.kickoff(inputs={"topic": "AI Agent"})
内部：先跑"研究任务"(研究员) → 产出资料 → 自动作为上下文喂给"写作任务"(写手) → 产出成文 →
print(result) → 拿到最后一个任务（写作）的成品；result.tasks_output 里还留着研究任务的中间产物。
→ 一次 kickoff = 整条流水线自动跑完，你只管收最终交付物。
读法：kickoff 是"模板方法"——定义统一骨架：准备(prepare) → 按 process 分发执行 → 回调 → 输出。具体怎么执行委托给 _run_sequential_process / _run_hierarchical_process（Day 06 精讲）。finally 块负责收尾：排空记忆写入、清理文件。
这是"策略模式"：process 是策略标签，kickoff 据它选算法。两种流程可插拔，未来还能加（源码里注释了未实现的 consensual 共识制）。骨架固定、策略可换——扩展新流程不用改 kickoff。
L05

kickoff 的变体

方法作用行号
kickoff()跑一次crew.py:966
kickoff_for_each(inputs=[...])对一批输入分别各跑一次crew.py:1061
kickoff_async(...)"假异步"：线程池包装同步 kickoffcrew.py:1097
akickoff(...)"真异步"：全程 await（原生 async）crew.py:1177
两套异步的区别（有意思的对比） kickoff_async 是"假异步"——用 asyncio.to_thread(self.kickoff) 把同步代码丢到线程里跑（兼容性好，实现简单）。akickoff 是"真异步"——原生 async 贯穿任务执行、记忆、知识查询（性能更好）。假异步是"把同步的活扔给别的线程"，真异步是"从头到尾都不阻塞"。kickoff_for_each 每次都 self.copy() 一个新 crew（L07），保证多次执行互不污染。
L06

CrewOutput：统一最终输出

整个 Crew 跑完，无论多少任务，归一为一个 CrewOutput（crews/crew_output.py:13）：

raw: str              # 原始文本
pydantic: BaseModel   # 结构化对象
json_dict: dict
tasks_output: list    # 每个任务的 TaskOutput（备查）
token_usage           # token 用量
读法：由 _create_crew_output（crew.py:1880）构造，取最后一个有效任务的输出作为 crew 的最终结果。符合流水线直觉——最后一道工序的成品就是交付物，中间产物保留在 tasks_output 里备查。output["key"] 能像字典一样取 pydantic/json 字段。
构造 CrewOutput 时还顺便：排空记忆写入、flush 事件总线、发 CrewKickoffCompletedEvent（crew.py:1895）。和 Day 03 的 TaskOutput 一样是"统一输出容器"，只是层级更高（整个团队 vs 单个任务）。
L07

copy：隔离执行

copy()（crew.py:2027）深拷贝一个 Crew。用在 kickoff_for_each、train、test 等需要"多次独立执行"的场景。

为什么要拷贝？ Crew 执行时会积累状态（记忆写入、任务输出、token 计数）。如果 kickoff_for_each 对 10 个输入复用同一个 crew 对象，第 2 次执行就会被第 1 次的残留状态污染（比如记忆里混入了上一次的内容）。所以每次都 copy() 一个全新的 crew，各跑各的、互不干扰。这叫"原型模式"——用拷贝而非重新构造来快速得到干净的新实例。"隔离执行"是批量/并发场景的正确姿势。
