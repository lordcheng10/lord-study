Web 管理门户 portal

L2.5 研发体验层的门面：一个 Next.js 控制台，让工程师看清 agent 资产、成本、闸门命中、调用回放、评测。昨天(Day 15)我们把 20 多个业务 Agent 全家福点了一遍；今天进入第 4 周「平台化与收官」的第一站——给这一栋楼装上「物业监控大屏」，把 toolkit 一路采集的数据摊开给人看。看完门户，Day 17 就讲怎么把整栋楼部署上生产。

📍 你在 20 天里的位置（第 4 周：平台化与收官）
D15 Agent 全家福→ D16 门户 portal→ D17 部署→ D18 CI 闸门→ D19 起新 Agent→ D20 收官
💡 用一个类比先兜住今天（延续「盖楼/物业」世界观） 如果整个平台是那栋精装公寓楼，portal 就是楼下物业管理处的那面「监控大屏 + 服务台」：大屏上滚动显示各户用电量(成本)、消防报警记录(闸门命中)、访客登记回放(调用回放)、验房打分(评测)——它自己不产生这些数据，只是把楼里各处的传感器(toolkit 埋的指标)汇总到一块屏上给物业师傅看。记住这个画面，下面 8 讲讲的就是「这块大屏长什么样、数据怎么从各户传到屏上」。
L01

portal 定位与一次重要转向

gov-agents-portal 是 Day 01 讲的 L2.5 DevX（研发体验）层。它经历过一次明确的定位转向，值得了解——因为这解释了为什么代码里有个 _legacy_v01/ 目录：

v0.1（已下沉）

  • 给"业务方"用的配置型自助 UI
  • 网页点几下起一个 agent
  • 代码移到 _legacy_v01/ 留痕

v0.2（当前主线）

  • 定位改为服务研发工程师
  • 脚手架 CLI + Web 文档站 + 开发工具
  • 价值：写新 agent 快 10×、样板代码 -80%
为什么转向？ 因为实践发现"让业务方在网页上点点就造 agent"不现实——真正需要它的是研发工程师，而工程师更需要"脚手架 + 资产总览 + 调试工具"。这个转向本身就是产品迭代的真实案例。注意 portal 生成的 agent 不进 apps/，而是写成 configs/business-agents/<name>.yaml（配置即代码）。
💡 用物业的话讲这次转向 v0.1 就像物业想装一台「住户自助机」——让每户自己点几下就把家装好；结果发现住户根本不会用、也没这个需求。v0.2 把这台机器改成了「维修师傅工作站」——因为天天要造/调 agent 的是研发工程师(师傅)，他们要的是趁手的工具台(脚手架 + 资产总览 + 调试台)，不是给外行的自助按钮。_legacy_v01/ 就是那台被拆下来、留在仓库角落做纪念的旧自助机。

SWR（stale-while-revalidate）是个 React 数据请求库：先显示缓存的旧数据、同时后台拉新数据、到了就刷新。配上轮询（每 30 秒自动重拉），控制台的数字就能"准实时"更新——很适合监控类面板。

L04

前后端怎么对话

前端所有请求都打到后端的 /portal/*，有 4 条路径：

Next.js 前端浏览器
SWR fetcher+ Bearer token
FastAPI 后端/portal/*
  • SWR + fetcher（主路径，lib/fetcher.ts）：从 sessionStorage 读 dev 用户，拼 Authorization: Bearer dev-<userId>，大部分页面 useSWR("/portal/...", fetcher, {refreshInterval})。
  • rewrites 反向代理（next.config.mjs）：开发时把 /portal/* 和 /v1/* 反代到 PORTAL_BACKEND_URL（默认 localhost:8080）。
  • SSE 流式（lib/sse.ts）：用 fetch + ReadableStream 手工解 SSE（原生 EventSource 只支持 GET、不能带 header），用于 agentctl 起新 agent 的实时输出。
  • SSR fetch（仅 toolkit 文档页）：server component 直接 fetch，用固定 token。
为什么要 rewrites 反向代理？ 前端跑在 3000 端口、后端在 8080，浏览器直接跨端口请求会有 CORS 麻烦。让 Next.js 把 /portal/* 转发到后端，前端就当作"同源"调用，省去跨域配置。这是前后端分离项目的常见做法。
💡 用物业的话讲这 4 条路径 SWR 反向代理就像物业前台帮你转接电话：你只打「前台」一个号(/portal/*)，前台再转到对应科室(后端 8080)——你不用记每个科室的分机(跨端口)，也就没有"打错线路被保安拦下"(CORS)的麻烦。SWR 轮询则像大屏每 30 秒自动刷新一次车位余量牌：先给你看牌上的旧数字(缓存)，同时后台去数一遍最新车位，数完了再把牌翻新。
📝 举个例子：工作台一个 KPI 卡怎么来的 页面挂 useSWR("/portal/dashboard", fetcher, {refreshInterval:30000})
→ fetcher 从 sessionStorage 取到 dev 用户 alice，拼上 Authorization: Bearer dev-alice（fetcher.ts:28）
→ Next.js 按 next.config.mjs 的 rewrites 把 /portal/dashboard 反代到 localhost:8080
→ 后端返回 {"active_agents":15,"month_invocations":8421,"data_source":"live"}
→ 卡片显示「生产 agent 15」，30 秒后自动再拉一次刷新数字。
图注：前端不直接跨端口打后端，而是走 Next.js 反向代理「转接」到 8080，回来的数据靠 SWR 轮询定时刷新。
L05

通用页面模式：几乎每页一致

门户每个页面都遵循同一套健壮性模式（值得学的前端工程习惯）：

  • Skeleton loading：数据没到时显示骨架屏，不白屏。
  • Error 卡 + 重试按钮：请求失败显示错误卡（带 HTTP 状态码）和"重试"。
  • mock 数据横幅：当后端返回 data_source === "mock"（toolkit 可观测性还没接通时），页面顶部显示琥珀色"数据源 · mock"提示——诚实告诉用户"这是假数据"。
  • partial-data 防御：缺字段时走 error 路径，绝不因为一个字段缺失就整页崩。
又见"诚实"：和后端那些"诚实降级注释"一脉相承——前端也明确区分"真数据"和"mock 数据"，不糊弄用户。一个把"诚实"贯彻到前后端每个角落的项目，是值得信任的。这也呼应"可信工程化"的主题：可信不只是防幻觉，还包括"不误导使用者"。
⚠️ 小白常误以为「顶部弹出琥珀色横幅 = 页面出 bug 了」。其实那是诚实提示不是报错：横幅只是在说「这块数字现在是 mock 假数据（toolkit 可观测性还没接通）」，页面本身工作正常。真报错走的是另一套「Error 卡 + 重试按钮」。就像样板间门口挂「此为样板、非交付实景」的牌子——不是房子坏了，是明明白白告诉你这是演示。
L06

后端 & 沙箱预览

后端入口 backend/portal_backend/server.py::build_router(case_store, app)，注册了约 30 个 endpoint 模块（api/*_endpoint.py）。管理面端点如：GET /portal/health、GET/POST /portal/agents（POST 会 schema 校验 + 拒绝含 secret + 写 YAML 到 configs/business-agents/）。

一个亮点是沙箱预览：当后端拿到 app 时，会挂上 ai-trust-toolkit-sandbox 的反向代理中间件（/portal/v1/sandbox/）。它能在独立子进程里安全试跑 LLM 生成的 agent 代码——每个 sandbox 一个独立 Python 子进程跑自己的 uvicorn。

为什么用子进程而非直接 import 跑生成的代码？ 因为要跑的是"AI 现生成的、还没审过的代码"。用独立子进程能做到：崩溃/OOM 隔离（跑挂了不影响门户）、RLIMIT 资源限制生效、env 白名单防 secret 泄漏。这是"安全地执行不可信代码"的标准隔离手段，和 Day 15 agent-creator 的 sandbox 模式配套。

👶 小白：门户后端就在跑，直接 import 那份新代码跑一下不就完了？非要另起一个进程，图啥？

👨‍🏫 老师：因为那是AI 刚生成、还没人审过的代码。import 进来跑 = 让一个陌生装修队直接进主楼里施工，他一个死循环把内存吃光(OOM)、或者偷偷把水电图纸(secret 环境变量)拍下来带走，整栋楼(门户)就跟着遭殃。沙箱子进程 = 专门腾一间隔离的样板间给他试装：塌了只塌样板间(崩溃隔离)、限他最多用多少电(RLIMIT)、进门先搜身只放行白名单工具(env 白名单)。这就是"安全地跑不可信代码"的标准做法。

👶 小白：那和 Day 15 的 agent-creator 是什么关系？

👨‍🏫 老师：一套东西的两头。agent-creator（Day 15 的元 Agent）负责生成新 agent 代码，门户的 sandbox 负责在交付前安全试跑验证它能不能起来——生成 + 沙箱验证配套，才敢把 AI 写的东西给人预览。

L07

双仓镜像同步（一个真实工程约束）

一个容易困惑的点：前端真源码在一个独立 repo，本 monorepo 里的 frontend/ 是它的只读镜像（mirror）。有专门的 CI 检查（Day 18）保证两边不漂移、镜像只读。

为什么这么搞？前端团队用自己的 repo 和工具链迭代，但平台部署又需要前端代码在同一个镜像里构建——于是用"单向同步 + 只读镜像"折中。docs/cookbooks/portal-frontend-dual-repo-sync.md 有完整说明。

版本漂移再现：backend/pyproject.toml 还 pin 着 ai-trust-toolkit-bom[core]==0.5.0，而 packages 里的 starter 已经是 0.6.0——滞后了一个版本。看 portal 后端依赖时以实际 pyproject 为准（Day 01 原则）。
