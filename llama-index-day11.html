Day 11 / 共 20 天 · 第 3 周 检索与查询

检索器 Retriever

第 3 周进入 RAG 的"在线查询"阶段。检索器是查询的第一步：给一个问题，找出最相关的 Node。今天精读 BaseRetriever 和 VectorIndexRetriever——retrieve 的模板方法、递归检索、各种检索器变体。

L01

进入在线查询

前两周建好了库（离线摄入 + 索引存储）。第 3 周是"在线查询"：问题 → 检索（Retriever，今天）→ 后处理（Day 14）→ 合成答案（Synthesizer，Day 13），QueryEngine（Day 12）把它们串起来。

检索器 = "找相关内容"的那一步 用户问"公司的退款政策是什么?"——检索器负责从知识库里找出最相关的几个 Node（比如"退款条款"那几段）。它只找、不生成答案（生成是后面 Synthesizer 的事）。检索器返回 List[NodeWithScore]（Node + 相关度分数，Day 02）。检索质量直接决定答案质量——找错了内容，LLM 再强也答不对。
L02

BaseRetriever

base/base_retriever.py:34：class BaseRetriever(PromptMixin, DispatcherSpanMixin)。对外方法 retrieve(query)（:192），子类实现 _retrieve(query_bundle)（:263，抽象方法）。

读法：经典"模板方法模式"：基类 retrieve 定义流程骨架（转换查询、埋点、递归处理），子类只填 _retrieve（真正的检索逻辑）。VectorIndexRetriever 的 _retrieve 就是"嵌入查询 + 向量库 query"。
L03

retrieve 模板方法

base/base_retriever.py:192-227：

def retrieve(self, str_or_query_bundle: QueryType) -> List[NodeWithScore]:
    dispatcher.event(RetrievalStartEvent(...))       # 埋点（Day 19 可观测）
    if isinstance(str_or_query_bundle, str):
        query_bundle = QueryBundle(str_or_query_bundle)  # 字符串 → QueryBundle
    else:
        query_bundle = str_or_query_bundle
    with self.callback_manager.event(CBEventType.RETRIEVE, ...):
        nodes = self._retrieve(query_bundle)              # ★ 子类实现的真正检索
        nodes = self._handle_recursive_retrieval(query_bundle, nodes)  # 递归（L06）
    dispatcher.event(RetrievalEndEvent(..., nodes=nodes))
    return nodes
基类包办"周边"，子类只管"核心" retrieve 做了：把字符串包成 QueryBundle、发检索事件（可观测/追踪）、调子类的 _retrieve、处理递归检索、发结束事件。子类（VectorIndexRetriever 等）只需实现 _retrieve 那一句核心逻辑。这样"埋点/事件/递归"这些通用逻辑写一次，所有检索器共享——又是模板方法减少重复。还有 aretrieve（异步版）。
L04

VectorIndexRetriever

indices/vector_store/retrievers/ 的 VectorIndexRetriever._retrieve（简化）：

def _retrieve(self, query_bundle):
    # 1. 把查询文本嵌入成向量（Day 06 的 get_query_embedding）
    query_bundle.embedding = self._embed_model.get_query_embedding(query_bundle.query_str)
    # 2. 构造 VectorStoreQuery（含向量、top_k、filters）
    query = VectorStoreQuery(query_embedding=..., similarity_top_k=self._similarity_top_k, ...)
    # 3. 向量库 query（Day 09）
    result = self._vector_store.query(query)
    # 4. 把结果（node_id + score）包装成 NodeWithScore 返回
    return self._build_node_list_from_query_result(result)
把前两周串起来的"检索" 这一段回收了好几天的内容：嵌入查询（Day 06）→ 向量库检索（Day 09）→ 从 docstore 取回 Node（Day 08）→ 包成 NodeWithScore（Day 02）。Day 07 的 index.as_retriever(similarity_top_k=5) 造的就是它。这就是"语义检索"的完整落地——问题变向量、找最近邻、返回相关 Node。
L05

QueryBundle

schema.py:1449 的 QueryBundle：封装一次查询——query_str（原始问题）、embedding（查询向量）、custom_embedding_strs（用于嵌入的替代文本）等。

为什么查询要包成对象？ 一次查询不只是"一个字符串"——它可能带查询向量、可能有"用于检索的文本"和"给用户看的文本"不同（比如查询改写、HyDE 假设文档嵌入）。QueryBundle 把这些打包。比如 HyDE 技术：先让 LLM 根据问题"编一个假想答案",用假想答案的向量去检索（往往比原问题更接近文档）——这时 query_str 是原问题、custom_embedding_strs 是假想答案。QueryBundle 让这些高级查询变换成为可能。
L06

递归检索

_handle_recursive_retrieval（base/base_retriever.py）：如果检索到的是 IndexNode（指向另一个索引/检索器的节点），就"递归"进去继续检索。

检索到"引用"就顺藤摸瓜 有时一个 Node 不是最终内容，而是"指向别处"的引用（IndexNode，Day 02）——比如"这个摘要对应某份完整文档的检索器"。递归检索遇到 IndexNode 就跟进去，检索它指向的目标。这支撑了 Day 10 的"两级检索"（DocumentSummaryIndex：先检索摘要 IndexNode，递归进文档内检索）。让复杂的"分层检索"能自动展开。
L07

各种检索器

  • VectorIndexRetriever：向量检索（最常用）。
  • BM25Retriever：关键词检索（integration）。
  • QueryFusionRetriever：融合多个检索器结果（向量 + 关键词 = 混合检索）。
  • AutoMergingRetriever：命中小块自动合并成父块（配 HierarchicalNodeParser）。
  • RecursiveRetriever：显式递归检索。
检索策略是 RAG 调优的重头 纯向量检索有时不够——混合检索（QueryFusion 融合向量+BM25）通常更稳（语义 + 精确词兼顾）；auto-merging 解决"小块命中但上下文不足"。它们都是 BaseRetriever，接口统一、可组合。"检索什么内容"比"用什么 LLM"更影响 RAG 效果——所以检索器值得多实验。
