Day 10 / 共 20 天 · 第 2 周收官

上下文与 Token 管理

对话越长，塞给模型的东西越多，迟早撑爆"上下文窗口"。今天讲 Claude Code 怎么层层瘦身、必要时大摘要，以及各种"续命"和"刹车"机制。

L01

上下文窗口的约束

大模型每次请求能接受的 token 有上限，叫上下文窗口（context window）。Agent 干活时，每一轮都要把"之前所有对话 + 工具结果 + 系统提示 + CLAUDE.md"全塞进去。干得越久，这堆东西越大，早晚超窗口。

token 是什么？ 模型处理文本的最小单位，大致 1 个 token ≈ 0.75 个英文单词 / 1-2 个汉字。"上下文窗口 20 万 token"意思是这次请求（历史+新内容）加起来最多 20 万 token。超了 API 直接报错。所以长对话必须主动瘦身——这就是 compaction（压缩）。

Claude Code 的策略是分级瘦身：先用最轻的手段（删过期内容），不够再用重的（大摘要）。全在 queryLoop 每轮开头做（query.ts:523-741）。

L02

每轮开头的瘦身阶梯

循环层每轮调模型之前，按"从轻到重"的顺序做多级瘦身（query.ts:523 起）：

最轻

裁掉 compact 边界前的历史：上次大摘要之后，边界之前的老消息不再带（query.ts:523）

轻

释放旧 toolUseResult 大对象：把已经用不到的大工具结果对象删掉省内存（:542）

中

tool-result 预算：每条工具结果超过大小上限就替换内容（:567）

中

snip：删除僵尸/过期消息（:589，feature 门控）

较重

microcompact 微压缩：清空旧工具结果内容，不动结构（:601，L03）

最重

autocompact 大摘要：调 LLM 把历史压成摘要（:652，L04）

为什么分这么多级？ 大摘要（autocompact）要额外调一次 LLM——花钱、花时间、还可能丢信息。所以能用便宜手段（删过期、清空旧工具结果）解决就绝不上大摘要。这跟 gov-agents 教程里"能用代码就别用 LLM"是同一个成本哲学：先用确定性的廉价手段，实在不行才动用昂贵的 LLM。
L03

microcompact：清空旧工具结果

microcompactMessages（src/services/compact/microCompact.ts:257）是"较重但不调 LLM"的一档。它就地清空旧工具结果的内容，但保留消息结构：

// microCompact.ts:36 —— 把旧 tool_result 的内容换成占位
"[Old tool result content cleared]"
// 结构（哪条消息、tool_use_id 对应关系）都不动，只是把大块内容清掉
为什么"清内容留结构"？ 因为 Anthropic 协议要求每个 tool_use 必须有对应的 tool_result（Day 03 讲过），不能直接删掉工具结果消息（会破坏配对、API 报错）。但那些很久以前的工具结果内容（比如 20 轮前读的一个文件）模型早就不需要了。于是把内容换成"[已清空]"占位、保留结构——既省了 token 又不破坏协议。这是"在协议约束下尽量瘦身"的巧妙折中。
L04

autocompact：大摘要（最后手段）

轻手段都不够时，上 autoCompactIfNeeded（src/services/compact/autoCompact.ts:270）——调一次 LLM 把前面的历史压缩成一段摘要：

  • fork 一次 LLM 调用生成摘要（compact.ts:411 的 compactConversation）。
  • 压缩产物 = buildPostCompactMessages（compact.ts:336）：一个边界标记 + 摘要消息 + 保留的尾部消息 + attachments。
  • 之后 messagesForQuery = postCompactMessages，并 yield 摘要消息（query.ts:726）。

会话层（QueryEngine.ts:958）收到 compact_boundary 后，会把边界之前的消息从 mutableMessages 里 splice 掉以便垃圾回收。这就是你有时看到的 "Compacting conversation…" + 一条摘要。你也能手动 /compact 触发（Day 11）。

"边界标记"是什么？ 一个特殊消息，标记"从这里往前的历史已被摘要替代"。Day 02/06 提过的 getMessagesAfterCompactBoundary 就靠它——每轮只带边界之后的消息 + 那段摘要。相当于给对话"打了个存档点"，之前的浓缩成一句话，之后的照常。fork 一次 LLM 指开一个独立的小请求专门做摘要，不影响主对话。
L05

阈值与预测式压缩

什么时候触发 autocompact？autoCompact.ts 算出几档水位线：

autocompact error
0有效窗口 = 模型窗口 − 预留摘要输出满
  • 有效窗口 = 模型窗口 − 预留给摘要输出的空间（getEffectiveContextWindowSize，:33）。
  • autocompact 阈值 = 有效窗口 − buffer（buffer 随窗口大小变：800k 窗口留 50k，普通留 13k，:62）。
  • calculateTokenWarningState（:122）算出 warning / error / autocompact / blocking 各档。

预测式压缩（query.ts:852）更聪明：即使当前没超，如果"当前 tokens + 本轮预计增长"会超窗口，就提前压缩——避免这一轮跑到一半才发现超了。

为什么要预留摘要输出空间、要 buffer？ 因为压缩本身也要生成 token（摘要文本）；而且下一轮模型的回复也要占空间。如果卡到窗口边缘才压缩，可能"连生成摘要的空间都没有了"。留 buffer + 预测式提前压，是给系统留出腾挪余地。不要等撞墙才刹车，要预判着减速——这是资源管理的通用智慧。
L06

Stop hook：能"逼"模型继续

Day 03 提过——模型说"我完事了"（不再要工具），一轮本该结束。但停止前会跑 Stop hooks（query.ts:1557，handleStopHooks 在 src/query/stopHooks.ts:62）：

// query.ts:1557 附近
const stopResult = yield* handleStopHooks(...)
if (stopResult.preventContinuation) return { reason: 'stop_hook_prevented' }
if (stopResult.blockingErrors) {
  // ★ hook 说"还没达标" → 把错误插回消息，continue，逼模型继续干
  messages.push(...blockingErrorsAsMessages)
  stopHookActive = true
  continue   // 不结束，回循环顶再来一轮
}
Stop hook 的用途：你可以配一个 Stop hook（Day 14），在模型想收工时检查"活干完了吗"——比如"测试还没过""还有 TODO 没做"。如果不满意，hook 返回 blockingErrors，循环就把这些当作新消息喂回去，相当于对模型说"不行，接着弄"。这让你能强制 Agent"不达标不许停"。stopHooks.ts 还顺带在后台做提示建议、抽取记忆、auto dream 等（:137）。
L07

token budget：鼓励用满预算

还有一个反方向的机制（feature('TOKEN_BUDGET')，query.ts:1598）——token 预算。它不是省 token，而是"你给了这么多预算，别没干够就收工"：

  • checkTokenBudget（src/query/tokenBudget.ts:45）：如果还没用到预算的 90%（COMPLETION_THRESHOLD=0.9）且非"收益递减"，就返回 continue，插一条 nudge 消息让模型继续（query.ts:1606）。
  • 但如果 continuationCount >= 3 且每次增量 < 500 token（DIMINISHING_THRESHOLD），判为"收益递减"→ 停（tokenBudget.ts:59）。
为什么要"鼓励用满预算"？ 有时模型会过早收工（"我觉得差不多了"），但其实任务还能做得更完整。给它一个预算目标 + nudge，鼓励它多探索、多验证。同时用"收益递减检测"防止它为凑预算而空转（连续几轮几乎没产出就停）。这是"既防偷懒又防空耗"的平衡——和 Stop hook 一起，构成了对"何时该停"的精细控制。

把 Day 03 的停止原因和今天连起来：一轮结束前要过 prompt-too-long 恢复 → max-tokens 恢复 → Stop hooks → token budget，全通过才真 completed。"结束"不是一个简单判断，而是一串协商。
