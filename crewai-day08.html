Agent 间委派 delegation

多智能体的"协作"具体怎么发生？一个 Agent 怎么"喊同事帮忙"？今天揭示：委派被巧妙地实现成了"工具"，复用 Agent 已有的工具调用能力。

L01

委派是什么

委派（delegation）= 一个 Agent 把某件事交给另一个 Agent 去做。allow_delegation=True 的 Agent（或层级模式的经理，Day 06）才有这能力。

用团队打比方 写手 Agent 写着写着发现"我需要一个具体的数据，但这是研究员的专长"。如果它 allow_delegation=True，就能"喊研究员帮忙查一下"——把这个子任务委派给研究员，拿到结果后继续自己的工作。层级模式的经理更是把整个任务都委派给合适的下属。委派 = 团队成员之间互相求助/分派——这就是"协作"的具体机制。
L02

委派被做成"工具"（精妙设计）

关键洞察：CrewAI 没有另造一套"协作协议"，而是把委派实现成 Agent 的工具（tool）。AgentTools.tools()（tools/agent_tools/agent_tools.py:22）生成两个工具：

delegate_tool = DelegateWorkTool(agents=self.agents, ...)  # 把整件事交给同事做
ask_tool = AskQuestionTool(agents=self.agents, ...)        # 只是问同事一个问题
读法：委派 = 给 Agent 装一个"委派工具"。Agent 想找同事帮忙时，就像调用普通工具（Day 07）一样"调用委派工具"——填上"找谁、什么任务/问题"。这样多 Agent 协作复用了 Agent 已有的 function-calling 能力，不用另造轮子。
为什么这个设计聪明？ Agent 本来就会"用工具"（Day 07 的 ReAct）。把"找同事帮忙"也包装成一个工具，Agent 就能用它已经掌握的方式去协作——不需要学一套新的"协作 API"。对框架来说，也不用维护单独的多 Agent 通信机制。用已有的抽象（工具）去实现新需求（协作）——这是优雅设计的标志。
L03

两个委派工具

两者共享基类 BaseAgentTool（base_agent_tools.py:15），区别只在参数：

  • DelegateWorkTool（delegate_work_tool.py）：参数 task（要做的事）+ context + coworker（找谁）。"把这件事交给同事做完"。
  • AskQuestionTool（ask_question_tool.py）：参数 question（问题）+ context + coworker。"只是问同事一个问题"。
为什么分"委派整件事"和"只问一个问题"？ 粒度不同。有时你需要同事完整做一件事（"帮我写一段代码"），有时只需要问一句（"这个 API 的参数是什么？"）。分成两个工具，让委派方能精确表达意图，也让被委派方知道该做多少。两者的 _run 都转调基类的 _execute。
L04

_execute：委派的核心

BaseAgentTool._execute（base_agent_tools.py:46）做三件事：

# 1. 规范化同事名字（容错，L05）
# 2. 按 role 找到目标 agent（找不到返回可用同事列表）
# 3. 动态新建一个 Task 交给目标 agent 执行（:112-120）
task_with_assigned_agent = Task(
    description=task, agent=selected_agent,
    expected_output=I18N_DEFAULT.slice("manager_request"),
)
return selected_agent.execute_task(task_with_assigned_agent, context)
读法：委派的本质 = "临时造一个 Task，指定目标 agent，让它执行，拿回结果"。没有神秘的通信机制——就是动态创建一个新任务、调目标 agent 的 execute_task（Day 02）、返回结果。委派方拿到这个结果，继续自己的 ReAct 循环。
串起来看 写手 Agent（在自己的 ReAct 循环里）→ 决定调"委派工具"、参数 coworker="研究员"、task="查 X 的数据" → _execute 临时造一个 Task 交给研究员 Agent → 研究员跑它自己的 ReAct 循环完成 → 结果作为"工具返回值"回到写手 → 写手继续写。一个 Agent 的执行嵌套了另一个 Agent 的执行——这就是多智能体协作在代码层的真身。
L05

名字容错 sanitize_agent_name

_execute 第一步就规范化同事名字（base_agent_tools.py:20）——小写、去引号、合并空白，再按 role 模糊匹配。

为什么需要这么多容错？（源码注释点明了） 因为弱一点的模型经常把同事名字写得乱七八糟——加引号（"研究员"）、大小写不一致、多余空格、甚至编成非法 JSON。如果严格匹配，委派就总失败。所以框架做了大量容错：规范化名字、模糊匹配 role、找不到时返回"可用同事列表"的友好错误（而不是直接崩），让模型看到列表后重新选。"假设模型会犯错并优雅兜底"——又一次体现 Agent 框架的健壮性哲学（Day 07）。
L06

委派工具怎么注入

委派工具在 _prepare_tools（crew.py:1606）里按需注入：

if getattr(agent, "allow_delegation", False):
    if self.process == Process.hierarchical:
        tools = self._update_manager_tools(task, tools)   # 给经理注入
    elif agent:
        tools = self._add_delegation_tools(task, tools)   # 给普通 agent 注入
读法：只有 allow_delegation=True 的 agent 才被注入委派工具。_add_delegation_tools（crew.py:1781）把"除自己之外"的所有 agent 作为可委派对象。层级模式的经理（Day 06）则总是被注入——它的全部工具就是委派工具（Day 06 讲的"经理不能带普通工具"）。
所以：顺序模式下某个 agent 设了 allow_delegation=True，它就能在需要时喊别的同事帮忙；层级模式下经理靠委派工具把每个任务分派给下属。两种协作场景，同一套委派工具机制。
L07

为什么用"工具"实现委派（设计回味）

  • 复用能力：Agent 本就会用工具，委派复用这个能力，零学习成本。
  • 统一循环：委派发生在 Agent 的 ReAct 循环里，和调普通工具没区别，执行引擎不用特殊处理。
  • 自然嵌套：被委派的 Agent 跑自己的循环，结果作为工具返回值——天然支持多层协作。
  • LLM 友好：模型擅长"选工具、填参数"，委派用这个它熟悉的方式表达。
这是"命令模式 + 工具抽象"的结合：委派被封装成一个可调用的命令对象（工具），协作复用 LLM 的 function-calling。回味 Day 13 的 OpenHands——它也把"子 Agent 委派"实现为 TaskAction/子 Agent 工具；eino 也推荐"Agent-as-Tool"。三个框架不约而同——因为"把协作做成工具"确实是最优雅的方案。
