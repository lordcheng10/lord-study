Flow 装饰器

Flow 的"接线工具"。精读 @start / @listen / @router / and_ / or_——它们如何把普通方法连成事件驱动的图。核心洞察：装饰器只"贴元数据"，不含执行逻辑。

L01

装饰器只贴元数据（关键认知）

最重要的认知：这些装饰器不改变方法的运行时行为，只是在方法上盖一个"元数据章"。真正的"接线"发生在引擎启动时读取这些元数据。

每个装饰器把原函数包进一个 FlowMethod 子类（flow_wrappers.py:48）：StartMethod、ListenMethod、RouterMethod。它实现了描述符协议 __get__，所以包装后仍能像普通方法 self.xxx() 调用，同时携带 __flow_method_definition__ 元数据。

"贴元数据"是什么意思？ 想象你在每个方法上贴一张便利贴：@start 贴"我是入口"、@listen(A) 贴"A 完成后叫我"、@router 贴"我会发射事件决定分支"。方法本身的代码没变，只是多了这些"说明标签"。Flow 引擎启动时把所有便利贴收集起来，画出"谁触发谁"的图，然后照图执行。装饰器 = 声明关系的便利贴，引擎 = 读便利贴干活的人。这种"声明 vs 执行分离"是 Flow 三段式架构的基础（Day 11）。
L02

@start：入口点

# dsl/_start.py:18
def decorator(func):
    wrapper = StartMethod(func)
    _merge_flow_method_definition(wrapper, FlowMethodDefinition(
        do=_method_action(func),
        start=(条件 if condition else True),   # 无参 → start=True 无条件入口
    ))
    return wrapper
读法：@start() 无参 → 该方法是"无条件入口"（Flow 一启动就跑它）。@start("某事件") → 满足某条件时才作为入口。可以有多个 @start，它们会并行执行（Day 11）。
L03

@listen：响应他人完成

# dsl/_listen.py:18
wrapper = ListenMethod(func)
_merge_flow_method_definition(wrapper, FlowMethodDefinition(
    do=_method_action(func),
    listen=_to_definition_condition(condition),   # 监听的条件
))
读法：@listen(condition) 的 condition 可以是：方法名字符串、方法引用，或 or_()/and_() 的结果。_to_definition_condition（dsl/_conditions.py:75）把它归一化成 str 或 {"or":[...]}/{"and":[...]} 结构存进元数据。
监听单个 vs 监听组合 @listen(step_a)：step_a 一完成就触发我。@listen(and_(a, b))：a 和 b 都完成才触发我（等所有）。@listen(or_(a, b))：a 或 b 任一完成就触发我（竞速）。这三种覆盖了工作流里"依赖前置步骤"的所有常见情况。用声明式的方式表达"我依赖谁"，比手写 if 判断清晰得多。
L04

@router：条件分支

@router（dsl/_router.py:97）特殊在：它既 listen 触发，又把自己的返回值当成新的事件名发射出去，供下游 listen：

@router(analyze)
def decide(self, result):
    if result.score > 0.8:
        return "SUCCESS"      # ← 返回值变成事件名
    return "RETRY"

@listen("SUCCESS")           # 接住 router 发射的 "SUCCESS"
def celebrate(self): ...
@listen("RETRY")
def try_again(self): ...
读法：router 根据逻辑返回不同字符串（如 "SUCCESS"/"RETRY"），这些字符串成为事件名，下游用 @listen("SUCCESS") 接住——实现分支。emit 列表（可能的返回值）可显式传，也可从返回类型注解 Literal[...] 或 Enum 自动推断。
router = 工作流的 if/else 岔路口 普通 @listen 是"固定的边"（A 完成一定触发 B）。@router 是"运行时决定走哪条边"——看结果返回不同事件名，把流程导向不同分支。就像流程图里的菱形判断框。有了 router，Flow 就能表达"根据结果走不同路径"的复杂工作流。
L05

and_ / or_：组合触发条件

# dsl/_conditions.py:22
def or_(*triggers):  return _condition_tree(OR_CONDITION, triggers)   # 任一触发
def and_(*triggers): return _condition_tree(AND_CONDITION, triggers)  # 全部触发
# 生成 {"type":"OR"/"AND", "conditions":[...]} 的树，可嵌套
读法：or_=任一前置完成即触发；and_=所有前置都完成才触发。它们生成一棵条件树（可嵌套 and_(a, or_(b, c))），存进 listen 的元数据。
用汇聚场景理解 and_：一个"汇总"步骤要等"研究"和"竞品分析"都完成才能开始（等齐所有输入）。or_：一个"通知"步骤只要"成功"或"失败"任一发生就触发（竞速，谁先来）。这两个组合子让 Flow 能表达并行分支的"汇聚"和"竞速"——真实工作流的常见形态。（呼应 eino Graph 的 AllPredecessor/AnyPredecessor 触发模式！同一个概念。）
L06

懒加载接线

接线的时机很讲究：类定义时装饰器只贴元数据；首次访问 Flow.flow_definition() 时才扫描所有方法、构建成 FlowDefinition（runtime/__init__.py:469 → build_flow_definition）。

为什么"懒加载"（用到时才构建）？ 如果每次 import 这个 Flow 类都立刻解析所有装饰器、构建图，会拖慢导入速度（尤其你只是 import 但还没运行）。懒加载 = "第一次真要用（kickoff）时才构建图"，之后缓存。import 快、运行时才付出构建成本、且只付一次。"延迟到必要时才做重活"是常见的性能优化——和 crewAI 的 litellm 懒加载、很多框架的思路一致。
构建时 _iter_flow_methods（dsl/_utils.py:385）扫描类上所有带 __flow_method_definition__ 的 wrapper，_build_method_definition 汇总成 FlowDefinition（Day 11 的"中间表示"）。这张纯数据的图，就是引擎执行的依据，也是能从 YAML 加载 Flow 的原因。
L07

or_ 竞速（进阶）

or_ 监听有个精细处理——竞速（racing）：多个事件都能触发同一个 or_ 监听器时，只让最先到达的那个触发，其余取消（_execute_racing_listeners，runtime/__init__.py:1116）。

为什么要竞速？ 想象 @listen(or_(success, failure)) 的"清理"步骤。如果 success 和 failure 都发生了（罕见但可能），你不希望清理跑两次。竞速保证"or_ 监听器只被最先到的事件触发一次"。这是并发编排里的细节——防止重复执行。条件判定 _condition_met（:2860）用一个"已见事件集合"seen 来跟踪：and_ 等 seen 集齐所有、or_ 见第一个就触发。
回忆 Day 11 的 max_method_calls 防死循环——Flow 引擎处理了大量并发编排的边界情况（循环流、竞速、汇聚），这些是"事件驱动工作流引擎"的硬核部分。你不用手动处理这些，引擎替你兜住。
