工具系统 Tool 接口

Agent 的"手脚"。今天讲一个工具必须实现什么、怎么注册、怎么变成发给模型的 tool 定义，以及执行一次工具经过哪些关卡。

L01

工具是什么：让模型能"动手"的接口

Day 01 说过 Agent = 模型 + 工具 + 循环。工具就是"模型能调用去改变世界的能力"——读文件、写文件、跑命令、搜代码、上网。模型本身只会输出文字；是"工具"让它能真正干活。

流程上（Day 03 讲过）：模型在回复里输出一个 tool_use 块（"我要调 Read，参数是这个文件路径"）→ 系统执行对应工具 → 把结果作为 tool_result 回给模型。所以"工具"在代码里要解决三件事：①怎么告诉模型有这个工具（定义/schema）②怎么判断这次调用能不能执行（权限）③怎么真执行并返回结果（call）。

L02

两层接口：协议层 vs 宿主层

理解工具系统，先搞清它有两层定义——这是最容易懵的地方：

① 协议层 CoreTool（宿主无关）

packages/agent-tools/src/types.ts

一个"纯类型 + 零运行时依赖"的最小内核接口。只约定工具的本质：name、inputSchema、call、权限。不关心 React/UI。

② 宿主层 Tool（Claude Code 实际用）

src/Tool.ts

在协议层之上，加了一大堆 UI 渲染方法（怎么在终端里画这个工具的调用/结果）。宿主工具"结构上满足"协议层接口。

为什么分两层？ packages/agent-tools（协议层）零依赖，能被任何环境复用——比如子代理、SDK、测试。src/Tool.ts（宿主层）才绑定终端 UI。这样"工具是什么"（协议）和"工具在这个 CLI 里怎么显示"（宿主）解耦了。你写业务逻辑只关心协议层；写终端渲染才碰宿主层。
L03

一个工具要实现什么

宿主层 Tool（src/Tool.ts:372）的核心契约。必须实现的：

字段/方法作用
name工具名（模型看到的）
inputSchema输入参数的 zod schema，用于校验 + 转成给模型的 JSON Schema
call(args, ctx, canUseTool, ...)★ 真正执行，返回 ToolResult（:389）
prompt(options)★ 发给模型的工具说明（:528）——注意不是 description！
description(input, opts)给 UI/权限对话框看的描述（:396）
checkPermissions(input, ctx)返回三态权限结果（:510）
isReadOnly / isConcurrencySafe / isDestructive行为标志（能否并发、是否只读、是否破坏性）
maxResultSizeChars结果超过这个字符数就落盘，模型只看预览+文件路径
mapToolResultToToolResultBlockParam把结果映射成 API 的 tool_result 块

权限结果是三态（types.ts:87）：

type PermissionResult =
  | { behavior: 'allow'; updatedInput }    // 放行（可改写入参）
  | { behavior: 'deny'; message }          // 拒绝
  | { behavior: 'passthrough' }            // 交给通用权限系统裁决
zod 是什么？ 一个 TypeScript 的"运行时数据校验"库。你用 z.object({ file_path: z.string() }) 声明"输入长这样"，它既能在运行时校验模型传来的参数合不合法，又能自动转成 JSON Schema 发给模型当"参数说明"。一处声明，同时管校验和文档——这是本工具系统的基石。
L04

buildTool：安全默认值（fail-closed）

你读工具代码会发现很多工具没写 checkPermissions/isReadOnly。因为它们都通过 buildTool()（Tool.ts:767）导出，工厂帮它们填了"往安全一侧靠"的默认值：

const TOOL_DEFAULTS = {
  isEnabled: () => true,
  isConcurrencySafe: () => false,   // ← 默认假设"不可并发"（保守）
  isReadOnly: () => false,          // ← 默认假设"会写"（保守）
  isDestructive: () => false,
  checkPermissions: (input) => ({ behavior: 'allow', updatedInput: input }),
  // ...
}
export function buildTool(def) {
  return { ...TOOL_DEFAULTS, userFacingName: () => def.name, ...def }
}
fail-closed（默认保守）：安全设计原则——不确定时选"更安全"的默认。这里默认"不可并发、会写"，工具只有主动声明 isReadOnly: () => true 才会被当只读、才能并发执行。这样漏写标志的工具会被当成"危险的写工具"串行执行，而不是被误当只读并发跑坏。忘记声明的代价是"慢一点"而不是"出事"——这就是 fail-closed 的价值。

所有工具都用 buildTool({...}) 导出，如 FileReadTool、BashTool。Day 08 精读几个时你会反复看到这个模式。

L05

注册与发现

工具从"全部候选"到"这次能给模型用的"，经过几道过滤（src/tools.ts）：

1

getAllBaseTools()（tools.ts:218）：返回当前环境所有可能的工具（受 process.env/feature() 门控）

2

getTools(permissionContext)（tools.ts:304）：去掉被整工具 deny 的、被 REPL 包裹的、isEnabled()===false 的

3

assembleToolPool（tools.ts:378）：内置工具 + MCP 工具合并、按名排序、去重（内置优先）

为什么要"按名排序"？ 因为工具定义会被放进发给模型的 prompt，而 Anthropic 有 prompt 缓存——完全相同的 prompt 前缀能命中缓存、省钱省时间。如果工具顺序每次都变，prompt 字节就变，缓存永远命中不了。排序保证工具列表稳定，从而缓存稳定。这种"为了缓存稳定而排序"的细节在本项目随处可见。

还有个提前过滤：filterToolsByDenyRules（tools.ts:295）在把工具给模型之前就剔除被整工具 deny 的（包括 MCP mcp__server 前缀级 deny）——被禁的工具模型根本看不到，而不是"看到了但调用时被拒"。

L06

暴露给模型：一个反直觉点

工具怎么变成 Anthropic API 的 tool 定义？靠 toolToAPISchema（src/utils/api.ts:119）：

// api.ts:169 —— 产出发给模型的工具定义
base = {
  name: tool.name,
  description: await tool.prompt({...}),   // ← ★ 用 prompt() 不是 description()！
  input_schema,                            // ← zod 转 JSON Schema
}

⚠️ 反直觉但很重要：发给模型的工具"描述"字段，取自 tool.prompt()，不是 tool.description()。description() 是给界面/权限弹窗看的（简短），prompt() 才是给模型看的（详细的使用说明，教模型什么时候、怎么用这个工具）。看工具代码时别搞混——想知道"模型看到的工具说明"，去读 prompt()。

schema 来源二选一（api.ts:157）：内置工具用 zodToJsonSchema(tool.inputSchema) 把 zod 转成 JSON Schema；MCP 工具直接用它原始的 inputJSONSchema。

延迟加载工具（deferred）：有些不常用的工具（Artifact、LSP、NotebookEdit 等）标了 shouldDefer: true，它们的 schema 不发给模型（省 prompt 空间）。模型需要时先调 SearchExtraTools("select:工具名") 发现它们、再用 ExecuteExtraTool 调用（claude.ts:1187）。这就是你在系统提示里偶尔看到"deferred tools"的由来——工具太多，按需加载。
L07

执行管线全景：一次工具调用过哪些关卡

模型说"调 Edit"后，到真正执行、返回结果，中间过一条流水线（src/services/tools/toolExecution.ts）。唯一的 tool.call() 调用点在 :1256，它前后被一堆关卡包着：

1

找工具 findToolByName（支持别名，如老 KillShell→TaskStop）

2

zod schema 校验（:657）：参数不合法 → InputValidationError

3

validateInput（:725）：工具自定义的业务校验

4

backfill 可观察输入（:826）：把 file_path 展开成绝对路径给 hook/权限看（防绕过）

5

PreToolUse hooks（:842）：可拦截/改输入/直接放行或拒绝（Day 14）

6

权限检查：走 canUseTool（Day 09）

7

★ tool.call() 真执行（:1256）——唯一执行点

8

结果映射（:1367）+ 超大结果落盘（:1478，按 maxResultSizeChars）

9

PostToolUse hooks（:1558）：可改写结果/追加消息（Day 14）

并发分区（toolOrchestration.ts:106）：一批工具调用会被分成"连续的只读工具"（并发跑，上限 10）和"写工具"（串行跑），依据就是 L04 讲的 isConcurrencySafe。所以模型一次要读 5 个文件，它们会并发执行；但要改 3 个文件，会串行——避免写冲突。这是 fail-closed 默认值直接影响性能与安全的地方。
