Day 09 / 共 20 天 · 第 2 周 过滤器与请求

Router 路由过滤器

Router（router.cc，2600+ 行）是 decode 链的终端过滤器——它选上游、发请求、收响应，把响应灌回 encode 链。它是"请求进"和"响应出"的交汇点。

L01

终端过滤器

Filter（router.h:298）继承 Http::StreamDecoderFilter——它是 decode 链的最后一个过滤器。

"终端过滤器"是什么？ 前面的 L7 过滤器（认证、限流…）处理完都调 Continue 往下传。Router 是最后一站——它不再往下传，而是把请求转发到上游后端，然后等响应。它是"请求方向的终点、响应方向的起点"。好比工厂流水线的最后一个工位负责"打包发货（转发上游）"，收到回执（响应）后再启动"返程流水线（encode 链）"。所有请求最终都汇到 Router 转发出去（除非被前面的过滤器 sendLocalReply 截胡）。
L02

拿路由

// router.cc:440 Filter::decodeHeaders
route_ = callbacks_->route();       // :471 读 HCM 已缓存的路由（Day 05/07 强调：路由在 HCM 算好）
if (!route_) { sendLocalReply(404); return StopIteration; }  // :472 没路由 → 404
// 直接响应（direct response）处理 :483
route_entry_ = route_->routeEntry();  // :512
读法：Router 不算路由，只读 HCM 缓存好的 route() 结果（Day 05 易错点）。没匹配到路由就直接返回 404。routeEntry() 拿到路由条目（含目标集群名、重试策略、超时等）。
L03

选集群主机

// router.cc:517 从线程本地拿目标集群（Day 13 的 getThreadLocalCluster）
cluster = config_->cm_.getThreadLocalCluster(route_entry_->clusterName());
cluster_ = cluster->info();                    // :529
// :677 cluster->chooseHost(this) 负载均衡选一个上游主机（Day 14 的 chooseHost）
// 同步选到主机 → continueDecodeHeaders（:686）→ return StopIteration（:688 等上游）
读法：把第 3 周的知识用起来了：getThreadLocalCluster（Day 13 无锁拿集群）→ chooseHost（Day 14 负载均衡选后端）。选到主机后返回 StopIteration——因为要等上游响应，decode 链暂停。
L04

发上游请求

continueDecodeHeaders（router.cc:725）：createConnPool（:732）拿连接池 → 选主机 → 创建 UpstreamRequest（:831）向上游编码请求。请求体经 decodeData（:975）转发给上游。

连接池：复用上游连接 Router 不为每个请求都新建一条到上游的连接（太慢）。它用"连接池"——把到某个上游主机的连接缓存复用。要发请求时从池里取一条空闲连接（或新建），用完放回。这对性能至关重要：建立 TCP + TLS 连接开销大，复用能省掉大量握手。UpstreamRequest 代表"这次转发到上游的请求"，管理它的生命周期。
L05

响应回程（启动 encode 链）

// router.cc:1711 Filter::onUpstreamHeaders（上游响应头到达）
// 处理 gRPC 状态映射、outlier detection（Day 15 被动健康检查上报）
callbacks_->encodeHeaders(std::move(headers), end_stream, ...);  // :1927 ★启动 encode 过滤器链！
// onUpstreamData（:1931）→ callbacks_->encodeData（:1945）
读法：上游响应回来，Router 调 callbacks_->encodeHeaders——这就是启动 encode 过滤器链的触发点（Day 08 的 encode 路径从这里开始）。它还顺便向 outlier detection 上报请求结果（Day 15 被动健康检查靠这个累积统计）。
L06

重试与超时

Router 还负责重试（上游失败/超时时按路由配置的重试策略换个主机再试）和超时（请求太久没响应就中断）。这些配置来自 route_entry_（路由条目）。

重试为什么在 Router 做？ 重试需要"重新选一个上游主机再发一次"——这正是 Router 的职责范围。比如后端 A 返回 503，Router 按重试策略（重试 2 次、只对 5xx 重试）换后端 B 再发。这对用户透明（用户只看到最终结果）。超时同理——Router 起个定时器（Day 04），到点还没响应就放弃/重试。把"选主机 + 发请求 + 重试 + 超时"都放在 Router，因为它掌握着"和上游打交道"的全部上下文。这是 Envoy 提供"弹性"（resilience）的核心。
L07

交汇点

Router 是理解 Envoy 请求流的枢纽：
• decode 链在这里终结（请求方向的终点）
• 在这里选集群（Day 13）+ 负载均衡选主机（Day 14）+ 用连接池发上游
• 上游响应回来，在这里启动 encode 链（响应方向的起点）
所以 Router 是"decode 和 encode 的交汇点"，也是"L7 过滤器世界和上游世界的边界"。搞懂 Router，就把前 3 周（过滤器 + 集群 + 负载均衡）全串起来了。想看更简单的过滤器例子，可读 source/extensions/filters/http/ 下的 cors、buffer 等。
