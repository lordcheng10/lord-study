Day 08 / 共 20 天 · 第 2 周 路由/配置/数据面

六大抽象对象

昨天配置从 etcd 同步进内存，今天看"配置长什么样"——APISIX 的六大核心对象。它们的 schema 定义都在 apisix/schema_def.lua，理解它们的字段和引用关系，就理解了 APISIX 的配置模型。

L01

etcd 里的组织

每类对象在 etcd 里有自己的前缀，一个对象一个 key：

/apisix/routes/{id}          Route
/apisix/services/{id}        Service
/apisix/upstreams/{id}       Upstream
/apisix/consumers/{name}     Consumer
/apisix/plugin_configs/{id}  Plugin Config
/apisix/global_rules/{id}    Global Rule
/apisix/ssls/{id}  /apisix/plugin_metadata/{name}  ...
读法：各子系统 watch 自己那个前缀（Day 07）。对象的 schema（有哪些字段、什么类型）定义在 schema_def.lua——_M.route（:553）、_M.service（:684）、_M.upstream（:756）、_M.consumer（:715）、_M.plugin_config（:1018）、_M.global_rule（:905）。
L02

Route（路由）

schema_def.lua:553-680。核心字段：

字段含义
uri / uris匹配的路径
host / hosts匹配的域名
methods匹配的 HTTP 方法
vars更复杂的匹配表达式
priority优先级（多路由匹配时）
plugins这条路由启用的插件
upstream / upstream_id内联上游 或 引用上游
service_id / plugin_config_id引用可复用配置
Route 是"中心枢纽" Route 把三件事绑在一起：匹配什么（uri/host/methods/vars）、怎么处理（plugins）、转发到哪（upstream）。它可以内联一切（自己写死上游和插件），也可以引用 service/upstream/plugin_config 复用。Day 04 的 matched_route 就是它。
L03

Service（服务）

schema_def.lua:684-714：含 plugins + upstream/upstream_id（和 Route 类似，但没有匹配条件）。

Service = "可复用的插件+上游套餐" 如果 20 条路由都指向同一组后端、用同样的限流/鉴权，与其在 20 条路由里重复配，不如建一个 Service 装好这些，20 条路由都 service_id: X 引用它。改一次 Service，20 条路由全生效（Day 04 的 merge_service_route 就是运行时把 Service 合并进 Route）。Service 没有"匹配条件"——匹配是 Route 的职责，Service 只管"处理和转发"。
L04

Upstream（上游）

schema_def.lua:756（upstream_schema）核心字段：nodes（后端实例列表 host:port + weight）、type（负载均衡算法 roundrobin/chash/...）、scheme（http/https/grpc）、checks（健康检查）、discovery_type（服务发现）、timeout、retries。

读法：Upstream 描述"一组后端 + 怎么在它们之间分流"。nodes 可以是静态列表，也可以留空用 discovery_type（Day 16 服务发现动态获取）。Day 10 的负载均衡就是在 nodes 里按 type 挑一个。Route/Service 都能引用 upstream_id 复用。
L05

Consumer（消费者）

schema_def.lua:715-755：username + plugins（consumer 专属插件，通常是鉴权凭据如 key-auth 的 key）+ group_id。还有 credential（:736）分离凭据。

Consumer 是"API 调用方的身份" Consumer 代表"谁在调 API"——通常配合鉴权插件：consumer "alice" 的 plugins 里有 key-auth: {key: "alice-secret"}。请求带这个 key，鉴权插件就识别出"这是 alice",然后能给 alice 用专属配置（专属限流等）。回想 Day 04 的 merge_consumer_route——识别 consumer 后合并她的专属配置。Consumer 用 username 而非数字 id 做 key（/apisix/consumers/alice）。Day 14 详讲。
L06

Plugin Config / Global Rule

  • Plugin Config（:1018）：一组可复用的插件配置（只有 plugins，比 Service 更轻，不含上游）。Route 用 plugin_config_id 引用。
  • Global Rule（:905）：对所有请求生效的插件（不绑任何路由）。Day 04 里"匹配路由前后都跑 global_rules"就是它。
三种"复用/全局"层次 Plugin Config = "可复用的插件套餐"（多路由共享一组插件）；Service = "插件+上游套餐"；Global Rule = "全站生效的插件"（如全局的 prometheus 指标、全局限流）。层层递进的复用粒度，让你不用到处重复配置。还有 Consumer Group（:1039）——一组 consumer 共享配置。
L07

引用关系

Route ──plugin_config_id──> Plugin Config（复用插件）
      ──service_id────────> Service ──upstream_id──> Upstream
      ──upstream_id───────> Upstream（也可内联 upstream）
Consumer（鉴权识别）──> 合并专属 plugins
Global Rule（无引用，全局生效）
读法：运行时 Day 04 的合并顺序：Route 基础 → 合并 plugin_config → 合并 service → 识别 consumer 后合并 consumer 配置。越具体的覆盖越通用的（consumer > route > service）。这套引用+合并模型让配置既能复用又能精细定制——和上一站 Higress Console 的路由/服务/插件概念完全相通。
