多维评测 Eval + CI 阻断

怎么量化"这个 Agent 靠不靠谱"？怎么防止改一版 prompt 就偷偷变差？答案是像跑单元测试一样，给 Agent 跑一套"标准考卷"打分，不及格就拦合并。

L01

为什么 Agent 必须评测

传统代码有单元测试：输入固定，输出对就 PASS。但 Agent 输出的是"自然语言 + 大模型推理结果"——同一个问题两次回答可能措辞都不一样，没法简单 assert 相等。

可如果不评测，你改一句 prompt、换个模型，根本不知道 Agent 变好了还是变差了。所以框架把评测做成一等公民：准备一套"标准考卷"(golden set)，给 Agent 跑一遍，从多个维度打分，不及格就拦住不让合并。代码在 packages/ai-trust-toolkit/src/ai_trust_toolkit/eval/。

AGENTS.md 里有条硬规矩：新 Agent 必须先有评测样本 + Critic，才能合并。评测不是可选项，是准入门槛。
L02

golden set 与评测样本

"标准考卷"就是一批 EvalSample（schemas.py:61），存成 JSONL 文件（每行一个样本），放在每个 agent 的 data/eval_samples.jsonl。一个样本长这样：

{
  "id": "sample-001",
  "description": "DB 连接池耗尽导致的服务雪崩",
  "input": { "user_question": "service-A 大量超时" },
  "ground_truth": {              // 标准答案（人工标注）
    "primary_category": "db_connection_pool",
    "candidate_categories": ["db_connection_pool", "slow_query"],
    "keywords_in_hypothesis": ["连接池", "耗尽"],
    "min_supporting_specialists": 2,
    "overall_confidence_at_least": "中"
  },
  "mock_responses": { ... }      // 喂给 FakeLLM 的固定回复，保证可复现
}
ground_truth（标准答案）：人工标注的"这题正确答案应该长什么样"。评测就是拿 Agent 的输出跟它比。
mock_responses：因为评测走 FakeLLM（Day 11），这里预置了假大模型该返回什么——保证每次评测结果完全可复现，不受真实 LLM 随机性干扰。

EvalSample.load_jsonl()（schemas.py:84）批量读入。GroundTruth.from_dict()（schemas.py:44）还有个巧思：不认识的 key 自动塞进 detail，方便非 RCA 类 agent 复用同一套结构。

L03

对话型：5 维评分（FiveDimScorer）

像 sre-rca 这种"给结论"的 agent，用 FiveDimScorer（scorers.py:48）打 5 个布尔维度——每一维过没过：

🎯
top1_hit

第一根因命中标准答案

🥉
top3_hit

Top-3 里命中候选之一

📏
confidence

置信度校准达标

👥
specialists

足够多专家支撑

🔑
keywords

关键词命中率≥50%

匹配逻辑很务实（scorers.py:321 _category_match）：大小写不敏感、去下划线、支持子串——避免因为"DB_pool" vs "db pool"这种格式差异误判。置信度比较用 {低:1, 中:2, 高:3} 的等级映射（scorers.py:77）。

为什么用"多维布尔"而不是"一个总分"？ 因为不同维度反映不同问题：top1 不中但 top3 中，说明"方向对但排序不准"；关键词全中但置信度虚高，说明"过度自信"。分维度看，你能精确知道是哪一项退步了，而不是只看到一个模糊的总分下降。
L04

coding 型：6 维加权（CodingAgentScorer）

像 spec-executor 这种"改代码"的 agent，评价标准不同——用 CodingAgentScorer（scorers.py:107）打 6 个加权浮点维度（权重之和=1.0）：

维度衡量
tool_success工具调用成功率
build_pass改完能否通过构建/测试
patch_count补丁数量是否合理
iterations迭代轮数（越少越好）
risk_distribution改动风险分布
change_minimality改动是否最小化（可选用 Haiku 当裁判）

change_minimality 支持两种裁判模式：heuristic（纯计算）或 haiku（用便宜 LLM 判断"这次改动是不是过度了"，失败自动回退启发式，scorers.py:177）。

两种 scorer 都实现同一个 BaseScorer 协议——所以 run_eval 不用关心具体是哪种，传进去就能跑。这又是 Day 09 讲的"依赖抽象接口"套路。EvalScore.all_passed（schemas.py:142）会自动识别是 5 维布尔还是 coding 加权，选对应的判据。
L05

run_eval：批量跑考卷

把样本、图、scorer 交给 run_eval()（runner.py:17）就能跑批：

加载golden set→ 并发跑图每题 ainvoke→ 打分scorer.score→ 汇总EvalReport 
samples = EvalSample.load_jsonl("data/eval_samples.jsonl")
report = await run_eval(graph, samples, scorer=FiveDimScorer())
report.print_summary()              # 漂亮打印各维通过率

# CI 里用阈值判定，不达标就退出码非 0
if not report.meets_thresholds(EvalThresholds(top1=0.5, top3=0.7)):
    raise SystemExit(1)

关键细节：用 asyncio.Semaphore 控制并发（runner.py:42）；单条样本挂了不影响整体——异常被捕获记进那条的 EvalScore.error（runner.py:55）。整套评测走 FakeLLM，所以几秒跑完、结果可复现。

L06

阈值与 CI 阻断：不达标合不了

EvalThresholds（schemas.py:98）定义每一维的及格线，默认：top1=0.5、top3=0.7、confidence=0.7、specialists=0.7、keywords=0.6。report.meets_thresholds()（schemas.py:222）任一维不达标就返回 False。

这个能力被接进了 CI 流水线（Day 18 细讲）——有一道专门的闸门 ci-gate-eval：

🚫

ci-gate-eval：评测不达标 → 阻止 merge

PR 里改了某个 agent，CI 自动对它重跑评测，任一维掉到阈值以下，流水线直接失败，合并按钮点不动。PR 模式只跑变更的 agent，省时间。

这就是"防退步"的护城河：你改 prompt、换模型、重构节点——只要让 Agent 的核心能力退步了，CI 立刻拦下来。评测样本和业务代码放在同一个仓库、同一个 PR，所以能力和考卷永远同步演进。这是把"Agent 质量"纳入工程化管控的关键一步。
L07

在线评测 & 回归检测

除了 CI 里用 golden set 的"离线评测"，框架还有两个进阶能力：

ObservableScorer — 在线评测（scorers.py:381）

golden set 需要人工标答案，成本高、覆盖有限。ObservableScorer 不依赖标准答案，纯从线上真实调用的 envelope 信号统计：成功率分布、延迟/成本的百分位、SLO 违约率。它回答的是"线上整体健康吗"，而不是"这道题对不对"。

RegressionDetector — 回归检测

对比"这次评测"和"历史基线"，自动找出哪一维退步了。配合仓库里的 eval-replay skill（Day 19）：给一个线上出问题的 case_id，能拉出历史输入重放、对比 5 维评分、定位是哪一维掉了。

离线 vs 在线评测：离线 = 拿固定考卷考（可控、可复现、进 CI）；在线 = 观察真实流量表现（覆盖真实分布、发现考卷没覆盖的问题）。两者互补——离线保下限，在线抓意外。
