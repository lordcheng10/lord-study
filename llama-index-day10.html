Day 10 / 共 20 天 · 第 2 周 索引/嵌入/存储

其他索引类型

第 2 周收官。VectorStoreIndex 最常用，但不是唯一。今天概览其他索引——SummaryIndex/KeywordTable/DocumentSummary/Tree/PropertyGraph，看它们各自的组织方式和适用场景。理解"索引类型 = 检索策略"。

L01

索引不止向量

indices/ 目录：vector_store/（Day 07）、list/（SummaryIndex）、keyword_table/、document_summary/、tree/、property_graph/、knowledge_graph/、struct_store/（SQL 等）。

"索引类型"决定"怎么找" 不同索引 = 不同的"数据组织方式" = 不同的"检索策略"。向量索引按语义找；关键词索引按词找；摘要索引先看摘要再定位；图索引按实体关系找。它们都继承 BaseIndex（Day 07 统一接口），但内部 index_struct 和检索逻辑不同。选对索引类型能大幅提升特定场景的效果。
L02

SummaryIndex（列表索引）

indices/list/：把所有 Node 存成一个列表，检索时遍历全部（或用 LLM/嵌入辅助选）。

最简单：全都要 SummaryIndex 不做"筛选"——它把所有 Node 都拿来（或按顺序过一遍）。适合"需要综合全部内容"的场景，比如"总结这份文档"（要看全文）。缺点：文档多了慢（全遍历 + 全喂 LLM）。它的 index_struct 就是一个 Node id 列表。和 VectorStoreIndex（只取最相关几个）相反——一个"全要"，一个"精选"。
L03

KeywordTableIndex（关键词索引）

indices/keyword_table/：给每个 Node 抽取关键词，建"关键词 → Node"的倒排表。查询时从问题抽关键词，找含这些关键词的 Node。

经典的关键词/倒排检索 这是搜索引擎式的检索——按词匹配（像 Google 早期）。适合"精确术语匹配"场景（产品型号、专有名词），这些用向量反而可能不准。缺点：不懂语义（"退款"和"退货"是不同词）。实践中常和向量检索"混合"（既按词又按语义），取长补短。关键词可用 LLM 抽或简单规则抽。
L04

DocumentSummaryIndex

indices/document_summary/：给每份文档生成一个摘要，检索时先按摘要选出相关文档，再深入其 Node。

"两级检索"：先选文档再选段落 当你有很多份文档（每份很长）时，直接在所有 Node 里找可能被"局部相似但整体无关"的段落误导。DocumentSummaryIndex 先用摘要判断"哪几份文档相关",再在这些文档里细找。好比先看书的目录/简介选书，再翻具体章节。提升"文档级相关性"的准确度。
L05

TreeIndex（树索引）

indices/tree/：把 Node 建成树——叶子是原始 Node，上层是 LLM 生成的"子节点摘要"，层层向上。检索时从根往下走（或从叶子向上）。

层级摘要，支持"从粗到细" 建树时用 LLM 把每组 Node 摘要成父节点，形成"摘要金字塔"。查询时可以从顶层摘要逐层向下定位到最相关的叶子。适合超长文档的层级导航。回想 Day 02 的 PARENT/CHILD 关系——TreeIndex 就是用它们建的层级结构。建树要调很多次 LLM（贵），但检索时能高效聚焦。
L06

PropertyGraphIndex（知识图谱）

indices/property_graph/（较新，取代旧的 knowledge_graph）：用 LLM 从文档抽取"实体-关系-实体"三元组，建成知识图谱。检索时按图关系遍历（GraphRAG）。

GraphRAG：按"关系"检索 普通向量检索找"语义相似的段落";但有些问题需要"多跳推理"——"A 公司的 CEO 创办的另一家公司在哪上市?"。这要顺着"CEO→创办→公司→上市地"的关系链走。PropertyGraphIndex 把文档变成知识图谱（实体是点、关系是边），检索时沿图遍历。这是 2024 年很火的 GraphRAG 方向——适合需要关系推理、多跳问答的场景。建图要大量 LLM 抽取（贵），但能回答向量检索答不了的关系型问题。
L07

怎么选索引

场景推荐索引
通用问答（默认）VectorStoreIndex
总结/需要全文SummaryIndex
精确术语匹配KeywordTableIndex（或混合）
多份长文档DocumentSummaryIndex
关系/多跳推理PropertyGraphIndex
可以组合（Router/Composable） 不必二选一——LlamaIndex 支持"路由"（RouterQueryEngine，问题来了自动选合适的索引）和"可组合"（composability，一个索引嵌套另一个）。比如用 DocumentSummaryIndex 选文档、再用 VectorStoreIndex 在文档内检索。90% 的入门场景 VectorStoreIndex 就够——其他是特定需求的进阶选择。
