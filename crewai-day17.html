Knowledge 知识与 RAG

给 Agent 灌外部资料（文档/PDF/网页），让它基于你的知识库回答。今天讲知识源、切块、向量库检索，以及如何把 RAG 知识接给 Agent。

📍 你在第 4 周（记忆/知识/生态）的位置 · 今天：Knowledge
Memory 记忆（D16）· Knowledge 知识（D17）· Events 事件（D18）· 脚手架 YAML（D19）· 测试收官（D20）
L01

知识 vs 记忆（先分清）

🤔 场景：你让 Agent 回答"我们公司的产品参数" 你做了个客服 Agent，用户问"你们 X 型号的续航是多久？"。可这型号是你们上个月才发布的新品，大模型训练时根本没见过——它只能瞎猜或说"抱歉我不知道"。你手上明明有产品手册 PDF，怎么让 Agent 用上它？
💡 一句话本质：Knowledge = 给 Agent"开卷考试"（RAG） Knowledge 就像考试时允许你带一箱参考书进考场。大模型脑子里只有训练时背下的公开知识（闭卷），不知道你的私有文档、也不知道最新资料。Knowledge 把你的资料切块、向量化存起来，Agent 答题前先从"参考书"里翻出最相关的几页、塞进提示词再作答。这正是 Day 01 讲过的 RAG。
💬 对话体：Memory 和 Knowledge 到底有啥区别？ 问：都是 RAG 向量检索，为啥要分两个东西？
答：来源不同。Memory 是"你自己的日记"——干活过程中一点点记下来的经历（"上次这客户嫌贵"）；Knowledge 是"别人给你的教科书"——你开工前就塞给它的外部资料（产品手册 PDF）。
问：一句话记住？
答：Memory 记"我经历过什么"，Knowledge 记"我读过什么"。考试时，前者是你的错题本，后者是允许带进考场的参考书。
  • 记忆（Memory，Day 16）：Agent 在运行中自己积累的经历（做过什么、学到什么）。
  • 知识（Knowledge，今天）：你外部灌给它的资料（产品手册、公司文档、PDF、网页）。
用人打比方 记忆 = 员工干活过程中记住的事（"上次这个客户投诉过 X"）。知识 = 你发给员工的参考资料（产品说明书、公司规章）。员工回答问题时，既靠自己的经历（记忆），也翻参考资料（知识）。两者都用 RAG（向量检索）技术，但来源不同：记忆是内生的、知识是外灌的。代码在 knowledge/ 目录。
L02

三层架构

Knowledge集合入口→ KnowledgeSource加载+切块→ KnowledgeStorage嵌入+向量库+检索

Knowledge（knowledge/knowledge.py:88，query 方法 :135、add_sources :154）是入口，管理多个 KnowledgeSource（各种资料源），底层用 KnowledgeStorage（默认 ChromaDB 向量库）。

Knowledge 全流程：青色"建库"（资料→切块→嵌入→向量库），蓝色"检索注入"（每次执行把命中片段拼进 Agent 提示词）。这就是 RAG 在 CrewAI 里的样子。
读法：Knowledge=总管、Source=资料源（负责把 PDF/文本读进来并切块）、Storage=向量库（负责嵌入和检索）。三层各司其职：加载 → 切块 → 向量化存储 → 检索。这是标准的 RAG 管道结构。
🎵 记忆口诀：RAG 六字诀"读、切、嵌、存、检、答" 读（把 PDF/文本读进来）→ 切（切成小块）→ 嵌（每块变成向量）→ 存（存进向量库）→ 检（拿问题去检索最相关的块）→ 答（把命中片段塞进提示词让 LLM 作答）。前四步"读切嵌存"是建库（做一次），后两步"检答"是每次提问都走。背下这六个字，你就记住了整个 RAG 流程——今天讲的所有代码都只是在实现这六个字。
❗ 常见误解：以为"挂了知识库，Agent 就把整份文档背下来了"。错——它只在每次回答前临时检索出最相关的几段来看，看完就'忘'（不进模型参数）。所以文档更新了，重新建库即可，不用"重新训练"模型。这正是 RAG 相比"微调模型"最省事的地方。
L03

知识源与切块

抽象基类 BaseKnowledgeSource（base_knowledge_source.py:16）定义切块参数和方法：

chunk_size = 4000        # 每块字符数
chunk_overlap = 200      # 相邻块重叠字符数
# _chunk_text (:43) 固定字符窗口滑动切块
return [text[i:i+chunk_size]
        for i in range(0, len(text), chunk_size - chunk_overlap)]
为什么要"切块"？为什么块之间要"重叠"？ 切块：一份长文档（几万字）不能整个喂给模型（太长、检索不精准）。切成小块（4000 字），每块单独向量化——检索时能精准定位到相关的那一小块。重叠：如果硬切，一句话可能被切成两半（前半在块1、后半在块2），检索时哪块都不完整。让相邻块重叠 200 字，保证跨边界的内容不被割裂。这是 RAG 切块的经典技巧。
L04

各种文件源

具体知识源（都实现 load_content）：

  • StringKnowledgeSource：直接切一段字符串。
  • PDFKnowledgeSource：用 pdfplumber 逐页抽取文本。
  • CSV / Excel / JSON / TextFile 各自实现。
  • CrewDoclingSource（crew_docling_source.py:82）：特殊——用 docling 的 HierarchicalChunker 做语义切块（而非固定字符窗口），支持 PDF/DOCX/MD/HTML/URL。
"语义切块"比"固定字符切块"好在哪？ 固定字符切块可能把一个完整的段落/章节从中间切开。语义切块（HierarchicalChunker）按文档的结构（标题、段落、列表）来切——每块是一个语义完整的单元。检索时召回的块更连贯、更有意义。处理结构化文档（有标题层级的 PDF/Markdown）时，语义切块效果明显更好。普通文本用固定切块够了。
L05

存储与 RAG 检索

默认 KnowledgeStorage（knowledge_storage.py:22）基于 ChromaDB：

  • _init_client（:37）：用 build_embedder 构造嵌入函数、建专属 Chroma collection（前缀 knowledge_<name>）。
  • save（:105）：把文本块交给 client 嵌入 + upsert。
  • search（:59）：RAG 检索——多个 query 交向量库做相似度检索，受 limit（默认 5）和 score_threshold（默认 0.6）约束。
读法：知识块被向量化存进 ChromaDB；查询时把问题也向量化，找最相似的块。score_threshold=0.6 过滤掉不够相关的（相似度低于 0.6 的不返回）——保证喂给 Agent 的是真正相关的知识，不是勉强凑数的。
L06

挂到 Agent/Crew

  • Crew：字段 knowledge_sources/knowledge（crew.py:340/358），create_crew_knowledge()（crew.py:675）构建 Knowledge(collection_name="crew") 并加载源。
  • Agent：set_knowledge()（agent/core.py:408）构建 Knowledge(collection_name=self.role)——每个 agent 有自己的知识库（按 role 命名）。
from crewai.knowledge.source.pdf_knowledge_source import PDFKnowledgeSource

pdf_source = PDFKnowledgeSource(file_paths=["产品手册.pdf"])
agent = Agent(role="客服", goal="...", knowledge_sources=[pdf_source])
# 现在这个客服 agent 回答问题时会自动查产品手册
📝 挂一个 PDF 源 → 提问 → 答案带私有知识 产品手册 PDF 里有一句：X 型号续航 18 小时。
用户问客服 Agent：你们 X 型号能用多久？
没挂知识时 → 抱歉，我没有该型号的具体信息……（🤷 大模型没见过新品）
挂了 PDFKnowledgeSource 后 → 检索命中手册片段，提示词里带上 Additional Information: X 型号续航 18 小时 → Agent 答：X 型号续航约 18 小时。（✅ 用上了你的私有资料）
Crew 级 vs Agent 级知识 Crew 级：整个团队共享的知识（公司通用文档）。Agent 级：某个 agent 专属的知识（客服 agent 有产品手册，法务 agent 有合同模板）。按需分配——不用给每个 agent 灌所有资料，各自拿自己领域的。这和 Day 16 记忆的 scope 分层思路一致。
L07

检索注入 prompt

任务执行时，handle_knowledge_retrieval（agent/utils.py:119）是关键——它做三件事：

# 1. 用 LLM 把任务改写成检索 query（agent._get_knowledge_search_query, core.py:1300）
# 2. 查询 agent 和 crew 的知识库
# 3. 用 extract_knowledge_context 把命中片段追加到 task_prompt：
agent_knowledge_snippets = query_func([agent.knowledge_search_query], ...)
if agent_knowledge_snippets:
    task_prompt += extract_knowledge_context(agent_knowledge_snippets)  # 前缀 "Additional Information: "
读法：第 1 步很妙——不是直接拿任务描述去检索，而是先用 LLM 把任务改写成一个更适合检索的 query。然后查知识库、把命中的知识片段（带"Additional Information:"前缀）拼进 prompt。于是 Agent 看到任务时，prompt 里已经带上了相关资料。
为什么要"用 LLM 改写检索 query"？ 任务描述可能很长、很啰嗦，直接拿去做向量检索效果不好。先让 LLM 提炼出"这个任务的核心检索意图"（比如任务是"写一篇关于我们新产品定价策略的分析"，改写成检索 query "产品定价策略"），检索更精准。这是 RAG 的进阶技巧——query 改写（query rewriting）提升检索质量。和 Day 16 RecallFlow 的 analyze_query 一个思路。
