Agent 执行循环 ReAct

Day 02 说 Agent 把活交给"执行器"跑 ReAct 循环。今天就拆开这个执行器，读 crew_agent_executor.py 的真实循环，看 AI 如何"思考→用工具→观察→再思考"。

L01

ReAct 是什么（一次运行轨迹）

ReAct = Reasoning + Acting：让 AI 交替"思考"和"行动（用工具）"，用工具结果指导下一步。轨迹长这样：

🤔 Thought 思考
我需要查一下 SF 的天气
🔧 Action 行动
调用 search 工具，输入 "SF weather"
👀 Observation 观察
工具返回："SF 今天 18°C"
🤔 Thought
我知道了，可以回答了
✅ Final Answer 最终答案
SF 今天 18 度
这套范式在 eino、OpenHands 教程里都见过——它是工具型 Agent 的通用骨架。CrewAI 的实现在 agents/crew_agent_executor.py 的 CrewAgentExecutor（:98）。
L02

两种执行模式分流

invoke（crew_agent_executor.py:208）进入 _invoke_loop，一开始就分流（:318）：

use_native_tools = (
    self.llm.supports_function_calling()   # 模型支持"原生函数调用"吗？
    and self.original_tools)
if use_native_tools:
    return self._invoke_loop_native_tools()   # 现代模型：用 LLM 原生 function calling
return self._invoke_loop_react()              # 老模型：文本解析 ReAct
读法：现代模型（GPT-4、Claude）支持结构化"函数调用"，就走原生模式（更可靠）；不支持的老模型就把工具说明塞进 prompt、靠解析文本来调工具（传统 ReAct）。两条路都能用，向后兼容。
"原生函数调用" vs "文本 ReAct" 的区别 文本 ReAct：让模型按 Thought:/Action:/Action Input: 的文本格式输出，框架用正则解析出"要调哪个工具"。缺点：模型可能格式写错、解析容易失败。原生函数调用：模型直接返回结构化的 tool_call（模型训练时就学过这个格式），框架直接读，不用解析文本。原生更可靠，是现代首选；文本 ReAct 是老模型的兜底。
L03

文本 ReAct 循环

核心循环 _invoke_loop_react（crew_agent_executor.py:330），循环直到得到 AgentFinish：

# :341-360（精简）
while not isinstance(formatted_answer, AgentFinish):
    if has_reached_max_iterations(self.iterations, self.max_iter):
        formatted_answer = handle_max_iterations_exceeded(...)  # 到上限强制收尾
        break
    enforce_rpm_limit(...)                              # 限流
    answer = get_llm_response(llm=..., messages=self.messages)  # 问一次 LLM
    formatted_answer = process_llm_response(answer_str, ...)     # 解析成 Action/Finish
    if isinstance(formatted_answer, AgentAction):
        tool_result = execute_tool_and_check_finality(...)       # 执行工具
        formatted_answer = self._handle_agent_action(...)        # 把结果写回
    self._append_message(formatted_answer.text)          # 结果进对话历史
读法：这就是 ReAct 的精髓：问 LLM → 解析出"要调工具(AgentAction)"还是"给答案(AgentFinish)" → 若调工具则执行、把结果写回消息 → 循环，直到给答案。每一步的工具结果都 append 进 self.messages，所以下一轮 LLM 能看到上一步的观察。
L04

parser：把文本解析成结构

parser.py 是文本 ReAct 的关键翻译器。它把 LLM 的文本输出解析成两个数据类之一（parser.py:25）：

@dataclass
class AgentAction:   # "我要调工具"
    thought: str; tool: str; tool_input: str; text: str
@dataclass
class AgentFinish:   # "我给出最终答案"
    thought: str; output: str | BaseModel; text: str

parse()（parser.py:62）看文本里有没有 Final Answer: 或 Action:：有 Final Answer → AgentFinish；有 Action → AgentAction；两者都没有 → 抛 OutputParserError。

解析失败了怎么办？（自愈设计） 如果 LLM 输出的既没有 Action 也没有 Final Answer（格式跑偏），parse 抛 OutputParserError，并附一句提示（如"你漏了 Action:"）。这个提示会被塞回给 LLM，让它自己纠正重来。还有 _safe_repair_json（parser.py:161）用 json_repair 修复模型输出的破损 JSON。面对"模型可能不听话"，框架不是直接崩，而是"给提示让它改"——这种容错是 Agent 框架健壮性的关键。
L05

原生函数调用循环

_invoke_loop_native_tools（crew_agent_executor.py:484）先把工具转成 OpenAI schema，然后循环里 LLM 直接返回结构化 tool_calls。有个有意思的策略（:667 _handle_native_tool_calls）：

  • 默认一次只执行第一个工具调用，把结果写回后让模型重新推理再决定下一步（顺序 + 反思，更稳）。
  • 但如果模型一次返回多个工具、且都不涉及 result_as_answer/max_usage_count，就用线程池并行执行（:746，提速）。
为什么默认只执行第一个工具？ 因为 Agent 干活常常有依赖——"先查 A，根据 A 的结果再决定查什么"。如果一次把模型说的所有工具都执行了，可能第 2 个工具的参数本该依赖第 1 个的结果。默认"执行一个、看结果、再想"更符合真实推理链；只有当多个工具明显独立时才并行提速。正确性优先，性能其次——这个权衡很稳健。
L06

出错与自愈

循环里对各种异常有细致处理（crew_agent_executor.py:434-447）：

  • 解析失败（OutputParserError）：把纠错提示喂回 LLM，重来。
  • 上下文超长：走 handle_context_length（:447）自动压缩历史后 continue。
  • 原生模式不支持：优雅降级到文本 ReAct 模式（:577）。
"自愈"是 Agent 健壮性的核心。真实运行中模型会犯各种错（格式错、上下文爆、工具用错）。CrewAI 的执行器不是遇错就崩，而是尽量把错误信息转化成"给模型的反馈"，让它自己修正。这和 OpenHands 的"看 Observation 自我纠错"、eino 的容错设计一脉相承——Agent 系统必须假设"模型会犯错"并优雅应对。
L07

上限与降级

循环的终止保障：

  • max_iter（默认 25，Day 02）：迭代次数到上限，handle_max_iterations_exceeded 强制收尾——让模型基于目前信息给个最终答案，而不是无限循环。
  • max_execution_time：超时抛错（Day 02 的线程池/asyncio.wait_for）。
  • RPM 限流：enforce_rpm_limit 保证不超过每分钟请求数。
三道保障防失控：次数上限、时间上限、频率上限。能自主循环的 Agent 必须有这些"刹车"——否则一个跑偏的 Agent 可能无限循环烧钱。这是所有 Agent 框架的共识（eino 的 MaxRunSteps、OpenHands 的 max_iterations）。
