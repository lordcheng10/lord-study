Day 01 / 共 20 天 · 第 1 周 全景与请求生命周期

项目全景：Lua/OpenResty API 网关

欢迎来到 Apache APISIX。如果你学过 higress-group 系列，这是"另一条网关技术路线"——不用 C++/xDS，而是 Lua/OpenResty + etcd。第一天先建立整体印象，看清它"快"和"动态"从哪来。

L01

APISIX 是什么

README.md 标题就是"Apache APISIX API Gateway ｜ AI Gateway"——一个 Apache 顶级项目，动态、实时、高性能的云原生 API 网关。它处理"南北向流量"（外部请求进入你的服务），提供路由、负载均衡、鉴权、限流、可观测、AI 代理等能力。

"API 网关"是干嘛的？ 你有一堆后端服务，不能让客户端直接连——中间需要一个"总入口"统一处理：谁能访问（鉴权）、每秒多少次（限流）、请求转发到哪个服务（路由/负载均衡）、记录日志、监控……这个总入口就是 API 网关。APISIX 就是这样一个网关，特点是用 Lua 写、性能极高、配置全动态。它和 Higress/Envoy 解决同一类问题，但技术路线不同。
L02

OpenResty 内核

APISIX 建立在 OpenResty 之上——OpenResty = Nginx + LuaJIT。整个 apisix/ 目录几乎全是 .lua 文件。

OpenResty 是什么？为什么用它？ Nginx 是世界上最流行的高性能 Web 服务器（C 写的，快）。但 Nginx 的配置是静态的、扩展要写 C 模块很难。OpenResty 在 Nginx 里嵌入了 LuaJIT（一个超快的 Lua 解释器），让你能用 Lua 脚本在 Nginx 的各个处理阶段编程。于是你既有 Nginx 的 C 级性能，又有 Lua 的开发灵活性。APISIX = 用 Lua 在 OpenResty 上写出来的一整套网关逻辑。这就是它"快"的根源：底层是 Nginx，热点路径靠 LuaJIT 即时编译。
L03

etcd 全动态

APISIX 用 etcd（一个分布式键值存储）当配置中心。所有配置（路由、上游、插件、证书）都存 etcd，每个 APISIX 节点 watch etcd 的变化。

"全动态"到底多方便？ 传统 Nginx 改配置要编辑 nginx.conf 然后 nginx -s reload——reload 有开销、有风险。APISIX 完全不用：你调 Admin API 把新路由写进 etcd，所有网关节点秒级 watch 到、内存里更新，立即生效、零 reload、零重启。加一条路由、改一个插件参数、换一张证书——都是瞬时的。这对"频繁变更"的云原生环境（微服务动态上下线）至关重要。"OpenResty 给性能，etcd 给动态"是 APISIX 的两大支柱。
L04

目录结构

apisix/
  init.lua        ★ 请求生命周期总控（各 Nginx 阶段的 Lua 入口）
  plugin.lua      ★ 插件系统（加载/过滤/运行）
  router.lua      ★ 路由（radixtree）
  core/           基础设施：ctx/config_etcd/schema/json/log/lrucache...
  plugins/        104 个插件（.lua）
  balancer/       负载均衡算法
  discovery/      服务发现（nacos/consul/dns/eureka/kubernetes）
  admin/          Admin API（增删改配置）
  control/        control API（健康检查等运维接口）
  stream/         L4（TCP/UDP）代理子系统
  ssl/ secret/ pubsub/ wasm.lua   其他子系统
  cli/            启动命令行（bin/apisix 背后）
读法：三个核心文件先记住：init.lua（请求怎么走）、plugin.lua（插件怎么跑）、router.lua（路由怎么匹配）。core/ 是它们依赖的基础设施。本课主线就在这几个文件里游走。
L05

六大抽象对象

APISIX 用几个核心对象描述配置（都存在 etcd，Day 08 详讲）：

对象作用
Route（路由）匹配规则（uri/host/method）+ 绑定插件/上游
Service（服务）可复用的插件+上游配置，多个 Route 共享
Upstream（上游）后端服务集群 + 负载均衡策略
Consumer（消费者）API 调用方 + 鉴权凭据
Plugin Config（插件配置）可复用的一组插件配置
Global Rule（全局规则）对所有请求生效的插件
读法：核心是 Route——它把"什么请求（匹配）→ 怎么处理（插件）→ 转发到哪（上游）"串起来。Service/Upstream/Plugin Config 是"可复用的零件",避免每条路由重复配。这套对象模型和上一站 Higress Console 的路由/服务/插件概念相通——网关的共性。
L06

和 Envoy/Higress 对照

Envoy/HigressAPISIX
语言C++（数据面）Lua（OpenResty）
配置分发控制面生成 xDS 下发直接 watch etcd
架构控制面 + 数据面分离单体（每节点自给自足）
扩展Wasm 插件 / C++ filterLua 插件（也支持 Wasm）
两条路线各有取舍 Envoy/Higress："控制面算好配置、下发 xDS 给数据面"——适合超大规模、多语言扩展，但架构复杂（要 istiod）。APISIX："每个网关节点自己连 etcd 取配置"——架构简单、部署轻、Lua 上手快，但节点自己扛更多逻辑。没有绝对优劣，看场景。学过 higress-group 再学 APISIX，你就理解了业界两大网关流派的设计哲学差异。Day 20 会做完整对比。
L07

一句话数据流

请求进入（Nginx access 阶段 → init.lua http_access_phase）
  → router 匹配路由（radixtree）
    → 识别 consumer（鉴权）+ plugin.filter 选出该跑的插件
      → 各阶段跑插件（rewrite/access/header_filter/body_filter/log）
        → balancer 选一个上游实例 → 转发
          （配置全程来自 etcd，watch 到变化即热更新）
读法：这条链就是本课主线。第 1 周走通它（今天全景 + 后面 Nginx 阶段/启动/生命周期/ctx）；第 2 周展开路由/配置/上游；第 3 周深入插件；第 4 周讲子系统。核心入口是 init.lua 的 http_access_phase（Day 04 精读）。
