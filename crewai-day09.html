Planning 规划

复杂任务，先做计划再动手效果更好。CrewAI 有两套规划：Crew 级（开工前一次性生成计划）和 Step 级（执行中动态观察、按需重规划）。今天讲清它们的区别与实现。

📍 你在整门课的位置（第 2 周 Crew 编排深入 → 第 3 周 Flow）
委派协作（W2）· Planning 规划· Task 输出与护栏· Flow 编排（W3）· Flow 装饰器
L01

为什么要规划

🤔 场景：让一个 Agent 直接做"写市场调研报告"这种大任务 任务很大、环节很多。Agent 没有全局观，容易东一榔头西一棒子：先写了点竞品，又跳去写建议，回头发现市场范围还没定义，来回返工、甚至遗漏关键部分。它缺的不是能力，是"先想清楚整体步骤再动手"。
💡 一句话本质：Planning = 先规划再执行 就像出门旅行前先列一张行程单：几点到哪、先玩哪个景点、中午在哪吃——列好了就不会到了当地手忙脚乱、来回折返。Planning 让一个"规划师"在开工前把复杂任务拆成清晰的分步计划，再交给干活的 Agent 照着走。规划 = 把"复杂任务"分解成"清晰步骤"，降低 AI 迷路的概率。
❌ 错误驱动：不规划，会翻成什么样？ 同一个任务"写多智能体市场调研报告"，不开规划时 Agent 的真实轨迹常常是：先写了两段竞品 → 想起没定义市场范围，回头补 → 又跳去写建议 → 发现趋势数据还没收集 → 回头查 → 最后交上来结构散、还漏了"竞品对比"整节。没有"先想清楚整体"，就会走一步退一步、返工又遗漏。这正是 Planning 要消灭的痛。

直接让 Agent 硬做复杂任务，它容易"走一步看一步"、缺乏全局规划、跑偏。先制定计划再执行——像人接到大项目先列提纲——能显著提升成功率。

规划的价值：给 AI 一张"路线图" 想象让 Agent"写一份市场调研报告"。没有计划，它可能想到哪写到哪，遗漏关键部分。有计划：先明确"① 定义市场范围 → ② 收集竞品数据 → ③ 分析趋势 → ④ 给建议"，Agent 照这张路线图走，产出更完整、更有条理。规划 = 把"复杂任务"分解成"清晰步骤"，降低 AI 迷路的概率。
L02

两套规划（别混淆）

📋 Crew 级规划（静态）

  • 开工前一次性生成计划
  • 由 crew.planning=True 触发
  • 把每个任务的详细步骤塞进任务描述
  • "开工前定好整体计划"

🔍 Step 级观察（动态）

  • 执行中每一步后观察
  • 由 PlannerObserver 实现
  • 看情况判断计划是否还成立、要不要改
  • "边做边看、动态调整"
一句话区分 Crew 级 = "开工前写好作战计划"（静态，一次性）；Step 级 = "打仗过程中随时评估战况、必要时改计划"（动态，持续）。两者可配合：先有整体计划，执行中再动态微调。
L03

Crew 级规划的触发

触发点在 prepare_kickoff（crews/utils.py:355）——kickoff 一开始、任务执行前就跑：

if crew.planning:
    crew._handle_crew_planning()   # 开工前生成计划
读法：只要你建 Crew 时设了 planning=True，kickoff 会在任何任务执行之前先跑一次规划。这符合"先规划后执行"的直觉——规划发生在最前面。
Crew 级规划全流程：kickoff(planning=True) → 规划师 Agent 通盘生成分步计划 → 每任务的计划追加进 description → 各 Task 照计划执行。
L04

CrewPlanner 干什么

_handle_crew_planning（crew.py:1417）委托给 CrewPlanner（utilities/planning_handler.py:37）：

  • _create_planning_agent（:80）：造一个专门的"规划 Agent"（role="Task Execution Planner"），默认用 gpt-5.4-mini（便宜的规划模型）。
  • _create_tasks_summary（:137）：把所有任务（描述、期望输出、负责的 agent、工具）汇总成文本。
  • 让规划 Agent 输出结构化的 PlannerTaskPydanticOutput——每个任务一条 PlanPerTask（含 task_number + plan 详细步骤）。
用一个专门的"规划师" 注意：规划不是让干活的 Agent 自己规划，而是专门造一个"规划师 Agent"来通盘看所有任务、给每个任务写详细步骤。用便宜模型（mini）做规划——因为规划是"想清楚步骤"，不需要最强模型，省钱。结构化输出（每任务一条 plan）让后面能精确地把计划对应回每个任务。
L05

计划塞进任务描述

规划师产出计划后，回到 crew.py:1435，把每个任务的计划追加到它的 description 后面：

# crew.py:1435-1443（概念）
task.description += plan_map[task_number]   # 把该任务的详细步骤附加到描述
读法：规划的落地方式很朴素——把"该任务的详细步骤"直接拼进任务描述。于是实际执行这个任务的 Agent，在 prompt 里就看到了"我该分几步做、每步做什么"的指引，产出更有条理。
📝 planning=True 前后，任务 description 的变化 建 Crew：Crew(agents=..., tasks=..., planning=True)
规划前，任务描述只有：写一份关于"多智能体"的市场调研报告
规划后（规划师补了步骤，拼进同一个 description）：写一份关于"多智能体"的市场调研报告\n\n[计划] 步骤1：定义市场范围；步骤2：收集竞品数据；步骤3：分析趋势；步骤4：给出建议
→ 干活的 Agent 读到的 prompt 里自带了提纲，产出更完整有条理。想换更强的规划模型？建 Crew 时传 planning_llm="gpt-5.4" 即可。
为什么用"拼进描述"这么简单的方式？ 因为 Agent 执行任务时本就会读 task.description（拼进 prompt）。把计划附加进去，Agent 自然就"看到"了计划——不需要新增任何机制。规划的产出（计划文本）通过已有的"任务描述→prompt"通道传递给执行者。又是"复用已有通道"的朴素智慧。
L06

Step 级观察重规划 PlannerObserver

PlannerObserver（agents/planner_observer.py:39）实现 ReAct 里的"观察"阶段——每一步执行后都跑（不只失败时）。核心方法 observe（:113）让 LLM 返回结构化的 StepObservation：

# StepObservation 字段
step_completed_successfully   # 这步成功了吗
key_information_learned       # 学到了什么新信息
remaining_plan_still_valid    # 剩余计划还成立吗
needs_full_replan             # 需要彻底重新规划吗
suggested_refinements         # 建议怎么微调
读法：每执行一步，观察者就问 LLM："这步干得怎样？学到了什么？原计划还行吗？要不要改？"——这让 Agent 能边做边评估、动态调整，而不是死守开工前定的计划。发现计划不对就 needs_full_replan，微调则用 suggested_refinements。
为什么"每步都观察"而不只在失败时？ 因为很多"跑偏"不是明显的失败——比如某步查到了意外信息，可能让后续计划部分失效。只在失败时观察会错过这些。每步都反思，能及早发现"虽然没报错但方向不对"的情况。还有 heuristic_observation（:87）降级模式——当关掉 observe 或 reasoning_effort=low 时，不调 LLM、仅凭执行元数据生成观察，省 token。
L07

一次调用省 token 的巧思

apply_refinements（planner_observer.py:215）有个关键优化——注释明确写了 "No LLM call needed"：

observe 一次调用，同时返回"分析"和"修订建议" 天真的做法：第一次调 LLM 分析"这步怎样"，第二次调 LLM"那你说怎么改"。CrewAI 的做法：observe 那一次 LLM 调用就同时返回分析结果 和 具体的修订建议（suggested_refinements），然后直接把修订应用到剩余计划，不用第二次调 LLM。省了一半的规划开销。"一次调用拿全所需信息"——在 Agent 里，每省一次 LLM 调用就是省钱省时间。这是成本经济学的精细体现。
观察者还通过事件总线广播 StepObservationStarted/Completed/Failed（Day 18 的事件系统），可观测性好。整套 Step 级规划：每步观察 + 一次调用拿分析和修订 + heuristic 降级——智能与成本的精细平衡。
