Day 18 / 共 20 天 · 第 4 周 平台化与收官

CI 流水线与治理闸门

前面讲的"可信"都是能力；CI 是把这些能力变成"合并前强制执行"的地方。不达标，代码进不来。

L01

CI = 把"可信"变成硬约束

前 17 天讲了 Critic、闸门、评测、成本治理、BOM 版本锁……但这些如果只是"能力"，总有人偷懒不用。CI（持续集成，.gitlab-ci.yml）的作用就是在合并前强制跑一遍，不达标就拦住。

核心原则叫 R-CI-DEFAULT-FAIL：任何一道 gate 失败都阻止 merge（allow_failure: false）。

🚫

默认失败原则（R-CI-DEFAULT-FAIL）

闸门不是"建议"，是"硬门"。评测掉了、成本涨了、BOM 版本漂了、敏感度红线碰了——任一触发，流水线红、合并按钮点不动。可信从"靠自觉"变成"靠机制"。

L02

7 个 stage

lintBOM 审计→ testpytest→ ci-gates核心闸门群→ canary金丝雀→ publish-internal发 Nexus→ build-portal前端镜像→ nightly-sync镜像同步

CI 全程用 python:3.12-slim + pip install uv==0.11.* + uv sync --all-packages——和 Day 02/17 本地一致。核心是中间的 ci-gates 阶段，里面一堆治理闸门，下面几讲挑重点看。

L03

BOM 审计闸（呼应 Day 05/17）

Day 05 讲过 agent 依赖走 BOM 一行、Day 17 讲过 uv.lock 的分量。CI 有三道闸守着依赖不漂移：

bom-audit

跑 scripts/check_bom_lockfile.py：检查是不是所有 agent 都引了 BOM（adoption），不足直接 exit 阻 merge。

ci-gate-bom-pin

禁止 agent 绕过 BOM 直接 pin toolkit 子模块版本。

ci-gate-bom-version-sync

校验 toolkit ↔ BOM ↔ uv.lock 三方版本声明一致。

为什么这么在意依赖？ 20+ 个 agent 共享一套 toolkit，如果各自 pin 不同版本，很快就会"这个 agent 要 0.5、那个要 0.6"，地狱般的依赖冲突。强制走 BOM + CI 三道闸校验，保证全平台永远用同一组对齐的版本——这是 monorepo 能规模化的前提。
L04

评测回归闸（呼应 Day 10）

Day 10 的评测能力，在这里变成硬门 ci-gate-eval：

ci-gate-eval

14 agent × 5 维 eval 回归。PR 模式用 --changed 只跑改动的 agent（省时间），任一维掉到阈值以下 → 流水线失败。

red-line-regression

红线回归：核心能力绝不能退步的硬底线。

还有个配套工具链（scripts/ci/）：full_agent_eval.py（全量评测）、compatibility_matrix.py（兼容矩阵）。仓库还提供 case-to-eval-sample skill——线上出问题的 case 可以一键变成回归测试样本追进 golden set（Day 19 会提）。

闭环：线上发现 Agent 判错 → 把那个 case 变成 eval 样本追进 golden set → 以后任何 PR 都会跑这条样本 → 同样的错误不会再溜过去。每一次线上事故都变成一道永久的回归防线——这是评测进 CI 最有价值的地方。
L05

成本 & 敏感度红线

ci-gate-cost

成本感知路由的 diff 拦截——就是拦 Day 11 那个 cost-routing.json。改了某 agent 的模型 tier 或基线用量，CI 会算成本影响（cost_impact.py / estimate_cost_vector），异常涨幅会被拦。

ci-gate-red-line

DD-001 敏感度红线 diff 拦——守 Day 08 讲的敏感度分级，防止有人误改红线 service 的分级逻辑。

ci-gate-semver

PR 标签 / conventional commit 前缀校验——保证版本号语义正确。

"diff 拦截"是什么意思？ 就是 CI 检查这次 PR 改动了哪些敏感文件/字段，命中就要求额外审查或直接拦。成本配置、敏感度红线这类"改错了后果严重"的地方，用 diff 拦截强制"改这里必须过特别检查"。这是把高风险变更纳入管控的常见手法。
L06

DB 迁移 & 兼容矩阵

ci-gate-db-dryrun

用临时的 pgvector/pgvector:pg16 服务，真跑一遍 alembic upgrade + downgrade——保证数据库 schema 迁移脚本可用、可回滚。

ci-gate-matrix

14 agent × 5 extras 的兼容矩阵，5 个 shard 并行跑（当前是 --dry-run 占位）。

ci-gate-frontend / storybook / sync / readonly

门户前端 Playwright e2e + Lighthouse 性能预算、Storybook 构建、Day 16 讲的双仓 drift 检测和镜像只读校验。

最后 publish-internal 阶段：打 toolkit-vX.Y.Z tag 触发，把 8 个 wheel 包发到公司内部 Nexus（供独立仓 agent 用一行 BOM 依赖拉取，Day 19 会提）。

L07

金丝雀发布

scripts/canary/ 是一套金丝雀（canary）发布工具包：cli.py / monitor.py / phase.py / prom.py / rollback.py / override.py / state.py。

金丝雀发布：新版本上线时不一次性全量切换，而是先放一小部分流量给新版本，盯着 Prometheus 指标（错误率、延迟、成本），没问题再逐步放量，出问题立刻回滚。名字来自"矿工带金丝雀下矿"——用小代价先探风险。

它的能力：分阶段放量（phase）、Prometheus 监控（prom + monitor）、紧急覆盖（override）、一键回滚（rollback）。配合 canary-emergency-override skill 用。这让"上一个可能有风险的新 agent 版本"变得可控——先小流量验证，坏了马上退。
