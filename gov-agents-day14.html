精读旗舰 Agent：sre-rca

前面 D03-D13 把 State / 图 / 专家 / Critic / 闸门 / 记忆 / 成本 / 运行时一块块拆开讲了。今天(D14)是总演练：逐文件读一个真实的故障根因分析 Agent，把这些零件在一个 agent 上完整看一遍怎么咬合。读懂它，D15 再横扫其它 20+ 个 agent 就都是它的简化/变体了。

📍 你在 20 天里的位置（可信底座 → 运行时 → 精读）
D09 记忆→ D10 评测→ D11 安全底座→ D12 server 运行时→ D13 CLI/MCP→ D14 精读 sre-rca→ D15 全家福+元 Agent
💡 用一个类比先兜住今天（延续「盖楼/物业」世界观） 一次 sre-rca 就像物业接到一通报修电话："3 号楼漏水了(service-A 大量超时)"。流程是：前台按关键词分派工单(triage，不用请专家，规则就够)→翻旧档案看有没有类似报修(recall)→同时派 4 个师傅上门：查水管(trace)、查电表读数(metric)、查最近谁装修过(deploy)、看监控录像(log)→对照维修手册(rag)→工头汇总出 3 个最可能原因(synthesizer)→质检员复核别瞎写(critic)→把这次经验归档(writeback)，下次同样报修先翻它。简单活派学徒(Haiku)、难活派老师傅(Sonnet)——省钱三档就在其中。记住这通报修电话，10 个节点就活了。
L01

sre-rca 做什么

apps/sre-rca-agent 是平台的旗舰范本——一个 SRE 故障根因分析（Root Cause Analysis）Agent。你给它一个告警/现象（"service-A 大量超时"），它自动从 trace、指标、发布记录、日志四个视角取证，综合出 Top-3 最可能的根因，并给出带证据、带教学性的分析。

它是"满配"agent：10 个节点、4 专家并行、双层 Critic 三态重试、四层记忆全用上。读懂它，其它 agent 都是它的简化/变体。

📝 举个例子：一次报修的输入→输出 输入：{"user_question":"service-A 大量超时","trace_id":"t-9f2"}
→ 分诊归为 latency 类 → 4 专家取证(trace 发现下游 DB 慢、metric 发现连接池打满、deploy 发现 14:02 上过线、log 发现大量 timeout)
输出：{"conclusion":{"top1":"14:02 v1.7 发布把连接池 50→5 导致耗尽","confidence":"高","evidence":[...],"candidates":[...top3]}} + 一段给人看的 summary_for_human。
宝藏参照：server.py:142 的 /agents/rca/graph 端点，把每个节点的 role/model/purpose/输入/输出以 JSON 硬编码——相当于官方的"节点职责表"。今天讲的每个节点都能在那里对照。

全图动画走一遍

下图会自动依次点亮，模拟一次真实执行。每个节点标了它用哪档模型（🟣Sonnet / 🔵Haiku / ⚪规则不调 LLM）——留意"省钱三档"的分布：

critic 那个虚箭头 ⇢ 是三态条件边：通过→writeback，不过→回 synthesizer 重做（最多 2 次），触顶→END。下面逐个节点看真实代码。

把上面那通"报修电话"当调试器单步走一遍，跟踪关键 state 字段随每个节点怎么变：

步节点此刻做什么关键 state 变化模型

2recall捞相似历史 caserecalled=[2 条]记忆

⚠️ 小白常以为「4 个专家并行写同一个 state 会互相覆盖/打架」。不会——每个专家写不同字段(state_field 各不相同：trace_finding / metric_finding…)，加上 LangGraph 并行时自动 copy 上下文，所以并行累加安全(呼应 D03 的 reducer、D11 的 ContextVar)。
🎯 一句话口诀（10 节点 = 一次报修）「派单 → 翻档 → 四师傅上门 → 查手册 → 工头汇总 → 质检 → 归档」= triage → recall → 4 专家 → rag → synthesizer → critic → writeback。能顺着这通报修电话把 10 个节点讲下来，这个满配 agent 你就吃透了。
L03

triage — 规则分诊（0 成本）

triage_node nodes/triage.py:27

入口节点。用关键词字典 ALERT_KEYWORDS 把 user_question 归到 5 类 alert_type，并算 need_full_dag（健康查询走简版）。纯规则、不调 LLM、0 成本。

一个耐人寻味的细节：prompts/triage-v1.md 里其实设计了一个基于 Haiku 的 LLM 版分诊 prompt，但生产代码退化成了纯规则版。这正是"能用代码就别用 LLM"省钱哲学的落地——分诊这种简单分类，规则就够了，何必花钱调模型。读代码时对照 prompt 和实现的差异，能读出很多设计取舍。
L04

recall — 情景记忆召回

build_recall_node nodes/recall.py:10

工厂函数，把 EpisodicStore 闭包进去（Day 09）。用 trace_id/service/question 拼 query，await episodic.recall(...) 捞相似历史 case（默认 top_k=3）。异常吞掉返回空列表（recall.py:20）——挂了不影响主流程（Day 08 韧性思想）。

为什么用"工厂返回节点"而不是直接写节点函数？因为节点需要访问 EpisodicStore 这个依赖。用工厂 build_recall_node(episodic) 把依赖闭包进去，返回的闭包函数签名还是标准的 async def node(state) -> dict——既满足 LangGraph 的节点约定，又能拿到依赖。这是本框架里节点的常见写法（对照 Day 05）。

L05

4 专家并行取证

核心取证环节。trace/metric/deploy/log 四个专家从 recall 出发并行跑、汇入 rag（Day 03 的扇出扇入 + Day 05 的专家工厂）。每个专家文件才 ~30 行，因为都用 make_specialist_node：

# specialists/metric_sp.py:13
metric_specialist = make_specialist_node(SpecialistConfig(
    name="metric_specialist",
    state_field="metric_finding",           # 写进 state 的哪个字段（并行不冲突）
    system_prompt=load("metric-specialist-v1.md"),
    fetch_fn=lambda state: get_metrics(...), # 先抓数据（@safe_tool_result 包过）
    fallback_finding={"health": "unknown"},  # 抓失败的降级结果
    model_tier="sonnet",                     # 取证是难活，用 Sonnet
))

工厂内部（specialists/factory.py:84）自动做：fetch 拉数据（判 ok）→ get_llm 调模型 → 解析写字段 →（关键）自动包 Day 08 的 wrap_with_fallback。所以哪怕某个专家的数据源彻底挂了，它也只返回 fallback=True 的降级 finding，其余 3 个照常，图不崩。

回扣 Day 07：Critic 的 L1 会检查"至少 2 个专家真出了结果（非 fallback）"。所以"降级不崩"和"证据不足就诚实收尾"配合——降级是允许的，但不能靠降级结果瞎下结论。
L06

rag + synthesizer

build_rag_node nodes/rag.py:10

用 4 个专家 finding 里的 hint/hypothesis 拼查询，await semantic.lookup(query, record_type="sop") 检索运维手册（Day 09 语义记忆）。没有有效 finding 就直接返回空。

build_synthesizer_node nodes/synthesizer.py:49

综合节点，调 Sonnet（难活）。把 4 专家 + 历史 case + SOP + 上轮 Critic 反馈拼成 user message，system prompt 从 synthesizer-v1.md 读。产出 Top-3 根因假设。

两个工程细节值得学：

  • 外层用 toolkit 的 build_synth_safeguard(..., min_real_specialists=1) 包裹（synthesizer.py:54，Day 08 闸②）——真实证据不够时跳过 LLM直接返回"信息不足"，省钱又诚实。
  • _parse_conclusion（synthesizer.py:60）容错解析：先试裸 JSON → 再试 ```json 代码块 → 最后兜底 dict。因为 LLM 输出格式不总是完美，解析必须能容错。
L07

critic + writeback

build_critic_for_rca nodes/critic.py:12

直接复用 toolkit 的 build_critic_node(CriticConfig(...))（Day 07）。关键配置：llm_factory=lambda: get_llm("haiku", cache_system=True)——用 Haiku 省 80% + prompt 缓存再省；conclusion_field="conclusion"；soft_fail=True。system prompt 来自 critic-v1.md。

build_writeback_node nodes/writeback.py:12

先用 should_writeback(state) 守门（Day 08 闸④，仅"质检通过且信息充分"才写），再 episodic.writeback(...) 把这次 case 沉淀进记忆库。无论写不写，都生成 summary_for_human 给人看。

Critic 之后的三态路由就是 builder 里那句 build_critic_router(pass_dest="writeback", retry_dest="synthesizer", end_dest=END, max_retries=2)（Day 07）。整个"综合→质检→（不过就回炉）"构成一个受控循环，最多转 2 圈，转不出满意结果就诚实收尾。

图注：综合→质检→(不过就回炉)构成受控循环，最多转 2 圈；转不出满意结果就诚实收尾，绝不硬编一个结论。
看到闭环了吗？ writeback 把"通过质检的好结论"沉淀进情景记忆 → 下次相似故障，recall 就能召回它当参考 → Agent 越用越准。而 should_writeback 守门保证"没通过质检的"不会污染记忆。这就是 Day 09 说的"越用越聪明又不学坏"。
L08

prompt 也是工程文档

别忽略 prompts/*.md——它们是本仓最好的 prompt 工程教材。以 critic-v1.md 为例，它不只是一段 prompt，而是包含：

  • 6 项检查：证据 ID 真实性 / 置信度校准 / 语言风格铁律 / 矛盾处理 / 动作安全性 / 教学性；
  • 三态决策：PASS / PASS_WITH_NOTES / FAIL，各自的判定条件；
  • few-shot 示例：1 个 FAIL + 1 个 PASS 的完整样例；
  • 设计说明表格：逐段解释"为什么这么写"；
  • Token/成本估算：critic-v1.md 里算过——同样工作 Haiku ¥0.04 vs Sonnet ¥0.20，全链路约 ¥0.44/次，压在 ¥0.5 预算内。

synthesizer-v1.md 更狠：8 步思考 + 语言铁律（禁绝对措辞、必引 ≥2 专家证据、教学性、失败开关）+ 一个完整的"DB 慢连锁"分析范例。

为什么把这些写进 prompt 文件？ 因为 prompt 是 Agent 行为的"源代码"。把检查项、决策规则、示例、成本都写清楚，等于给 prompt 配了完整文档——换人维护、A/B 新版、排查为什么某次判错，都有据可查。版本号 -v1 支持回滚。这是把 prompt 当一等工程产物对待。
