Supervisor 模式与多 Agent 协作

昨天(Day 03)你会读单个 Agent 的流程图了；今天往上一层：一个任务来了，谁来干？多个 Agent / 多个专家怎么配合？今天讲"主管调度"模式，并厘清本框架里两种容易混淆的 supervisor，为 Day 05 解剖真实 Agent 铺路。

📍 你在 20 天里的位置（第 1 周：建立心智）
D01 全景架构→ D02 跑起来→ D03 LangGraph→ D04 Supervisor→ D05 Agent 解剖
💡 用一个类比先兜住今天（延续「盖楼/物业」世界观） Supervisor 就像装修工地的领班/工头：他自己不砌墙、不刷漆，只干三件事——接活、判断这道活该派给哪个工种师傅、收结果；师傅之间不越级私聊，全走工头。本框架里有两个"工头"别搞混：① 图内 supervisor_node = 一户装修内部的施工领班（真派真监工，活是它带着干的）；② 跨 agent router = 物业大厅的问询导览员（你说句人话，它只告诉你"该去几号窗口找哪位"，绝不替你去办）。记住"领班真干、导览只指路"，今天就通了。
L01

什么是 Supervisor 模式

Supervisor（主管）模式是多智能体协作最经典的一种结构：设一个"中央主管"，它负责接任务、判断该派给哪个"下属"去做、收集结果，下属之间不直接对话，全部经过主管。

Supervisor 主管接任务 · 决定派给谁 · 汇总
↙   ↓   ↓   ↘
worker A
worker B
worker C
worker D

对比另一种"去中心化"结构（每个 agent 都能直接叫别的 agent），主管模式的好处是：调度逻辑集中、可控、可观测——你永远知道现在是谁在干、为什么派给它。缺点是主管可能成为瓶颈。本框架选了主管模式，因为可信/可控是第一优先级。

L02

为什么不用官方的 langgraph-supervisor 库

LangChain 官方出过一个 langgraph-supervisor 库。但本框架默认不用它——README.md:302-307 和 docs/architecture.md:65 明确说明：官方后来自己都建议改用"用 tools 直接实现 supervisor"的模式，所以仓里只在 third_party/langgraph-supervisor-py 保留一份副本供参考。

这给你一个重要认知：AI/Agent 领域演进极快，"官方推荐"半年就可能翻篇。本框架的应对是 Day 01 讲过的分层——把易变的东西（supervisor 实现方式）放在能替换的位置，而把稳定的可信能力（toolkit）攥在自己手里。所以本框架的 supervisor 是自己实现的，不绑定那个三方库。

于是问题变成：本框架自己怎么实现 supervisor？答案是——它有两种，分别解决两个不同层面的问题。这是今天最容易搞混、也最该厘清的地方。

L03

两种 supervisor 全景（务必分清）

① 图内 supervisor_node（进程内）

包：ai-trust-toolkit-starter-supervisor

  • 解决："一个 agent 内部，下一步该调哪个 specialist（专家）"
  • 是 LangGraph 图里的一个节点
  • 真的会去执行被选中的专家
  • 用在：单个复杂 agent 的图内调度

② 跨 agent router（进程外）

app：apps/supervisor-router-agent

  • 解决："一句话任务，该路由到平台上哪个 agent"
  • 是一个独立的 agent/服务
  • 只出决策、不真执行（scope guard）
  • 用在：工程师说人话，帮他选对入口
一句话区分：①是"图内、选专家、真跑"；②是"进程外、选 agent、只给建议不跑"。下面两讲分别看它们的代码。

👶 小白：都叫 supervisor，我还是分不清什么时候是哪个……

👨‍🏫 老师：用工地类比。① 施工领班站在一户装修工地内部，手里是这户的专家名单（trace/metric/deploy/log 师傅），他喊"下一个上 trace 师傅"，师傅真的上去干——所以它是图里的一个节点，会执行。② 大厅导览员面对整个小区几十户，你问"我这需求找谁"，他答"去 risk-reviewer 那户"，但他不会拉着你去敲门。看它在"一户内"还是"跨户"、"真干"还是"只指路"，就分清了。

L04

① 图内分派：supervisor_node

代码在 packages/ai-trust-toolkit-starter-supervisor/.../dispatch.py。核心是 supervisor_node(state, specialists, llm, max_iter=10)（dispatch.py:82）：给 LLM 一份 specialist 名单 + 当前对话，让它输出"下一个调谁"或"给最终答案"。

# LLM 被要求只输出这两种 JSON 之一：
{"next": "trace_specialist"}      # 还要继续，调这个专家
{"final_answer": "根因是..."}      # 够了，收尾

配套的 route_after_supervisor()（dispatch.py:186）就是 Day 03 学的条件边路由函数——把 LLM 的决策翻译成"图里下一步走哪个节点"。max_iter 防止 LLM 反复横跳陷入死循环（dispatch.py:103-115）。默认它用 get_llm("haiku")——用便宜的 Haiku 做调度决策，省钱。

组装出来的图长这样：START → supervisor → 条件分派 → {各 specialist / END}，specialist 干完再回到 supervisor 让它决定下一步。这就是 auto_configure_supervisor() 自动搭好的骨架（要求必须开 Critic，否则 raise）。

L05

② 跨 agent 路由：router

代码在 apps/supervisor-router-agent/supervisor_router/core.py。它没有 LangGraph 图，就是一个 route(task, tier) 函数（core.py:53），5 步走完：

1

list_agents()

拿到平台上有哪些 agent（优先查门户 registry，失败用本地 mock，5 分钟缓存）。

2

get_llm("haiku")

用便宜模型做决策。

3

渲染 prompt → LLM

把任务 + agent 名单塞进模板，让 LLM 选。

4

正则抓 JSON → 构建 RouteDecision

拿到 {agent_id, confidence, reasoning, fallback_alternatives}。

5

_critic_validate

校验：选的 agent 不在名单里 → 退回 unsure；置信度低于阈值(默认0.5) → 也退回 unsure，把原选放候选。

返回的 RouteDecision（core.py:38）包含：选了哪个 agent、置信度、理由、建议命令、备选方案，以及 token/耗时。关键设计：任何一步失败都优雅返回 "unsure"，绝不抛异常（_unsure, core.py:130）——路由器自己挂了也不能拖垮调用方。

📝 举个例子：导览员怎么应答两种问法 输入 route("帮我看下这个 PR 的上线风险")
→ 高置信 → RouteDecision{agent_id:"risk-reviewer", confidence:0.86, suggested_command:"agentctl invoke risk-reviewer ...", alternatives:["doc-checker"]}

输入 route("今天天气怎么样")（平台没这类 agent）
→ _critic_validate 发现选出的 agent 不在名单 / 置信度低于阈值(默认 0.5) → 优雅退回 RouteDecision{agent_id:"unsure", ...}，把原选放进候选。它宁可说"不确定"，也不硬塞一个错窗口。
图注：router 只吐"该找谁 + 命令怎么写"，把执行权留给人——这就是 scope guard。
⚠️ 小白常误以为"路由器选好 agent 后会顺手把它调了"。其实它只出决策、绝不执行：一个错误决策若自动触发一串真实操作（回滚、重启），后果不可控。把"决策"与"执行"分开，正是可信 Agent 系统的通用安全原则（见 L06）。
L06

scope guard：只决策，不执行

这是 router 一个刻意的、重要的约束：它只告诉你"应该调 X agent、命令大概这么写"，但绝不替你真的去调。为什么？

🚫 如果 router 自动执行下游

  • 一个决策错误会级联触发一串真实操作
  • 权限/审计边界模糊，谁为副作用负责？
  • 成本不可控，一句话可能烧一大笔

✅ 只出决策的好处

  • 人（或上层）看过决策再决定要不要执行
  • 决策可解释、可审计、可回放
  • 路由器本身零副作用、极安全

这个"scope guard（范围守卫）"思想在框架里到处都是——比如 Day 15 会讲的 spec-executor 只往 agent/* 分支提交、绝不碰 main。把"决策"和"执行"分开，是可信 Agent 系统的一条通用安全原则。

L07

handoff 与 route_chain：多步接力

有时一个任务要好几个 agent 接力完成。框架用两个东西支持：

HandoffSignal（交接信号）

定义在 ai_trust_toolkit/handoff.py:14，是个很简单的数据类：一个 agent 干完，可以在返回结果上挂一个"建议下一个谁接手"的信号，但同样只是建议——由 supervisor 决定要不要真交接（又是 scope guard）。

@dataclass(frozen=True)
class HandoffSignal:
    next_agent_hint: str | None   # None = 这条链结束
    context_for_next: dict        # 传给下一棒的上下文
    chain_id: str                 # 同一条链共享的 ID
    reason: str

chain_id 把一条接力链上的多次调用串起来，便于在门户里回放整条链。telemetry 会自动把它上报，业务无需手动处理。

route_chain（多步规划）

core.py:322 的 route_chain(task, max_steps=5) 让 LLM 一次性规划出 2-5 步的 agent 调用链：

任务→ 1. requirement-discoverer→ 2. spec-author→ 3. spec-executor→ 4. release-coordinator

依然是只规划、不执行——打印出计划 + 共享 chain_id 给你看。上面这条链其实就是 Day 15/20 要讲的平台"自我开发"闭环。
