Day 12 / 共 20 天 · 第 3 周 运行时与实战

gov-agents-server 运行时

把 Agent 变成能对外服务的 HTTP 接口。看清"一个镜像跑任意 agent 组合"的机制，以及一个 agent 只写业务、鉴权/记账/落库全自动的秘密——build_v1_router。

L01

server 的角色：只做托管，不含业务

packages/gov-agents-server 是平台主进程——一个 FastAPI 服务。它自己没有任何业务逻辑，只干四件事：

  • 维护一张"哪个 agent 名对应哪个模块"的注册表；
  • 按 ENABLED_AGENTS 环境变量，懒加载并挂载对应 agent 的路由；
  • 提供首页、健康检查、静态资源（skills 目录、安装脚本）；
  • 统一接可观测性。

主文件 gov_agents_server/main.py（约 1021 行）。它是 Day 02 "启动平台"那条命令 uvicorn gov_agents_server.main:app 背后的东西。

L02

一个镜像跑任意 agent 组合

平台的核心部署理念（写在 Dockerfile 开头）：构建一个镜像，靠 ENABLED_AGENTS 环境变量决定这个实例跑哪些 agent。

一个镜像build 一次
+
ENABLED_AGENTS环境变量
=
实例A：sre-rca,alert-triage
实例B：doc-checker,risk-reviewer
实例C：不设 = 挂全部

好处：同一个制品在不同环境按需组合，SRE 相关的部一台、质量相关的部一台，互不干扰又共用一份代码。不设 ENABLED_AGENTS 就挂全部；写了不存在的名字立刻报错退出（fail-fast，绝不静默忽略）。

L03

AGENT_REGISTRY：显式注册表，不是自动扫描

server 怎么知道有哪些 agent？靠 main.py:62-81 一张写死的字典——{agent名: (模块路径, 工厂函数名)}：

AGENT_REGISTRY: dict[str, tuple[str, str]] = {
    "sre-rca":        ("sre_rca.server",        "build_router"),
    "risk-reviewer":  ("risk_reviewer.server",  "build_router"),
    "alert-triage":   ("alert_triage.server",   "build_router"),
    # ... 共 18 条
}

启动时按名字用 importlib.import_module 懒加载对应模块，取出它的 build_router 函数。_load_router()（main.py:299）还有三条调用约定：

1

需要 DB 池的 agent（如 arch-compliance）→ fn(pool) 位置传参

2

普通 agent → fn(case_store=...) 关键字传参

3

用 inspect.signature 探测：build_router 含 app 参数就额外注入 FastAPI 实例（给 agent-creator 的 sandbox 用）

重点：是显式注册表，不是文件系统自动发现。 所以加一个新 agent 必须手动往这张表加一行（还要加 workspace 依赖 + pyproject）。Day 19 起新 agent 时你会亲手改它。这种"显式 > 隐式"的选择，牺牲了一点便利，换来了"打开这张表就知道平台到底有哪些 agent"的可读性。
L04

create_app：启动流程

create_app()（main.py:375）是平台工厂。模块底部 app = create_app()（main.py:1021）就是 uvicorn 直接 import 的实例。启动做这些：

1

load_config()

模块顶层就加载配置，缺字段直接抛错终止——启动即校验（Day 02）。

2

凭据桥接 _bridge

把 yaml 里的 ANTHROPIC_API_KEY / Lark 配置在"env 未设时"补进环境变量（非空 env 优先，方便 K8s Vault 覆盖）。

3

建单例 CaseStore

make_case_store_from_env()——跨 agent 共享的"调用历史存储"，首页据此列最近 case。

4

lifespan 生命周期

启动时初始化 SqliteCaseStore、给需要的 agent 建 DB 池（不可达就 warning 降级、跳过该 agent，其余照常）；退出时清理。

5

挂路由 + 静态资源 + 可观测

遍历 enabled 逐个 _load_router 并 include；挂 /skills、/install；setup_observability 挂 /metrics。

韧性设计：某个 agent 需要的数据库连不上时，平台不会整体启动失败，而是打个 warning、跳过这个 agent，让其它 agent 正常服务。这种"部分降级而非全盘崩溃"的思路，和 Day 08 的失败闸门一脉相承。
L05

build_v1_router：一行装齐所有治理

这是全平台覆盖率最高、最该理解的抽象。每个 agent 的 server.py 里的 build_router，核心就是调 toolkit 的 build_v1_router()（api/router.py:261）。业务只写一个 _invoke 函数，其余全自动：

# apps/sre-rca-agent/sre_rca/server.py:66
def build_router(case_store=None):
    router = APIRouter(tags=["sre-rca"])
    graph = build_rca_graph()                    # 你的 LangGraph 图
    store = case_store or make_case_store_from_env()

    async def _invoke(body, ctx, tracker) -> AgentOutcome:
        # ↑ 你只写这个：校验入参 → 跑图 → 包成结果
        with anthropic_key_override(ctx.anthropic_api_key):
            result = await graph.ainvoke(initial, config)
        return AgentOutcome(...)

    router.include_router(build_v1_router(         # ← 一行装齐下面全部
        agent_name="rca", invoke_fn=_invoke,
        stream_fn=_stream, case_store=store))
    return router

这一行 build_v1_router 自动给这个 agent 挂上标准端点：

POST /v1/agent/{name}/invoke同步调用
POST /v1/agent/{name}/streamSSE 流式（逐节点推）
GET /v1/agent/{name}/cases历史调用列表 + 单条
POST /v1/agent/{name}/feedback人工反馈打分
为什么这个抽象这么重要？ 因为"鉴权、限流、配额、预算、生成 case_id、成本追踪、构造统一 envelope、脱敏落库、推 Prometheus 指标、老路径 alias"这一整套每个 agent 都需要、且必须一致的东西，全被 build_v1_router 收了。业务作者只写业务推理（_invoke），治理白拿——这正是整个框架"业务代码 + 调 API，可信能力开箱即用"承诺的最终兑现点。
L06

一次 invoke 的完整治理链

把前面所有天串起来——一次 POST /v1/agent/rca/invoke 进来，_do_invoke（router.py:318）按顺序过这条链（前面的日子学的东西全在这里汇合）：

1

限频 ratelimit：这个 user 每分钟没超 60 次？（Day 08 四件套）

2

token 配额 quota：日/月 token 没超？

3

租户预算 budget：本月 USD 没超上限？超了 429（Day 08）

4

生成 case_id（ULID）+ 透传父 case / 调用深度

5

bind CostTracker：绑定记账器（Day 11 ContextVar）

6

执行你的 _invoke：跑 LangGraph 图（Critic/闸门/记忆全在图里，Day 05-09）

7

构造 envelope：统一返回外壳

8

持久化 case：字段脱敏 → PII scrub → 落库（Day 08）

这就是"跟一次请求走全程"的主线。你现在应该能看懂：一个请求先过一堆治理闸（限频/配额/预算），再进业务图（分诊→取证→综合→Critic），出来包成统一信封、脱敏落库、推指标。前 11 天的知识点在这一条链上全部各就各位。
L07

统一 envelope & 鉴权契约

统一 envelope（api/envelope.py:63）

所有 agent 返回的外壳完全一致（Day 02 见过）：

class InvokeResponse(BaseModel):
    case_id: str        # 26 字符 ULID（带校验）
    agent: str
    status: InvokeStatus            # success / critic_end / failed
    result: dict                    # agent 的业务字段装这
    metrics: Metrics                # elapsed_ms / tokens_in|out / cost_usd / retry_count
    trace_id: str
    deprecated_path: str | None     # 走老路径时的提示

鉴权 header 契约（api/auth.py）

请求通过几个 header 传身份：X-User-Id / X-Tenant-Id / X-Trace-Id / X-Anthropic-Api-Key。这些被封装成 CallContext（auth.py:45）传给业务——注意 per-request 的 API key 不落库，用完即弃。三档鉴权模式 PLATFORM_AUTH_MODE：open / header / strict。

命名的三层别混淆（Day 13 还会遇到）：注册表名（sre-rca）≠ 路由名（rca，由各 agent 的 build_router 传给 build_v1_router 决定）≠ CLI/MCP 认的 canonical 名。同一个 agent 在不同层可能叫不同名字，看代码时留意 agent_name= 参数到底传的啥。
