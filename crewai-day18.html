Events 事件系统

贯穿全框架的事件总线。前面反复出现的 CrewKickoffStartedEvent/ToolUsageStartedEvent/LLMCallStartedEvent 都走它。今天看它如何解耦日志、遥测、集成。

L01

事件总线是什么

🤔 场景：你想给每一步加日志/监控，但又不想改核心代码 Crew 跑起来了，你想：每个任务开始/结束打条日志、统计每次 LLM 调用花了多少 token（算钱）、把整个执行过程上报到 Langfuse 看板。难道要在 Crew、Agent、Task、Tool、LLM 的源码里到处插 print 和上报代码？那核心逻辑就被日志/监控搅成一团了，以后升级框架还全冲突。
💡 一句话本质：事件总线 = 发布-订阅（解耦） 事件总线就像一个微信群。核心代码在群里发一条消息（"我开工了""我调完 LLM 了"），至于群里谁看、看了干什么，发消息的人一概不管。想加日志/监控/上报的人，各自作为"群成员"订阅感兴趣的消息——有人退群、有人进群、有人只看不回，都不影响发消息的那个人。这就是"解耦"。
🛠️ 如果让你自己实现"给每一步加日志"，会有多痛苦？ 没有事件总线时，你只能钻进 Crew、Agent、Task、Tool、LLM 每个类的源码，在开头和结尾手动插一行 print。想改日志格式？五个地方一起改。想临时关掉日志？又得五个地方删。想再加个"上报 Langfuse"？五个地方再插一遍……核心逻辑被日志代码搅成一团，还全是重复。事件总线把这份痛苦一次性解决：核心只发事件，日志逻辑集中写在一个监听器里，加删改都在一处。

CrewAI 在运行的关键节点（Crew 开工、任务开始/完成、工具调用、LLM 调用……）都会发出事件。事件总线（event bus）负责把这些事件分发给监听者。代码在 events/。

发布-订阅：左边框架各处 emit 事件 → 中间全局总线 crewai_event_bus → 右边任意多个监听器订阅。两边互不认识，靠总线解耦。
用"广播电台"打比方 框架各处在关键时刻"广播"消息："Crew 开工了！""某工具被调用了！""LLM 返回了！"。事件总线就是电台，谁想听就"订阅"。想加日志的订阅所有事件打印、想做监控的订阅统计耗时、想集成 Langfuse 的订阅上报追踪——它们都不用改框架核心代码，只需订阅事件。这就是"发布-订阅"模式，也是可观测性的基础。
L02

CrewAIEventsBus

核心是 CrewAIEventsBus（events/event_bus.py:95），全局单例 crewai_event_bus。两个核心操作：注册监听（on）和触发（emit）。

读法：全局单例意味着整个应用共享同一个事件总线。框架各处 crewai_event_bus.emit(...) 发事件，你的监听器 @crewai_event_bus.on(...) 接事件——通过这个共享总线连接。这和 OpenHands 的事件、Flow 的 FlowStartedEvent（Day 11）都是同一套 crewai 事件总线。
L03

注册监听 @on

# event_bus.py:245
@crewai_event_bus.on(CrewKickoffStartedEvent)
def log_start(source, event):
    print(f"Crew 开工了：{event.crew_name}")
# 支持 depends_on 声明依赖顺序（某监听器要在另一个之后跑）
读法：@crewai_event_bus.on(某事件类型) 装饰一个函数，该函数就成为"这个事件的监听器"——事件发生时自动被调用，收到 source（谁发的）和 event（事件详情）。你想在 Crew 开工时做点什么？注册一个监听 CrewKickoffStartedEvent 的函数即可。
📝 注册一个监听器 → 跑 Crew → 自动打印 你写下（event_bus.py:245 的 on）：
@crewai_event_bus.on(CrewKickoffStartedEvent)
def log_start(source, event): print(f"[事件] Crew 开工：{event.crew_name}")
然后照常 crew.kickoff() —— 你没改 Crew 任何代码，控制台却自动多出一行：
[事件] Crew 开工：research_crew（✅ 因为 kickoff 内部 emit 了这个事件，你的监听器被自动调用）
depends_on 声明依赖：某些监听器有先后要求（比如"初始化 trace"必须在"记录 span"之前）。depends_on 让总线按依赖顺序执行监听器。这是比朴素发布-订阅更精细的调度。
L04

emit 触发

emit(source, event)（event_bus.py:572）触发事件，按依赖顺序执行所有监听该事件的 handler：

  • 同步 handler 在线程池执行。
  • 异步 handler 是 fire-and-forget（发了不等）。
  • 流式 chunk 事件强制同步保序——因为流式输出必须按顺序，不能乱。
🎬 第一人称之旅：假如你是一个 CrewKickoffStartedEvent 「我诞生于 crew.kickoff() 刚被调用的那一刻。Crew 一边喊'我要开工了'，一边 new 出我，把它的名字、id 填进我肚子里。然后它把我交给 emit()（event_bus.py:572）。emit 翻出'谁订阅了我这类事件'的名单——哦，有个日志监听器、有个 Langfuse 监听器。它按 depends_on 顺序，把我一个个递给它们。日志监听器读了我，打印'Crew 开工：research_crew'；Langfuse 监听器读了我，开了一条 trace。我的使命完成，安静消失。整个过程 Crew 完全不知道刚才发生了什么——它只管喊了一嗓子。」
为什么流式事件要"强制同步保序"？ 大多数事件（日志、监控）谁先谁后无所谓，可以异步并发处理（快）。但流式输出的 chunk 事件不行——"你""好""吗"三个字的事件如果乱序处理，前端显示就成了"吗你好"。所以流式 chunk 事件强制按顺序同步处理。大部分求快（异步），关键的求正确（同步保序）——因场景而异的处理，是成熟框架的细节。
L05

丰富的事件类型

events/types/ 里有 20+ 类事件，覆盖框架各处：

  • crew_events：CrewKickoffStarted/Completed…
  • agent_events / task_events：Agent/Task 的生命周期
  • llm_events：LLMCallStarted/…（Day 15 见过）
  • tool_usage_events：ToolUsageStarted/Finished（Day 14 见过）
  • memory_events / knowledge_events：记忆/知识操作（Day 16/17）
  • flow_events：FlowStarted/MethodExecution…（Day 11）
  • reasoning_events：StepObservation…（Day 9 的规划观察）
这解释了前面所有"发事件"的地方！Day 5 的 CrewKickoffStarted、Day 9 的 StepObservation、Day 11 的 FlowStarted、Day 14 的 ToolUsage、Day 15 的 LLMCall——它们全走这套事件总线。事件系统是把整个框架各处"串起来做可观测"的中枢。理解它，前面散落的"发事件"就都连成一张网了。
L06

自定义监听器

做法：继承 BaseEventListener（base_event_listener.py），实现 setup_listeners，构造时自动注册：

class MyListener(BaseEventListener):
    def setup_listeners(self, bus):
        @bus.on(CrewKickoffCompletedEvent)
        def on_done(source, event):
            上报到你的监控系统(event.token_usage)

MyListener()   # 构造即注册
这能做什么实际的事？ ① 日志/审计：记录 Crew 每一步干了啥。② 成本监控：在 LLMCall 事件里累加 token、算钱。③ 接入可观测平台：Langfuse、OpenTelemetry（pyproject.toml 里有 opentelemetry 依赖）——把执行过程画成 trace。④ 业务集成：任务完成时发 Slack 通知。全都不用改框架代码，写个监听器订阅相应事件即可。这就是事件解耦的威力。
L07

为什么用事件解耦

  • 核心逻辑纯净：Crew/Agent/Task 只管干活、发事件，不掺杂日志/监控/上报代码。
  • 横切关注点分离：日志、遥测、集成这些"横切"需求，通过监听器挂在外部——加/删/改都不动核心。
  • 可扩展：想加新的观测/集成？写个监听器，零侵入。
这是 AOP（面向切面编程）思想——和 eino 的 callbacks（Day 16）、OpenHands 的事件流是同一个哲学：把"日志/监控/追踪"这类横切关注点，从业务逻辑里剥离出来，用事件/回调在外部统一处理。三个框架不约而同用事件/回调做可观测——因为这确实是解耦横切关注点的最佳实践。你学会一个，就懂了所有框架的可观测层。
