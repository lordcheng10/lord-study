Day 13 / 共 20 天 · 第 3 周 扩展能力

Skills 技能系统

Skill = 一段"教模型怎么做某类事"的 SOP。今天讲 SKILL.md 格式、三种来源、发现加载、两条调用路径，并印证 Day 11 的大一统洞察。

L01

Skill 是什么

Skill（技能）是一段沉淀好的操作说明——把"遇到某类需求该怎么一步步做、该调哪些工具"写成一个 Markdown 文件（SKILL.md）。当任务匹配时，这段说明会被注入给模型，让它照着做。

对比 Day 12 的 MCP：MCP 提供"工具"（能力），Skill 提供"流程"（怎么用这些能力办成一件事）。比如一个 "code-review" skill 告诉模型"审代码时先看 diff、按这几个维度检查、用 X 格式输出"。核心代码 src/skills/。

为什么需要 Skill？ 因为有些任务有固定的"最佳做法"，但你不想每次都在 prompt 里重复交代。把它写成一个 skill，需要时自动加载给模型——相当于给模型一本"操作手册"，用到哪一章翻哪一章。这也是 gov-agents 教程里 L4 skills 的同类概念（那边是团队 SOP，这边是本地/项目技能）。
L02

三种来源

① Bundled（内置）

src/skills/bundled/*.ts

编译进二进制的技能（如 simplify/verify/ultracode）。用 registerBundledSkill 注册。

② 目录型

.claude/skills/<name>/SKILL.md

用户/项目/托管目录下的技能文件。这是你自己写技能的方式。

③ MCP 提供

src/skills/mcpSkills.ts

MCP server 也能提供 skill（feature 门控）。

bundled vs 目录型：bundled 是官方内置、跟着程序发布的（改不了）；目录型是你放在 .claude/skills/ 里的，能自由增删——项目级（进 git 团队共享）、用户级（~/.claude/skills 个人全局）。又是 Day 09/12 那套"项目/用户/托管"分层。bundled skill 的内容直接是一段 prompt 字符串（如 simplify.ts），目录型则从 SKILL.md 读。
L03

SKILL.md 格式

一个 SKILL.md = YAML frontmatter（元数据）+ Markdown 正文（给模型的指令）。解析在 parseSkillFrontmatterFields（loadSkillsDir.ts:185）：

---
name: code-review                    # 显示名
description: 审查代码变更             # 缺失时从正文首段推断
when_to_use: 用户要求 review/审代码时  # 何时触发
allowed-tools: Read, Grep, Bash      # 限制可用工具
argument-hint: "[文件路径]"           # 参数提示
user-invocable: true                 # 用户能否 /code-review 直接调
disable-model-invocation: false      # 模型能否自己调
context: fork                        # 作为子代理运行
model: inherit                       # 跟随主模型
paths: "src/**/*.ts"                 # 条件技能：触碰匹配文件才可见
---

# 审查流程
1. 先看 diff...
2. 按这几个维度检查...
frontmatter 是什么？ Markdown 文件顶部用 --- 包起来的一段 YAML，放元数据。正文才是给模型的实际内容。context: fork 表示这个 skill 作为一个独立子代理运行（Day 15）——它有独立上下文，不污染主对话。getPromptForCommand（:344）会做参数替换、注入基础目录、执行内联 shell（!命令）——但 MCP 来源的技能禁止执行内联 shell（安全，:374）。
L04

发现与去重

getSkillDirCommands（loadSkillsDir.ts:638，memoized）扫描三处目录：托管 → 用户 ~/.claude/skills → 项目（从 cwd 向上直到 home 的各级 .claude/skills）+ --add-dir 附加目录。

  • 每个 skill 必须是 目录/SKILL.md 形式（单个 .md 不行，:407）。
  • 旧式 .claude/commands/ 仍兼容（loadedFrom: 'commands_DEPRECATED'）。
  • 符号链接去重：用 realpath 算文件真实身份（getFileIdentity，:118），同一个技能通过软链出现在多处只算一次。
为什么要"从 cwd 向上找各级 .claude/skills"？ 这样你在子目录工作时，能同时用到项目根、中间层、当前目录各级定义的技能——近的优先。这跟 Day 16 讲的 CLAUDE.md 记忆"向上逐级查找"是同一套目录发现机制。符号链接去重防止你把一个技能软链到多处导致重复注册。
L05

条件技能：碰到相关文件才出现

一个有意思的机制——带 paths frontmatter 的条件技能：平时"隐身"，只有当模型读写到匹配的文件时才激活可见。

  • discoverSkillDirsForPaths（:861）：模型读写文件时，从文件路径向上找嵌套的 .claude/skills（跳过 gitignored 目录）。
  • activateConditionalSkillsForPaths（:997）：用 ignore 库匹配 paths glob，命中才把技能激活进 dynamicSkills。
条件技能解决什么？ 假设你有个"React 组件规范"技能，只在改 .tsx 时才相关。如果它总是注入给模型，纯属浪费 token（改后端时用不上）。用 paths: "**/*.tsx" 让它按需出现——模型碰到 tsx 文件才加载这个技能。这是"上下文经济"的又一体现：只在相关时才占用宝贵的上下文空间。
L06

两条调用路径

Skill 有两种被触发的方式：

1

用户手敲 /skill-name args

走 Day 11 的斜杠命令 prompt 分支。若 user-invocable: false，用户直接调会被拒（"只能由 Claude 调用"，processSlashCommand.tsx:712）。

2

模型自己调（通过 Skill 工具）

getSkillToolCommands（commands.ts:650）把符合条件的技能（type:prompt、非 disableModelInvocation、非 builtin）暴露给模型，模型判断需要时用 Skill 工具（Day 08 那个）调用。

两条路径的分工：user-invocable 控制"你能不能主动敲 /xxx 用它"，disable-model-invocation 控制"模型能不能自己决定用它"。有的技能只给模型用（比如某个内部处理流程），有的只给用户用，有的两者都行。模型调用时，如果技能自带 hooks（Day 14），还会 registerSkillHooks 注册（:1136），并 addInvokedSkill 记录以便压缩时保留（:1155）。
L07

印证 Day 11 的大一统洞察

💡 回扣 Day 11：一个 SKILL.md 最终就是被 createSkillCommand（loadSkillsDir.ts:270）包成一个 type:'prompt' 的 Command。

所以 skill 根本不是一套独立机制——它复用了 Day 11 整套命令的解析/派发管线。它的 getPromptForCommand（:344）做的事（参数替换、注入目录、执行内联 shell）就是一个 prompt 命令展开内容的过程。loadedFrom 字段标着 skills 以区分来源，仅此而已。

把三周的扩展能力串起来：Day 11 命令、Day 12 MCP、Day 13 Skill——表面是三套不同的扩展，底层其实高度统一：MCP 工具 = Day 07 的 CoreTool；Skill = Day 11 的 prompt Command。Claude Code 的可扩展性不是靠堆砌 N 套插件机制，而是把一切归约到少数几个统一抽象（Tool / Command），再让各种来源（内置/MCP/skill/plugin）都实现这些抽象。这是整个项目架构上最优雅的地方——学会看穿"表面多样、底层统一"，你读任何大项目都会更快。
