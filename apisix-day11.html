Day 11 / 共 20 天 · 第 3 周 插件系统

插件机制全景

第 3 周进入 APISIX 的灵魂——插件系统。104 个插件（鉴权/限流/可观测/AI）都是同一套机制。今天看 plugin.lua 怎么加载插件、按 priority 排序、以及 filter 怎么为一个请求选出该跑的插件。

L01

插件是 APISIX 的灵魂

apisix/plugins/ 有 104 个插件。网关的几乎所有功能（key-auth 鉴权、limit-count 限流、prometheus 监控、proxy-rewrite 改写、ai-proxy AI 代理…）都是插件。

"内核小、插件多"的哲学 APISIX 核心只做"路由 + 把请求交给插件链 + 转发上游"，具体能力全靠插件。这样内核稳定精简，功能靠插件无限扩展。你只启用需要的插件，不用的零开销。这和 Envoy 的 filter 链、Higress 的 Wasm 插件是同一思想——网关都走"插件化"路线。区别是 APISIX 插件是纯 Lua（改起来快、热加载），Envoy 是 C++/Wasm。
L02

一个插件的结构

每个插件是一个 Lua 模块，标准结构：

local _M = {
    version  = 0.1,
    priority = 1002,          -- 优先级（越大越先跑）
    name     = "limit-count",
    schema   = schema,         -- 配置校验 schema（Day 09）
}
function _M.check_schema(conf) ... end       -- 校验配置
function _M.rewrite(conf, ctx) ... end       -- rewrite 阶段逻辑
function _M.access(conf, ctx) ... end        -- access 阶段逻辑
function _M.header_filter(conf, ctx) ... end -- 响应头阶段
function _M.log(conf, ctx) ... end           -- 日志阶段
return _M
读法：插件就是"一个带 priority/name/schema + 若干阶段方法的 Lua 表"。它想在哪个 Nginx 阶段做事，就实现对应的方法（access/header_filter…）。这和上一站 wasm-go 的"填阶段钩子"如出一辙——只是这里是 Lua 函数、那里是 Go 回调。
L03

plugin.load 加载

plugin.lua:342-374 的 load：从配置读出要启用的插件名列表，逐个 require 进来，存到 local_plugins。

function _M.load(config)
    local ignored, http_plugin_names, stream_plugin_names = get_plugin_names(config)
    -- http 子系统：加载 http_plugin_names（+ wasm 插件）
    load(http_plugin_names, wasm_plugin_names)
    -- stream 子系统：加载 stream 插件
    load_stream(stream_plugin_names)
    return local_plugins
end
只加载"启用"的插件 104 个插件不是全部加载——你在 config.yaml 的 plugins: 列表里写要启用哪些，APISIX 只 require 这些。没启用的插件不占内存、不影响性能。启用列表变了（改 config），load 会重新加载——插件也能"热更新"（配合 Admin 的 reload 接口）。还支持 stream 子系统的插件（Day 18）和 wasm 插件。
L04

priority 排序

加载后，插件按 priority 排序（越大越先执行）。local_plugins 是排好序的插件对象列表。

priority 决定谁先跑，很关键 插件有执行顺序——比如"鉴权"必须在"限流"之前（先确认身份再按身份限流）、"改写请求"要在"转发"之前。priority 就定这个顺序。鉴权类插件 priority 很高（如 key-auth 2500）、改写类中等、日志类较低。你自己的项目里有一张"插件优先级表"（本博客还有 apisix-plugin-order.html 专门讲）——理解顺序才能理解插件如何协作。filter 选出插件后，它们就按这个全局顺序跑。
L05

阶段方法

插件通过实现不同阶段方法，在请求生命周期的不同点介入（对应 Day 02 的 Nginx 阶段）：

  • rewrite / access：请求处理阶段（鉴权、限流、改写——决策类）
  • before_proxy：转发上游前最后一改
  • header_filter / body_filter：改响应
  • log：记录/上报
读法：一个插件不必实现所有阶段——只实现它需要的。limit-count 主要在 access（拦截超限请求）；prometheus 主要在 log（上报指标）；proxy-rewrite 在 rewrite（改请求）。Day 12 看这些方法怎么被 run_plugin 在各阶段调起。
L06

filter 选插件

plugin.lua:469-520 的 filter（Day 04 access 阶段调它）：从"全局加载的插件"里，挑出"这个路由启用了的"：

function _M.filter(ctx, conf, plugins, route_conf, phase)
    local user_plugin_conf = conf.value.plugins   -- 路由/服务配置里的 plugins
    if not user_plugin_conf then return ... end
    for _, plugin_obj in ipairs(local_plugins) do  -- 遍历所有已加载插件（按 priority 序）
        local plugin_conf = user_plugin_conf[plugin_obj.name]
        if type(plugin_conf) ~= "table" then goto continue end  -- 这条路由没配这个插件
        if check_disable(plugin_conf) then goto continue end     -- 显式禁用
        core.table.insert(plugins, plugin_obj)    -- 选中：插件对象
        core.table.insert(plugins, plugin_conf)   -- + 它的配置（成对存）
        ::continue::
    end
    return plugins
end
"成对存"的巧思 结果 plugins 是 {插件对象1, 配置1, 插件对象2, 配置2, ...}——插件和它的配置成对相邻存。这样 run_plugin 遍历时 plugins[i] 是对象、plugins[i+1] 是配置，一步到位（Day 12 会看到 for i=1,#plugins,2）。因为按 local_plugins（已按 priority 排序）的顺序遍历，选出的 plugins 天然也是 priority 序。
L07

启用/禁用/自定义排序

filter 里还有几个细节：

  • check_disable：插件配置里可写 _meta.disable=true 临时禁用（保留配置但不跑）。
  • run_policy == "prefer_route"：某些插件路由级配置优先于 consumer 级（:494-500）。
  • _meta.priority（:513）：单个插件实例可覆盖默认 priority，此时 custom_sort 重排。
读法：这些让插件编排更灵活：能临时禁用、能针对某路由调整顺序。_meta.priority 的自定义排序会临时 fetch table 重排（:522+）——又用了 tablepool。Day 13 讲配置合并时会再见到这些优先级规则。
